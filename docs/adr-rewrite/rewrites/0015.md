# 15. Skill Inventory and audit-skills

The Skill Inventory grades each Skill's `importance` by how essential it is
when its kind of work happens, never by how often it runs. The `audit-skills`
Skill checks from session logs that our own Skills fire when needed and deliver
what they promise, and keeps the Inventory in line with that evidence. Pack
Skills stay exactly as installed: the Gate pins each one, and its Inventory
entry is where this repo says how it fits here.

## Scope and limits

Grades:

- `importance` is conditional essentialness, in the five grades `CONTEXT.md`
  defines. `routine` follows from an observed fact: scheduled sessions run the
  Skill. The other four are judged from usage.
- Disuse alone never lowers a grade. A grade drops only when the Skill went
  unused in sessions of the kind it serves.
- A grade moves, up or down, only on 2 or more windowed sessions, cited.
- A missed invocation of our own Skill is a trigger problem, handled as a
  finding, never as a demotion. For a pack Skill, whose trigger we can't fix,
  the grade is the lever.

Inventory entries:

- `role` says what the Skill does for this Platform and why it matters, in its
  own words rather than the Skill's description, and carries no PR, issue or
  session ids.
- `observations` hold the ids: each entry is one run's citable finding (a
  grade or `role` change, a verified or unverified finding, an idea). They
  carry evidence between runs for 40 days. A run drops older entries and adds
  one only when it cites a session no remaining entry cites. The Inventory page
  doesn't show them; `audit-docs` may read them as corroboration.
- An entry records real use, so a Skill gets one when `audit-skills` first sees
  it used.
- A pack Skill's advice for this repo goes in its Inventory entry.

`audit-skills`:

- Runs as a scheduled Routine and is never model-invoked.
- Reads the session logs of a fixed span of recent days, not a count of logs.
- A script gathers the evidence; the session makes every judgement.
- Each of our own Skills used often enough in the window gets a read-only
  subagent check for silent failure (it ran but didn't deliver) and, if
  model-invoked, missed invocation.
- A verified finding becomes an issue only when it is significant (it did real
  damage) or repeated (an earlier observation records it). Every other finding
  becomes an observation, and so does one not yet verified, marked unverified.
- Grades and `role` cover every Skill, pack Skills included. Checks, issues and
  comments cover our own Skills only; a finding about a pack Skill becomes an
  observation on its entry.
- Writes only Inventory entries, issues and issue comments. A Skill's text
  changes through an issue, since that is a judgement call.
- Its Inventory PR stays inside its ADR-0003 ledger row; it never uses the
  ADR-0009 direct-to-`main` path.
- Records a new, split or retired Skill as an idea in its session log and acts
  on none; retiring a Skill is a human's call (ADR-0003).

Pack Skills:

- A pack Skill is one keyed in `skills-lock.json`. Its `SKILL.md` isn't ours
  to edit, because a re-install overwrites local edits.
- The Gate pins each inventoried pack Skill's installed `SKILL.md` hash in its
  Inventory entry and fails on drift. A pack Skill with no entry yet stays
  unpinned. `skills-lock.json` belongs to the installer; we read only its keys.

## Why

- Grading by frequency penalises the Skills we most want to keep: a Skill can
  be the tool for its job while that job is rare.
- Disuse mostly shows which work happened, not whether a Skill is worth having.
  Only a missed chance says something about the Skill.
- Frictions miss the two failures that matter most: a Skill that runs quietly
  without delivering, and one that should have fired and didn't.
- Scheduled runs add logs every day, so a count of logs shrank the window to a
  couple of days. A span of days holds steady.
- Daily runs over overlapping windows repeat each other's findings; a 40-day
  span with no repeats keeps what a later run needs, and git keeps the rest.
- `role` is what visitors read; ids in it turned it into an audit log.
- Escalating only significant or repeated findings is the owner's rule.
  Recording the rest as observations lets a later run see a repeat.
- The lock's own hash is of the upstream source, not the installed file, and
  can't be recomputed offline. Our pin checks the installed file.

## Rejected alternatives

- **One global scale** (`core | supporting | peripheral`). It mixed breadth
  with essentialness, so most entries piled into `supporting`.
- **Grading scheduled Skills `specialist`.** It reads as a narrow tool seldom
  used, the opposite of a Skill that drives whole sessions.
- **Helpfulness or friction-per-use.** Confounded: hard sessions use more
  Skills and log more frictions. We ask whether a Skill delivered instead.
- **A friction-based regression watch.** About 80 runs yielded one confirmed
  finding, and it couldn't see failures that leave no friction.
- **The newest 40 logs as the window.** See Why.
- **Append-only observations.** Repeats piled up.
- **Evidence ids in `role`.** See Why.
- **Pinning in `skills-lock.json`, or trusting its hash.** The file is the
  installer's, and its hash can't check the installed file.
- **Failing the Gate on a pack Skill with no entry.** Entries record real use,
  so a freshly installed Skill has none yet.
- **Referring Skill findings to `frictions-to-fixes`.** That Skill mines
  session-log frictions, not issues, so the referral went nowhere.

## Consequences

- Grades can move every run as usage shifts; read one as current evidence.
- A legitimate pack install must regenerate the pins, or the Gate fails.
