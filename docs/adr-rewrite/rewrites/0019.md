# 19. Recovering from failed content loads

`@nuxt/content` runs unpatched, so a failed client-side content load leaves its
Collection unloadable until the page reloads. Every page that queries Content
shows the failure in `ContentLoadErrorDialog`, whose Reload button is the
recovery. A failed chunk import is the one failure that reloads itself, once
per path.

## Scope and limits

- **Where it applies.** Any `useAsyncData` query that runs against the client
  DB. Since ADR-0028, navigation reads a server payload instead, so the client
  DB loads only for Tinkerfund search, re-queries after mount, and a failed
  payload fetch.
- **The dialog.** Each page that queries Content passes `useAsyncData`'s
  `status` and `error` to `ContentLoadErrorDialog`. On error it opens a modal:
  a plain message, a technical-details disclosure, and a Reload page button. A
  failed load is never a silent blank.
- **The recovery is a full reload,** never an in-page retry.
- **The one auto-reload: a chunk-load error.** An error counts when Nuxt's
  `app:chunkError` hook saw it, matched by identity anywhere in its `cause`
  chain, or when its message reads as a failed dynamic import in any browser
  engine. The app then calls `reloadNuxtApp` itself.
- **Once per path.** `reloadNuxtApp`'s own `sessionStorage` guard is the only
  attempt counter. The app reads it before calling, and if a reload of this
  path is already recorded, it shows the dialog instead.
- **Every other failure keeps the dialog:** a rejected dump fetch, a
  decompression or `db.exec` error on a 200, and a missing Document.

## Why

`@nuxt/content` caches each client DB load as a module-level promise and clears
it only on success. A load that fails stays failed for the life of the page,
and app code cannot reach that state to reset it. A fresh page renders from the
server DB, so a reload recovers every failure, whatever its trigger.

A visible dialog with a reload holds across `@nuxt/content` upgrades and shows
the error that occurred. A patch to the dependency does neither.

Auto-reload is limited to chunk-load errors because only there does a reload
demonstrably fix the cause: production showed a transient 500 on an existing
build chunk, the one `@nuxt/content` imports lazily for its first client query.
That import fails inside `useAsyncData`, so the error never reaches the router
and Nuxt's own chunk-reload plugin does nothing. For any other failure, a
reload may fail the same way, and a reload loop is worse than a modal.

## Rejected alternatives

- **Patch `@nuxt/content`** (`pnpm patch` of its compiled `dist`): clear the
  cached load on failure, retry the dump fetch, and log failures to a
  `localStorage` buffer. It fixed only loads that reject, not loads that
  resolve over an empty table or cache a corrupt dump. It was also pinned to
  one version's build output and had to be re-checked on every upgrade. Empty
  pages still recurred with it in place.
- **Retry inside the page.** App code cannot clear the cached failure, so a
  retry hits the same error.
- **Auto-reload every failure.** A failure a reload can't fix would loop.
- **A second attempt counter.** `reloadNuxtApp` already keeps one and declines
  silently, so a separate counter could disagree with it.

## When to revisit

- A `@nuxt/content` release clears a failed client load, so a retry inside the
  page could work.
- An invisible self-heal for brief dump-fetch failures is wanted. It belongs
  upstream, or in a new patch checked against the current release.

## Consequences

- A brief dump-fetch failure that a retry would survive now shows the dialog
  and needs a manual reload.
- The auto-reload is a full page load: unsaved in-page state is lost, and the
  user sees a flash, not an explanation.
- An e2e test of this recovery must fail the route's payload first, or
  navigation never reaches the client DB.
