# 14. The #routing build-time module

The routing map is derived from the Tenant manifests at build time, never
committed. `modules/routing.ts` runs `expand(loadManifests())`, writes the map
to `.nuxt/routing.mjs` and registers it as the `#routing` virtual module, so a
manifest edit needs no regenerate step.

## Scope and limits

- `#routing` exports one value, `routingMap`: Tenant → Space → Collection →
  collection key. It comes from the same expansion `content.config.ts` uses
  (ADR-0013).
- Code imports `#routing` with a plain static import. The resolver in
  `shared/routing.ts` stays free of Nuxt context, so its unit tests run without
  Nuxt.
- `.nuxt/` is a build output, and anything reading `#routing` needs it fresh.
  `nuxt prepare` writes it; `pnpm install` and `pnpm test` run that. After you
  add a layer or rebase onto others' manifest changes, run `pnpm install`.
- Nuxt sets the `#routing` alias. Two tools run outside Nuxt and mirror it:
  `vitest.config.ts` for unit tests and `tsconfig.node.json` for the node half
  of `pnpm typecheck`. A new `#` virtual module gets the same mirrors wherever
  its importers run.
- In dev, editing an existing Tenant's manifest or `shared/expand.ts` restarts
  the server. A brand-new layer folder needs a manual restart.
- The L2 entry-route list is not in `#routing`. The e2e support derives it from
  the same expansion with `entryRoutesFrom` in `shared/expand.ts`.
- The module and the resolver are isolation-critical, so they are Human-only
  (ADR-0004).

## Why

The client needs the routing map at runtime. Deriving it in the browser would
pull every manifest, and zod, into the client bundle. So the map must be
computed at build time and shipped as plain data, but nothing requires it to be
a committed file.

A committed copy needs a regenerate step and a drift gate to stay honest, and
"manifest edited, regeneration not committed" was a recurring PR failure.
Deriving at build time removes that failure instead of detecting it. One
mechanism remains: manifests → `expand()` → collections and routing.

## Rejected alternatives

- **Commit the routing map and drift-check it** (ADR-0007, kept by ADR-0013).
  Its one-line-per-collection diff showed reviewers which tables a manifest
  change created or removed. The manifest diff already carries that intent, and
  the expansion can be printed on demand, so the regenerate step and drift gate
  were not worth it.
- **Derive the map in the browser.** It would ship every manifest and zod to
  the client.

## When to revisit

- A fourth module would run its own `expand(loadManifests())`. ADR-0025 asks to
  fold `content.config.ts`, `modules/routing.ts` and `modules/catalog.ts` into
  one derived-data module first.

## Consequences

- PR diffs no longer show the routing map. Review the manifest diff, and print
  the expansion when you need the keyed view.
- The Platform depends on Nuxt's module and template API rather than on a plain
  committed file.
