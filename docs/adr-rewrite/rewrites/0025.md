# 25. Cross-Tenant reads through collection kinds

Tenants stay isolated unless a Collection opts in by naming a Collection kind,
a shared read contract registered in `shared/kinds.ts`. The build derives the
Catalog of opted-in Collections from the same manifest expansion as routing,
and an Aggregator reads it only through `queryAcrossTenants`, read-only and
over baked content. The kind registry and read primitive need a human merge,
while each Aggregator keeps its own normalization in its own layer.

## Scope and limits

- **Opt-in per Collection.** A Collection opts in with `kind:` in its manifest
  entry. A Collection with no kind is invisible to every Aggregator, and a
  Tenant that names no kind is fully isolated.
- **One registry.** `shared/kinds.ts` is the single home for every kind. A
  kind is separate from a Collection's `type`: `type` is how the Collection
  builds and routes, the kind is its cross-Tenant contract and its opt-in.
- **Minimum contract.** Every kind carries a contract: the fields an
  Aggregator may rely on. A Collection's effective schema is that contract
  merged with its own `schema`, for page and data Collections alike, so opting
  in costs a Tenant none of its own fields. A contract may be a few optional
  fields (`page`) or a Collection's whole shape (`session`); that is one
  mechanism, not two.
- **Fields a view reads belong in the contract.** An Aggregator reads only
  fields its kind guarantees, never a per-Tenant convention read by cast.
- **Manifest checks.** The manifest validator rejects an unknown kind, a kind
  whose `type` differs from the Collection's, and a `data` Collection with
  neither a `schema` nor a kind. These fail where the manifest is written
  (ADR-0002).
- **A shape moves into `shared/` only when it is truly shared.** A Collection
  can keep its own schema beside its kind, so a Tenant's shape that others
  also want need not move. The session log schema did move
  (`shared/schemas/session.ts`): it is Platform self-documentation (ADR-0009)
  that the Journal, the Timeline and `scripts/log-session.ts` all use.
- **The Catalog is derived.** `modules/catalog.ts` builds `#catalog` from
  `expand(loadManifests())` at build time. A Tenant with a kinded Collection
  appears on the next build; a removed one drops.
- **One read primitive.** An Aggregator reads across Tenants only through
  `queryAcrossTenants(kind, project)` in `app/composables/catalog.ts`. It
  serves any kind, projects each row inside the fan-out (so large fields such
  as a page body stay out of the result), and stamps each row with its Tenant,
  Space and Collection. Each consumer's projector holds its one cast.
- **Read-only, baked content only.** The Catalog and the primitive never
  write, and they read only content committed and baked at build (ADR-0001).
- **Aggregators are few and governed.** An Aggregator is an ordinary Tenant
  layer that reads the Catalog. Ordinary Tenants never read across. One
  Aggregator Tenant hosts several views, one per Space, so a new cross-Tenant
  view is a new Space in the Commons, not a new Tenant.
- **Normalization lives in the Aggregator's layer.** Which kinds a view reads,
  what counts as a post, how an entry is dated or linked: all of it sits in
  the Aggregator's own layer and merges like any layer edit. The Aggregator
  owns any coupling it chooses to another Tenant's conventions, and cites
  their source.
- **Human-only.** `shared/kinds.ts`, `shared/schemas/`, `modules/catalog.ts`
  and `app/composables/catalog.ts` need a human merge (ADR-0004), with
  `content.config.ts`, `shared/expand.ts`, `modules/routing.ts` and
  `shared/routing.ts`. `shared/schemas/` is included because it supplies kind
  contracts. An Aggregator's layer is not Human-only.
- **A kind is a versioned contract.** Several Tenants and Aggregators depend
  on each kind, so widening or removing one is a breaking change.
- **`page` means aggregatable, not enumerable.** A sitemap needs every routed
  page, including unkinded ones. Decide how a sitemap reads (from `#routing`,
  or a separate opt-in) before building one.
- **The Commons is the first Aggregator.** Its own pages carry no kind, so
  its views never list the Commons itself.

## Why

The Platform had no sanctioned way to read across Tenants, yet a global
search or activity feed needs one. Without it, a view must re-declare every
Tenant's schema, which drifts, or import Tenants' manifests, which couples
them; the "dollhouse" fork (#631) went further and faked a roster and data.

Every cross-Tenant fact already flows from `expand(loadManifests())`.
Extending that one source, as `#routing` (ADR-0014) did, keeps a single home.
With two such derivations, kind and Aggregator earned names.

Opt-in keeps isolation the default: exposure is an explicit act per
Collection. Putting the fields views read into the contract means renaming a
manifest field cannot silently drop a Tenant out of a view.

Keeping the primitive generic and each view's policy in its layer keeps the
Human-only surface small: changing a view is a layer edit, and only widening
the read itself needs a human.

## Rejected alternatives

- **Re-declare each Tenant's schema in the Aggregator.** It drifts.
- **Import a Tenant's manifest or hardcode a roster.** It couples Tenants, and
  a hardcoded roster goes stale.
- **A static microsite with faked or runtime data**, the dollhouse's shape. It
  bypasses the model and breaks ADR-0001.
- **A parallel source of cross-Tenant data** beside `expand()`. Two sources
  drift.
- **View normalization in the platform composable.** Every view change would
  touch a Human-only file.
- **Deriving the row type from the kind name.** It would remove the
  projector's cast but fights Nuxt Content's per-collection types for little
  gain.

## When to revisit

- A cast at the projector causes real bugs: derive the row type from the kind.
- The corpus grows enough that fetching whole rows before projection costs:
  select fields in the query, or bake a build-time index.
- A fourth module runs `expand(loadManifests())` beside `content.config.ts`,
  `modules/routing.ts` and `modules/catalog.ts`: fold them into one
  derived-data module, at the latest when one of them is next changed.
- A directory-style view needs a Tenant's display name or tagline: add a small
  optional manifest block surfaced through the Catalog.
- Someone builds a sitemap (see the `page` limit above).

## Consequences

- A new kind is one entry in `shared/kinds.ts`. `expand()`, the Catalog module
  and `queryAcrossTenants` need no change.
