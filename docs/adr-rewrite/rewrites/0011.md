# ADR-0011: The live site's container builds and serves `main` itself

The public site runs in one container that clones `main`, builds it and serves
the result. It checks for new commits, builds each one beside the live copy,
and switches only when the build succeeds. So a merge to `main` runs that code
on the server, and no push to `main` needs a new image.

## Scope

- **What moves to runtime.** Only the build, and only inside this container.
  Content is still declared in files and baked into the database at build
  time, and nothing creates Tenants or collections while the site runs
  (ADR-0001).
- **The image holds tools, not the app.** It changes only when `deploy/`
  changes. A merged change to `deploy/` reaches the server only when the
  operator rebuilds the image by hand.
- **A failed install or build changes nothing.** The last good build stays
  live, and the next commit tries again.
- **A merge is where code reaches the server.** Whoever can merge to `main` can
  run code there. This is why the merge is the step to guard: who may merge
  what is set by ADR-0004, ADR-0020 and ADR-0023.

## Why

Content is baked at build time, so keeping the site current means building
after every change. The only choice is where that build runs. Running it in
the serving container keeps the site current with no step per merge: no
pipeline that builds and publishes an image, and no redeploy.

Building beside the live copy and switching only on success means a bad
commit cannot take the site down.

The owner chose this for one server that already hosts other apps behind a
shared proxy.

## Rejected alternatives

- **CI builds a fixed image for each release, and the server redeploys it.**
  This is ADR-0001's first plan. It needs a build-and-publish pipeline and a
  redeploy for every content edit. It stays the way back: switching to it
  changes only `deploy/`, not the app.

## When to revisit

- Pushes become frequent or Tenants many. Every update is a full rebuild, and
  a build needs a lot of memory.
- The site needs releases pinned to a fixed image that can be rolled back.

## Consequences

- What the site serves is not fixed by an image. It is the newest commit on
  `main` that built. The container log says which commit is live.
