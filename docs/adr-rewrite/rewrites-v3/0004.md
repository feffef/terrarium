# ADR-0004: Objective safety gate

Every PR passes the Gate: a set of machine-checkable checks that run locally
and in CI, where the result decides whether the PR may merge. A branch passes
the local gate and a code review before its first push. Agents then merge
their own PRs once the gate is green, except a few kinds that a person with
write access must merge.

## Scope and limits

- **Every PR passes the Gate.** CI's run is the one that counts. Locally,
  `pnpm gate:scoped` runs the same checks; the full `pnpm gate` is left to CI.
- **Four layers.**
  - L0, build: every Tenant manifest validates and expands, the app builds,
    and lint, typecheck and the drift checks pass.
  - L1, content: every Document validates against its Collection's schema.
    `pnpm validate:content` does this, because the build validates no content.
  - L2, smoke render: every entry route of every Tenant and Space returns 200
    and loads in a real browser with no console errors.
  - L3, isolation: a query for one Tenant and Space never returns another
    Tenant's or Space's Documents. Collection keys are unique and correctly
    scoped, checked when manifests expand and again when a request resolves.
- **Skipping the costly steps.** The Gate's steps form two tiers. The Floor
  always runs. The Heavy tier (unit tests, build, e2e) is skipped only when
  every changed path is Inert, meaning no Heavy step reads it. Any doubt runs
  everything: no usable diff base, a shallow checkout, a failed decision step,
  an empty changeset, or a push to `main`. CI and `gate:scoped` take this
  decision from the same code.
- **Skill files.** A change made only of Inert paths and a Skill's own files
  (`.agents/skills/`, `.claude/workflows/`) skips build and e2e but still runs
  unit tests. This holds only while nothing the build or an e2e spec loads
  lives in those folders.
- **Before the first push.** `pnpm gate:scoped` passes and the `code-review`
  Skill reviews the branch. This holds even when the Stop hook asks you to
  push. `docs/agents/pr-workflow.md` lists when the review may be skipped.
- **Later pushes.** A code change runs `gate:scoped` first. A change of prose
  or docs may rely on CI's gate.
- **CI fails after `gate:scoped` passed.** Check whether the base moved, then
  log a `major` Friction.
- **Where tests live.** A test lives with the code it exercises: a Tenant's
  tests in `layers/<tenant>/tests/`, the Platform's in `tests/`, a Skill
  helper's beside its Skill.
- **One build for e2e.** The e2e specs reuse the gate's build, so a spec never
  builds the app. Each Tenant may have its own specs, and they run in parallel.
- **Who merges.** The agent that wrote a PR merges it once the gate is green
  (ADR-0003). A person with write access merges it instead when the PR:
  - adds a dependency;
  - changes behaviour no test covers;
  - decides which Tenant's data a request can reach;
  - comes from someone without write access, from a fork, or from the guest
    pipeline (ADR-0020, ADR-0023);
  - changes a Human-only file.
- **Behaviour no test covers.** Runtime behaviour that no gate layer can vouch
  for. Examples: new client-side behaviour that no test asserts; a hook, cron
  job or script meant to run unattended with no dry run or test around it;
  logic that depends on timing, ordering or concurrency, which a unit test
  can't reliably exercise; and effects L0–L2 can't see, such as an external
  side effect or a webhook delivery. A change with real test coverage does
  not count just because it touches unfamiliar code.
- **Deciding which Tenant's data a request can reach.** A Tenant page that
  finds its Space through the shared `resolveSpaceRoute` and reads only its
  own Space's collections decides nothing about reach. It is presentation and
  merges normally.
- **Human-only files.** The list is the `paths` of
  `.claude/rules/adr-0004-human-merge.md` and lives nowhere else. It holds the
  files where a mistake could mix Tenants' data, weaken the Gate or the merge
  rules, or change governance. `scripts/merge-pr.ts` reads the list from
  `origin/main`, so a PR cannot shorten it for itself. It refuses to merge a
  PR that changes a listed file, and refuses every PR if the list reads empty.
- **Exceptions with no file to match.** `merge-pr.ts` also refuses fork PRs
  and PRs from someone without write access. Nothing checks for a new
  dependency, untested behaviour or Tenant reach: the agent that wrote the PR
  recognises them and leaves the merge to a person, even on a green gate.
- **Merging, not editing.** Agents change Human-only files routinely. The
  control is the human review at merge.

## Why

- Agents write nearly everything, on a Platform that edits its own tooling.
  Automated checks are what make that safe enough, so this is the one place
  the Platform does not keep things minimal. A person and an agent reviewing a
  PR need the same objective signals.
- The Gate checks what a PR produces, not what its author meant, so it can be
  trusted without trusting the author. For the same reason it misses some
  risks. A new dependency, untested runtime behaviour or a hostile request can
  all pass a green gate, and no file path reveals them. Those exceptions stand
  beside the file list.
- A green gate shows the change builds and passes its tests. A review shows it
  is the right change, written to the repo's standards. Both come first
  because pushing opens the PR (ADR-0003).
- A skip may only ever err toward running more. The build reads
  `.agents/skills/` only to list which folders hold a `SKILL.md`, which no
  other file can change. It reads nothing in `.claude/workflows/`. No e2e spec
  reads either folder.
- One list in the rule's `paths` does two jobs. It shows the agent a warning
  when it touches a listed file, and it drives `merge-pr.ts`'s refusal.
- Keeping tests with their code shows which tests belong to which Tenant and
  lets the suite grow with each Tenant. Each extra build would repeat the
  gate's slowest step, so the e2e specs share one.

## Rejected alternatives

- **Listing the Human-only files in this ADR.** Two attempts each went stale
  the next time the list changed.
- **Judging risk by file path alone.** A path cannot show a new dependency,
  untested runtime behaviour or where a PR came from.
- **A human merges every PR except a low-risk tier** (content only, or one
  Tenant's layer). In practice only a few scheduled Skills ever merged on
  green, and every ordinary PR waited for a person. The owner chose to let
  agents merge their own PRs, with this ADR naming the exceptions.
- **One e2e spec for every Tenant, to keep L2 to one build.** It assumed each
  spec builds the app. Once specs reuse the gate's build, a spec per Tenant
  costs no extra build and runs in parallel.
- **Relying on the build to validate content.** Nuxt Content coerces
  wrong-typed frontmatter and skips an unparseable file with only a warning,
  so the build catches neither.

## When to revisit

- CI passes a PR classified as Inert that the full gate would have failed.
  Then the classifier is wrong: tighten `isInert` or drop the skip.

## Consequences

- Strict Collection schemas do two jobs: they are the content contract and the
  L1 check.
- The files that decide the Gate's steps and who merges (`scripts/gate.ts`,
  `scripts/merge-pr.ts`, the rule's `paths`) are themselves Human-only.
- `tests/unit/gate-scope.spec.ts` catches code outside a Skill importing from
  its folder, but not a new build step that reads a file there. Keeping build
  inputs out of Skill folders stays review's job.
