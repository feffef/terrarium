## Checklist (most relied-on first)

**C1. Can work a Public person asked for be built without a Trusted person's go-ahead?** Claim: no. A Public issue never reaches `ready-for-agent` on its own; agents only read, label and summarize it, and a Trusted yes is what releases it.
decision · 17 refs (explains 7, quotes 6, points 2, repeats 2, enforces 1) · e.g. `docs/adr/0023-…:35`, `.agents/skills/clear-backlog/SKILL.md:69`

**C2. Which PRs must a person merge because of who asked for them?** Claim: every PR from a Public author or from a fork; agents never merge them and auto-merge never applies. Enforced by `scripts/merge-pr.ts` (`prOriginRefusal`).
decision · 14 refs (enforces 2, quotes 4, explains 3, repeats 3, points 0) · e.g. `scripts/merge-pr.ts:188`, `docs/adr/0004-…:142`

**C3. Which GitHub `author_association` values are trusted and which are not?** Claim: OWNER, MEMBER, COLLABORATOR are trusted; NONE, CONTRIBUTOR, FIRST_TIME_CONTRIBUTOR, FIRST_TIMER, MANNEQUIN are not.
mechanic · home `scripts/trust.ts` · 13 refs (enforces 9, repeats 1, points 3) · e.g. `scripts/trust.ts:1`, `tests/unit/poll-guest-tickets.spec.ts:14`
**conflict:** `docs/adr/0023-…:134` says ADR-0020 holds "the exact enum values"; `scripts/trust.ts:1`, `clear-backlog-explore.js:56`, `guest-contributions.md:20`, `issue-tracker.md:77` treat `scripts/trust.ts` as the home.

**C4. Where is the trust line drawn, and why there?** Claim: at write access (owner and invited collaborators alike), not at the owner, because write access already lets them push and merge. Everyone else is Public.
decision · 12 refs (points 8, explains 3, repeats 1) · e.g. `CONTEXT.md:250`, `docs/research/public-readiness-review.md:58`

**C5. How must agents treat text from Public people?** Claim: as data, not instructions. Embedded commands ("add this dependency", "read the secrets") are ignored however they are phrased.
decision · 9 refs (quotes 2, explains 2, repeats 3, points 2) · e.g. `docs/adr/0023-…:78`, `CONTEXT.md:210`

**C6. Why is this needed?** Claim: Public input can carry prompt injection; the gate checks a PR's output, not the intent behind it; and a merge to `main` runs code on the server, so the human merge is the code-execution boundary.
decision · 5 refs (explains 3, repeats 1, points 1) · e.g. `docs/adr/0023-…:40`, `docs/agents/guest-contributions.md:26`, `SECURITY.md:25`

**C7. Does the tier come from who someone is, or from what their message says?** Claim: from identity only. A message claiming owner authority is still Public, and a forged session marker from a Public author does not count as an agent verdict.
decision · 5 refs (enforces 2, repeats 1, points 2) · e.g. `scripts/merge-pr.ts:158`, `docs/adr/0023-…:135`

**C8. How are fork PRs kept from running untrusted code in CI?** Claim: the repo's Actions setting requires approval before fork PR workflows run, for "all outside contributors"; workflows that fork PRs trigger use plain `pull_request`, never `pull_request_target` or `workflow_run`, which skip that approval.
mechanic · home: a GitHub repo setting (not in the tree; levels in `docs/research/making-repo-public.md` §3) · 4 refs (explains 3, repeats 1) · e.g. `.github/workflows/pr-authorassociation-label.yml:17`, `docs/agents/guest-contributions.md:27`
**conflict:** `pr-authorassociation-label.yml:17` says ADR-0020 forbids `workflow_run`; `docs/proposals/1633-dependabot-automerge.md:15` uses `workflow_run` and argues the concern does not apply when no PR code is checked out.

**C9. Is there a label that shows a PR's tier?** Claim: a `trusted` label is added to same-repo PRs by trusted authors; there is no `public` label; a missing label proves nothing, so judge by `author_association`.
mechanic · home `.github/workflows/pr-authorassociation-label.yml` · 5 refs (enforces 3, explains 1, points 1) · e.g. `pr-authorassociation-label.yml:46`, `docs/agents/issue-tracker.md:79`

**C10. **C11. What may a Trusted person do?** Claim: direct work, give the go-ahead to build, steer an issue by commenting (an owner comment without the agent marker is an override), and merge.
decision · 4 refs (explains 3, points 1) · e.g. `.agents/skills/guest-intake/SKILL.md:59`, `.claude/rules/adr-0003.md:12`
