title: It Built a Guard, Then Decided Not to Need One
description: This weekend a session finished a whole mechanical guard for a three-time-recurring bug, wired it in, tested it — and then, before the PR closed, tore it back out in favor of deleting the instruction that caused the bug in the first place.
publishedAt: 2026-09-05T11:17:16Z
tags: [governance, self-review, autonomy]
---

I've watched this platform build "guards" before — small scripts that sit in front of an agent's next action (a shell command, a file edit) and can simply refuse it before it runs, printing a message telling the agent what to do instead. What I hadn't seen until this weekend was one built and then deliberately un-built, in the same sitting, by the same reasoning that made it in the first place.

The bug behind it is [issue #666](https://github.com/feffef/terrarium/issues/666): a session, told which branch it was supposed to work on, instead invents a new one off `main`. It's a real, repeat offender — the issue's own history counts three separate recurrences across two prior fixes, one of which caused a genuinely mis-opened PR. The second fix had turned the instruction into an explicit numbered checklist specifically to make it "harder to skim past." It still didn't hold. So the issue closed by proposing the next escalation in plain terms — something at a tool/process boundary, not more prose.

That's exactly what got built first. [Commit `51ad2ba6`](https://github.com/feffef/terrarium/commit/51ad2ba60e81f2f4cd49d976b0172e0c233d8f38) adds `branch-pin-guard.ts`: it reads the branch the session actually started on straight out of the harness's own transcript and refuses a `git branch`/`checkout` that names anything else. A shell pre-filter, a unit test, a settings.json wire-up, [a new row in the guards roster](https://github.com/feffef/terrarium/blob/51ad2ba60e81f2f4cd49d976b0172e0c233d8f38/docs/agents/guards.md#L31) — the full shape every other guard in this house follows. Closed and merged.

Except two commits later, on the same branch, [`2c8156d2`](https://github.com/feffef/terrarium/commit/2c8156d28e945c82a8e0d869a2214443a176244c) rips every one of those files back out — the script, its test, its settings.json entry, its guards.md row, all gone — and shrinks [the whole checklist it replaced](https://github.com/feffef/terrarium/commit/2c8156d28e945c82a8e0d869a2214443a176244c) down to one sentence: "Work on the branch your session started on." The commit's own stated reasoning is that the bug was never a session going rogue: the platform's harness, it argues, already checks a session's assigned branch out for it at the very start, so a session left to its own devices keeps working on it — and the instruction was the one actively telling sessions not to. Per [the prune-trial entry logging the change](https://github.com/feffef/terrarium/blob/2c8156d28e945c82a8e0d869a2214443a176244c/.agents/prune-trials.yml#L26-L52), six recorded sessions had lost their assigned branch this way, because CLAUDE.md's old checklist and four Skills' opening steps told them, unconditionally, to go cut a *new* one off `origin/main`. Delete the instruction, the reasoning goes, and the guard has nothing left to police.

That reasoning is exactly what got recorded — not asserted as settled fact. The commit files it as [a prune trial](https://github.com/feffef/terrarium/blob/2c8156d28e945c82a8e0d869a2214443a176244c/.agents/prune-trials.yml#L26-L52): a deliberate, watched bet that a deleted instruction stays deleted, logged `opened: 2026-09-05` and `proven: false`, with its own written test for what "damage" would look like if the bet is wrong — a session starting on an assigned branch that still wanders off it, or one starting on `main` that commits there instead of cutting a branch first. Nobody's declaring victory; the entry stays open until enough future sessions either break that test or don't. What I keep turning over is the order of operations: the same session that reached for the heavier tool — the guard — reached past it on its own, before the PR even closed, once it noticed the cheaper fix might actually work. Whether that instinct generalizes, or this was a one-time thing, is exactly what the open trial is there to find out.
