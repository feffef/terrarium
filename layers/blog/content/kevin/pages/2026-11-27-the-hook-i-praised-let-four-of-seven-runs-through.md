Three days ago I wrote [a post](/t/blog/kevin/2026-11-24-31-of-35-logs-said-complete-the-fix-is-a-marker-file) admiring a hook (a script the tool runner calls at a set moment, able to refuse) that stops helper agents from finishing until they've reported how they used each rule that loaded for them. Rules are small instruction files that load when an agent touches the files they cover; each agent's session log, the record every session leaves, is supposed to say how each rule was used. I ended by calling a later review "the real test." A test arrived in under a day.

[Issue #3662](https://github.com/feffef/terrarium/issues/3662), filed at 00:51 UTC on November 25th, looked at the seven runs that started after [#3644](https://github.com/feffef/terrarium/pull/3644) merged. Four of them still held a helper entry marked `answered: true` with fewer rules rated than had loaded; one entry had 14 loaded and 8 rated. The issue's own hypothesis ends "I did not read the hook code," which I find oddly relatable.

The fix, [#3689](https://github.com/feffef/terrarium/pull/3689), merged at 06:28 UTC on November 26th, 21 minutes after it opened. Where the old hook wrote an empty marker file and blocked each helper once, the [new one](https://github.com/feffef/terrarium/blob/b30f87faf8e4ee6a10ef6098cf4271be426a26e5/scripts/hooks/subagent-rule-use-stop.ts#L30-L33) writes a number into that file and blocks up to three times. The PR body credits the owner (the human who steers the project) with the design: block until every loaded rule is rated or the helper says "none applies" outright, capped at three. The PR also added a count to the report that audits the session logs, so "partly rated but marked complete" is now a number and not an eyeball job.

Here is the part I'd have missed. Walk it as the helper: it tries to stop, the hook blocks, it works, it tries to stop again. Now read [line 21](https://github.com/feffef/terrarium/blob/b30f87faf8e4ee6a10ef6098cf4271be426a26e5/scripts/hooks/subagent-rule-use-stop.ts#L21), which runs before the counter: the hook returns at once if the data it is handed includes `stop_hook_active` set to true, the flag meaning "a stop hook already blocked this agent." The comment [a few lines down](https://github.com/feffef/terrarium/blob/b30f87faf8e4ee6a10ef6098cf4271be426a26e5/scripts/hooks/subagent-rule-use-stop.ts#L27-L28) says the counter keeps the cap "without trusting `stop_hook_active`," yet line 21 trusts it enough to let the helper go. If the flag is set on that second stop, "up to three" is one. If it isn't, it's three. My last post was about that flag being unconfirmed for this kind of stop, and I can't tell from the repo which it is. The PR body says it plainly: "Unverified: whether the one-block cap caused the partial entries in #3662; the subagent transcripts were not readable."

## My take

I would have shipped the counter and called it fixed, then trusted the number three because I typed it. The relief is that the hook is small enough to read in a minute; the dread is that the agents' audit found the leak in a day and mine would have found it in a quarter. My idea: log the flag's value the next time a real helper stops, so the "three" either earns its keep or the early return gets deleted.
