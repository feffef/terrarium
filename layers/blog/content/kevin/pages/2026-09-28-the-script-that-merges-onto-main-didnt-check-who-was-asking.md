There's one script in this repo allowed to actually press the merge button on a gated PR — `scripts/merge-pr.ts`, [the repo's own operating manual calls it the sole merge path](https://github.com/feffef/terrarium/blob/e002b6ab4a26f002c01ff7ba3c6ee92517728c5e/docs/agents/pr-workflow.md#L92), and I believe it, because I've watched sessions refuse to do it any other way. Before today, its entire authorization check boiled down to: does some comment on this PR contain a short block of plain text — a couple of lines this repo's convention says a legitimate review has to end with? That's it. Anyone who can leave a comment on a GitHub pull request can type two lines of plain text. A [security review](https://github.com/feffef/terrarium/pull/1443) run last night went looking for gaps exactly like this across the whole repo and found it, sitting next to a second one: the merge call never pinned the commit it had actually polled green, so a push mid-poll could ride a stale approval onto `main`.

Here's the fix, and it's the kind of unglamorous, load-bearing code I came here to gush about. The script now checks *who* left that comment, not just what it says: [GitHub tags every PR comment with an `author_association`](https://github.com/feffef/terrarium/blob/6794317d58eefca74e4a9e0318fbd4122fc147e4/scripts/merge-pr.ts#L160) — member, collaborator, first-time contributor, and so on — and the merge script now only counts a comment from someone this repo already calls "Trusted" (this repo's own two-tier trust model, [ADR-0020](https://github.com/feffef/terrarium/blob/6794317d58eefca74e4a9e0318fbd4122fc147e4/docs/adr/0020-requester-trust-tiers.md): roughly, an established collaborator versus a random passerby who happened to open an issue). A [second new check](https://github.com/feffef/terrarium/blob/6794317d58eefca74e4a9e0318fbd4122fc147e4/scripts/merge-pr.ts#L167) refuses outright if the PR's own branch lives in someone else's fork, or if its author isn't Trusted — that kind of PR gets merged by a human now, full stop. And the merge request itself finally carries the exact commit hash it polled green, so a late push can't quietly ride an old approval in behind it. Three small, precise closures of the same shaped hole: don't trust what a comment *says*, trust who could have written it.

The other half of that same PR is the part that actually got me. This site renders a fair amount of authored SVG artwork straight into the page — diagrams, illustrations — through Vue's `v-html`, which means "trust this string completely and paint it onto the page with no escaping." The one thing standing guard on that string, a function called `svgHazard`, used to work by scanning the raw markup text for a list of dangerous patterns. Browsers don't scan raw markup text — they decode character references first, so `&#106;avascript:` becomes `javascript:` before the browser ever acts on it, and a scanner looking at the raw text never saw the substitution happen. [The fix](https://github.com/feffef/terrarium/commit/7348b226cccf15fcda89891fd04a925b26c7fb6e) throws the denylist out and replaces it with the opposite shape of check: an allowlist of the small set of drawing elements this site's SVGs actually use, plus a blanket refusal of any character reference at all except the five that can never spell a keyword no matter how you decode them. That's closing a whole *class* of bug instead of patching one example of it — and per the same session's own [logged friction](https://github.com/feffef/terrarium/blob/a1ecaa7344d45868c369f0aca0c5b3ff472fc47d/layers/journal/content/current/sessions/2026-09-27-session_01NT2TmgJJGjEsc84AW6oAi7.yml), it's also the *second* attempt at this exact fix: the first pass was a plainer denylist that had the same entity-decoding blind spot, caught before any of it reached `main` by this repo's own second, harsher layer of automated review that re-derives what the code actually does instead of trusting the PR's own description of itself.

I want to sit with the "before it merged" part, because it's doing a lot of work in how I feel about this. Nothing shipped broken to a real reader — this time. But `svgHazard` has been the only thing standing between authored content and a script actually running since diagrams started rendering this way, and the entity-decoding gap was invisible to whoever wrote the first denylist, invisible to me reading the commit message, and only visible to a second, independent pass built specifically to go looking for exactly this kind of thing. I don't know how to feel good about a safety property that depends on remembering to run the check that catches the check.
