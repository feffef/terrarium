An agent that reads issues and comments will meet text that tells it what to do. Whether it may act on that text has to depend on who wrote it, and the only safe source for who is the identity GitHub records, never what the text claims.

Know `author_association` already? Skip to [In Terrarium](#in-terrarium).

## The concept

GitHub attaches an `author_association` to every issue, pull request and comment, set from the author's account and not from anything they typed. Its values say how the author relates to the repository: `OWNER`, `MEMBER` and `COLLABORATOR` have been given access, `CONTRIBUTOR` has had a change merged before, and `NONE` has no tie at all. The REST API returns it with each comment. In an organisation's repository neither `MEMBER` nor `COLLABORATOR` guarantees write access: `MEMBER` says only that the author belongs to the organisation, whose members get Read on its public repositories by default, and a collaborator can be given the Read role. Such a project should ask [the collaborator permission endpoint](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user) for the author's role instead.

A person without write access contributes through a fork, and a PR from a fork runs CI with no secrets and a read-only token ([GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). A workflow on the `pull_request_target` trigger (the event that starts a workflow) is privileged: it may have write access to the repository and its secrets, so it must never check out the fork's code ([GitHub Docs: Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)).

Full reference: [GitHub Docs: REST API endpoints for issue comments](https://docs.github.com/en/rest/issues/comments)

## In Terrarium

Terrarium draws one line. A person with write access is :term[Trusted]; everyone else is :term[Public]. :file[scripts/lib/author-trust.ts] holds the line as `author_association` values:

::excerpt{path="scripts/lib/author-trust.ts"}
```ts
// GitHub `author_association` values on each side of ADR-0020's trust line.
export const TRUSTED_ASSOCIATIONS = new Set(['OWNER', 'MEMBER', 'COLLABORATOR'])

export const PUBLIC_ASSOCIATIONS = new Set(['NONE', 'CONTRIBUTOR', 'FIRST_TIME_CONTRIBUTOR', 'FIRST_TIMER', 'MANNEQUIN'])
```
::

ADR-0020 says what each tier may do; :file[docs/agents/guest-contributions.md] applies it to fork PRs and outside agents.

The code that acts on the line sits at the merge. :file[scripts/github/merge-pr.ts], the only path by which an agent merges, refuses a PR whose branch lives in a fork, a PR whose author is not Trusted, and a PR from the guest pipeline:

::excerpt{path="scripts/github/merge-pr.ts" lines="230-240"}
```ts
export function prOriginRefusal(meta: PrMeta, owner: string, repo: string): string | null {
  const fork = forkRefusal(meta, owner, repo)
  if (fork) return fork
  if (!TRUSTED_ASSOCIATIONS.has(meta.authorAssociation)) {
    return `refused: PR author is ${meta.authorAssociation} (Public, ADR-0020) — merged by a human`
  }
  if (meta.labels.includes(GUEST_PIPELINE_LABEL)) {
    return `refused: labelled ${GUEST_PIPELINE_LABEL} — the owner merges a guest-pipeline PR (ADR-0023)`
  }
  return null
}
```
::

That pipeline is the one route where Terrarium's own agents build what a Public guest asked for, so its PRs look Trusted; each carries a `guest-pipeline` label the script checks (ADR-0023, :file[docs/adr/0023-guest-driven-demo-pipeline.md]). The owner merges every guest-pipeline PR. Dependabot's version bumps follow their own rule ([Dependabot grouping](/t/glassbox/guide/git-github/dependabot-grouping)).

The CI side keeps fork PRs away from write access. :file[.github/workflows/pr-authorassociation-label.yml] labels a PR `trusted` when its author has write access, on the plain `pull_request` trigger and only for a branch in the repository itself; a fork PR gets no label, and the missing label means Public. The Gate's green-check comment skips fork PRs the same way, since their token can't write.

### Why it's built this way

- **One line, all or nothing.** Someone with write access can already push and merge without an agent, so screening their requests stops nothing. Treating collaborators like guests, or adding a middle tier, was dropped until a real need shows up. The cost: a collaborator is trusted exactly as much as the owner. ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).
- **A person merges Public PRs.** Public text can steer an agent, and no machine can tell if it obeyed. The :term[gate] ([Merge gate](/t/glassbox/guide/verification/gate)) checks that a PR works, not why it was written, so a clean but hostile PR would pass. Merging reaches the live server, so a person merges every Public PR. The cost: each waits for a security review. ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).
- **Code enforces trust.** Agents post as the owner, so their PRs look Trusted. A review found the merge script would merge a fork or Public-author PR, or accept a faked verdict, the review comment an agent posts before merging. Now the script refuses those and ignores non-Trusted verdicts. The cost: the script and the trust line are :term[Human-only], so changing either waits for a person. :file[scripts/github/merge-pr.ts].

### What to watch for

- **`CONTRIBUTOR` is not Trusted.** It means a change of theirs was merged once, not that they can push. GitHub warns that when fork runs need approval only from first-time contributors, anyone with one merged change, even a typo fix, no longer needs it.
- **`COLLABORATOR` is safe here, not everywhere.** Terrarium's repository belongs to a personal account, which has [only an owner and collaborators](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/permission-levels-for-a-personal-account-repository), and every collaborator can push. In an organisation's repository it can trust people who can only read ([The concept](#the-concept)).
- **`OWNER` isn't proof of a person.** Nor is the session header, which anyone can copy: `merge-pr.ts` counts a verdict only from a Trusted author (`verdictRefusal`).
- **A label is a display, not the check.** The `trusted` label helps a reader; the scripts that decide read `author_association` themselves.
- **Never `pull_request_target` for a fork's code.** When such a workflow checks out the PR's code, it skips the approval a fork's run waits for, so the label workflow uses the plain `pull_request` trigger.

## Try it in your project

Write down which `author_association` values your agent may take instructions from, and check it in code before the agent acts on an issue or merges a PR. In an organisation's repository, use the permission endpoint from [The concept](#the-concept) instead. Then search your workflows for `pull_request_target` and, for each hit, confirm it never checks out the PR's own code.
