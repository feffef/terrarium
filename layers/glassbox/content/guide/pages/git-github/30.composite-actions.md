GitHub Actions is GitHub's CI: a workflow file in the repository says which events start a run and which jobs and steps run. A workflow can hold every step, but it doesn't have to. Terrarium keeps its :term[gate] workflow to a few lines and moves the steps into a composite action, a bundle of steps in a file of its own. A cloud session, a Claude Code session that runs by default on infrastructure Anthropic manages, can push the action but not the workflow; the concept below says why.

Know GitHub Actions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A GitHub Actions workflow is a YAML file in `.github/workflows/`. Its [workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) has three main keys: `on` names its triggers, the events that start a run, such as `pull_request`; `permissions` says what the run's `GITHUB_TOKEN` may do; and `jobs` lists the jobs. Each job runs on a runner, a fresh machine GitHub provides or one you host, and holds steps that run in order. A step either runs a shell command (`run`) or calls an action (`uses`), a packaged step such as `actions/checkout`, which puts the repository on the runner.

Steps can also move out of the workflow into a file of their own. A [composite action](https://docs.github.com/en/actions/tutorials/create-actions/create-a-composite-action) bundles a list of steps into one step. It is a folder with an `action.yml` whose `runs.using` is `composite`, and each of its `run` steps names its `shell`. It can live in the repository that uses it, and GitHub suggests `.github/actions/`. A workflow calls it by its path, `uses: ./.github/actions/<name>`, after a checkout has put that folder on the runner. A composite action can't read the `secrets` context, so a workflow that needs a secret inside it passes the secret in as an input.

Its usual purpose is reuse: write a step list once and call it from any job in any workflow, instead of copying it. It is the wrong tool when the work needs jobs of its own, or a different runner from the job that calls it: a [reusable workflow](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations) holds whole jobs, and each picks its runner. For steps that only one job runs, moving them out adds a file to read and saves no copy, unless the move itself is the point, as below.

A workflow file and a composite action are guarded differently. A token needs GitHub's `workflow` scope to add or update a workflow file, as [GitHub Docs: Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) describes, and [workflows are defined in `.github/workflows/`](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows); a composite action's `action.yml` sits outside that folder.

Full reference: [GitHub Docs: Understanding GitHub Actions](https://docs.github.com/en/actions/get-started/understand-github-actions)

## In Terrarium

Terrarium's workflows live in `.github/workflows/`. :file[.github/workflows/pr-authorassociation-label.yml] labels a pull request on the `pull_request` trigger's `opened` and `reopened` types; [Author trust](/t/glassbox/guide/git-github/author-trust#in-terrarium) explains the label. :file[.github/workflows/gate.yml] runs the :term[gate] in CI on `pull_request` and on a `push` to `main`, and its whole job is a full-history checkout and one call. Its `fetch-depth: 0` fetches every commit, not only the latest:

::excerpt{path=".github/workflows/gate.yml" lines="15-22,27,31-33"}
```yaml
  gate:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v7
        with:
          # …
          fetch-depth: 0
      # …
      - uses: ./.github/actions/gate
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
```
::

The workflow keeps only the triggers, the permissions, the runner, the checkout and the token. Everything else is in :file[.github/actions/gate/action.yml], which declares the token as an input, marks itself `composite`, and names a `shell` for each `run` step:

::excerpt{path=".github/actions/gate/action.yml" lines="8-16,24-26"}
```yaml
inputs:
  github-token:
    description: Token for the doorbell comment. Passed in because the `secrets` context is unreachable inside a composite action.
    required: false
    default: ''

runs:
  using: composite
  steps:
    # …
    - name: Install
      shell: bash
      run: pnpm install --frozen-lockfile
```
::

After setting up Node and pnpm and installing the dependencies, the action runs the step that decides whether the slow checks may be skipped, each check as its own named step, and a last step that comments on the PR when the gate is green. A session subscribed to a PR hears about its comments and failed checks, not a passing one: this comment, which the action calls the doorbell, is how a green gate reaches it. The comment step reads the token from `inputs.github-token`, skips a PR from a fork and can't turn the gate red.

A cloud session's token lacks the `workflow` scope; a local session, one on the owner's own computer, pushes with the owner's key, which has it. [Cloud sessions](/t/glassbox/guide/agents/cloud-sessions) shows the hook that denies a cloud session's workflow edit.

The steps are also written in the `gate` script in :file[package.json] and the tier lists in :file[scripts/gate/gate.ts]. A test, :file[tests/unit/gate-parity.spec.ts] (the parity test), fails when these and the action run different steps, in a different order, or with different skip conditions. [Merge gate](/t/glassbox/guide/verification/gate) explains the tiers and the skip.

### Why it's built this way

- **Only what can't move stays in the workflow.** The push fence is the limit that a cloud session's token can't push `.github/workflows/`. With every step there, each gate change waited for a person to copy YAML. The fence covers that folder only, so setup, install and the steps moved to the action. The cost: a cloud session hands a trigger or permission change to a person. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).
- **Pushable files already steered CI.** Editing the steps in the workflow needed a person to copy YAML, but pushable files such as `package.json` already set what CI runs, so moving the steps adds no new reach. CI runs the PR's own copy of each, and a person reviewing the merge is what guards the gate. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).
- **One set of steps, checked by a test.** The local gate's list was pushable, but the CI list sat in the workflow, past the push fence. A new check reached the local gate while its CI step waited, so CI checked less, unnoticed. With every copy pushable, the parity test catches that drift. The cost: it sees which steps run, not what each does. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).

### What to watch for

- **Pushable is not mergeable.** The workflow and the action are both on the :term[human-only] list in :file[.claude/rules/adr-0004-human-merge.md], so an agent can change the action, but a person merges the change.
- **CI runs the PR's own copy.** A local `uses: ./…` action comes from the checkout, so a PR that edits the action is checked by its edited version.

## Try it in your project

Move the steps of one CI job into `.github/actions/<name>/action.yml` and leave the workflow with its triggers, permissions, checkout and a single `uses: ./.github/actions/<name>`:

```yaml
# .github/actions/check/action.yml
name: Check
description: The checks CI runs
runs:
  using: composite
  steps:
    - name: Lint
      shell: bash
      run: npm run lint
    - name: Test
      shell: bash
      run: npm test
```

```yaml
# the job's steps in .github/workflows/ci.yml
    steps:
      - uses: actions/checkout@v7
      - uses: ./.github/actions/check
```

On the Actions tab, open the latest run: the job lists one step, `Run ./.github/actions/check`, and its log holds a `Run npm run lint` and a `Run npm test` group, one per action step. Then add a check that fails when the action and your local command differ. With `"check": "npm run lint && npm test"` in `package.json`, `node parity.cjs` exits 0; drop `npm run lint &&` from the script and it prints both lists and exits 1:

```js
// parity.cjs
const fs = require('fs')
const yml = fs.readFileSync('.github/actions/check/action.yml', 'utf8')
const ci = [...yml.matchAll(/^\s+run: (.+)$/gm)].map((m) => m[1]).join(' && ')
const local = require('./package.json').scripts.check
if (ci !== local) { console.error(`CI:    ${ci}\nlocal: ${local}`); process.exit(1) }
```
