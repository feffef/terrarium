A GitHub Actions workflow can hold every step of a CI job, but it doesn't have to. Terrarium keeps its workflow file to a few lines and moves the steps into a composite action: a cloud session can push the action, but not the workflow.

Know composite actions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A GitHub Actions workflow is a YAML file in `.github/workflows/`. It says when CI runs (its triggers, such as `pull_request`), what its token may do (`permissions`), and which jobs and steps run.

A composite action bundles a list of steps into one step. It is a folder with an `action.yml` whose `runs.using` is `composite`, and each of its `run` steps names its `shell`. It can live in the repository that uses it, and GitHub suggests `.github/actions/`. A workflow calls it by its path, `uses: ./.github/actions/<name>`, after a checkout has put that folder on the runner. A composite action can't read the `secrets` context, so a workflow that needs a secret inside it passes the secret in as an input.

Its usual purpose is reuse: write a step list once and call it from any job in any workflow, instead of copying it. It is the wrong tool when the work needs jobs of its own, or a different runner from the job that calls it: a [reusable workflow](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations) holds whole jobs, and each picks its runner. For steps that only one job runs, moving them out adds a file to read and saves no copy, unless the move itself is the point, as below.

The two files are guarded differently. A token needs GitHub's `workflow` scope to add or update a workflow file, as [GitHub Docs: Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps) describes, and [workflows are defined in `.github/workflows/`](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflows); a composite action's `action.yml` sits outside that folder.

Full reference: [GitHub Docs: Creating a composite action](https://docs.github.com/en/actions/tutorials/create-actions/create-a-composite-action)

## In Terrarium

:file[.github/workflows/gate.yml] runs the :term[Gate] in CI, and its whole job is a full-history checkout and one call:

::excerpt{path=".github/workflows/gate.yml" lines="15-22,27,31-33"}
```yaml
  gate:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v7
        with:
          # …
          fetch-depth: 0
      # …
      - uses: ./.github/actions/gate
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
```
::

The workflow keeps only the triggers, the permissions, the runner, the checkout and the token. Everything else is in :file[.github/actions/gate/action.yml], which declares the token as an input, marks itself `composite`, and names a `shell` for each `run` step:

::excerpt{path=".github/actions/gate/action.yml" lines="8-16,24-26"}
```yaml
inputs:
  github-token:
    description: Token for the doorbell comment. Passed in because the `secrets` context is unreachable inside a composite action.
    required: false
    default: ''

runs:
  using: composite
  steps:
    # …
    - name: Install
      shell: bash
      run: pnpm install --frozen-lockfile
```
::

After setting up Node and pnpm and installing the dependencies, the action runs the step that decides whether the slow checks may be skipped, each check as its own named step, and a last step that comments on the PR when the Gate is green: the comment wakes a session subscribed to the PR, and the action calls it the doorbell. The comment step reads the token from `inputs.github-token`, skips a PR from a fork and can't turn the Gate red.

A cloud session's token lacks the `workflow` scope; a local session pushes with the owner's key, which has it. [Cloud sessions](/t/glassbox/guide/agents/cloud-sessions) shows the hook that denies a cloud session's workflow edit.

The same step list also lives in the `gate` script in :file[package.json] and the tier lists in :file[scripts/gate/gate.ts]. A test, :file[tests/unit/gate-parity.spec.ts] (the parity test), fails when these and the action run different steps, in a different order, or with different skip conditions. [Merge gate](/t/glassbox/guide/verification/gate) explains the tiers and the skip.

### Why it's built this way

- **Only what can't move stays in the workflow.** A cloud session can't push `.github/workflows/`, the push fence. With every step there, each Gate change waited for a person to copy YAML. The fence covers that folder only, so setup, install and the steps moved to the action. The cost: a cloud session hands a trigger or permission change to a person. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).
- **Pushable files already steered CI.** Moving the steps into one gives agents no new power over what CI runs, which was already set by files such as `package.json`, and CI runs the PR's own copy of each. A person reviewing the merge is what guards the Gate. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).
- **One list, checked by a test.** With the steps split across the push fence, a new check reached the local Gate while its CI step waited for a person, so CI checked less, unnoticed. With both halves pushable, the parity test catches that drift. The cost: it sees which steps run, not what each does, so a script emptied of its work still passes. ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).

### What to watch for

- **Pushable is not mergeable.** Both files are on the :term[Human-only] list in :file[.claude/rules/adr-0004-human-merge.md], so an agent can change the action, but a person merges the change.
- **CI runs the PR's own copy.** A local `uses: ./…` action comes from the checkout, so a PR that edits the action is checked by its edited version.

## Try it in your project

Move the steps of one CI job into `.github/actions/<name>/action.yml` and leave the workflow with its triggers, permissions, checkout and a single `uses: ./.github/actions/<name>`. Then add a test that reads the action and fails when its steps differ from the command you run locally.
