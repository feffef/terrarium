A GitHub Actions workflow can hold every step of a CI job, but it doesn't have to. Terrarium keeps its workflow file to a few lines and moves the steps into a composite action, because agents can push one of those files and not the other.

Know composite actions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A GitHub Actions workflow is a YAML file in `.github/workflows/`. It says when CI runs (its triggers, such as `pull_request`), what its token may do (`permissions`), and which jobs and steps run.

A composite action bundles a list of steps into one step. It is a folder with an `action.yml` whose `runs.using` is `composite`, and each of its `run` steps names its `shell`. It can live in the repository that uses it, and GitHub suggests `.github/actions/`. A workflow calls it by its path, `uses: ./.github/actions/<name>`, after a checkout has put that folder on the runner. A composite action can't read the `secrets` context, so a workflow that needs a secret inside it passes the secret in as an input.

The two files are guarded differently. A token needs GitHub's `workflow` scope to add or change a file in `.github/workflows/`; other files, including `.github/actions/`, need only ordinary write access. The scope is described in [GitHub Docs: Scopes for OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps).

Full reference: [GitHub Docs: Creating a composite action](https://docs.github.com/en/actions/tutorials/create-actions/create-a-composite-action)

## In Terrarium

:file[.github/workflows/gate.yml] runs the :term[Gate] in CI, and its whole job is a checkout and one call:

::excerpt{path=".github/workflows/gate.yml" lines="14-33"}
```yaml
jobs:
  gate:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v7
        with:
          # …
          fetch-depth: 0

      # Everything the Gate actually does. `secrets` is unreachable inside a
      # composite action, so the doorbell's token is passed in here.
      - uses: ./.github/actions/gate
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
```
::

The workflow keeps only what can't move: the triggers, the permissions, the runner, a full-history checkout and the token. Everything else is in :file[.github/actions/gate/action.yml]: installing Node and pnpm, the dependencies, the step that decides whether the slow checks may be skipped, each check as its own named step, and a last step that comments on the PR when the Gate is green. That comment is there because CI success doesn't reach a session waiting on the PR, and a new comment does. It skips a PR from a fork, whose token can't write, and it can't turn the Gate red.

Agent sessions can't push `.github/workflows/`: their token lacks the `workflow` scope. :file[scripts/workflow-edit-guard.ts] stops an agent's edit to a workflow file before it becomes a commit that the push would reject. A change that must go into the workflow, such as a new trigger, goes to a person as a :term[Proposal]. Because the steps sit in the action, an agent can change what CI runs in an ordinary PR.

The step list now has three copies: the `gate` script in :file[package.json], the tier lists in :file[scripts/gate.ts], and the action. :file[tests/unit/gate-parity.spec.ts] fails when they run different steps, in a different order, or with different skip conditions. [The Gate](/t/glassbox/guide/terrarium-practice/gate) explains the tiers and the skip.

### Why it's built this way

When the steps lived in the workflow file, every Gate change waited for a person to copy YAML by hand, and a new check could run locally while CI still lacked it, with nothing to notice the gap. With both halves pushable, a test can keep them equal: ADR-0026 (:file[docs/adr/0026-gate-workflow-thin-shell.md]).

### What to watch for

- **Pushable is not mergeable.** Both files are :term[Human-only], so an agent can change the action, but a person merges the change.
- **CI runs the PR's own copy.** A local `uses: ./…` action comes from the checkout, so a PR that edits the action is checked by its edited version. The parity test catches a step that goes missing, not one emptied of its work; a person reviewing the merge catches that.
- **Secrets stop at the action's edge.** Inside a composite action, `secrets` is empty; pass what a step needs as an input, as `github-token` is here.
- **Each check stays its own step.** One step running `pnpm gate:scoped` would be shorter, but the run's summary would no longer name the check that failed.

## Try it in your project

Move the steps of one CI job into `.github/actions/<name>/action.yml` and leave the workflow with its triggers, permissions, checkout and a single `uses: ./.github/actions/<name>`. Then add a test that reads the action and fails when its steps differ from the command you run locally.
