Work an agent can't finish in one session has to wait somewhere a later session will find it. In Terrarium that place is a GitHub issue, and a label on the issue usually says what may happen to it next: wait for more facts, go to an agent, or go to a person.

Know GitHub labels already? Skip to [In Terrarium](#in-terrarium).

## The concept

A label is a name, a color and a description that you attach to issues, pull requests and discussions. A label belongs to one repository and can go on any issue in it. Anyone with write access can create, edit or delete a label; anyone with triage access can apply one.

You can [filter an issue list by label](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests#filtering-issues-and-pull-requests-by-labels), so a label can stand for a step in your own workflow, such as "ready to build", and the filter shows the queue for that step. GitHub doesn't know the labels mean that. Nothing stops an issue from carrying two steps at once or none at all, so the rules for moving between steps are yours to write down and keep.

Full reference: [GitHub Docs: Managing labels](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)

## In Terrarium

Proposals, bugs and follow-ups go in issues, and the open issues are the work queue. Its states come from the installed `triage` :term[skill] ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)). :file[docs/agents/triage-labels.md] maps each state to the label string used here and says what it means. `needs-triage` means a maintainer must evaluate the issue, and `needs-info` that it waits on the reporter for more information. `ready-for-agent` means it is fully specified for an agent working alone, and `ready-for-human` that it needs a person for a judgment call, a decision or a human merge. Another state, `wontfix`, marks a request that will not be actioned.

That file also says who may set each state. It names `to-spec` and `to-tickets`, installed planning skills that publish a spec and its tickets as issues ([Planning skills](/t/glassbox/guide/skill-pack/planning-with-the-pack)). A spec is an ordinary issue with its user stories linked as sub-issues; one on hold says in its body not to build it yet. `triage`, `auto-triage`, `clear-backlog` and the guest pipeline set the two ready labels, `harvest` files its issues as `ready-for-human`, and every other skill, the planning ones included, files `needs-triage`, except a spec on hold; a trusted user may also label an issue `ready-for-agent` by hand (ADR-0003, :file[docs/adr/0003-agent-operating-model-and-governance.md]). `harvest` turns session-log ideas into :term[seedling] issues, and the guest pipeline builds what a :term[public] user asks for on their own issue. The doc's rule for who sets a state reads:

::excerpt{path="docs/agents/triage-labels.md" lines="20-31"}
```md
> **Who sets the state.** Only triage sets `ready-for-agent` and
> `ready-for-human`: `triage`, `auto-triage`, `clear-backlog` and the guest
> pipeline. The one exception: `harvest` files its `Seedling:` issues as
> `ready-for-human`, since a Trusted user's green light is what they wait for.
> Every other Skill, installed Skills included, files its issues
> `needs-triage`, however settled they look (`to-spec` and `to-tickets` say
> `ready-for-agent`; don't apply it), except a spec on hold, which carries no
> label (`issue-tracker.md`, Specs).

> **Requester-trust gate.** A Public issue reaches `ready-for-agent` only
> after a Trusted user approves it (ADR-0020), except in the guest pipeline
> (ADR-0023). What the `auto-triage` sweep may label: ADR-0022.
```
::

The `triage` skill, in :file[.agents/skills/triage/SKILL.md], expects every triaged issue to carry one state and one category, `bug` or `enhancement`.

A `ready-for-agent` label a :term[trusted] user sets is an approval to build; [Human-in-the-loop agents](/t/glassbox/guide/terrarium-practice/human-in-the-loop) says why, and when a run may set it instead.

A person runs `triage` on the issues they pick. :file[.agents/skills/auto-triage/SKILL.md] is the sweep: one unattended pass, started by a person, that applies `triage`'s rules to the open issues it picks:

::excerpt{path=".agents/skills/auto-triage/SKILL.md" lines="26-40"}
```md
For everything else, fetch the **most recent comment** and check who wrote it:

- **A `Seedling:` issue** (filed by `harvest`) **stays `ready-for-human`** until a
  Trusted user relabels it or says to build it. Skip it, even uncommented or
  with a human comment that only asks a question.
- **No state label, `needs-triage`, or no comments.** Always eligible, whoever
  filed it or commented last, except an on-hold spec or sub-issue
  (`docs/agents/issue-tracker.md`'s Specs), which follows the next bullet.
- **Any other state** (`needs-info`, `ready-for-human`, even `ready-for-agent`)
  **is eligible when its most recent comment is human-authored.**
  Every agent comment carries an ADR-0017 mark, so a comment without one is human (`isAiAuthored`). Never go by the author or `author_association`: agents post as the owner.

Skip any other ticket whose most recent comment is already AI's own. That keeps
repeated sweeps **idempotent**: once an agent answers the human's comment,
the ticket stays quiet until a human writes again, whatever its label reads.
```
::

Idempotent means a repeated sweep changes nothing more. The mark is the session header every agent post carries ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution)). The sweep's other rules are in its skill and ADR-0022 (:file[docs/adr/0022-autonomous-triage-sweep.md]).

A request that gets `wontfix` is closed. Its closing comment depends on why. A feature that already exists gets a pointer to where it lives, a rejected bug a polite explanation, and a rejected enhancement an out-of-scope record. A record is one file per rejected idea in :file[.out-of-scope/], in the format :file[.agents/skills/triage/OUT-OF-SCOPE.md] sets: what the project won't do and why, with every later request for the same idea added to it. Before it recommends anything, `triage` reads every record and shows any that resembles the new request. The sweep closes only what the repo can prove, an already-implemented request or a duplicate; it sends a rejection as out of scope to `ready-for-human` and writes a record only on a trusted user's confirm (:file[.agents/skills/auto-triage/SKILL.md]).

Agents build from the `ready-for-agent` filter: :file[.agents/skills/clear-backlog/SKILL.md] takes every open issue in it, plus the ones the sweep above would pick up, and carries each to a merged PR, a closed issue or a question for the owner. It leaves out any issue with a `wayfinder:*` label, which [Wayfinder](/t/glassbox/guide/skill-pack/wayfinder), an installed skill that maps a big effort as issues, drives with the owner.

### Why it's built this way

- **The installed names, unchanged.** Installed skills name the states by role, and each label string here matches its role exactly, so an installed skill's own wording is already the label to set. The cost: a label name changed here on purpose is a decision to keep, so it must never be overwritten from the installed skill's template. :file[docs/agents/triage-labels.md]
- **The label holds the queue, the comment holds the turn.** A label says where an issue waits, not whether a person wrote since an agent last answered, and no label query can express that. So the sweep reads every open issue's latest comment and stays quiet once an agent has replied. The cost: each sweep fetches every open issue's comments. :file[.agents/skills/auto-triage/SKILL.md]
- **Public issues wait for a person.** A :term[public] author's issue goes to `ready-for-human` until a trusted user approves it, since public text can steer an agent ([Author trust](/t/glassbox/guide/git-github/author-trust) gives that reason for public PRs). The cost: a PR built from it still waits for a person to merge ([Protected paths](/t/glassbox/guide/terrarium-practice/protected-paths#what-to-watch-for)). ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).
- **A rejection waits for a person.** Whether an idea is out of scope is a judgement call, and a wrong close hides a request. The cost: every rejection waits for a person. ADR-0022 (:file[docs/adr/0022-autonomous-triage-sweep.md]).

### What to watch for

- **A label write replaces the whole set.** Setting labels through the GitHub MCP tools sends the full list the issue ends with, so a call that names only the new state drops the category and any `wayfinder:` label; :file[docs/agents/github-integration.md] lists this trap.
- **A comment can claim a move that never happened.** An agent may write "moved to `ready-for-agent`" and fail to change the label. :file[scripts/github/check-triage-drift.ts] lists the issues whose most recent agent comment claims a label the issue doesn't carry. It is a command you run yourself. It checks a capped number of open issues, which its argument raises, and knows only a short list of phrasings, so a claim worded another way slips past.
- **Ready doesn't mean still needed.** An issue can wait long enough for other work to solve it, so :file[docs/agents/issue-tracker.md] has an agent check for a merged fix before it builds a `ready-for-agent` issue.
- **A missing label doesn't always mean untriaged.** An issue with no label is usually untriaged, but a spec on hold carries none either, and the sweep picks it up only when a person wrote its latest comment.
- **Reread a record before you lean on it.** Its reasons are as of when it was written, and the skills that audit or prune instructions skip :file[.out-of-scope/], so no check notices one going stale (:file[.agents/skills/prune-trial/SKILL.md]).

## Try it in your project

Create a state label in your repository for each step an issue can wait in, and write one short doc that says, for each, who may set it and what an agent may do with an issue that carries it. With the [GitHub CLI](https://cli.github.com/manual/):

```sh
gh label create needs-triage --description "A maintainer needs to evaluate this issue"
gh label create needs-info --description "Waiting on the reporter for more information"
gh label create ready-for-agent --description "Fully specified for an agent working alone"
gh label create ready-for-human --description "Needs a person: a judgment call, a decision or a human merge"
```

Then tell your agent to take work only from this queue:

```sh
gh issue list --label ready-for-agent --state open
```

An issue you label `ready-for-agent` appears in it. Tell the agent to move an issue it can't finish to `needs-info` or `ready-for-human` with a comment that says why; the issue then drops out of the queue:

```sh
gh issue edit 42 --remove-label ready-for-agent --add-label needs-info
```
