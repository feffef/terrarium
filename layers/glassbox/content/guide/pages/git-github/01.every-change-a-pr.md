A change pushed straight to the main branch is seen only after it has landed. A pull request puts the change where people and machines can look at it first, and Terrarium sends every change, an agent's included, through one.

Know pull requests already? Skip to [In Terrarium](#in-terrarium).

## The concept

A pull request (PR) proposes to merge the commits on one branch, the head, into another, the base. It gathers what a reviewer needs in one place: a description, the diff, comments and reviews, and the results of automated checks. Nothing reaches the base branch until someone merges the PR.

GitHub describes two ways to work with PRs. In the shared repository model, everyone who changes the code has push access to one repository and opens a PR from a topic branch there. In the fork and pull model, a contributor without push access copies the repository into a fork, pushes there, and opens a PR back to the original. Either way the merge is the one step that changes the base branch, so it is where checks and review belong.

A PR only helps while someone works on it. One that nobody opens stays invisible to review, and one that nobody follows goes stale while its base branch moves on.

Full reference: [GitHub Docs: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

## In Terrarium

Terrarium uses the shared repository model for its own agents, which push branches to the repository itself. :file[docs/agents/pr-workflow.md] holds the steps from push to merge:

::excerpt{path="docs/agents/pr-workflow.md" lines="36-39,49-53,57-61"}
```md
## The recipe

1. Run `pnpm gate:scoped` and wait (a prose- or docs-only follow-up push may skip
   it, above). A red gate never merges.
<!-- … -->
4. Before merging, post your verdict as a PR comment, even a clean "merging
   as-is": the merge must never be the only trace. End it with a line
   `Reviewed: <sha>` naming the head commit your `code-review` run (or your
   Skill's own review step) covered; after any later push, review the new head
   and post a new verdict. Use `event=COMMENT` or
<!-- … -->
5. Land through `scripts/merge-pr.ts <pr-number>`, the only merge path. It
   refuses without your step-4 verdict naming the PR's head (#1276, #1844),
   and refuses a fork or
   Public-authored PR (ADR-0020), a `guest-pipeline` PR (ADR-0023) and one
   that changes a Human-only path (ADR-0004), each of which a human merges.
```
::

`pnpm gate:scoped` is the local run of the :term[Gate]. The same doc has the agent run it, and the `code-review` Skill, before a branch's first push, since the PR follows the push straight away. Once the PR is open, the agent subscribes to its activity. :file[scripts/merge-pr.ts] polls the PR's checks, merges on green, and refuses the cases the excerpt names.

The one change that skips a PR is the :term[session log], the record a session writes about its own work: :file[scripts/log-session.ts] commits that single file straight to `main`. [Session logs](/t/glassbox/guide/terrarium-practice/session-logs) follows it there.

### Why it's built this way

Agents here change a system that includes their own tools: the Skills, hooks and checks that steer them. A change pushed straight to `main` is seen only after it lands, and a bad one can break the next agent's work before anyone notices. A PR keeps every change reviewable and easy to undo, and it is where the :term[Gate] runs. The cost is that even a one-word typo fix needs a branch, a PR and a CI run. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).

Agents used to ask "shall I open a PR?", a question whose answer was always yes and which stalls a run nobody is watching. Later a rule let a system prompt's "no PR unless asked" win, and an agent then pushed finished, passing work and opened nothing, so the branch sat as a dead end until a person stepped in. Opening a PR merges nothing, since the Gate and the merge rules still decide, so Terrarium now always opens it. The cost: an instruction meant to keep a session review-only can no longer stop its PR once it pushes. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).

A person can't read every PR agents open, so the agent that wrote one also merges it on green, except for the few a person must merge. The written order "post your verdict, then merge" did not hold on its own: an agent once merged without a verdict, even after the doc had been reworded to stress that step. So the check moved into code. The merge script is the only way in, and it refuses until this session's verdict names the commit its review covered, which costs a fresh review after every push. :file[scripts/merge-pr.ts]

The session log is the one change that skips a PR. A log is worth most when every session writes one honestly, and a PR per log is a chore that makes agents skip or thin them; no PR fits every session anyway, since some open none and some several. A log is checked data that changes no code, so once it passes its schema it can't break the build. The cost is that the credential the landing script uses could push anything to `main`, and only that script narrows it to one file. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).

### What to watch for

- **A green check isn't an event.** A session subscribed to a PR hears about comments and failed checks, not a passing one, so Terrarium's CI posts a comment when the Gate is green.
- **Closing keywords close everything they name.** `Closes #N` in a PR description closes that issue when the PR merges, so Terrarium uses it only for an issue the PR completes and writes "relates to #N" otherwise.
- **The description is part of the change.** Reviewers judge a PR by what its description says it does, so a push that changes what the PR does updates its title and description too.
- **A PR from outside is a different case.** A PR from a fork or a :term[Public] author is never merged by an agent; [Trust tiers](/t/glassbox/guide/git-github/trust-tiers) explains why.

## Try it in your project

Give your agent one written rule: every change goes on a branch, and the agent opens the PR itself as soon as it pushes. Then name what it does next, such as answering review comments and fixing failed checks, until the PR is merged or closed.
