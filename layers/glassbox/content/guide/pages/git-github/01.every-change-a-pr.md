A change pushed straight to the main branch is seen only after it has landed. A pull request puts the change where people and machines can look at it first, and Terrarium sends every change, an agent's included, through one.

Know pull requests already? Skip to [In Terrarium](#in-terrarium).

## The concept

A pull request (PR) proposes to merge the commits on one branch, the head, into another, the base. It gathers what a reviewer needs in one place: a description, the diff, comments and reviews, and the results of automated checks. Nothing reaches the base branch until someone merges the PR.

GitHub describes two ways to work with PRs. In the shared repository model, everyone who changes the code has push access to one repository and opens a PR from a topic branch there. In the fork and pull model, a contributor without push access copies the repository into a fork, pushes there, and opens a PR back to the original. Either way the merge is the one step that changes the base branch, so it is where checks and review belong.

A PR only helps while someone works on it. One that nobody opens stays invisible to review, and one that nobody follows goes stale while its base branch moves on.

Full reference: [GitHub Docs: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

## In Terrarium

Terrarium uses the shared repository model for its own agents, which push branches to the repository itself. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]) sets the rule:

::excerpt{path="docs/adr/0003-agent-operating-model-and-governance.md" lines="10-17"}
```md
- **Every change is a PR.** It comes from a feature branch and passes the gate.
  A session log is the only change that goes straight to `main` (ADR-0009).
  Who merges, and which PRs wait for a human: ADR-0004.
- **Opening the PR.** Once a branch has a pushed commit that is not a session
  log, the agent opens its PR itself. It does not ask first, even when a
  harness or system prompt says not to open one.
- **Following it.** The agent watches the PR's activity and keeps working on
  it until it is merged, closed or taken over by a human.
```
::

The one exception is the :term[session log], the record a session writes about its own work. It is a single file in the Journal, committed straight to `main` (ADR-0009, :file[docs/adr/0009-session-logs-commit-directly-to-main.md]).

The steps around a PR are in :file[docs/agents/pr-workflow.md]. Before a branch's first push, the agent runs `pnpm gate:scoped`, the local run of the :term[Gate], and the `code-review` Skill on its diff, because the push is followed straight away by the PR. Once the PR is open, the agent subscribes to its activity, so new comments, reviews and failed checks arrive in its session. Before it merges, it posts its review verdict on the PR as a comment, so the merge is never the only trace. It then merges through :file[scripts/merge-pr.ts], the one merge path, which waits for green checks and refuses the PRs a person must merge.

Opening the PR is not the same as being allowed to build. An agent may propose any change by filing an issue, but it builds new work, such as a new Tenant, feature or Skill, only after a :term[Trusted] person approves it, by asking for it or by labelling its issue `ready-for-agent`.

### Why it's built this way

Agents change a system that includes their own tools, and a PR keeps each change reviewable and reversible. It is also where the Gate runs. Asking before opening one would stall unattended runs on a question whose answer is always yes: ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]). Who merges, and which PRs wait for a person: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **A green check isn't an event.** GitHub doesn't tell a waiting session that CI passed, so Terrarium's CI posts a comment when the Gate is green; [A thin CI workflow plus a composite action](/t/glassbox/guide/git-github/thin-ci-workflow) shows where that step lives.
- **Closing keywords close everything they name.** `Closes #N` in a PR description closes that issue when the PR merges, so Terrarium uses it only for an issue the PR completes and writes "relates to #N" otherwise.
- **The description is part of the change.** Reviewers judge a PR by what its description says it does, so a push that changes what the PR does updates its title and description too.
- **A PR from outside is a different case.** A PR from a fork or a :term[Public] author is never merged by an agent; [Trust tiers and fork safety](/t/glassbox/guide/git-github/trust-tiers) explains why.

## Try it in your project

Give your agent one written rule: every change goes on a branch, and the agent opens the PR itself as soon as it pushes. Then name what it does next, such as answering review comments and fixing failed checks, until the PR is merged or closed.
