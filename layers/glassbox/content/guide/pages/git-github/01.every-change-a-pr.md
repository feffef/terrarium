A change pushed straight to the main branch is seen only after it has landed. A pull request puts the change where people and machines can look at it first, and Terrarium sends every change, an agent's included, through one.

Know pull requests already? Skip to [In Terrarium](#in-terrarium).

## The concept

A pull request (PR) proposes to merge the commits on one branch, the head, into another, the base. It gathers what a reviewer needs in one place: a description, the diff, comments and reviews, and the results of automated checks. Nothing reaches the base branch until someone merges the PR.

GitHub describes two ways to work with PRs. In the shared repository model, everyone who changes the code has push access to one repository and opens a PR from a topic branch there. In the fork and pull model, a contributor without push access copies the repository into a fork, pushes there, and opens a PR back to the original. Either way the merge is the one step that changes the base branch, so it is where checks and review belong.

A PR only helps while someone works on it. One that nobody opens stays invisible to review, and one that nobody follows goes stale while its base branch moves on.

Full reference: [GitHub Docs: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

## In Terrarium

Terrarium uses the shared repository model for its own agents, which push branches to the repository itself. :file[docs/agents/pr-workflow.md] holds the steps from push to merge:

::excerpt{path="docs/agents/pr-workflow.md" lines="32-35,44-55"}
```md
## The recipe

1. Run `pnpm gate:scoped` and wait (a prose- or docs-only follow-up push may skip
   it). A red gate never merges.
<!-- … -->
4. Before merging, post your verdict as a PR comment, even a clean "merging
   as-is": the merge must never be the only trace. End it with a line
   `Reviewed: <sha>` naming the head commit your `code-review` run (or your
   Skill's own review step) covered; after any later push, review the new head
   and post a new verdict. Use `event=COMMENT` or `add_issue_comment`, never an
   APPROVE review: it fails on our own PRs, and on a fork PR it would fake the
   human merge authority [`guest-contributions.md`](./guest-contributions.md)
   reserves.
5. Land through `scripts/github/merge-pr.ts <pr-number>`, the only merge path; never
   call `enable_pr_auto_merge`. The script refuses what a human must merge
   (ADR-0004, ADR-0020, ADR-0023) and a PR without your step-4 verdict
   naming its head (why: #1276).
```
::

`pnpm gate:scoped` is the local run of the :term[Gate]. The same doc has the agent run it, and the `code-review` Skill, before a branch's first push, since the PR follows the push straight away. Once the PR is open, the agent subscribes to its activity. :file[scripts/github/merge-pr.ts] polls the PR's checks, merges on green, and refuses the cases the excerpt names.

The one change that skips a PR is the :term[session log], the record a session writes about its own work: :file[scripts/session/log-session.ts] commits that single file straight to `main`. [Session logs](/t/glassbox/guide/terrarium-practice/session-logs) follows it there.

### Why it's built this way

- **Review before landing.** Agents change their own tools (Skills, hooks, checks), so a bad change pushed straight to `main` can break the next agent unnoticed. A PR keeps changes reviewable and easy to undo, and is where the :term[Gate] runs. Cost: even a one-word fix needs a branch, PR and CI run; only session logs skip it ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs)). ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **Always open the PR.** Asking "shall I open a PR?" stalled unwatched runs, and a system prompt's "no PR unless asked" once stranded finished work on a branch. Opening a PR merges nothing, since the Gate and merge rules decide, so agents always open one. Cost: a review-only instruction can't stop a PR once the session pushes. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **The script checks the verdict.** An agent merges its own PR on green ([The Gate](/t/glassbox/guide/terrarium-practice/gate)) after posting a verdict, but the written order failed once. So the merge script refuses until this session's verdict names the commit reviewed. Cost: a fresh review after every push. :file[scripts/github/merge-pr.ts].

### What to watch for

- **A green check isn't an event.** A session subscribed to a PR hears about comments and failed checks, not a passing one, so Terrarium's CI posts a comment when the Gate is green.
- **Closing keywords close everything they name.** `Closes #N` in a PR description closes that issue when the PR merges, so Terrarium uses it only for an issue the PR completes and writes "relates to #N" otherwise. The merge script refuses a PR whose keywords would close an open `ready-for-human` issue.
- **The description is part of the change.** Reviewers judge a PR by what its description says it does, so a push that changes what the PR does updates its title and description too.
- **A PR from outside is a different case.** A PR from a fork or a :term[Public] author is never merged by an agent; [Trust tiers](/t/glassbox/guide/git-github/trust-tiers) explains why.

## Try it in your project

Give your agent one written rule: every change goes on a branch, and the agent opens the PR itself as soon as it pushes. Then name what it does next, such as answering review comments and fixing failed checks, until the PR is merged or closed.
