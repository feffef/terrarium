A change pushed straight to the main branch is seen only after it has landed. A pull request puts the change where people and machines can look at it first, and Terrarium sends every change, an agent's included, through one, except a session's own log.

Know pull requests already? Skip to [In Terrarium](#in-terrarium).

## The concept

A pull request (PR) proposes to merge the commits on one branch, the head, into another, the base. It gathers what a reviewer needs in one place: a description, the diff, comments and reviews, and the results of automated checks. Nothing reaches the base branch until someone merges the PR.

GitHub describes two ways to work with PRs. In the shared repository model, everyone who changes the code has push access to one repository and opens a PR from a topic branch there. In the fork and pull model, a contributor without push access copies the repository into a fork, pushes there, and opens a PR back to the original. Either way the merge is the one step that changes the base branch, so it is where checks and review belong.

A PR only helps while someone works on it. One that nobody opens stays invisible to review, and one that nobody follows goes stale while its base branch moves on.

Full reference: [GitHub Docs: Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

## In Terrarium

Terrarium uses the shared repository model for its own agents, which push branches to the repository itself. :file[docs/agents/pr-workflow.md] holds the steps. They start with a review and a local :term[gate] run before the PR opens, and end with the merge. That review is the `code-review` skill ([Engineering skills](/t/glassbox/guide/skill-pack/engineering-skills)). Pushing opens nothing; once the branch has passed that review and the gate, the agent opens the PR, then subscribes to the PR's activity, which brings its comments into the session, and keeps working on it until it is merged, closed or taken over by a person (ADR-0003, a short decision record: :file[docs/adr/0003-agent-operating-model-and-governance.md]). Every agent merge goes through :file[scripts/github/merge-pr.ts], which waits for the checks and refuses the PRs a person must merge; a person merges those by hand ([Merge gate](/t/glassbox/guide/verification/gate)).

One refusal checks the review itself. Before merging, the agent posts its verdict on the PR, ending in a `Reviewed: <sha>` line that names the commit it reviewed. `verdictRefusal` reads only comments from a trusted author (`OWNER`, `MEMBER` or `COLLABORATOR`), which Terrarium treats as write access, as [Author trust](/t/glassbox/guide/git-github/author-trust) explains. Of those, it keeps the ones whose header names this session. It refuses the merge unless one of their `Reviewed:` lines names the head commit, the newest commit on the PR's head branch:

::excerpt{path="scripts/github/merge-pr.ts" lines="166-173,183-184"}
```ts
export function verdictRefusal(bodies: VerdictBody[], sessionId: string | null, headSha: string): string | null {
  const mine = bodies
    .filter(
      ({ body: b, authorAssociation }) =>
        TRUSTED_ASSOCIATIONS.has(authorAssociation) &&
        (sessionId === null ? hasAuthorshipMarker(b) : readProvenanceHeader(b)?.sessionId === sessionId),
    )
    .map(({ body }) => body)
  // …
  const named = mine.flatMap((b) => [...b.matchAll(REVIEWED_LINE_RE)].map((m) => m[1]!.toLowerCase()))
  if (named.some((sha) => headSha.toLowerCase().startsWith(sha))) return null
```
::

A short id counts when the head commit starts with it. A push after the review moves the head, and the old verdict no longer names it. When the session id can't be read, any agent's authorship mark, the header or a footer ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution)), counts instead of the header.

The one change that skips a PR is the :term[session log], the record a session writes about its own work: :file[scripts/session/log-session.ts] commits that single file straight to `main`. [Session logs](/t/glassbox/guide/terrarium-practice/session-logs) follows it there.

### Why it's built this way

- **Review before landing.** Agents change their own tools (skills, hooks, checks), so a bad change pushed straight to `main` can break the next agent unnoticed. A PR keeps changes reviewable and easy to undo, and is where the :term[gate] runs. The cost: even a one-word fix needs a branch, PR and CI run. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **Always open the PR.** Asking "shall I open a PR?" stalled unwatched runs, and a system prompt's "no PR unless asked" once stranded finished work on a branch. Opening a PR merges nothing: the gate and merge rules decide. The cost: a session that stops before its review ends leaves a pushed branch with no PR. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **Review before the PR opens.** The PR is where an agent can merge its own change on a green run, so review comes before it opens, for prose too: skills, rules and agent docs steer every later session. The cost: nothing checks that a review ran; the merge script checks only that this session's verdict names the head. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).
- **One more review for an integration PR.** An integration PR gathers several smaller changes, each already reviewed on its own, into one PR, and a review of one change can't see how correct changes interact. So the whole diff gets one more review before the integration PR opens. The cost: code already reviewed is read again, as part of the whole. :file[docs/agents/pr-workflow.md].
- **The script checks the verdict.** The written steps say to post the verdict before the merge, and once that order failed, so the merge script now checks it. The cost: a fresh verdict after every push. :file[scripts/github/merge-pr.ts].

### What to watch for

- **A passing check sends the session no notice.** A session subscribed to a PR hears about comments and failed checks, not a passing one, so Terrarium's CI posts a comment when the gate is green.
- **Closing keywords close everything they name.** `Closes #N` in a PR description closes that issue when the PR merges, so Terrarium uses it only for an issue the PR completes and writes "relates to #N" otherwise. The merge script refuses a PR whose keywords would close an open issue that is not labelled `ready-for-agent`.
- **The description is part of the change.** Reviewers judge a PR by what its description says it does, so a push that changes what the PR does updates its title and description too.
- **A PR from outside is a different case.** An agent never merges a PR from a fork or from a :term[public] author, someone without write access; [Author trust](/t/glassbox/guide/git-github/author-trust) explains why. The one exception is a minor or patch npm bump that Dependabot opens from the repository itself, which an agent may merge ([Dependabot grouping](/t/glassbox/guide/git-github/dependabot-grouping)).

## Try it in your project

Give your agent one written rule: every change goes on a branch, and the agent opens the PR itself once review and the local gate pass. Then name what it does next, such as answering review comments and fixing failed checks, until the PR is merged or closed.
