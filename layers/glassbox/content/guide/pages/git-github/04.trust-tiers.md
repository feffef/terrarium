An agent that reads issues and comments will meet text that tells it what to do. Whether it may act on that text has to depend on who wrote it, and the only safe source for who is the identity GitHub records, never what the text claims.

Know fork PR security already? Skip to [In Terrarium](#in-terrarium).

## The concept

GitHub attaches an `author_association` to every issue, pull request and comment, set from the author's account and not from anything they typed. Its values say how the author relates to the repository: `OWNER`, `MEMBER` and `COLLABORATOR` have been given access, `CONTRIBUTOR` has had a change merged before, and `NONE` has no tie at all. The [GitHub Docs: REST API endpoints for issue comments](https://docs.github.com/en/rest/issues/comments) return it with each comment.

A person without write access contributes through a fork, and a PR from a fork runs CI with less power. GitHub passes no secrets to it, apart from a `GITHUB_TOKEN` that normally can't write. On a public repository, a fork PR's workflows may wait until someone with write access approves the run; by default GitHub asks that only for first-time contributors.

The riskiest trigger breaks those limits. A `pull_request_target` workflow runs in the base repository's context, with its token and secrets, and it runs regardless of the approval setting. It is safe only while it never checks out and runs the fork's code; the plain `pull_request` trigger is the safe choice when no secret is needed.

Full reference: [GitHub Docs: Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

## In Terrarium

Terrarium draws one line. A person with write access is :term[Trusted]; everyone else is :term[Public]. :file[scripts/trust.ts] holds the line as `author_association` values:

::excerpt{path="scripts/trust.ts"}
```ts
// GitHub `author_association` values on each side of ADR-0020's trust line.
export const TRUSTED_ASSOCIATIONS = new Set(['OWNER', 'MEMBER', 'COLLABORATOR'])

export const PUBLIC_ASSOCIATIONS = new Set(['NONE', 'CONTRIBUTOR', 'FIRST_TIME_CONTRIBUTOR', 'FIRST_TIMER', 'MANNEQUIN'])
```
::

ADR-0020 says what each tier may do; :file[docs/agents/guest-contributions.md] applies it to fork PRs and outside agents.

The code that acts on the line sits at the merge. :file[scripts/merge-pr.ts], the only path by which an agent merges, refuses a PR whose branch lives in a fork, a PR whose author is not Trusted, and a PR from the guest pipeline, the one route where Terrarium's own agents build what a Public guest asked for (ADR-0023, :file[docs/adr/0023-guest-driven-demo-pipeline.md]). A person merges those.

The CI side keeps fork PRs away from write access. :file[.github/workflows/pr-authorassociation-label.yml] labels a PR `trusted` when its author has write access, on the plain `pull_request` trigger and only for a branch in the repository itself; a fork PR gets no label, and the missing label means Public. The Gate's green-check comment skips fork PRs the same way, since their token can't write.

### Why it's built this way

Someone with write access can already push and merge without any agent, so screening what they ask an agent to do would add friction and stop nothing. Early drafts treated invited collaborators like outside guests; Terrarium dropped that, and also left out a middle tier until a real need shows up. The cost is that the line is all or nothing: a collaborator is trusted exactly as much as the owner. ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).

Public text can try to steer an agent into a change nobody wanted, and no machine can check whether an agent treated a text as data or obeyed it. The :term[gate] checks that a PR works, not why it was written, so a clean but hostile PR would pass. A merge to `main` is where code reaches the live server, so that is the step a person keeps; letting Public PRs merge on a green gate was rejected. The cost is that every Public PR waits for a person and a real security review. ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).

Agents post through the owner's account, so a PR an agent opens looks Trusted. A whole-repo security review once found that the merge script would merge a fork or Public PR, and would count a review verdict anyone had faked by copying the session header. Later, guest-pipeline PRs turned out to be stopped only by one "never merge" line in a Skill. Now the script itself refuses those PRs and ignores a verdict whose author is not Trusted. :file[scripts/merge-pr.ts]

Terrarium wanted a guest to file an issue and watch its agents interview them and build the idea, all on GitHub, which means skipping the per-issue Trusted approval. The owner starting the guest Skills counts as that approval, so turning it off needs no code change, and the owner still merges every PR it opens. The cost is build time and an owner review for every guest issue. ADR-0023 (:file[docs/adr/0023-guest-driven-demo-pipeline.md]).

A Public author can open a PR only from a fork, and a fork's CI token can't write, so writing a `public` label would mean handing write tokens to the fork's own workflow code. Labelling only branches in the repository itself, and reading no label as Public, avoids that and fails safe. :file[.github/workflows/pr-authorassociation-label.yml]

### What to watch for

- **`CONTRIBUTOR` is not Trusted.** It means a change of theirs was merged once, not that they can push. GitHub warns that approving fork runs only for first-time contributors lets someone qualify with one harmless typo fix.
- **`OWNER` isn't proof of a person.** Agents post as the owner, so `OWNER` doesn't mean a person wrote it, and the session header can be copied: `merge-pr.ts` counts a verdict only from a Trusted author (`verdictRefusal`).
- **A label is a display, not the check.** The `trusted` label helps a reader; the scripts that decide read `author_association` themselves.
- **Never `pull_request_target` for a fork's code.** It ignores the approval setting and holds the secrets; the header comment of the label workflow says why it uses the plain `pull_request` trigger instead.

## Try it in your project

Write down which `author_association` values your agent may take instructions from, and check it in code before the agent acts on an issue or merges a PR. Then search your workflows for `pull_request_target` and, for each hit, confirm it never checks out the PR's own code.
