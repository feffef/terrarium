Which part of a project a pull request touches is already written in the paths it changes, so a workflow can turn those paths into labels. Terrarium does this in a short workflow that gives each pull request from its own repository one label for each area its paths reach, an area being one site, the home page or everything else.

Know path-based labelling already? Skip to [In Terrarium](#in-terrarium).

## The concept

A workflow on the [`pull_request` trigger](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request) runs, by default, when a pull request is opened or reopened and when its head branch gets new commits: the activity types `opened`, `reopened` and `synchronize`. A labelling job lists the pull request's files, maps each path to a label and adds the labels.

The [List pull requests files](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests-files) REST endpoint, `GET /repos/{owner}/{repo}/pulls/{pull_number}/files`, returns 30 files per page by default and up to 100 with `per_page`, and at most 3000 files in all. Each entry has a `filename` and a `status`; a renamed file, with the status `renamed`, also carries `previous_filename`, its old path. A label rule that reads only `filename` misses where a moved file came from.

The [GitHub CLI](https://cli.github.com/manual/gh_pr_edit) adds labels by name with `gh pr edit --add-label`. It looks each name up in the repository and fails when no label has it, so a label must exist, made with `gh label create`, before a run adds it. A pull request from a fork runs `pull_request` workflows with a read-only `GITHUB_TOKEN` and no secrets, so such a run can't label it.

The common ready-made tool is [actions/labeler](https://github.com/actions/labeler). It reads its rules from `.github/labeler.yml`: each label lists globs under `changed-files`, such as `any-glob-to-any-file`. With `issues: write` it creates a label that doesn't exist yet, and its `sync-labels` input removes a configured label that no longer matches. Its labels and their globs are all written in that one config file, so a label taken from a folder's name, or paths that must match a list kept elsewhere, fit a short shell loop better.

Full reference: [GitHub Docs: Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

## In Terrarium

Area labels say which part of Terrarium an issue or PR concerns: `area:<tenant>` names a :term[tenant], `area:homepage` the home page and `area:platform` everything else. The `auto-triage` sweep sets them on issues and `harvest` on its :term[seedling] issues (:file[docs/agents/triage-labels.md]). The sweep gives every issue at least one. A tenant counts where the issue's problem shows up or its fix lands, and `area:platform` is added when any part lies elsewhere. For an issue built on the :term[friction ledger], the sweep opens each occurrence's :term[session log] and takes where its problem showed up, not what that session was working on (:file[.agents/skills/auto-triage/SKILL.md]).

On PRs, :file[.github/workflows/pr-area-label.yml] sets them from the paths. It runs on the `pull_request` trigger's `opened`, `reopened` and `synchronize` types, and its job runs only when the PR's branch lives in this repository:

::excerpt{path=".github/workflows/pr-area-label.yml" lines="8-10,17-18,20"}
```yaml
on:
  pull_request:
    types: [opened, reopened, synchronize]
# …
jobs:
  label:
    # …
    if: github.event.pull_request.head.repo.full_name == github.repository
```
::

The job lists the PR's files, a renamed file's old path included, and adds one label per area:

::excerpt{path=".github/workflows/pr-area-label.yml" lines="29-39"}
```sh
          gh api --paginate "repos/$REPO/pulls/$PR/files" \
            --jq '.[] | .filename, (.previous_filename // empty)' | while read -r f; do
            case "$f" in
              layers/journal/*|layers/blog/*|layers/atlas/*|layers/midden/*|layers/marquee/*|layers/tinkerfund/*|layers/glassbox/*|layers/commons/*)
                echo "${f#layers/}" | cut -d/ -f1 ;;
              app/pages/index.vue|app/components/HomeShowcase.vue) echo homepage ;;
              *) echo platform ;;
            esac
          done | sort -u | while read -r area; do
            gh pr edit "$PR" -R "$REPO" --add-label "area:$area"
          done
```
::

A path in a listed tenant's folder adds that tenant's label, the home page's files add `area:homepage`, and any other path adds `area:platform`. A PR gets one label for each area its paths reach. The workflow's paths copy the sweep's Area labels section, and each file says to change both.

### Why it's built this way

- **The areas are copied, not shared.** The sweep reads its areas from its skill and the workflow from its own shell list, so the workflow copies the skill's paths. It names each tenant rather than matching every folder under `layers/`, since adding a label that doesn't exist fails the run. The cost: an area change edits both files, and a new tenant needs its label created. :file[.github/workflows/pr-area-label.yml]
- **A rename counts both its paths.** The files list names a renamed file by its new path, so a rule that reads only that path misses the area the file left. The workflow reads `previous_filename` too, as the merge check does for its own list ([Protected paths](/t/glassbox/guide/terrarium-practice/protected-paths#why-its-built-this-way)). :file[docs/agents/git-conventions.md]

### What to watch for

- **An unlisted tenant's PRs read `area:platform`.** A path under a `layers/` folder the workflow doesn't name falls through to `area:platform`, so a new tenant's PRs carry the wrong area until its line is added.
- **A fork's PR gets no area label.** The job's condition skips a PR whose branch lives in a fork, whose run gets a read-only token; [Author trust](/t/glassbox/guide/git-github/author-trust#in-terrarium) says how Terrarium treats fork PRs.
- **Labels are added, never removed.** The workflow only runs `gh pr edit --add-label`, so a PR whose later commits no longer touch an area keeps that area's label.

## Try it in your project

List a pull request's changed paths with the [GitHub CLI](https://cli.github.com/manual/), a renamed file's old path included, and map each path to an area:

```sh
gh api --paginate "repos/OWNER/REPO/pulls/123/files" \
  --jq '.[] | .filename, (.previous_filename // empty)' |
  while read -r f; do
    case "$f" in
      *.md) echo docs ;;
      *) echo code ;;
    esac
  done | sort -u
```

Each area prints once: a pull request that changes Markdown and other files prints `code` and `docs`. To label pull requests with it, create each label with `gh label create`, then run the loop in a workflow on `pull_request` with `issues: write` and `pull-requests: write` permissions, as :file[.github/workflows/pr-area-label.yml] does, ending in `gh pr edit "$PR" -R "$REPO" --add-label "$area"` for each area, with `GH_TOKEN` set to the run's token.
