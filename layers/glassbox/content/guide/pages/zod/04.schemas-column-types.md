Give a Nuxt Content collection a strict Zod schema, add a file with a misspelt field, and the build still passes. A schema checks nothing until something parses data with it. Terrarium doesn't rely on the build for that: its own step checks every Document against its schema.

Know Zod's `safeParse` already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Zod schema is a description until you run it. `schema.parse(data)` checks `data` and throws on the first failure; `schema.safeParse(data)` returns `{ success: true, data }` or `{ success: false, error }`, and `error.issues` lists every problem with its path. `.strict()`, an enum's list of values, and a `.refine` all take effect only inside one of those calls.

Other tools can read a schema for other jobs. [Nuxt Content](https://content.nuxt.com/docs/collections/define) takes each collection's schema, converts it to JSON Schema to choose the columns of the collection's database table, and uses it as the source of the collection's TypeScript types. Its docs say schemas enforce data consistency, but in the build Terrarium uses it never calls `parse` or `safeParse` on a file's data. A value outside an enum, or an extra field on a strict schema, goes into the database as written.

So the check has to be a step you add: load each schema, parse every file it covers, and fail on any issue.

Full reference: [Zod 3 docs: .safeParse](https://v3.zod.dev/?id=safeparse)

## In Terrarium

Many :term[Collection] schemas in the Tenant manifests are strict. The Blog's `pingbacks` schema, for one, is `.strict()` and allows only the Blog's Personas in `fromPersona`. Neither rule would stop `pnpm build`.

:file[scripts/validate-content.ts] runs the schemas instead. It calls the same `loadManifests()` and `expand()` from :file[shared/expand.ts] that `content.config.ts` calls, so each collection it checks carries the very schema that built its table. Then it reads every file the collection covers, the frontmatter of a Markdown page or the whole of a YAML file, and parses it:

::excerpt{path="scripts/validate-content.ts" lines="129-160"}
```ts
  for (const col of cols) {
    const schema = col.schema
    if (!schema) continue // page Collection with no additional schema — nothing authored to check
    // …
      const res = schema.safeParse(data)
      if (!res.success) {
        messages.push(
          ...res.error.issues.map((i) => {
            const where = i.path.join('.')
            return where ? `${where}: ${i.message}` : i.message
          }),
        )
      }
```
::

It lists every failure with its collection key and file, and exits with an error if there is any. `pnpm validate:content` runs it, then :file[scripts/validate-content-refs.ts], which checks what no single Document's schema can see, such as a field that names another Document missing from its Space. `validate:content` is a step of the :term[Floor], the part of the :term[Gate] that always runs, so a content-only change is checked in seconds without a build.

### Why it's built this way

Every Document must match its Collection's schema, and the Gate checks it: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]) names this check L1. Agents write most of Terrarium, and the ADR's reason holds here too: checks a machine runs are what make that safe, since no reviewer reads every file.

### What to watch for

- **The claim is tied to a version.** It holds for the `@nuxt/content` version Terrarium installs at this revision, 3.16.1. If a later release starts parsing content at build time, this step may become redundant.
- **Only the fields you declare are checked.** A page's built-in fields, such as `title` and `body`, come from Nuxt Content and aren't checked here, and a `page` Collection with no schema of its own is skipped.
- **A valid shape can still point nowhere.** A field holding another Document's slug passes its schema as any string. That's the job of the reference check, and it covers only the Tenants it was written for.

## Try it in your project

Add a field your schema doesn't allow to one content file and run your build. If it passes, add a script that loads each collection's schema, calls `safeParse` on every file it covers, and exits non-zero on any failure. Run it in CI before the build.
