A config file is data, and data can be wrong. If nothing checks it, a typo in a key is silently ignored and the mistake turns up much later, somewhere far from the file. Terrarium checks each Tenant's manifest with a Zod schema before anything is built from it.

Know Zod refinements already? Skip to [In Terrarium](#in-terrarium).

## The concept

Zod describes the shape of data as a schema in TypeScript, then checks a value against it at runtime with `parse` or `safeParse`, as [Schemas give column types, not validation](/t/glassbox/guide/zod/schemas-column-types) explains.

A few tools cover what a config check needs:

- **`.strict()`.** A Zod object drops keys it doesn't know by default. `.strict()` makes an unknown key an error, so a misspelt key fails instead of vanishing.
- **`.refine` and `.superRefine`.** Some rules span several fields, such as "this field is required when that one has this value". A refinement is a function that runs after the shape has parsed. `.refine` returns true or false; `.superRefine` gets a `ctx` and may call `ctx.addIssue` as often as it needs, each issue with its own `path` and message.
- **`z.custom`.** For a value Zod has no schema for, `z.custom` takes your own test function. With no function it accepts anything.

Two ways combine object schemas. `A.extend({ … })` adds fields to `A`. `A.merge(B)` does the same with `B`'s fields, and the result also takes `B`'s policy for unknown keys.

Full reference: [Zod 3 docs: .superRefine](https://v3.zod.dev/?id=superrefine)

## In Terrarium

Each :term[Tenant] declares its :term[Spaces]{id="space"} and :term[Collections]{id="collection"} in one :term[manifest]. [Collections expanded from one manifest](/t/glassbox/guide/nuxt-content/manifest-collections) says what the checks catch; this Lesson shows how they're built. :file[shared/manifest.ts] holds the schema for one Collection entry:

::excerpt{path="shared/manifest.ts" lines="77-131"}
```ts
const zodSchemaField = z.custom<ZodObject<ZodRawShape>>(
  (v) => typeof (v as { safeParse?: unknown })?.safeParse === 'function',
  'schema is not a zod schema',
)
// …
const collectionDefSchema = z
  .object({
    type: z.enum(['page', 'data'], { message: 'has an invalid type (expected "page" or "data")' }),
    source: z.string().optional(),
    schema: zodSchemaField.optional(),
    kind: z.string().optional(),
  })
  .strict()
  .superRefine((val, ctx) => {
    // …
    if (val.type === 'data' && val.schema === undefined && val.kind === undefined) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['schema'],
        message: 'data collection requires a schema (or a `kind` whose contract supplies one)',
      })
    }
  })
```
::

Each part does one job. The manifest holds real Zod schema objects, which Zod has no schema for, so `z.custom` accepts any value with a `safeParse` method. `.strict()` turns a misspelt key into an error. The `.superRefine` holds the rules that span fields: a `data` Collection needs a `schema` or a :term[kind]{id="collection-kind"}, a `kind` must exist in :file[shared/kinds.ts], and its type must match the Collection's. A second `.superRefine`, on the whole set of Collections, checks that the one named `pages`, and only that one, is a `page` Collection.

`validateManifest()` runs `safeParse` and turns every issue into one line, led by its path when it has one. `expand()` in :file[shared/expand.ts] calls it on each manifest before expanding it, and throws with all of that manifest's lines at once. A manifest with a misspelt `source` key on a `data` Collection that has no schema stops the build with:

```text
invalid manifest "demo":
- collections.notes: Unrecognized key(s) in object: 'sorce'
- collections.notes.schema: data collection requires a schema (or a `kind` whose contract supplies one)
```

### Combining two schemas: `.extend`, not `.merge`

A Collection that names a kind gets the kind's contract plus its own schema. `effectiveSchema()` in :file[shared/expand.ts] builds that with `.extend`, and its comment says why `.merge` would break:

::excerpt{path="shared/expand.ts" lines="97-114"}
```ts
 *  Built via `local.extend(<contract fields local doesn't declare>)`, NOT
 *  `contract.merge(local)`: the manifests are loaded by `loadManifests()`'s own
 *  jiti instance, so a local schema's zod and the contract's zod can be two
 *  module instances — `.merge()` adopts the *other* instance's catchall, whose
 *  `instanceof ZodNever` strip-check then fails and silently turns
 *  strip-unknown-keys into reject-as-never. Extending keeps the local schema's
 *  own class and unknown-keys policy. */
// …
  const additions = Object.fromEntries(
    Object.entries(contract.shape).filter(([field]) => !(field in local.shape)),
  )
  return local.extend(additions)
```
::

Zod 3 decides whether to drop an unknown key with an `instanceof` test against its own classes. The manifests are loaded through their own TypeScript loader, so their `zod` can be a second copy of the library, with its own classes. `.merge` builds the new object in the contract's copy but keeps the Tenant's catchall, which comes from the other copy, so the test fails. Each unknown key is then checked against that catchall, a schema that accepts nothing. The Blog's `pages` schema isn't strict, because Nuxt Content adds fields such as `title` to every page. Merged that way, every such field would fail. `.extend` builds the result in the Tenant's own copy and keeps its policy, and a local field still wins over a contract field of the same name, because only the contract fields the Tenant doesn't declare are added.

### Why it's built this way

Checking a manifest before it is expanded: ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).

A kind as a minimum that each Collection extends: ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

### What to watch for

- **A refinement waits for the shape.** Zod runs a refinement only once the object it sits on has parsed. An invalid `type` hides the refinements above it: the kind checks, and the rule about which Collection may be a `page`, don't run until it's fixed, so the next run can show new errors. An unknown key doesn't hold them back, since `.strict()` reports it and parsing goes on.
- **`z.custom` checks what you test, nothing more.** The schema field passes any object with a `safeParse` method, whichever copy of Zod made it. That loose test is what lets two copies meet in `effectiveSchema()`.
- **The type and the schema say the same thing twice.** `CollectionDef` in :file[shared/manifest.ts] is a TypeScript union with the same rules as the Zod schema. The type catches a mistake in the editor and the schema catches it at build; a change to one needs the same change to the other.

## Try it in your project

If your app reads a config file, give it a strict schema and check it before you use it, listing every problem at once:

```ts
import { z } from 'zod'

const config = z
  .object({ mode: z.enum(['static', 'server']), port: z.number().optional() })
  .strict()
  .superRefine((c, ctx) => {
    if (c.mode === 'server' && c.port === undefined) {
      ctx.addIssue({ code: z.ZodIssueCode.custom, path: ['port'], message: 'a server needs a port' })
    }
  })

const result = config.safeParse(loadedConfig)
if (!result.success) {
  throw new Error(result.error.issues.map((i) => `${i.path.join('.')}: ${i.message}`).join('\n'))
}
```
