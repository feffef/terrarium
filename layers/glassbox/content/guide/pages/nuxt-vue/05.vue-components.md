A Vue page is built from components, each one file that holds its markup, its code and its styles. The code in a component runs once for each copy of it on the page, and Vue redraws the markup when the data that code works with changes. Code that several components need can be pulled out into a composable.

Know Vue components and composables already? Skip to [In Terrarium](#in-terrarium).

## The concept

A **single-file component** is a `.vue` file with up to three blocks: `<template>` for the markup, `<script setup>` for the code, and `<style>` for the CSS, which `scoped` limits to this component's elements. A compiler turns it into JavaScript at build time. Code in [`<script setup>`](https://vuejs.org/api/sfc-script-setup.html) runs once for each copy of the component on the page, and the template can use every name it declares. `defineProps` declares the inputs a parent passes in, typed with TypeScript; it needs no import.

A template redraws when its data changes, because Vue tracks what each render reads. [`ref(value)`](https://vuejs.org/guide/essentials/reactivity-fundamentals.html) holds a value in `.value`; the template reads it without `.value`. A [`computed`](https://vuejs.org/guide/essentials/computed.html) derives a value from refs and props, keeps it, and works it out again only when one of them changes.

A [composable](https://vuejs.org/guide/reusability/composables.html) is a function, named `useSomething` by convention, that calls these APIs for whichever component calls it and returns the state. Lifecycle hooks such as `onMounted` attach to the component whose setup code is running, so a composable is called from `<script setup>` or from another composable, never later from a timer or a click handler.

Full reference: [Vue docs: Single-File Components](https://vuejs.org/guide/scaling-up/sfc.html)

## In Terrarium

Terrarium's pages and components are single-file components, and each that has code writes it in `<script setup lang="ts">`. Nuxt renders every page on the server first, so a component's code runs there too; [Hydration](/t/glassbox/guide/nuxt-vue/hydration) says what that asks of it. Tinkerfund's funding bar shows the blocks at work:

::excerpt{path="layers/tinkerfund/app/components/tinkerfund/ProgressBar.vue" lines="1-20"}
```vue
<script setup lang="ts">
const props = withDefaults(defineProps<{ percent: number; segments?: number }>(), { segments: 20 })
const filled = computed(() => Math.round((Math.min(props.percent, 100) / 100) * props.segments))
</script>

<template>
  <div
    class="bar"
    :class="{ over: percent >= 100 }"
    role="meter"
    aria-label="Funding"
    aria-valuemin="0"
    aria-valuemax="100"
    :aria-valuenow="Math.min(percent, 100)"
    :aria-valuetext="`${percent}% funded`"
    :style="{ '--n': segments }"
  >
    <i v-for="i in segments" :key="i" :class="{ on: i <= filled }" :style="{ '--i': i }" />
  </div>
</template>
```
::

The parent passes `percent`; `segments` defaults to 20. `filled` counts the lit segments and changes only when a prop does. A `:` before an attribute binds it to an expression, and `v-for` repeats the `<i>` once per segment. A `<style scoped>` block below the template colours the segments. Nuxt names the component from its folder, so pages use it as `<TinkerfundProgressBar>` with no import ([Nuxt layers](/t/glassbox/guide/nuxt-vue/layers) says how).

Shared code goes in composables, in a layer's `app/composables/` folder, which Nuxt auto-imports like its components. The Journal's `useMaintainerView` decides whether to show maintainer-only links, and every session card calls it ([Hydration](/t/glassbox/guide/nuxt-vue/hydration) shows its code). `useSpace`, which every page inside a :term[Space] starts with, is in [File routing](/t/glassbox/guide/nuxt-vue/file-routing).

### Why it's built this way

- **One composable, not a check per card.** Each session card needs to know if the maintainer view is on, and every card re-parsed the address and touched the tab's storage. One composable keeps the answer in shared state: the first card to mount works it out and the rest reuse it. The cost: a hook-registering composable works only during a component's setup. :file[layers/journal/app/composables/maintainerView.ts].

### What to watch for

- **Register hooks before the first `await`.** In an async composable, Vue loses track of the calling component after an `await`, and a hook registered there is dropped, with only a warning in development. `useTinkerfundClock` in :file[layers/tinkerfund/app/composables/clock.ts] registers `onMounted` and `onUnmounted` first, then awaits. A top-level `await` in `<script setup>` itself is safe: the compiler restores the component.
- **A module-level ref is shared by every visitor.** A `ref` created outside any function lives once per server process, so one request's value leaks into the next. State that belongs to a request goes in `useState`, as the Nuxt docs advise; `useState` carries a value from the server to the browser ([Hydration](/t/glassbox/guide/nuxt-vue/hydration)).

## Try it in your project

In a Nuxt app, add `app/components/Percent.vue`:

```vue
<script setup lang="ts">
const props = defineProps<{ value: number; max?: number }>()
const percent = computed(() => Math.round((props.value / (props.max ?? 100)) * 100))
</script>

<template><p>{{ percent }}% done</p></template>
```

Use it in a page with `<Percent :value="3" :max="12" />`, which renders `25% done` with no import. Then give the page a `ref`: write `const n = ref(3)` in its script, pass `:value="n"`, and add `<button @click="n++">More</button>`. Each click redraws the text, and `percent` is worked out again only because `n` changed.
