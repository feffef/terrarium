A Vue page is built from components, each one file that holds its markup, its code and its styles. When the server renders the page, each component's code runs twice: once on the server to write the HTML, and again in the browser to take that HTML over. The browser's first render has to match the server's. Only after that may it show something the server couldn't know, such as the visitor's time zone.

Know Vue and server rendering already? Skip to [In Terrarium](#in-terrarium).

## The concept

A **single-file component** is a `.vue` file with up to three blocks: `<template>` for the markup, `<script setup>` for the code, and `<style>` for the CSS, which `scoped` limits to this component's elements. A compiler turns it into JavaScript at build time. Code in [`<script setup>`](https://vuejs.org/api/sfc-script-setup.html) runs once for each copy of the component on the page, and the template can use every name it declares. `defineProps` declares the inputs a parent passes in, typed with TypeScript; it needs no import.

A template redraws when its data changes, because Vue tracks what each render reads. [`ref(value)`](https://vuejs.org/guide/essentials/reactivity-fundamentals.html) holds a value in `.value`; the template reads it without `.value`. A [`computed`](https://vuejs.org/guide/essentials/computed.html) derives a value from refs and props, keeps it, and works it out again only when one of them changes.

A [composable](https://vuejs.org/guide/reusability/composables.html) is a function, named `useSomething` by convention, that calls these APIs for whichever component calls it and returns the state. Lifecycle hooks such as `onMounted` attach to the component whose setup code is running, so a composable is called from `<script setup>` or from another composable, never later from a timer or a click handler.

With server rendering, the server runs each component's setup code and renders HTML. [`onMounted`, `onUpdated` and `onUnmounted`](https://vuejs.org/api/composition-api-lifecycle.html) never run there. The browser shows that HTML, loads the same code and runs it again, but instead of building new elements it **hydrates**: it walks the HTML the server sent, matches it to its own render and attaches event listeners. When the two renders differ, that is a **hydration mismatch**. Random values, the current time, the time zone or locale, and browser-only APIs such as `localStorage` are the usual causes. Vue replaces mismatched text with the browser's, but leaves a mismatched class, style or attribute as the server wrote it. In development it warns about each; a production build logs one console error, `Hydration completed but contains mismatches.`, and leaves out the details.

The fix is to give both renders the same input, and to change the page only in `onMounted`, once hydration is done. Nuxt's [`useState(key, init)`](https://nuxt.com/docs/4.x/api/composables/use-state) carries a value across: the server runs `init`, sends the result in the page's payload, and the browser starts from it instead of running `init` again. Every component that calls `useState` with the same key shares one value: on the server for one request, in the browser for the whole visit. [Nuxt's hydration guide](https://nuxt.com/docs/4.x/guide/best-practices/hydration) lists the common mismatches with fixes.

Full reference: [Vue docs: Server-Side Rendering](https://vuejs.org/guide/scaling-up/ssr.html)

## In Terrarium

Terrarium's pages and components are single-file components, and each that has code writes it in `<script setup lang="ts">`. Nuxt renders every page on the server and the browser hydrates it. Tinkerfund's funding bar shows the blocks at work:

::excerpt{path="layers/tinkerfund/app/components/tinkerfund/ProgressBar.vue" lines="1-20"}
```vue
<script setup lang="ts">
const props = withDefaults(defineProps<{ percent: number; segments?: number }>(), { segments: 20 })
const filled = computed(() => Math.round((Math.min(props.percent, 100) / 100) * props.segments))
</script>

<template>
  <div
    class="bar"
    :class="{ over: percent >= 100 }"
    role="meter"
    aria-label="Funding"
    aria-valuemin="0"
    aria-valuemax="100"
    :aria-valuenow="Math.min(percent, 100)"
    :aria-valuetext="`${percent}% funded`"
    :style="{ '--n': segments }"
  >
    <i v-for="i in segments" :key="i" :class="{ on: i <= filled }" :style="{ '--i': i }" />
  </div>
</template>
```
::

The parent passes `percent`; `segments` defaults to 20. `filled` counts the lit segments and changes only when a prop does. A `:` before an attribute binds it to an expression, and `v-for` repeats the `<i>` once per segment. A `<style scoped>` block below the template colours the segments. Nuxt names the component from its folder, so pages use it as `<TinkerfundProgressBar>` with no import ([Nuxt layers](/t/glassbox/guide/nuxt-vue/layers) says how).

Tinkerfund shows each exact date in the visitor's own time zone, which only the browser knows. Its date component renders UTC on the server and in the browser's first render, then switches:

::excerpt{path="layers/tinkerfund/app/components/tinkerfund/Time.vue" lines="1-17"}
```vue
<script setup lang="ts">
// The exact date is in the visitor's own time zone (issue #1364), which only
// the browser knows: the server renders UTC and the browser swaps it after mount.
// Without `text`, the exact date is the visible text; with it, a hover title.
const props = defineProps<{ at: number; text?: string }>()
const locale = useTinkerfundLocale()
const mounted = ref(false)
onMounted(() => (mounted.value = true))
const exact = computed(() => {
  const date = new Date(props.at).toLocaleString(locale.value, { dateStyle: 'long', timeStyle: 'short', timeZone: mounted.value ? undefined : 'UTC' })
  return mounted.value ? date : `${date} UTC`
})
</script>

<template>
  <time :datetime="new Date(at).toISOString()" :title="text && exact">{{ text ?? exact }}</time>
</template>
```
::

`mounted` is `false` on the server and while the browser hydrates, so both renders format the same UTC date. `onMounted` then sets it, `exact` is worked out again, and Vue redraws the date in local time. Both renders use the same locale too: `useTinkerfundLocale`, in :file[layers/tinkerfund/app/composables/locale.ts], reads it from the request's `Accept-Language` header on the server and keeps it in `useState`, so the browser starts from the server's value. The Journal's :term[Friction Ledger] page, `frictions.vue` in :file[layers/journal/app/pages/t/journal/], does the same with today's date: `useState` holds the server's date for the first render, and `onMounted` replaces it with the browser's.

A composable gives that pattern one home. The Journal shows a link to each session's Claude Code page only in a maintainer view, which a `?maintainer` query or the browser tab's storage turns on:

::excerpt{path="layers/journal/app/composables/maintainerView.ts" lines="8-14"}
```ts
export function useMaintainerView() {
  const on = useState<boolean | null>('journal-maintainer-view', () => null)
  onMounted(() => {
    if (on.value === null) on.value = resolveMaintainerView(location.search, () => sessionStorage)
  })
  return on
}
```
::

The value is `null`, not yet known, on the server and through hydration, so neither render draws the link. Every session card calls `useMaintainerView`; they share one value through the key, and the first card mounted reads the address and storage for all of them. The most-used composable, `useSpace`, which every page inside a :term[Space] starts with, is in [File routing](/t/glassbox/guide/nuxt-vue/file-routing).

The smoke test, :file[tests/e2e/smoke.spec.ts], loads every Space's entry page from a production build in a real browser, and :file[tests/support/e2e.ts] fails it on any console error, Vue's mismatch error included.

### Why it's built this way

- **Hydrate, don't reload.** The owner wants view transitions and in-memory state, such as Tinkerfund's cart, to survive a click, so the browser takes over the server's page and builds later pages itself, rather than loading each from the server. The cost: every component's setup runs twice, and both renders must agree. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **The server's value first, the browser's after mount.** A cached page's server-computed "today" can be slightly old, and only the browser knows the visitor's time zone. Rendering the server's value and replacing it in `onMounted` keeps hydration clean. The cost: the server's value shows until the page mounts. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Request facts travel in `useState`.** Money and dates follow the visitor's locale, which the server reads from a request header. Passing it in `useState` makes the browser render with the server's locale, not its own. The cost: the page cache must vary by that header ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro)). :file[layers/tinkerfund/app/composables/locale.ts]
- **Dates spelled out by hand.** `toLocaleDateString` can format one date differently on the server and in the browser, which breaks hydration. The Midden and Glass Box build `16 Jul 2026` from a fixed list of month names instead. The cost: those dates read in English for everyone. :file[layers/midden/app/utils/find.ts]

### What to watch for

- **The tests miss a mismatched attribute.** A production build reports mismatched text but never a mismatched class, style or attribute, and Vue doesn't correct one, so the server's value stays until that binding changes. The smoke test passes on it. Run `pnpm dev` and read the browser console: development builds warn about each.
- **Register hooks before the first `await`.** In an async composable, Vue loses track of the calling component after an `await`, and a hook registered there is dropped, with only a warning in development. `useTinkerfundClock` in :file[layers/tinkerfund/app/composables/clock.ts] registers `onMounted` and `onUnmounted` first, then awaits. A top-level `await` in `<script setup>` itself is safe: the compiler restores the component.
- **`useState` keys share one namespace.** Every layer's `useState` calls share one set of keys, the way their names share one set of auto-imports. Terrarium's keys start with the Tenant's name, as in `journal-maintainer-view`, or two Tenants' state could collide.
- **A module-level ref is shared by every visitor.** A `ref` created outside any function lives once per server process, so one request's value leaks into the next. State that belongs to a request goes in `useState`, as the Nuxt docs advise.

## Try it in your project

In a Nuxt app, add a page that renders the time:

```vue
<!-- app/pages/clock.vue -->
<script setup lang="ts">
const now = new Date().toISOString()
</script>

<template><p :title="now">Rendered at {{ now }}</p></template>
```

Run `nuxt dev`, open `/clock` and the browser console: Vue warns of a text mismatch and an attribute mismatch, and the paragraph shows the browser's time while its `title` keeps the server's. Run `nuxt build`, then `nuxt preview`: the console shows only `Hydration completed but contains mismatches.` Then fix it: keep the time in `useState('now', () => new Date().toISOString())`, and update it in `onMounted`. Both warnings go.
