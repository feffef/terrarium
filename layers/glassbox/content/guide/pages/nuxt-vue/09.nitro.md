Vue draws a page, and Nuxt decides which page an address means. Something still has to take each request, decide whether a stored copy of the page will do, and package everything into one server that runs on its own. In a Nuxt app, that is Nitro.

Know Nitro already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nitro is a toolkit for web servers: it builds request handlers and settings into one server that runs on Node, on a serverless platform or elsewhere. [Nuxt's server is Nitro](https://nuxt.com/docs/4.x/guide/concepts/server-engine). Nuxt registers its page renderer as Nitro's catch-all handler, `/**`, so every request that no other handler takes becomes a page render.

A request is split three ways. **Nitro** takes it, applies its route's rules, answers from its cache when it can, and otherwise calls a handler. **Nuxt's renderer**, that handler, finds the page file for the address, runs its data loading and writes the payload. **Vue** renders the components to HTML on the server, and hydrates them in the browser.

`routeRules` in `nuxt.config.ts` maps path patterns to options, and Nuxt hands them to Nitro. A route with a `cache` rule has its handler wrapped in a cache, which keeps each response for `maxAge` seconds. By default (`swr: true`) Nitro then keeps serving the expired copy while it renders a new one in the background; with `swr: false` the next request waits for a fresh copy. Nitro drops every request header when it renders and serves a cached response, except those the rule lists in `varies`. `cache: false` turns the cache off for a route. Cached responses go to the `cache:` mount of Nitro's storage: in memory in a production build by default, in files under the build folder in development. A config can mount another storage driver there.

`nuxt build` runs Nitro's build, which writes the whole server to `.output/`. With the default Node server preset, `.output/server/index.mjs` starts it, and the folder needs nothing else installed. Nuxt 4 runs Nitro v2, documented at v2.nitro.build; nitro.build documents v3.

Full reference: [Nitro v2 docs](https://v2.nitro.build/guide)

## In Terrarium

Terrarium has no `server/` folder and no handlers of its own. Nitro runs Nuxt's renderer and the routes modules add, such as Nuxt Content's. What Terrarium writes is configuration. The Platform's config caches the home page and every Tenant page, and changes the cache's store:

::excerpt{path="nuxt.config.ts" lines="20-25"}
```ts
  routeRules: {
    '/': { cache: { maxAge: 60, swr: false } },
    '/t/**': { cache: { maxAge: 60, swr: false } },
  },
  // Bounds that page cache's memory (ADR-0028, #1446).
  nitro: { storage: { cache: { driver: 'lru-cache', max: 200 } } },
```
::

A page stays cached for `maxAge` seconds and is never served after that. The `cache:` mount uses an LRU driver: past `max` entries it drops the one used least recently. :file[tests/unit/page-cache.spec.ts] loads that driver with the real config's options and fills it past the cap. Which routes these rules give a payload file is in [useAsyncData & payloads](/t/glassbox/guide/nuxt-vue/use-async-data).

A Tenant adds rules for its own pages in its layer's config, and Nuxt merges them with the Platform's. Tinkerfund lists a header in `varies` and turns the cache off for its search:

::excerpt{path="layers/tinkerfund/nuxt.config.ts" lines="10-14"}
```ts
  // Page cache (ADR-0028): money and dates follow the visitor's locale (#1365); search stays in the browser.
  routeRules: {
    '/t/tinkerfund/**': { cache: { varies: ['accept-language'] } },
    '/t/tinkerfund/*/search': { cache: false },
  },
```
::

`pnpm build` runs `nuxt build`, and Nitro writes `.output/`. `.output/server/` holds `index.mjs`, the server's code in `chunks/`, and a `node_modules/` with only the packages that code imports. `.output/public/` holds the files the server sends as they are: the browser's JavaScript in `_nuxt/`, and in `__nuxt_content/` the Collection dumps a browser query downloads. The live container copies `.output/` into its serve folder and starts that copy:

::excerpt{path="deploy/entrypoint.sh" lines="79-83"}
```bash
start_server() {
  log "starting server on :$PORT"
  NODE_ENV=production HOST=0.0.0.0 PORT="$PORT" node "$SERVE_DIR/server/index.mjs" &
  SERVER_PID=$!
}
```
::

Nuxt Content runs inside that server. Its queries during a render use the server's SQLite database, and the routes that send dumps to the browser are Nitro handlers the module adds ([The content database](/t/glassbox/guide/nuxt-content/content-database)).

### Why it's built this way

- **Cache to get payloads.** Nuxt writes a page's payload only for cached routes ([useAsyncData & payloads](/t/glassbox/guide/nuxt-vue/use-async-data) says why Terrarium wants them). Caching is safe because content changes only with a new build. The cost: one copy serves every visitor, so a page reading a request header must list it in `varies`; Tinkerfund's pages once showed everyone English until it did. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **No stale copies.** The cache is short and `swr` is off. `swr` (stale-while-revalidate) would serve the first visitor after a quiet spell a copy of any age, and some pages work out "today" while rendering. The cost: the first request after a copy expires waits for a fresh render. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Capped cache store.** Nitro keeps one copy per address, query string included, and its default in-memory store never drops expired copies, so made-up query strings could grow memory until restart. A store capped at a fixed number of copies, dropping the least recently used, fixes that in one config line. A dropped copy costs one extra render. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).

### What to watch for

- **A page that reads a request header or cookie.** On a cached route its server render gets none that `varies` doesn't list; ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]) says what such a page must do.
- **`pnpm dev` keeps its cache on disk.** In development the `cache:` mount is files under `.nuxt/cache/nitro/routes`, not the LRU store, and they outlast a restart of `pnpm dev`. If an edited page comes back unchanged, delete that folder.
- **A server route brings generated types.** Add a handler under `server/api/` and Nitro generates types for it into `.nuxt/`; `useFetch` takes its result's type from them, and `pnpm typecheck` checks against them. A return type Nitro has to infer from the handler's body can come out as `{}` in one checkout while CI passes, and fail `pnpm typecheck` there; write the handler's return type out.

## Try it in your project

Add a page that prints when it was rendered, and cache it for half a minute:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: { '/now': { cache: { maxAge: 30, swr: false } } },
})
```

```vue
<!-- app/pages/now.vue -->
<script setup lang="ts">
const renderedAt = useState('renderedAt', () => new Date().toISOString())
</script>

<template><p>Rendered at {{ renderedAt }}</p></template>
```

Run `nuxt build`, list `.output/`, and start `node .output/server/index.mjs`. Reload `/now` a few times: the time stays the same until 30 seconds have passed.
