A page that renders on the server and then hydrates (the browser takes over the server's HTML) runs its setup code twice. Load data in setup the plain way and it is fetched twice too: once for the HTML, once more in the browser. Nuxt's `useAsyncData` fetches once, on the server for the first page, and sends the result along. For a page the server caches, Nuxt can also send that result as a file when the visitor clicks a link to it.

Know `useAsyncData` and payloads already? Skip to [In Terrarium](#in-terrarium).

## The concept

`useAsyncData(key, handler)` runs `handler`, an async function, and returns refs: `data` holds its result, `status` and `error` say how it went. On the server, Nuxt waits for the handler before it renders the HTML, then stores the result under `key` in the **payload**: the data Nuxt serializes into the page for the browser. When the browser takes over the page, `useAsyncData` finds its key in the payload and doesn't run the handler again. Calls with the same key share one result, so the key must be unique to the data. Without one, Nuxt makes a key from the file and the call's position among that file's calls.

That covers the first page. When the visitor follows a link, the browser builds the next page itself, and normally runs that page's handlers there. **Payload extraction** changes that for some routes: Nuxt serves the payload of a server render at a `_payload.json` URL next to the route, and on a client navigation fetches it and uses its data instead of running the handlers. With `experimental.payloadExtraction: 'client'`, the first page keeps its payload inline in the HTML, and only navigations fetch `_payload.json`.

Only some routes get one: a prerendered route has it written to a file at build, and a route the server caches renders it on request, like the page itself. A route is cached by a `cache` rule in `routeRules` ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro)).

Full reference: [Nuxt docs: useAsyncData](https://nuxt.com/docs/4.x/api/composables/use-async-data)

## In Terrarium

Terrarium's pages load their content inside `useAsyncData`, most of them keyed by the route's path. The Journal's document page loads its document under the route's path, then the steps of its onramp tour under that path plus `:onramp`:

::excerpt{path="layers/journal/app/pages/t/journal/[space]/[...slug].vue" lines="21-23,34-43"}
```ts
const { data: page, error } = await useAsyncData(route.path, () =>
  queryCollection(pagesKey).path(path).first(),
)
// …
const { data: tour } = await useAsyncData(`${route.path}:onramp`, async () =>
  page.value?.onramp == null
    ? []
    : onrampSteps(
        await queryCollection(pagesKey)
          .where('onramp', 'IS NOT NULL')
          .select('path', 'onramp', 'onrampLabel', 'onrampBlurb')
          .all(),
      ),
)
```
::

`queryCollection` is [Nuxt Content](https://content.nuxt.com/docs/advanced/database)'s query. On the server it reads the server's SQLite database. In the browser it downloads a SQLite runtime compiled to WebAssembly, and a dump of each collection it queries, the first time it runs. The platform's config turns on payload files and sets when a link prefetches, that is, fetches its route's code and payload before the click:

::excerpt{path="nuxt.config.ts" lines="16-21"}
```ts
  // In-app navigation reads a server-rendered `_payload.json` instead of
  // querying Content in the browser (ADR-0028).
  experimental: {
    payloadExtraction: 'client',
    defaults: { nuxtLink: { prefetchOn: { visibility: false, interaction: true } } },
  },
```
::

The same config gives the home page and every tenant page a short `cache` rule, so each has a payload. A link fetches its route's code and payload when the pointer moves onto it or presses it, or the keyboard focuses it, not when it scrolls into view. On the click, when the payload loads, `useAsyncData` finds its key in it, the handler never runs, and the browser loads no database.

Tinkerfund's search route is not cached and has no payload: after a click to it, its `useAsyncData` handler runs in the browser and queries the browser database (its search page is in :file[layers/tinkerfund/app/pages/t/tinkerfund/]).

### Why it's built this way

- **Payloads over browser queries.** Before payloads, the first click downloaded a database engine and each collection the next page queried, and a failed download left a section empty. Now a click fetches one small payload the server renders and caches, several to dozens of times lighter. The cost: the browser database still loads for an uncached page or a failed payload fetch. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Payloads keep the cart and survive Content upgrades.** The other options either broke a tenant's shop, which keeps a cart in the browser, or relied on undocumented Nuxt Content internals that break on upgrades. Payloads use only documented Nuxt settings. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Cache, not prerender.** Nuxt serves a payload only for pages it prerenders or caches. Prerendering every page would lengthen the build, need a kept-up address list, and miss query strings. Content changes only with a new build, so the server caches pages briefly instead. The cost: one cached copy serves every visitor, so a page reading a request header lists it in `varies` ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro)). ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Fetch on interaction.** Nuxt's default fetches every visible link's payload ahead of time, and one page fetched the same big payload many times, making page changes heavier than before payloads. Fetching only when the pointer moves onto or presses a link, or the keyboard focuses it, fixed that. The cost: the next page's code loads later. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).

### What to watch for

- **Return what the page reads.** A handler that returns whole documents sends every field. The Blog's front page, :file[layers/blog/app/pages/t/blog/index.vue], `.select()`s only the fields it lists.
- **One key per piece of data.** Two `useAsyncData` calls with the same key share one result, so the second gets the first's. Give each call its own key, as the Journal's page above does.
- **A query outside `useAsyncData` still loads the browser database.** A payload stands in only for `useAsyncData` results on a cached route. Tinkerfund's search field queries as the visitor types (:file[layers/tinkerfund/app/components/tinkerfund/shell/SearchField.vue]), so its first suggestion downloads the database, however light the page itself was ([Content database](/t/glassbox/guide/nuxt-content/content-database) says what that costs).

## Try it in your project

Take a page that loads its data in `useAsyncData`, and give its route a short cache and payload extraction:

```ts
export default defineNuxtConfig({
  experimental: { payloadExtraction: 'client' },
  routeRules: { '/blog/**': { cache: { maxAge: 60, swr: false } } },
})
```

Build and start the app (`nuxt build`, then `nuxt preview`). Open another page, then click a link to the cached one with the browser's network panel open: you should see its `_payload.json` and no request from the handler.
