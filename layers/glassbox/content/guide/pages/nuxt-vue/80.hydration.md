Each Vue component's setup code (the code in its `<script setup>` block) runs twice on a page the server renders: once on the server to write the HTML, and again in the browser to take that HTML over. The browser's first render has to match the server's. Only after that may it show something the server couldn't know, such as the visitor's time zone.

Know Vue and server rendering already? Skip to [In Terrarium](#in-terrarium).

## The concept

With server rendering, the server runs each component's setup code and renders HTML. [`onMounted`, `onUpdated` and `onUnmounted`](https://vuejs.org/api/composition-api-lifecycle.html) never run there. The browser shows that HTML, loads the same code and runs it again, but instead of building new elements it **[hydrates](https://vuejs.org/guide/scaling-up/ssr.html#client-hydration)**: it walks the HTML the server sent, matches it to its own render and attaches event listeners. When the two renders differ, that is a **hydration mismatch**. Random values, the current time, the time zone or locale, and browser-only APIs such as `localStorage` are the [usual causes](https://vuejs.org/guide/scaling-up/ssr.html#hydration-mismatch), as is HTML the browser's parser corrects, such as a `<div>` inside a `<p>`. Vue replaces mismatched text, and a mismatched bound attribute other than `class` and `style`, with the browser's value; a mismatched `class` or `style` it leaves as the server wrote it. In development it warns about each; a production build logs one console error, `Hydration completed but contains mismatches.`, and leaves out the details.

The fix is to give both renders the same input, and to change the page only in `onMounted`, once hydration is done. Nuxt's [`useState(key, init)`](https://nuxt.com/docs/4.x/api/composables/use-state) carries a value across: the server runs `init`, sends the result in the page's payload, and the browser starts from it instead of running `init` again. Every component that calls `useState` with the same key [shares one value](https://nuxt.com/docs/4.x/getting-started/state-management): on the server for one request, in the browser for the whole visit. [Nuxt's hydration guide](https://nuxt.com/docs/4.x/guide/best-practices/hydration) lists the common mismatches with fixes.

Full reference: [Vue docs: Server-Side Rendering](https://vuejs.org/guide/scaling-up/ssr.html)

## In Terrarium

Nuxt renders every page on the server and the browser hydrates it. Tinkerfund shows each exact date in the visitor's own time zone, which only the browser knows. Its date component renders UTC on the server and in the browser's first render, then switches:

::excerpt{path="layers/tinkerfund/app/components/tinkerfund/Time.vue" lines="1,5-17"}
```vue
<script setup lang="ts">
// …
const props = defineProps<{ at: number; text?: string }>()
const locale = useTinkerfundLocale()
const mounted = ref(false)
onMounted(() => (mounted.value = true))
const exact = computed(() => {
  const date = new Date(props.at).toLocaleString(locale.value, { dateStyle: 'long', timeStyle: 'short', timeZone: mounted.value ? undefined : 'UTC' })
  return mounted.value ? date : `${date} UTC`
})
</script>

<template>
  <time :datetime="new Date(at).toISOString()" :title="text && exact">{{ text ?? exact }}</time>
</template>
```
::

`mounted` is `false` on the server and while the browser hydrates, and both renders format the same UTC date. `onMounted` then sets it, `exact` is worked out again, and Vue redraws the date in local time. Both renders use the same locale too: `useTinkerfundLocale`, in :file[layers/tinkerfund/app/composables/locale.ts], reads it from the request's `Accept-Language` header on the server and keeps it in `useState`. The Journal's :term[friction ledger] page, `[space]/frictions.vue` in :file[layers/journal/app/pages/t/journal/], does the same with today's date: `useState` holds the server's date for the first render, and `onMounted` replaces it with the browser's.

The Journal shows a link to each session's Claude Code page only in a maintainer view: a per-browser setting for the site's maintainer, not access control, that a `?maintainer` query or the browser's stored flag turns on. Its [composable](/t/glassbox/guide/nuxt-vue/vue-components) `useMaintainerView` keeps that answer in `useState`:

::excerpt{path="layers/journal/app/composables/maintainerView.ts" lines="8-14"}
```ts
export function useMaintainerView() {
  const on = useState<boolean | null>('journal-maintainer-view', () => null)
  onMounted(() => {
    if (on.value === null) on.value = resolveMaintainerView(location.search, () => localStorage)
  })
  return on
}
```
::

The value is `null`, not yet known, on the server and through hydration, and neither render draws the link. Every session card, the summary of one session's log in the Journal's activity feed, calls `useMaintainerView`, and all of them share one value through the key. The first card mounted reads the address and storage and sets the value. The others then find it no longer `null` and skip the read.

The smoke test, :file[tests/e2e/smoke.spec.ts], loads every :term[space]'s entry page from a production build in a real browser, and :file[tests/support/e2e.ts] fails it on any console error, Vue's mismatch error included.

### Why it's built this way

- **Hydrate, don't reload.** The owner wants view transitions and in-memory state, such as Tinkerfund's cart, to survive a click, so the browser takes over the server's page and builds later pages itself, rather than loading each from the server. The cost: every component of a server-rendered page runs its setup twice, and both renders must agree. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **The server's value first, the browser's after mount.** A cached page's server-computed "today" can be slightly old, and only the browser knows the visitor's time zone. Rendering the server's value and replacing it in `onMounted` keeps hydration clean. The cost: the server's value shows until the page mounts. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Request facts travel in `useState`.** Money and dates follow the visitor's locale, which the server reads from a request header. Passing it in `useState` makes the browser render with the server's locale, not its own. The cost: the page cache must vary by that header ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro)). :file[layers/tinkerfund/app/composables/locale.ts].
- **Dates spelled out by hand.** `toLocaleDateString` can format one date differently on the server and in the browser, which breaks hydration. Tenants such as the Midden build `16 Jul 2026` from a fixed list of month names instead. The cost: those dates read in English for everyone. :file[layers/midden/app/utils/find.ts].

### What to watch for

- **The tests miss a mismatched `class` or `style`.** A production build checks no attributes while it hydrates, so its one console error never fires for them, and the smoke test passes while a mismatched `class` or `style` stays wrong on the page. Run `pnpm dev` and read the browser console: development builds warn about each.
- **`useState` keys share one namespace.** Every layer's `useState` calls share one set of keys, the way their components and composables share one set of names ([Auto-imports](/t/glassbox/guide/nuxt-vue/auto-imports)). Terrarium's keys start with the tenant's name, as in `journal-maintainer-view`, or two tenants' state could collide.

## Try it in your project

In a Nuxt app, add a page that renders the time:

```vue
<!-- app/pages/clock.vue -->
<script setup lang="ts">
const now = new Date().toISOString()
</script>

<template><p :class="now">Rendered at {{ now }}</p></template>
```

Run `nuxt dev`, open `/clock` and the browser console: Vue warns of a text mismatch and a class mismatch, and the paragraph shows the browser's time while its `class` keeps the server's. Run `nuxt build`, then `nuxt preview`: the console shows only `Hydration completed but contains mismatches.` Then fix it: keep the time in `useState('now', () => new Date().toISOString())`, and update it in `onMounted`. Both warnings go.
