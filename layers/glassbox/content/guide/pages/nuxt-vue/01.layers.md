Several sites in one codebase usually means one of two pains: a separate app per site, with every shared fix made several times, or one tangled app where nobody can tell which code belongs to which site. A Nuxt layer is the middle way: each site keeps its own folder, and Nuxt merges them all into one app.

Know Nuxt layers already? Skip to [In Terrarium](#in-terrarium).

## The concept

A layer is a partial Nuxt app. It has the same shape as a full one: a `nuxt.config.ts`, and optionally `app/pages/`, `app/components/`, `app/composables/`, `app/utils/`, `server/` and the rest. When an app uses a layer, Nuxt merges the layer's config into the app's and scans its folders as if they were the app's own, so its pages become routes and its components and composables are auto-imported everywhere.

There are two ways in. The `extends` key of `nuxt.config.ts` names layers from another folder, an npm package or a git repository. Any folder under the app's own `layers/` directory is registered without being named anywhere; it only needs a `nuxt.config.ts`, which may be empty. Nuxt also gives each such folder an alias, `#layers/<name>`.

When two layers define the same page, component or composable, one wins. The app's own files beat every layer; among the folders in `layers/`, the later name in alphabetical order wins, which a numeric prefix such as `1.base/` can change.

Two things in a layer resolve against the app, not the layer: the `~` and `@` aliases, and relative paths inside the layer's `nuxt.config.ts`. The docs suggest relative imports or the `#layers/<name>` alias in code, and a path built from the config file's own location in its config:

```ts
// layers/shop/nuxt.config.ts
import { fileURLToPath } from 'node:url'

export default defineNuxtConfig({
  css: [fileURLToPath(new URL('./app/assets/shop.css', import.meta.url))],
})
```

Full reference: [Nuxt docs: layers/ directory](https://nuxt.com/docs/4.x/directory-structure/layers)

## In Terrarium

Terrarium is one Nuxt app that serves every site, and each site is a :term[Tenant]. A Tenant is built as a layer: everything it owns sits in `layers/<tenant>/`, with its pages and components in `app/`, its own `nuxt.config.ts`, its manifest `tenant.config.ts`, and its content. The root of the repo is the Platform: shared code such as the catch-all page, the routing and the content config.

The root config names no Tenant. Nuxt finds them in :file[layers/] on its own:

::excerpt{path="nuxt.config.ts" lines="6-12"}
```ts
  // Tenants are Nuxt layers (GLOSSARY.md). They live under Nuxt's conventional
  // `layers/` directory (ADR-0018), so Nuxt auto-extends every `layers/*` — no
  // hand-curated `extends` list. A Tenant without its own fit-out simply has no
  // presentational code and falls back to the Platform's generic catch-all
  // renderer. Layers are presentation only — they never define content
  // collections (that stays in the root content.config.ts).
  modules: ['./modules/routing', '@nuxt/content', '@nuxt/eslint'],
```
::

A Tenant's layer config is small. Most only add the Tenant's stylesheet, with the path built from the config file's own location, as the Nuxt docs advise:

::excerpt{path="layers/blog/nuxt.config.ts" lines="10-15"}
```ts
export default defineNuxtConfig({
  // The `.bl` theme tokens + base layout, shared by the Persona landing and the
  // standalone post page so neither copy-pastes them. Resolved from this config's
  // own URL so it is unambiguous regardless of layer alias resolution.
  css: [fileURLToPath(new URL('./app/assets/theme.css', import.meta.url))],
})
```
::

Layers never need to override each other here. Each Tenant's pages live under its own `app/pages/t/<tenant>/`, so no two layers define the same page. A Tenant page replaces the Platform's catch-all for its addresses through routing, not layer priority: a path with the static segment `journal` is more specific than the catch-all's `[tenant]` parameter, so it wins. Components are kept apart by name: each Tenant puts its components in a folder named after itself, such as `layers/journal/app/components/journal/`, and Nuxt names them from that folder, as in `JournalStatTile`. Components in `app/components/content/`, the ones Markdown can use, are the exception: Nuxt Content registers them by their bare file name, such as `Sighting` for the Atlas's `Sighting.vue`, so every layer's content components share one namespace and their names must not clash.

A layer brings presentation only. It never declares a content collection: the root :file[content.config.ts] builds every collection from the manifests, and :file[shared/expand.ts] finds those manifests by listing the same `layers/` folder Nuxt scans.

### Why it's built this way

The owner wants one repo and one container to run, not one per Tenant. Nuxt Content also bakes all content into one database at build time and can't add collections while the site runs, so a separate app per site would only add more to deploy and keep in step. Layers let each Tenant keep its own folder inside that one app. The cost: every build ships every Tenant's content, kept apart in separate tables rather than sealed off. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

Tenants once lived in a folder named after the domain word, which Nuxt doesn't know. So the root config had to list every Tenant by hand, and the type check silently skipped all Tenant page code: the :term[Gate]{id="gate"} reported success on code it had never read. In `layers/`, Nuxt registers and type-checks each Tenant itself, and adding a Tenant no longer edits the root config, a :term[Human-only]{id="human-only"} file. The cost is a folder name that doesn't match the domain word, and one extra type-check include for the manifests, which a test guards. ADR-0018 (:file[docs/adr/0018-tenant-layers-under-layers-directory.md]).

Each collection is its own table and keeps Tenants apart, and its name is easy to get wrong by hand. So every :term[Collection]{id="collection"} comes from tested code that expands each Tenant's :term[manifest]{id="manifest"}, never from a layer. The rejected alternative, one hand-written list of every collection, would be a shared file every Tenant edits, prone to merge conflicts, where one mistake reaches every Tenant. The cost: a layer can only change how pages look; to hold new content, a Tenant edits its manifest. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).

### What to watch for

- **A layer is not a sandbox.** Its config merges into the one app, so a stylesheet it lists loads on every page of every Tenant. Terrarium scopes each Tenant's CSS under one wrapper class, and keeps a layer's plugins and config flags inert outside its own pages. The short list of these traps is :file[.claude/rules/tenant-layers.md].
- **One global namespace.** Components, composables and utils from every layer are auto-imported everywhere, and when two of them share a name, one silently replaces the other.
- **A folder in `layers/` is read twice.** Nuxt treats it as a layer, and :file[shared/expand.ts] loads its `tenant.config.ts` and stops the build if the manifest's name differs from the folder's. A folder there is a Tenant, or the build fails.
- **`~` means the Platform.** Inside a layer, `~` and `@` point at the root app. A layer imports its own files by relative path.

## Try it in your project

Pick one section of your Nuxt app, such as an admin area. Move its pages and components into `layers/admin/`, add a `layers/admin/nuxt.config.ts` holding only `export default defineNuxtConfig({})`, and check that its routes and components still work with nothing added to the root config.
