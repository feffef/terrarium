An agent that starts building before it knows what you want builds the wrong thing quickly. The planning Skills installed from `mattpocock/skills` slow that first step down: an interview settles the decisions, a prototype or a research note answers what talk can't, and the result is written to the issue tracker as a spec and tickets that a later session can pick up cold.

Know these Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

These installed :term[Skills]{id="skill"} split planning into steps that each do one job.

**`grilling`** is an interview. The agent maps the plan as a design tree, where each decision branches into the decisions that depend on it. It asks in rounds: each round holds every question whose prerequisites are already settled, numbered, each with the agent's recommended answer, worded so that "yes" accepts it. Facts are the agent's job, so it looks them up instead of asking; decisions are the person's. The interview ends when no open question is left, and the agent acts only once the person agrees they share an understanding.

**`wayfinder`** is for work too big for one session, where the way to the goal can't be seen yet. It charts a *map*: one issue that names the destination and indexes the decisions made so far. Each open question is a child issue, a *decision ticket* typed by the work it needs, such as research or a grilling, as the Skill's *Ticket Types* section defines. A ticket worked with a person is HITL (human in the loop); one the agent can drive alone is AFK. Tickets block each other through the tracker's own dependency links. A session claims a ticket by assigning it, and resolves at most one ticket, research tickets excepted. The *frontier* is every open ticket that is unblocked and unclaimed. Questions that can't be phrased sharply yet wait in the map's "Not yet specified" section until resolved tickets clear the way. The map produces decisions, not deliverables: when the way is clear, it hands off to the next step.

**`prototype`** builds throwaway code to answer one design question: a single HTML file for "does this logic feel right", or several switchable variants on one route for "what should this look like". When it is done, the decision goes into the real code and the prototype is kept on a branch outside `main`, linked from the issue.

**`research`** sends a background agent to answer a question from primary sources, such as official docs, source code and specs, and writes the findings with their sources to one Markdown file where the repo keeps such notes.

`wayfinder` names both as ticket types: a prototype ticket is HITL, and a research ticket is AFK and resolved by a subagent that runs `research`.

**`to-spec`** writes the conversation up as a spec, without asking anything new apart from checking the test seams. Its template covers the problem, the solution, a long list of user stories, implementation and testing decisions, and what is out of scope, and it leaves out file paths and code because they go stale, unless a prototype produced a snippet that states a decision more precisely than prose.

**`to-tickets`** breaks a plan or spec into tracer-bullet tickets: thin slices that each cut through every layer and can be checked on their own, each listing the tickets that block it. It shows the breakdown to the person, revises it until they approve, then publishes blockers first. A wide refactor that no single slice can land green goes through expand, migrate and contract steps instead.

The guide installed with these Skills, :file[.agents/skills/ask-matt/SKILL.md], routes a build too big for one session through them: grill, then `to-spec`, then `to-tickets`, then build ticket by ticket. A `wayfinder` map joins that route at `to-spec` once it clears. `grilling`, `prototype` and `research` can be reached for by the agent itself; `wayfinder`, `to-spec` and `to-tickets` set `disable-model-invocation: true`, so they run only when a person types them ([Claude Code docs: Skills](https://code.claude.com/docs/en/skills)). Both `to-spec` and `to-tickets` label what they publish `ready-for-agent`.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

These are installed Skills in :file[.agents/skills/], kept exactly as installed ([Installed Skills](/t/glassbox/guide/skill-pack/skill-packs)). They don't hard-code a tracker. Each expects to be told where issues live, and Terrarium tells them in :file[docs/agents/issue-tracker.md], a doc the installed setup Skill seeded and Terrarium now owns.

Its *Wayfinding operations* section maps the map onto GitHub. The map is an issue labelled `wayfinder:map`. Each ticket is a [sub-issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues) of it, labelled with its type. Blocking uses GitHub's native [issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies). A claim is an assignment, and a resolution is a comment, a close and one line added to the map's index. The same doc says how a spec looks here: an ordinary issue, with each user story a sub-issue that also starts with a `Part of` line naming the spec.

Terrarium's `auto-triage` sweep also triages wayfinder tickets, under wayfinder's rules for which tickets an agent may take:

::excerpt{path=".agents/skills/auto-triage/SKILL.md" lines="74-81"}
```md
- **Skip** a **claimed** (assigned) ticket and a **blocked** ticket (an open
  native dependency *or* a `Blocked by:` body line; `docs/agents/issue-tracker.md`'s
  Wayfinding operations): wayfinder's frontier is open + unblocked + unclaimed,
  so a blocked ticket is not takeable and must not be stamped `ready-for-agent`.
- **Preserve** every `wayfinder:*` label — this is an overlay, never a replacement.
- Honour the ticket type: `wayfinder:grilling` and `wayfinder:prototype` are
  **HITL** (human-in-the-loop) → `ready-for-human`; `wayfinder:research` is
  **AFK** and, when unblocked and unclaimed, is eligible for `ready-for-agent`.
```
::

`grilling` also runs inside other Skills. The installed `triage` Skill grills a vague request into shape, together with `domain-modeling`, which writes the settled terms into `GLOSSARY.md` and ADRs. Terrarium's own :file[.agents/skills/clear-backlog/SKILL.md] gathers every open question from a backlog run into one grilling with the owner, and leaves out every issue with a `wayfinder:*` label. How much each planning Skill matters here is graded in the :term[Skill Inventory].

### Why it's built this way

- **Stock Skills, our tracker doc.** The planning Skills are never edited, while the tracker doc the setup Skill seeded is Terrarium's own to edit; [Installed Skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way) gives both reasons and what each costs.
- **Writing a spec isn't approving it.** A finished spec or ticket list looks settled, but here `ready-for-agent` is a :term[Trusted] user's approval to build, so the planning Skills never set it; [Issue triage labels](/t/glassbox/guide/git-github/work-queue#in-terrarium) says who may. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **Triage labels beside wayfinder's.** `wayfinder` keeps triage labels off its tickets, which hold decisions, but an issue without `ready-for-agent` is invisible to building agents. So the sweep adds its label beside the `wayfinder:` one instead of moving the wayfinder backlog out of the map. The cost: two label sets on one issue; if that proves noisy, the ADR says to move them out. ADR-0022 (:file[docs/adr/0022-autonomous-triage-sweep.md]).
- **GitHub's own links first.** `wayfinder` wants the tracker's native dependencies, which show what's takeable in the tracker's own view without opening the map. Terrarium uses GitHub sub-issues and issue dependencies, with body lines only where those aren't available. The cost: the frontier query, and the sweep, must check both the native link and a `Blocked by:` line. :file[docs/agents/issue-tracker.md]

### What to watch for

- **Ignore their `ready-for-agent`.** `to-spec` and `to-tickets` tell the agent to label what they publish `ready-for-agent`, but in Terrarium only triage sets that label: file their issues `needs-triage`, and leave a spec on hold with no label at all. [Issue triage labels](/t/glassbox/guide/git-github/work-queue) has the rule and who may set the label.
- **A dependency link needs the issue's database id.** GitHub's endpoint takes the blocker's numeric id, not its `#number`. Write cross-references only once the issues exist: a placeholder `#n` links to whatever unrelated issue has that number.
- **Name a kept branch by the rules.** `wayfinder`'s research findings and the code `prototype` keeps each sit on a branch that gets no PR; name it as ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]) says.
- **Keep both label sets.** Never swap a ticket's `wayfinder:` label for a triage label: `wayfinder` reads a ticket's type from its label alone, never from its body.

## Try it in your project

Before your next change that would take more than an afternoon, ask your agent to grill you: one round of numbered questions, each with its recommended answer. Write the spec only after the last round leaves nothing open.
