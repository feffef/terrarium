An agent writes code faster than anyone can read it, so the useful question is what tells it, and you, that the code is right. Three installed Skills answer it as one loop: build from the spec, write a test that fails before the code that passes it, then review the change against both the repo's rules and the request.

Know these Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

These installed :term[Skills]{id="skill"} build a change and check it, in that order.

**`implement`** builds what a spec or a set of tickets describes. Given a ticket reference, it fetches the ticket and states its title before it starts, and asks when the reference is ambiguous. It hands each piece to `tdd` where it can, at seams agreed beforehand, runs the type check and single test files as it goes and the full test suite once at the end, then runs `code-review` and commits to the current branch. It sets `disable-model-invocation: true`, so it runs only when a person types it ([Claude Code docs: Skills](https://code.claude.com/docs/en/skills)).

**`tdd`** is the red-then-green loop: write one failing test, then only enough code to pass it, one slice at a time. Tests sit at *seams*, the public boundaries where behaviour can be seen without reaching inside, and the seams are agreed with the person before any test is written. The Skill names three traps: tests coupled to the implementation, tests that recompute the expected value the way the code does, and writing every test before any code. Refactoring is left out of the loop on purpose; it belongs to review.

**`code-review`** reviews the diff from a fixed point, such as a branch or commit, on two axes. *Standards* asks whether the change follows the repo's documented rules, plus a baseline of code smells from Martin Fowler's *Refactoring* that a documented rule always overrides. *Spec* asks whether it does what the originating issue asked, no more and no less. Each axis runs in its own sub-agent, and the two reports stay separate, so a change that passes one can't hide that it fails the other.

The agent can reach for `tdd` and `code-review` on its own when the task fits. For a bug, `diagnosing-bugs` first builds a check that goes red on it; the [Skill Inventory](/t/journal/current/skills) has its entry.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

Each of these sits in :file[.agents/skills/], kept exactly as installed ([Installed Skills](/t/glassbox/guide/skill-pack/skill-packs)). Terrarium makes one of them a fixed step.

That step is `code-review`. Before a branch's first push, a session runs `code-review` against `origin/main`, fixes what it finds, and then runs `pnpm gate:scoped` on the final head, as :file[docs/agents/pr-workflow.md] sets out. A simple change gets the author's own read of its diff instead, and the same file says what counts as simple. An integration PR that stacks several reviewed stories gets one more review of its whole diff. The Standards axis has no single standards file to read here: Terrarium's rules live in :file[CLAUDE.md], in :file[.claude/rules/] and in the docs those point to.

One :term[Workflow] runs the loop from end to end. In :file[.claude/workflows/clear-backlog-build.js], a build agent follows the `implement` Skill, test-first with `tdd`, but skips its `code-review` step. The script runs the two review axes as parallel agents of its own, each reading the `code-review` Skill and applying one axis. A fix agent takes the findings worth fixing, and the review runs again, up to a fixed number of rounds. When no finding is worth fixing, a final-gate agent runs `pnpm gate:scoped` again on the branch's head:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="156,163-174"}
```js
  for (let round = 1; round <= MAX_ROUNDS; round++) {
    // …
    const all = reviews.flatMap(r => r.findings)
    const toFix = all.filter(f => f.worthFixing)
    out.judgementCalls = all.filter(f => !f.worthFixing)
    if (!toFix.length) {
      // Re-gate unconditionally: a stale gatePassed: true is the usual failure (#2523).
      const gate = await agent(gatePrompt(b, out.worktree), { label: `gate ${b.name}`, phase: 'Review', schema: WORK, ...modelOf(b) })
      out.verdicts.push(...tagged(gate, `gate ${b.name}`))
      if (!gate || !gate.gatePassed) return { ...out, status: 'failed', reason: `final gate: ${gate ? gate.reason || 'gate:scoped did not pass' : 'gate agent returned nothing'}` }
      out.commits = gate.commits
      out.decisions.push(...gate.decisions)
      return { ...out, status: 'ready-to-push' }
    }
```
::

A branch comes out ready to push when only judgement calls are left and that gate passes; a failed gate, or findings still worth fixing after the last round, marks it failed. A ready branch is pushed and then checked again by the :term[Gate] in CI.

How much each Skill matters here, and why, is in the :term[Skill Inventory].

### Why it's built this way

- **Review before the first push.** A pushed branch gets its PR at once, and an agent merges its own PR on a green CI run, so review comes before the push, for prose too: Skills and rules steer every later session. The cost: nothing checks that the review ran; the merge script asks only for a posted verdict. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).
- **One more review for an integration PR.** Each story of a large change, built and reviewed as its own PR, was reviewed alone, and a review of one story can't see how correct stories interact. So the whole diff gets one more review before the integration PR opens. The cost: code already reviewed is read again, as part of the whole. :file[docs/agents/pr-workflow.md]
- **Kept as installed.** These Skills are never edited here, so a reinstall can't overwrite a local change; [Installed Skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way) gives the reason and its cost. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **The loop as a workflow script.** The loop's script is a real file in `.claude/workflows/`, named by the `clear-backlog` Skill that runs it; [Workflow scripts](/t/glassbox/guide/claude-code/workflow-scripts#why-its-built-this-way) says why it sits outside its Skill's folder. ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Re-check what a reviewer cites.** A review sub-agent can quote a line that isn't there. Terrarium's Inventory entry for `code-review` asks each review brief to restate "verify before you state", and every cited line to be read again before it is acted on.

## Try it in your project

Next time you review a change, run it as two separate passes: first only against your project's written rules, then only against the issue it closes. Note which findings the second pass found that the first missed.
