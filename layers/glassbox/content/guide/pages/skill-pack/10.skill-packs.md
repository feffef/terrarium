You don't have to write every :term[skill] your agents use. An installed skill is one someone else wrote and published, which you install into your project. The catch is that the files are then in your repo, where anyone can edit them, and reinstalling or updating the skill would undo that edit without a word.

Know installed skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

A skill is a folder with a `SKILL.md` file of instructions for one kind of job. One GitHub repository can publish many of them. The one Terrarium installs from, Matt Pocock's *Skills For Real Engineers* (`mattpocock/skills`), holds skills such as `tdd`, `diagnosing-bugs` and `grilling`. It can be installed as a plugin, or with the [`skills` command-line tool](https://github.com/vercel-labs/skills), which copies the skills into your project as ordinary files:

```bash
npx skills@latest add mattpocock/skills
```

The command-line tool installs into the project by default, so the skills are committed with your code and every clone has them. Later, `npx skills update` brings those copies up to date with their source.

Some sources also ship a setup skill, run once before the others. `setup-matt-pocock-skills` asks where the project keeps its issues, such as GitHub, then writes docs from templates that the other skills read.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

The installed skills sit in :file[.agents/skills/] beside Terrarium's own, and :file[.claude/skills/] holds a link to each folder, where Claude Code looks for skills. The installer's :file[skills-lock.json] records each installed skill: its source repository, its path there, and the installer's hash of the file in that repository, `computedHash`.

Being listed in `skills-lock.json` is what makes a skill an installed skill, and nobody in Terrarium edits an installed skill's files. An installed skill's :term[skill inventory] entry holds `installedSha256`, the sha256 hash of its installed `SKILL.md`. That stored hash is the skill's pin:

::excerpt{path="layers/journal/content/current/skills/tdd.yml" lines="1-4"}
```yaml
name: tdd
category: general-engineering
importance: supporting
installedSha256: 5505d25bbaa8fc14a79e4d20163936958992a2995b7f1dd1d6197edc9ed722e0
```
::

:file[scripts/gate/validate-skills-lock.ts] checks the pins. It runs as `pnpm verify:skills-lock`, one step of the :term[gate]'s :term[floor]. It reads the lock only to learn which skills are installed, and hashes each one's installed `SKILL.md`, no other file in its folder. Below, `onDisk` maps each installed name to that hash, or `null` when the file is missing; `inv` maps it to its inventory entry, where `cataloged` says whether it has one and `pin` is its `installedSha256`; `findings` collects each failure:

::excerpt{path="scripts/gate/validate-skills-lock.ts" lines="80-93"}
```ts
    const actual = onDisk.get(name) ?? null
    if (actual === null) {
      findings.push({ name, kind: 'missing' })
      continue
    }
    const entry = inv.get(name)
    if (!entry?.cataloged) continue
    if (!entry.pin) {
      findings.push({ name, kind: 'unpinned', actual })
      continue
    }
    if (entry.pin !== actual) {
      findings.push({ name, kind: 'drifted', expected: entry.pin, actual })
    }
```
::

`pnpm verify:skills-lock --write` rewrites each entry's pin from the file on disk, and skips a skill with no entry.

The setup skill seeded three docs: :file[docs/agents/issue-tracker.md], :file[docs/agents/triage-labels.md] and :file[docs/agents/domain.md]. Those are Terrarium's own now. Each opens with a note not to re-sync it against the template it came from.

### Why it's built this way

- **A reinstall would silently undo a local edit.** Reinstalling a skill overwrites its files, and the edit is lost without notice. Terrarium turns that into a visible failure: the gate compares each installed `SKILL.md` with its pin, where it has one. Notes on how a skill fits go in its inventory entry instead. The cost: an installed skill's wrong line can't be corrected in Terrarium. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Terrarium pins its own hash, not the lock's.** The lock's `computedHash` is the installer's hash of the source repository's file, taken before the installer handles its frontmatter. So it doesn't match the installed copy and can't be recomputed offline, and the lock belongs to the installer. The cost: every real update from the source re-pins in the same PR, or the gate fails. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Seeded docs become ours.** A setup skill writes generic docs from templates, and a project then fills them with its own facts, which a re-sync would wipe. A doc copied from an installed skill's template is Terrarium's to edit and is never re-synced. The cost: a later improvement to the template reaches the doc only if someone carries it over by hand. ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Check the lock before you touch a skill folder.** If the folder's name is a key in :file[skills-lock.json], the skill is installed and its files stay as they are. The gate may not catch an edit: the `audit-skills` skill adds an installed skill's inventory entry, and so its pin, only once it sees the skill in use. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Re-pin only after a real install.** `--write` makes any edited file pass, so run it only when the new content came from the source.

## Try it in your project

Pick one skill you installed from another repository, record the sha256 of its `SKILL.md` in a file you own, and add a CI step that fails when the installed file's hash differs.
