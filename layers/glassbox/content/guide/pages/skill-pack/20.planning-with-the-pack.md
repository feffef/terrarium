An agent that starts building before it knows what you want builds the wrong thing quickly. The planning skills installed from `mattpocock/skills` slow that first step down: an interview settles the decisions, and the result is written to the issue tracker as a spec and tickets that a later session can pick up cold.

Know these skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

These installed :term[skills]{id="skill"} split planning into steps that each do one job.

**`grilling`** is an interview. The agent maps the plan as a design tree, where each decision branches into the decisions that depend on it. It asks in rounds: each round holds every question whose prerequisites are already settled, numbered, each with the agent's recommended answer, worded so that "yes" accepts it. Facts are the agent's job, so it looks them up instead of asking; decisions are the person's. The interview ends when no open question is left, and the agent acts only once the person agrees they share an understanding.

**`to-spec`** writes the conversation up as a spec, without asking anything new apart from checking the test seams, the public boundaries where tests will see the feature's behaviour. Its template covers the problem, the solution, a long list of user stories, implementation and testing decisions, and what is out of scope. It leaves out file paths and code, because they go stale. The exception is a snippet from a throwaway prototype that states a decision more precisely than prose.

**`to-tickets`** breaks a plan or spec into tracer-bullet tickets: thin slices that each cut through every layer, such as schema, API, UI and tests, and can be checked on their own. Each ticket lists the tickets that block it. It shows the breakdown to the person, revises it until they approve, then publishes blockers first. A wide refactor, such as renaming a database column, can break every caller at once, so no single slice can land green. It goes through expand, migrate and contract steps instead: add the new form beside the old, move the callers over in batches, then delete the old.

**`triage`** moves incoming issues through state labels. The label `ready-for-agent` marks an issue fully specified, for an agent to build alone. The label `ready-for-human` marks one that needs a person. An agent brief is the comment `triage` posts on a `ready-for-agent` issue: the contract an agent works from, while the issue's body and discussion are only context. It gives the current and desired behaviour, the types or interfaces involved, testable acceptance criteria and what is out of scope. A `ready-for-human` issue gets the same structure, plus why it can't be delegated. The brief names no file paths or line numbers, and it says what the system should do, not how to write it.

`ask-matt` (:file[.agents/skills/ask-matt/SKILL.md]) is the guide installed with these skills: a person runs it to ask which skill fits their situation. It routes a build too big for one session through them: grill, then `to-spec`, then `to-tickets`, then build ticket by ticket.

Who starts each skill differs. The agent may start `grilling` on its own, for instance when the person asks to be grilled. `wayfinder`, `to-spec` and `to-tickets` set `disable-model-invocation: true` in their frontmatter, which stops the agent from starting them on its own: a person starts each by typing its name ([Claude Code docs: Skills](https://code.claude.com/docs/en/skills)). A skill can still run `grilling` as one of its own steps, as `triage` and `wayfinder` do.

As installed, `to-spec` and `to-tickets` label what they publish `ready-for-agent`. Terrarium overrides that ([what to watch for](#what-to-watch-for)).

Work whose way can't be seen yet first goes through `wayfinder`. It charts a map of open decision tickets on the issue tracker and settles them one at a time. Once the way is clear, the work joins that route at `to-spec`: [Wayfinder](/t/glassbox/guide/skill-pack/wayfinder).

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

These are installed skills in :file[.agents/skills/], kept exactly as installed ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)). They don't hard-code a tracker. Each expects to be told where issues live, and Terrarium tells them in :file[docs/agents/issue-tracker.md], a doc the installed setup skill seeded and Terrarium now owns. The same doc says a spec here is an ordinary GitHub issue with no dedicated label. Its rules below cover the label, the sub-issues (GitHub's native child issues, one per user story) and the hold (a line in the body that says the spec isn't to be built until a stated condition clears):

::excerpt{path="docs/agents/issue-tracker.md" lines="60-73"}
```md
- **Label**: none while it is on hold (below): not `needs-triage`, not
  `ready-for-agent`.
- **Sub-issues**: link each user story to the spec as a native GitHub
  sub-issue (`sub_issue_write` / `gh api` on the sub-issues endpoint, as for
  [Wayfinding's child tickets](#wayfinding-operations)), and also put
  `Part of #<spec>` at the top of the child's body, so the link reads even where
  native sub-issues aren't rendered.
- **Hold**: a spec that isn't yet actionable says so in its body, e.g. *"On
  hold: implementation starts only after \[condition] — read, discuss, refine
  the idea, don't build."* Every sub-issue repeats the on-hold line at the top
  of its own body, so a reader who lands on a user story sees it. There is no
  "on hold" label; the body text is the source of truth. When the condition
  clears, the spec and its sub-issues get ordinary triage labels
  (`docs/agents/triage-labels.md`).
```
::

The `auto-triage` skill runs a sweep: one unattended pass that applies `triage`'s rules to every open issue needing attention ([Issue triage labels](/t/glassbox/guide/git-github/issue-triage-labels)). It posts a full brief on every issue it marks `ready-for-agent`. It leaves choices such as naming or wording to the agent that builds it. Each of its subagents also tells the sweep which files a fix would touch, and that list stays out of the brief. When two open `ready-for-agent` issues share a file, the sweep marks the higher-numbered one blocked by the other until that one closes (:file[.agents/skills/auto-triage/SKILL.md]).

The installed `triage` skill grills a vague request into shape together with the `domain-modeling` skill, which writes the settled terms into `GLOSSARY.md` and ADRs. Terrarium's own :file[.agents/skills/clear-backlog/SKILL.md] gathers every open question from a backlog run into one grilling with the owner. It leaves out every issue with a `wayfinder:*` label, which the `wayfinder` skill drives with the owner. How much each planning skill matters here is graded in the :term[skill inventory].

### Why it's built this way

- **Stock skills, our tracker doc.** The planning skills name no tracker and expect to be told where issues live, so Terrarium maps them onto GitHub in a doc it owns and leaves the skills as installed. Why the skills are never edited and that doc is never re-synced: [Installed skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way). ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]), ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **A brief names behaviour, not files.** An issue can wait while its files are renamed, and a path in the brief would then point at nothing. The installed rule keeps paths and line numbers out. The cost: the agent explores the codebase fresh, from the types and functions the brief names, and is given no file to open. :file[.agents/skills/triage/AGENT-BRIEF.md]

### What to watch for

- **Ignore their `ready-for-agent`.** `to-spec` and `to-tickets` say to apply it, but a Terrarium rule overrides them: [Issue triage labels](/t/glassbox/guide/git-github/issue-triage-labels#in-terrarium) has the rule and who may set the label.

## Try it in your project

Before your next change that would take more than an afternoon, have your agent grill you. In Claude Code, save the rules as a project skill in `.claude/skills/grill-me/SKILL.md`; the folder name, or `name`, is the command you type, and `description` tells the agent when to load it:

```md
---
name: grill-me
description: Interview me about a plan before any spec or code is written. Use when I ask to be grilled.
---

Interview me until we share an understanding of the plan.

- Ask in rounds. A round holds every question you can ask now without guessing an answer I haven't given.
- Number each question and put your recommended answer under it, worded so "yes" accepts it.
- Look facts up in the code yourself; ask me only for decisions.
- Stop when no question is open. Write nothing until I confirm we agree.
```

Then type `/grill-me add CSV export to the reports page`. The first reply should be questions only, each with its recommendation, something like:

```text
Q1. Should every report get the export button?
→ Recommended: yes, from one shared component.

Q2. Should the file hold every row, not just the visible page?
→ Recommended: yes, every row.
```

If it starts on code or a spec instead, run `/skills` and check that `grill-me` is listed. Write the spec only after the last round leaves nothing open.
