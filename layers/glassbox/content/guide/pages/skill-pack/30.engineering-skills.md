An agent writes code faster than anyone can read it, so the useful question is what tells it, and you, that the code is right. Three installed skills answer it, one calling the other two: `implement` builds from the spec, hands each piece to `tdd`, which writes a test that fails before the code that passes it, then runs `code-review`, which checks the change against both the repo's rules and the request.

Know these skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

These installed :term[skills]{id="skill"} build a change and check it, in that order.

**`implement`** builds what a spec or a set of tickets describes. Given a ticket reference, it fetches the ticket and states its title before it starts, and asks when the reference is ambiguous. It calls `tdd` for each piece where it can, at *seams* agreed beforehand: the public boundaries where behaviour can be seen without reaching inside. It runs the type check and single test files as it goes and the full test suite once at the end, then calls `code-review` and commits to the current branch. It sets `disable-model-invocation: true`: the agent never starts it on its own, and it runs only when a person types it ([Claude Code docs: Skills](https://code.claude.com/docs/en/skills)).

**`tdd`** is the red-then-green loop: write one failing test (red), then only enough code to pass it (green), one slice at a time. Tests sit only at seams, and the seams are agreed with the person before any test is written. The skill names three traps: tests coupled to the implementation, tests that recompute the expected value the way the code does, and writing every test before any code. It keeps refactoring out of the loop and leaves it to review.

**`code-review`** reviews the diff from a fixed point, such as a branch or commit, on two axes. *Standards* asks whether the change follows the repo's documented rules, plus a baseline of code smells from Martin Fowler's *Refactoring*: patterns, such as a name that doesn't say what it holds, that hint at a design problem without proving one. Each smell comes with its fix, and a documented rule always overrides the baseline. *Spec* asks whether it does what the originating issue asked, no more and no less. Each axis runs in its own subagent, and the two reports stay separate, so a change that passes one can't hide that it fails the other.

Outside `implement`, the agent can reach for `tdd` and `code-review` on its own when a task fits. A fourth skill, `diagnosing-bugs`, is for hard bugs: before it looks for the cause, it builds a check that goes red on that exact bug; the [skill inventory](/t/journal/current/skills) has its entry.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

Each of these skills sits in :file[.agents/skills/], kept exactly as installed ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)). Terrarium puts them to work in two places: `code-review` is a step a session runs before its PR, and one :term[workflow] uses all three: its build agent follows `implement` with `tdd`, and its reviewers apply `code-review`, one axis each.

A session runs `code-review` on its branch before the PR opens; a simple change gets the author's own read of its diff instead. :file[docs/agents/pr-workflow.md] holds the steps and what counts as simple, and [Pull requests](/t/glassbox/guide/git-github/pull-requests#why-its-built-this-way) gives the reasons and when another review follows. The Standards axis has no single standards file to read here: Terrarium's rules live in :file[CLAUDE.md], in :file[.claude/rules/] and in the docs those point to.

That workflow is :file[.claude/workflows/clear-backlog-build.js], run by the `clear-backlog` skill. A person starts `clear-backlog`, and in one run it takes the open issues its sweep picks up, the issues `auto-triage` selects plus every open `ready-for-agent` issue, except `wayfinder:*` ones, to a merged PR, a closed issue or a decision only the owner can make. The script tells its build agent to read the file of `implement`, which no agent can start, and follow it, test-first with `tdd` and minus its `code-review` step. It gives each of its reviewers one axis of `code-review` to apply. The script stops after one review round; the `clear-backlog` orchestrator resumes the agents for fixes, re-checks and the final gate. [Workflow scripts](/t/glassbox/guide/agents/workflow-scripts#in-terrarium) follows how such a script runs its agents.

How much each skill matters here, and why, is in the :term[skill inventory].

### Why it's built this way

- **These skills are never edited here.** A reinstall would overwrite a local edit; [Installed skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way) gives the reason and its cost. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **The build-and-review loop is a workflow script.** `clear-backlog`'s build and review loop is a real file in `.claude/workflows/`, named by the skill that runs it; [Workflow scripts](/t/glassbox/guide/agents/workflow-scripts#why-its-built-this-way) says why it sits outside its skill's folder. ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Re-check what a reviewer cites.** A review subagent can quote a line that isn't there. Terrarium's skill inventory entry for `code-review` records that a spec reviewer once cited a fabricated line, and points to the "Verify before you state" rule in :file[CLAUDE.md]: check a cited line against its source before you act on it.

## Try it in your project

Next time you review a change, run two separate reviews of the same diff, each in its own agent session, so neither sees the other's findings. Save the diff and the issue's text first; three dots compare against the point where your branch left `main`, and GitHub's `gh` prints an issue:

```bash
git diff origin/main...HEAD > change.diff
gh issue view 123 > issue.md
cat CONTRIBUTING.md change.diff | claude -p "Review the diff only against the rules above it. Cite the rule for each finding."
cat issue.md change.diff | claude -p "Review the diff only against the issue above it: what it misses, adds unasked, or gets wrong."
```

Each `claude -p` call reads what is piped in, prints its answer and exits, and continues no earlier conversation. Copy the findings into a two-column list, *rules* and *issue*. A finding in the issue column alone, such as a requirement the diff skips, is one the rules review let through.
