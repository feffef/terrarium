An agent writes code faster than anyone can read it, so the useful question is what tells it, and you, that the code is right. Three installed Skills answer it, one calling the other two: `implement` builds from the spec, hands each piece to `tdd`, which writes a test that fails before the code that passes it, then runs `code-review`, which checks the change against both the repo's rules and the request.

Know these Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

These installed :term[Skills]{id="skill"} build a change and check it, in that order.

**`implement`** builds what a spec or a set of tickets describes. Given a ticket reference, it fetches the ticket and states its title before it starts, and asks when the reference is ambiguous. It hands each piece to `tdd` where it can, at seams agreed beforehand, runs the type check and single test files as it goes and the full test suite once at the end, then runs `code-review` and commits to the current branch. It sets `disable-model-invocation: true`, so it runs only when a person types it ([Claude Code docs: Skills](https://code.claude.com/docs/en/skills)).

**`tdd`** is the red-then-green loop: write one failing test, then only enough code to pass it, one slice at a time. Tests sit at *seams*, the public boundaries where behaviour can be seen without reaching inside, and the seams are agreed with the person before any test is written. The Skill names three traps: tests coupled to the implementation, tests that recompute the expected value the way the code does, and writing every test before any code. Refactoring is left out of the loop on purpose; it belongs to review.

**`code-review`** reviews the diff from a fixed point, such as a branch or commit, on two axes. *Standards* asks whether the change follows the repo's documented rules, plus a baseline of code smells from Martin Fowler's *Refactoring* that a documented rule always overrides. *Spec* asks whether it does what the originating issue asked, no more and no less. Each axis runs in its own subagent, and the two reports stay separate, so a change that passes one can't hide that it fails the other.

The agent can reach for `tdd` and `code-review` on its own when the task fits. For a bug, `diagnosing-bugs` first builds a check that goes red on it; the [Skill Inventory](/t/journal/current/skills) has its entry.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

Each of these sits in :file[.agents/skills/], kept exactly as installed ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)). Terrarium puts them to work in two places: `code-review` is a step a session runs before its PR, and one :term[Workflow] runs all three.

A session runs `code-review` on its branch before the PR opens; a simple change gets the author's own read of its diff instead. :file[docs/agents/pr-workflow.md] holds the steps and what counts as simple, and [Pull requests](/t/glassbox/guide/git-github/pull-requests#why-its-built-this-way) gives the reasons and when another review follows. The Standards axis has no single standards file to read here: Terrarium's rules live in :file[CLAUDE.md], in :file[.claude/rules/] and in the docs those point to.

That Workflow is :file[.claude/workflows/clear-backlog-build.js], run by the `clear-backlog` Skill, which works through the open issues its sweep picks up in one run. No person types `implement` there: the script tells its build agent to read that Skill's file, since no agent can start the Skill, and follow it test-first with `tdd`, skipping its `code-review` step, which the script's own reviewers do next: each reads the `code-review` Skill and applies one axis. They review in rounds, up to a fixed cap, with a fix agent fixing their findings between rounds, until only calls for the owner remain; then a final gate agent runs `pnpm gate:scoped` again on the branch's last commit. [Workflow scripts](/t/glassbox/guide/agents/workflow-scripts#in-terrarium) follows that loop in the code. A branch it marks ready is pushed and then checked again by the :term[Gate] in CI.

How much each Skill matters here, and why, is in the :term[Skill Inventory].

### Why it's built this way

- **These Skills are never edited here.** That way a reinstall can't overwrite a local change; [Installed skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way) gives the reason and its cost. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **The loop as a workflow script.** The loop's script is a real file in `.claude/workflows/`, named by the `clear-backlog` Skill that runs it; [Workflow scripts](/t/glassbox/guide/agents/workflow-scripts#why-its-built-this-way) says why it sits outside its Skill's folder. ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Re-check what a reviewer cites.** A review subagent can quote a line that isn't there. Terrarium's Inventory entry for `code-review` records that a spec reviewer once cited a fabricated line, and points to the "Verify before you state" rule in :file[CLAUDE.md]: check a cited line against its source before you act on it.

## Try it in your project

Next time you review a change, run it as two separate passes: first only against your project's written rules, then only against the issue it closes. Note which findings the second pass found that the first missed.
