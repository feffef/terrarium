You don't have to write every :term[Skill] your agents use. An installed Skill is one someone else wrote and published, which you install into your project. The catch is that the files are then in your repo, where anyone can edit them, and the next install would undo that edit without a word.

Know installed Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Skill is a folder with a `SKILL.md` file of instructions for one kind of job. One GitHub repository can publish many of them. The one Terrarium installs from, Matt Pocock's *Skills For Real Engineers* (`mattpocock/skills`), holds Skills such as `tdd`, `diagnosing-bugs` and `grill-me`. It can be installed as a plugin, which updates itself, or with the [`skills` command-line tool](https://github.com/vercel-labs/skills), which copies the Skills into your project as ordinary files that you update by hand:

```bash
npx skills@latest add mattpocock/skills
```

The command-line tool installs into the project by default, so the Skills are committed with your code and every clone has them. When one install serves several agents, it can link each agent's Skill folder to a single copy. `npx skills update` brings the copies up to date with their source.

Some sources also ship a setup Skill that writes a project's own configuration from templates. The `setup-matt-pocock-skills` Skill asks which issue tracker the project uses and, if the `triage` Skill from the same repository is installed, whether to keep its default triage labels. It picks the layout of the domain docs without asking unless the repo looks like a monorepo, then writes docs that the other Skills read.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

The installed Skills sit in :file[.agents/skills/] beside Terrarium's own, and :file[.claude/skills/] holds a link to each folder so Claude Code finds it. The installer's :file[skills-lock.json] records each installed Skill: its source repository, its path there, and a hash of that upstream file, `computedHash`.

Being listed there is what makes a Skill an installed Skill, and nobody in Terrarium edits an installed Skill's files. Each installed Skill's :term[Skill Inventory] entry carries an `installedSha256`, the sha256 of its installed `SKILL.md`:

::excerpt{path="layers/journal/content/current/skills/tdd.yml" lines="1-4"}
```yaml
name: tdd
category: general-engineering
importance: supporting
installedSha256: 5505d25bbaa8fc14a79e4d20163936958992a2995b7f1dd1d6197edc9ed722e0
```
::

:file[scripts/gate/validate-skills-lock.ts] is a step of the :term[Gate]'s :term[Floor]. It reads the lock only to learn which Skills are installed and hashes each one's installed `SKILL.md`, no other file in its folder. Its check walks those names:

::excerpt{path="scripts/gate/validate-skills-lock.ts" lines="79-94"}
```ts
  for (const name of externalNames) {
    const actual = onDisk.get(name) ?? null
    if (actual === null) {
      findings.push({ name, kind: 'missing' })
      continue
    }
    const entry = inv.get(name)
    if (!entry?.cataloged) continue
    if (!entry.pin) {
      findings.push({ name, kind: 'unpinned', actual })
      continue
    }
    if (entry.pin !== actual) {
      findings.push({ name, kind: 'drifted', expected: entry.pin, actual })
    }
  }
```
::

An installed Skill whose `SKILL.md` is missing fails, Inventory entry or not. A Skill with no Inventory entry is skipped; one with an entry fails when the entry has no pin or the hash differs from it. `pnpm verify:skills-lock --write` rewrites each entry's pin from the file on disk, and skips a Skill with no entry too.

The setup Skill seeded three docs: :file[docs/agents/issue-tracker.md], :file[docs/agents/triage-labels.md] and :file[docs/agents/domain.md]. Those are Terrarium's own now. Each opens with a note not to re-sync it against the template it came from.

### Why it's built this way

- **Installed Skills untouched.** Reinstalling would silently overwrite a local edit, so installed Skills are never edited. The Gate keeps a fingerprint (a hash) of each installed Skill's `SKILL.md` in its :term[Skill Inventory] entry and fails on a mismatch. Notes on fit go in that entry, not the files. The cost: an installed Skill's wrong line can't be corrected in Terrarium. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Our own pin, not the lock's.** The lock's `computedHash` is the installer's hash of the upstream source, which doesn't match the installed file and can't be checked offline, and the lock belongs to the installer. Terrarium keeps its own `installedSha256` in the Inventory instead. The cost: every real update from the source re-pins in the same PR, or the Gate fails. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Seeded docs become ours.** A setup Skill writes generic docs from templates, and a project then fills them with its own facts, which a re-sync would wipe. A doc copied from an installed Skill's template is Terrarium's to edit and is never re-synced. The cost: a later improvement to the template reaches the doc only if someone carries it over by hand. ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Check the lock before you edit a Skill.** An installed Skill not yet in use has no pin, so the Gate won't catch an edit to it; only :file[skills-lock.json] tells you it is installed. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Re-pin only after a real install.** `--write` makes any edited file pass, so run it only when the new content came from the source.

## Try it in your project

Pick one Skill you installed from another repository, record the sha256 of its `SKILL.md` in a file you own, and add a CI step that fails when the installed file's hash differs.
