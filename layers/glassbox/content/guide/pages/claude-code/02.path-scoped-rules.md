An agent can't follow an instruction it never sees, and a `CLAUDE.md` that holds every instruction about every file grows too long to follow. A path-scoped rule puts an instruction in front of the agent when it works on the files the instruction is about.

Know path-scoped rules already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code reads each Markdown file in a project's `.claude/rules/` folder, including its subfolders, as a rule. A rule without a `paths` field loads at the start of every session, like `CLAUDE.md`. A rule whose frontmatter lists `paths` loads only when Claude works with a file that one of its globs matches: when it reads, writes or edits that file with its own tools, or views it with a simple shell read such as `cat` on that one file.

```md
---
paths:
  - "src/api/**/*.ts"
---
# API handlers

- Validate every request body before you use it.
```

`paths` is the only frontmatter field Claude Code reads. It ignores any other field without an error, and removes the frontmatter before the rule reaches Claude's context.

Full reference: [Claude Code docs: Path-specific rules](https://code.claude.com/docs/en/memory#path-specific-rules)

## In Terrarium

Terrarium gives each instruction one home, chosen by what it is about. An instruction about certain files is a :term[Rule] in :file[.claude/rules/] whose `paths` match those files. An instruction every session needs, or one tied to an action such as a commit or a PR, stays in :file[CLAUDE.md]. For example, :file[.claude/rules/tenant-layers.md] matches each Tenant layer's `nuxt.config.ts`, `tenant.config.ts` and `app/` folder, so an agent editing a :term[Tenant] learns that a layer's CSS loads on every page.

Every ADR has a summary rule too, `adr-NNNN.md`. It gives the ADR's key parts as instructions and says when to read the whole ADR. Its `paths` list the files the ADR governs, so the decision arrives when an agent works on something it binds. Only a summary whose ADR binds every session has no `paths`, and it loads at session start.

:file[scripts/validate-adr-rules.ts], part of `pnpm validate:content` and so of the :term[Gate], fails a summary whose ADR changed since someone last checked the summary against it. It also fails any other rule that has no `paths`.

Two hooks fill the gaps where Claude Code loads no rule. Running a :term[Skill] reads no file, so :file[scripts/skill-rules-hint.ts] adds the rules whose `paths` name that Skill's folder. A piped or chained shell command is not a simple read, so :file[scripts/bash-rules-hint.ts] adds the rules for the files such a command read. :file[.claude/settings.json] wires both in, and both fail open: an error adds nothing and never blocks the call.

### Why it's built this way

`CLAUDE.md` once held lines like "before you edit X, read Y", and sessions often skipped them. A :term[Rule] needs no such pointer: Claude Code adds it by itself when the agent touches the files it is about. So an instruction about certain files moves out of `CLAUDE.md` into a rule. The cost: a rule arrives only once a file is touched, often after the plan, so `CLAUDE.md` still tells agents to search the ADRs before they recommend a change. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

ADRs were long, and many stated their current decision only below several amendments, so agents told to read every matching ADR in full often didn't. A short summary rule now brings each ADR's key parts to the files it governs, and says when the full ADR is worth reading. A summary is a copy that can drift, so the :term[Gate] fails until someone re-checks it after its ADR changes. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

Two other ways to deliver the ADRs were rejected. Printing every summary from a session-start hook fails because Claude Code caps how much a hook may print, and the summaries exceed it. Importing the full ADR into its rule with `@` fails because the import isn't expanded when a path-scoped rule loads, yet the imported file still loads in every session. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

`CLAUDE.md` loads in every session, and no file pattern can match an action such as a commit, so instructions for every session or for an action stay there. If other rules could also load at session start, such an instruction would have two possible homes, and the copies would drift. So only ADR summaries may skip `paths`, and the gate fails any other rule without them. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

Moving instructions into rules only works if rules actually load. Agents in auto mode, which runs tools without asking each time, often read files through the shell, and that loads no rule; one session got file rules only when it ran a :term[Skill]. The two hooks close those gaps, but only as hints: working out paths from a shell command is a guess, and a broken hint must never block a session. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

### What to watch for

- **A rule can't order a step.** Why, and where such steps go instead: [CLAUDE.md](/t/glassbox/guide/claude-code/claude-md#what-to-watch-for).
- **Read with the Read tool.** A file read through the shell gets its rules only from :file[scripts/bash-rules-hint.ts], a backstop.
- **A rule change waits for a person.** Every file in `.claude/rules/` is on the :term[Human-only] list, so an agent may edit a rule but not merge the change.

## Try it in your project

Find one line in your `CLAUDE.md` about a particular set of files. Move it into a file in `.claude/rules/` whose `paths` match those files, and delete the line from `CLAUDE.md`.
