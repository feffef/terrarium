In `default` mode Claude Code asks before it runs most tool calls. In `auto` mode, which Claude Code v2.1.283 or later starts a terminal session in unless a flag or setting picks another mode, a classifier, a second model, reviews actions instead of you. Permission rules in settings files decide which calls skip the prompt, which always prompt and which never run; the permission mode decides every call no rule settles. No allow rule ever approves a write to a protected path, such as `.git` or most of `.claude`; only some modes let one run without a prompt.

Know Claude Code permissions already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code reads [settings](https://code.claude.com/docs/en/settings) from several files. Highest first, they are an organization's managed settings, JSON passed with `--settings` on the command line, your uncommitted `.claude/settings.local.json`, the project's committed `.claude/settings.json`, and your user file `~/.claude/settings.json`. A key set higher overrides the same key lower down, but a list such as `permissions.allow` merges across the files. A cloud session reads fewer of them, as [Cloud sessions](/t/glassbox/guide/agents/cloud-sessions) shows. Besides permissions, a settings file can set `env` variables and [hooks](/t/glassbox/guide/hooks/hooks).

[Permission rules](https://code.claude.com/docs/en/permissions) name a tool, optionally narrowed to a command or path:

```json
{
  "permissions": {
    "allow": ["Bash(npm test *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)"]
  }
}
```

An `allow` rule lets a call run without a prompt, `ask` always prompts, and `deny` blocks. Claude Code checks deny first, then ask, then allow, and the first match decides, so a narrow allow can't carve an exception out of a broad deny, and a deny in any file blocks what another file allows. A project's allow rules apply only once you accept the folder's trust dialog, which lists what the folder would grant; its deny and ask rules apply at once, since they only restrict.

The [permission mode](https://code.claude.com/docs/en/permission-modes) sets what happens to a call no rule settles. `default` prompts on the first use of each tool; `acceptEdits` also accepts file edits and common file commands inside the working directory; `plan` explores without editing; `auto` has a classifier model check each action instead of asking; `dontAsk` never prompts: it runs a call that needs no approval or that an allow rule or a `PreToolUse` hook (one that runs before a tool call) approves, and denies the rest; and `bypassPermissions` skips prompts, where allow rules have no effect but a deny still blocks and an ask rule still prompts. `defaultMode` in a settings file sets the mode a session starts in, but a project's `.claude/settings.json` or `.claude/settings.local.json` can't set `auto` or `bypassPermissions`.

Writes to Claude Code's protected paths, such as `.git`, `.vscode`, `.mcp.json` and most of `.claude`, are never auto-approved, except in `bypassPermissions` and in `plan` mode in an interactive terminal session where `bypassPermissions` is available. No allow rule changes that: the safety check runs before the allow rules, so an `Edit(.claude/**)` entry does nothing. What happens instead depends on the mode: `default` and `acceptEdits` prompt, `auto` sends the write to the classifier, and `dontAsk` denies it.

A `PreToolUse` hook runs before the rules and can deny a call, force a prompt or let it run. A hook that blocks stops the call even when an allow rule matches it, but a hook's allow never skips a deny or ask rule; [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks) shows such a hook.

Full reference: [Claude Code docs: Configure permissions](https://code.claude.com/docs/en/permissions)

## In Terrarium

The committed :file[.claude/settings.json] holds Terrarium's only permission rules: a short allow list, with no `ask` or `deny` rule and no `defaultMode`. No `.claude/settings.local.json` is committed. The list does not always apply: :file[docs/agents/environment-caveats.md] records that an untrusted workspace drops `permissions.allow` before matching any rule (`deny` and `ask` rules stay, since they only restrict), which is the trust dialog rule above at work, and a cloud session can be such a workspace. A cloud session started on several repositories doesn't read the list at all ([Cloud sessions](/t/glassbox/guide/agents/cloud-sessions#in-terrarium)).

::excerpt{path=".claude/settings.json" lines="5-12"}
```json
  "permissions": {
    "allow": [
      "mcp__github__create_pull_request",
      "mcp__github__pull_request_read",
      "Workflow(clear-backlog-explore)",
      "Workflow(clear-backlog-build)"
    ]
  },
```
::

The calls Terrarium refuses, it refuses with hooks. The same file wires each guard, Terrarium's name for a blocking hook, as a `PreToolUse` hook on the tools it checks. This one denies an `Agent`, `Workflow` or `SendMessage` call from the main session, not a subagent, until the session has run or read the `dispatch-subagents` skill:

::excerpt{path=".claude/settings.json" lines="34-43"}
```json
      {
        "matcher": "Agent|Workflow|SendMessage",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/dispatch-read-guard.ts",
            "onFailure": "block"
          }
        ]
      },
```
::

With no `defaultMode` in the repo, the mode comes from where a session starts: a person picks a cloud session's mode when creating it, and a :term[routine]'s run starts in auto mode ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks)).

### Why it's built this way

- **Keep the settings prompt.** An unattended run's subagent (a helper session, in a run no one watches) stalled on the prompt to edit :file[.claude/settings.json]. Pre-approving the edit fails where a cloud session drops the allow list, and would let an agent switch off the guards that file wires. Unattended sessions are never sent to change guards. The cost: such a fix waits for an attended session. :file[.out-of-scope/pre-approved-settings-edits.md].
- **Allow the calls every PR makes.** Confirm dialogs on opening a PR and polling its checks stalled the open-then-watch flow every session follows, so the allow list in :file[.claude/settings.json] pre-approves the GitHub tools that open a PR and read it. The cost: it helps only a trusted session that reads the list (see [In Terrarium](#in-terrarium)).

### What to watch for

- **An unattended settings edit stalls.** In a mode that prompts, an edit to :file[.claude/settings.json] waits for an answer an unattended run can't give; in auto mode, which a routine runs in, the classifier decides instead. [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks) says who merges a guard change.
- **An allow entry may do nothing in the cloud.** A cloud session may not read the list at all ([In Terrarium](#in-terrarium)), and its GitHub tools run unprompted through a separate auto-approve path, not the allow list. Don't add an entry to silence a prompt you see in the cloud: :file[docs/agents/environment-caveats.md] says why it does nothing.

## Try it in your project

Add `"allow": ["Bash(git push origin *)"]` and `"ask": ["Bash(git push *)"]` to your project's `.claude/settings.json`, then ask Claude to push a branch: it prompts, since ask is checked before allow. Then add `Edit(.claude/**)` to the allow list, start a session with `claude --permission-mode default` and ask Claude to edit that settings file: it still prompts.
