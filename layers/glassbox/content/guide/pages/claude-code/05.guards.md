Some instructions keep being missed however they are worded. When one does, Terrarium stops asking and checks instead: a guard looks at a tool call before it runs, denies the wrong ones, and tells the agent what to do instead. A guard has to block when it breaks, too, or a crash quietly becomes a pass.

Know PreToolUse hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A guard is a `PreToolUse` hook. Claude Code runs it before each tool call its matcher names and hands it the call as JSON on stdin: `tool_name`, `tool_input`, and the path of the session's transcript. To block the call, the hook exits 0 and prints a decision:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep."
  }
}
```

Claude Code cancels the call and gives the reason to Claude, so the reason is the instruction the model acts on next. Printing nothing lets the call go on to the normal permission check; it doesn't approve it.

A hook that fails is another matter. If it exits with any code but 0 or 2 and prints no valid JSON, or fails to start at all, Claude Code reports a non-blocking error and the call goes ahead. A check that crashes is then the same as no check. The docs' advice for a hook that enforces a policy is to exit 2 to block, rather than 1. Newer versions of Claude Code also take `"onFailure": "block"` on a command hook, which blocks the call when the hook can't start, exits with a code other than 0 or 2, or times out.

Full reference: [Claude Code docs: Hooks reference, exit code output](https://code.claude.com/docs/en/hooks#exit-code-output)

## In Terrarium

Terrarium turns an instruction into a guard once prose has failed to hold it. The header of :file[scripts/skill-inline-guard.ts] tells a typical story: a fix written into a doc never reached the scheduled sessions that kept making the mistake, because none of them had reason to open that doc. A guard runs in every session that makes the call, and its deny message becomes the rule's home. :file[docs/agents/guards.md] lists every guard, what it denies, and where its rule lives. For example, :file[scripts/workflow-edit-guard.ts] denies an agent's write into `.github/workflows/`, which the session's GitHub credentials can't push anyway, before the write strands a whole push.

Each guard is a small script: a list of the cases it knows, a pure check, and a message. Most share their plumbing, in :file[scripts/guard-io.ts]. Its `runIfMain` runs the guard and turns any crash into a deny:

::excerpt{path="scripts/guard-io.ts" lines="124-130"}
```ts
  try {
    if (opts.dryRun && argv.includes('--dry-run')) opts.dryRun(argv)
    else opts.main()
  } catch (err) {
    if (opts.failOpen) return
    denyUninspectable(opts.label, opts.ref, `the guard itself crashed (${err instanceof Error ? err.message : String(err)})`)
  }
```
::

A guard that can't read what it needs, such as the transcript, denies the same way. But a guard can also fail before that `try` runs: the TypeScript runner may not start, or an import may throw. The process then exits with an error and prints nothing, which Claude Code reads as a non-blocking error, and the call goes ahead. So the guards are wired through :file[scripts/guard-wrap.sh], which does the job of `onFailure: "block"` by hand:

::excerpt{path="scripts/guard-wrap.sh" lines="45-54"}
```sh
out=$("$@")
status=$?

if [ "$status" -ne 0 ] && [ -z "$out" ]; then
  # …
else
  printf '%s' "$out"
fi

exit 0
```
::

The line left out prints a deny reason that names the guard and says the block is a guard fault, not the agent's mistake. The wrapper doesn't cover a guard that times out: Claude Code stops it before it can print, and the call goes ahead. Anything the guard printed passes through unchanged, and the wrapper itself always exits 0, so nothing in :file[.claude/settings.json] needs a `|| true` that would let a fault through again.

One guard fails open on purpose. :file[scripts/deferred-tool-guard.ts] catches a tool called with another tool's arguments, which it can recognize only by their shape, so it must never deny a call it couldn't positively identify. It passes `failOpen: true`, and its wiring keeps a bare `|| true` instead of the wrapper. The hints, which add guidance beside a call's result or a prompt, fail open too.

Each guard keeps its check pure, so a unit test in :file[tests/unit/] covers it, and a `--dry-run` flag shows by hand what it would decide for a given call.

### Why it's built this way

Why a guard is :term[Human-only] to merge: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **The deny message is the instruction.** Do what it says. If it is wrong, report it on the guard's issue rather than rewording the call until it slips past.
- **A guard can't see everything a call does.** The shell filters in front of the `Bash`, `Edit` and `Write` guards match text, so a call worded in a way they don't expect, or a payload whose keys the harness renames, goes ahead unchecked. Each guard's header lists its own gaps.
- **Tests can't watch a live deny.** A unit test checks the decision, not that the hook fires, so every guard is :term[Human-only] to merge, and a change to one is probed once by hand.
- **Don't send an unattended session to change a guard.** Editing one raises a permission prompt that nobody is there to grant; such a run files an issue with the fix instead.

## Try it in your project

Add `"onFailure": "block"` to a `PreToolUse` hook you rely on, then make it crash on purpose (an import of a module that doesn't exist will do) and check that the call is blocked. On a Claude Code version without `onFailure`, wrap the hook instead, so that a nonzero exit with no output prints a deny.
