Every session starts knowing nothing about the project. `CLAUDE.md` is the one file it is sure to read first, so it is where the instructions every session needs belong, and nothing else.

Know `CLAUDE.md` already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code loads the `CLAUDE.md` at a project's root into every session, at the start and again after the conversation is compacted. You write it in plain Markdown: build commands, conventions, where things live, "always do X" rules. Claude reads it as context, not as enforced configuration. It tries to follow each line, and it follows short, concrete, consistent lines best.

So the docs send everything else elsewhere. A procedure, or an instruction that matters for only one part of the code, goes in a :term[Skill] or a path-scoped :term[Rule]. Something that must happen at a fixed point whatever Claude decides, such as checking every shell command before it runs, goes in a hook.

A first `CLAUDE.md` in your own project's root can be this small:

```md
# CLAUDE.md

- Run `npm test` before you commit.
- API handlers live in `src/api/handlers/`.
- Before you change the database schema, read `docs/migrations.md`.
```

Full reference: [Claude Code docs: How Claude remembers your project](https://code.claude.com/docs/en/memory)

## In Terrarium

Every Terrarium session, whether a person started it or a schedule did, begins with :file[CLAUDE.md]. It opens with the house style: write the least code and the fewest words that stay exact. Everything after that is short sections of instructions every session needs.

The section that does most of the work names *when* to read each doc rather than copying the doc in. A trigger binds a doc to an action:

::excerpt{path="CLAUDE.md" lines="26-30"}
```md
- **Before your first git command** beyond `status` and `diff` (commit, fetch,
  pull, rebase, amend, reset, or `log`/`blame` to draw a conclusion):
  `docs/agents/git-conventions.md`.
- **Before your first GitHub operation** (`mcp__github__*` tool or `gh`):
  `docs/agents/github-integration.md`.
```
::

The docs themselves sit in :file[docs/agents/], and only the sessions that reach a trigger read its doc. Rules and Skills stay out of `CLAUDE.md`, which only points to them. Instructions about particular files are rules in :file[.claude/rules/], which Claude Code loads when an agent reads or edits those files; each ADR's summary is a rule too. Procedures are Skills in :file[.agents/skills/].

A trigger is still prose, and an agent can act before it notices one. For some triggers, :file[scripts/read-first-hint.ts] is a backstop: at the first matching call it adds a pointer to the doc, beside that call's result. It can't stop the call, and it stays silent once the doc has been read. :file[.claude/settings.json] wires it in as a hook.

### Why it's built this way

Every line of `CLAUDE.md` is paid for by every session, and most sessions are scheduled runs that skim. The file had grown to hundreds of lines of rules, incident stories and repeats of other docs, because adding a line after a mistake felt safe and removing one felt risky. So a :term[Prune Trial] cut it to the minimum: each rule's origin was traced, and a rule stayed only if it came from a serious problem and had no other home. The cost is that a cut can let an old mistake back in, which the :term[Frictions]{id="friction"} later sessions log are there to catch. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).

The read-first list used to be grouped by topic ("Git", "Landing a PR"), and another line asked agents to read every ADR, which they mostly didn't: in a survey of large sessions, most had read only one or two ADRs, and structural edits missed the ADRs that bound them. The same cut turned the list into "before you do X, read Y" triggers tied to a concrete action, and turned "read every ADR" into "find the ADRs that bind this change". A trigger still only works if the agent notices the moment it names.

A file-bound line such as "before you edit X, read Y" was skipped too often, so those instructions moved into rules, which Claude Code delivers by itself when the files are touched. A rule arrives only after the read or edit that loads it, and no file pattern can match an action like a commit, so instructions tied to an action, or needed by every session, stay in `CLAUDE.md`. Printing every summary from a session-start hook was rejected: hook output is capped below what they add up to. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

Even with action triggers, many sessions read the git or GitHub doc just after their first git or GitHub call, not before. One ran an unscoped search that flooded its context, the exact trap the unread doc warns about. More prose would have been read late too, so Terrarium added a hint that points to the doc at that call. It never blocks, so the cost, which the owner accepted, is that the first call still runs before the doc is read. :file[scripts/read-first-hint.ts].

### What to watch for

- **Loaded is not obeyed.** A line can load and still be skipped. Where a slip is costly, Terrarium backs the line with something that runs: a hint, a guard, or the Gate.
- **Each incident tempts a new line.** Lines added after every mistake bury the ones that matter. Terrarium tests a line by removing it in a :term[Prune Trial]; the open trials are listed in :file[.agents/prune-trials.yml].
- **A rule can't order a step.** A "before you do X" instruction stays in `CLAUDE.md`, however file-bound it looks; ADR-0029 says why.

## Try it in your project

Find the doc your agent most often forgets. Add one line to your `CLAUDE.md` that names the action and the doc ("Before you change the schema: read `docs/migrations.md`"), then delete any paragraph of `CLAUDE.md` that only repeats that doc.
