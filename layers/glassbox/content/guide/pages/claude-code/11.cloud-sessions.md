A session on your laptop has your tools, your sign-ins and your settings. A cloud session starts on a fresh machine with only what the repository holds. Whatever a project needs in every session must therefore be committed, and the rest of the session's limits come from settings and from the cloud's own network.

Know cloud sessions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A cloud session is a Claude Code session that runs on a virtual machine Anthropic manages, started from claude.ai/code, the Claude app, the Desktop app or `claude --cloud`. It clones your repository fresh. In a session with one repository, committed files arrive: `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`, `.mcp.json` and `.claude/settings.json`. Nothing from your own machine does, such as `~/.claude/settings.json` or a server you added only for yourself. Each session runs in a [cloud environment](https://code.claude.com/docs/en/cloud-environments), which sets its network access, its environment variables and a setup script. GitHub goes through a proxy that holds your credentials outside the machine, and that proxy refuses GitHub's GraphQL API.

Settings come in layers: your user file `~/.claude/settings.json`, the project's committed `.claude/settings.json`, your uncommitted `.claude/settings.local.json`, and an organization's managed settings, which override the rest. A project file can set `env` variables, hooks and [permissions](https://code.claude.com/docs/en/permissions):

```json
{
  "permissions": {
    "allow": ["Bash(npm test *)"],
    "deny": ["Read(./.env)"]
  }
}
```

An `allow` rule lets a call run without a prompt, `ask` always prompts, and `deny` blocks. Claude Code checks deny first, then ask, then allow, and the first match decides. The permission mode sets what happens to everything no rule matches, from `default`, which runs only reads without a prompt, to `bypassPermissions`, which skips prompts. No allow rule approves a write to a few protected paths, `.git` and `.claude` among them: outside bypass mode, such a write always gets a check of its own. [Settings files and precedence](https://code.claude.com/docs/en/settings) covers where each file lives.

Full reference: [Claude Code docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)

## In Terrarium

Every :term[Routine] runs as a cloud session, and so does any session started from claude.ai. Everything a Terrarium session needs is in the repo. A `SessionStart` hook installs dependencies and fetches full git history when the clone is shallow, as [Claude Code hooks](/t/glassbox/guide/claude-code/hooks) shows.

The committed :file[.claude/settings.json] holds one `env` variable, a short `permissions.allow` list and the hooks, and no `ask` or `deny` rule. Which of those a cloud session uses depends on how it starts. A session with one repository reads the file. :file[docs/agents/environment-caveats.md] records that a multi-repository cloud session reads only `enabledPlugins` and `extraKnownMarketplaces` from it, and that an untrusted workspace drops `permissions.allow` before matching any rule; it says an allow entry for the cloud host's own tools does nothing in Terrarium's cloud sessions. The [permissions docs](https://code.claude.com/docs/en/permissions#what-runs-before-you-trust-a-folder) list a project's hooks and `env` as used before the folder is trusted, and its `permissions.allow` rules as not used. Terrarium's guards are hooks, and :file[docs/agents/guards.md] records them firing in a cloud session, a dispatched subagent's calls included, when probed on 2026-08-06. [MCP servers](/t/glassbox/guide/claude-code/mcp-servers) covers why an allow entry for the GitHub tools does nothing there.

The cloud also fences what a session can reach. A few of the limits Terrarium has met: the token can't push `.github/workflows/`, a change there goes to a person as a :term[Proposal], and [Merge gate](/t/glassbox/guide/verification/gate) shows where the :term[Gate]'s CI steps live instead; the proxy refuses writes to repository settings; and some docs sites are blocked. For the first, :file[scripts/hooks/workflow-edit-guard.ts], a `PreToolUse` hook, denies an edit or a write-shaped command aimed at `.github/workflows/`, and only when a variable the cloud sets is present:

::excerpt{path="scripts/hooks/workflow-edit-guard.ts" lines="71-74,143-144,152"}
```ts
/** The variable the provenance guards also read; only a cloud session sets it. */
export function isCloudSession(env: NodeJS.ProcessEnv = process.env): boolean {
  return Boolean(env.CLAUDE_CODE_REMOTE_SESSION_ID)
}
// …
export function main(): void {
  if (!isCloudSession()) return
  // …
}
```
::

### Why it's built this way

- **Keep the settings prompt.** An unattended run's subagent stalled for hours on the prompt to edit :file[.claude/settings.json]. Pre-approving the edit wouldn't help in a cloud session, which can drop `permissions.allow`, and would let an agent switch off its own guards. So the prompt stays, and no unattended session is sent to change a guard. The cost: such a fix waits for a session someone attends. :file[.out-of-scope/pre-approved-settings-edits.md].
- **Stop a workflow edit before it is committed.** A cloud session's token can't push `.github/workflows/`, and the refusal covers every commit in the push, so one workflow edit strands the work beside it. So the guard denies the edit at the tool call, before any commit exists. The cost: it matches command text, so a path held in a variable slips past to the refused push. :file[scripts/hooks/workflow-edit-guard.ts].

### What to watch for

- **No allow rule makes settings edits silent.** `.claude/` is a protected path, so no rule lets an edit to :file[.claude/settings.json] go through unchecked. Where the edit prompts, an unattended run has nobody to answer; [Blocking hooks](/t/glassbox/guide/claude-code/blocking-hooks) says who merges a guard change instead.
- **A 403 is often the environment.** A GraphQL `gh` command, a blocked docs site or a refused settings call fails the same way every time. Read the caveats before you diagnose it as a bug in your change.
- **Settings in the cloud are only what is committed.** A hook or permission you set in your own `~/.claude/settings.json` never reaches a cloud session. Put what every session needs in the project file.

## Try it in your project

Commit a `SessionStart` hook to your project's `.claude/settings.json` that installs your dependencies. Start a cloud session on the repository and check that the install ran before Claude's first answer.
