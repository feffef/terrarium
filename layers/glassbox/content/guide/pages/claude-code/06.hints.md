Some advice only makes sense at the moment it applies: right after a push is rejected, or the first time an agent runs `git`. A hint is a hook that adds that advice beside the result of the call that needed it, and then gets out of the way.

Know hooks that add context already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Claude Code hook is a command that runs at a fixed point in a session, wired in the project's settings. A `PostToolUse` hook runs after a tool call succeeds, and a `PostToolUseFailure` hook runs after one fails. By then the tool has already run, so the hook can't stop it. What it can do is talk to Claude: if it prints JSON with an `additionalContext` string, Claude Code puts that string into the conversation beside the tool's result, as a system reminder Claude reads on its next step. A `UserPromptSubmit` hook can do the same beside the prompt a person just sent.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "This file is generated. Edit src/schema.ts instead."
  }
}
```

The exit code matters too. Exit 0 applies the JSON. Exit 2 is a blocking error on the events that can block. Any other non-zero code is a non-blocking error: the action goes ahead.

Full reference: [Claude Code docs: Add context for Claude](https://code.claude.com/docs/en/hooks#add-context-for-claude)

## In Terrarium

Terrarium splits its hooks into guards and hints. A guard runs before a call and can deny it. A hint runs after a call, or after a prompt, and only adds context. The roster in :file[docs/agents/guards.md] lists every hint beside the guards, and :file[.claude/settings.json] wires each one in.

Each hint watches for one situation:

- :file[scripts/stale-info-hint.ts] waits for a `git push` that git rejects as "stale info". Agents read that as someone else pushing at the same time, when usually the remote branch was deleted after its PR merged. The hint says so and names the fix.
- :file[scripts/read-first-hint.ts] waits for a session's first GitHub call, or its first git command beyond `status` and `diff`, and names the doc `CLAUDE.md` says to read before it. After the main session opens a PR, it also says to invoke the `close-session` Skill.
- :file[scripts/skill-rules-hint.ts] and :file[scripts/bash-rules-hint.ts] add the path-scoped rules that Claude Code doesn't load on its own: for a Skill that runs, and for a shell command that read files in a way Claude Code doesn't recognize.

A hint writes the same JSON as the example above. This is the stale-info hint's output:

::excerpt{path="scripts/stale-info-hint.ts" lines="42-56"}
```ts
function main(): void {
  const result = readHookPayload()
  if (result.kind !== 'ok') return
  const hint = staleInfoHint(result.payload)
  if (!hint) return
  const event = field(result.payload, 'hook_event_name')
  process.stdout.write(
    JSON.stringify({
      hookSpecificOutput: {
        hookEventName: event === 'PostToolUseFailure' ? event : 'PostToolUse',
        additionalContext: hint,
      },
    }),
  )
}
```
::

A rejected push is a failed call, so this hint is wired on both `PostToolUse` and `PostToolUseFailure`, and it answers with whichever event called it.

### Why it's built this way

A guard almost always fails closed: if it crashes, the call is blocked. A hint fails open. Each one is wired as `… || true`, and its script swallows its own errors, so a broken hint adds nothing and the session carries on. A hint's message is advice, so losing it costs little, while a crashing hint that blocked calls would stop every session.

A hint also says each thing once. The read-first hint stays silent once the session's transcript shows the doc was read or the pointer was already given, and the shell-read rules hint skips any rule the session already loaded. A line that repeats on every call soon gets ignored.

Why rules need these hints at all, and why the read-first pointer backs up a line of prose: [Path-scoped rules](/t/glassbox/guide/claude-code/path-scoped-rules) and [CLAUDE.md as the every-session contract](/t/glassbox/guide/claude-code/claude-md).

### What to watch for

- **A hint comes after the call.** It can't stop a mistake, only correct the next step. When the first wrong call is itself costly, a hint is the wrong tool; a guard, which runs before the call, is the right one.
- **Every matching call pays for the hook.** Starting a TypeScript script for each shell command adds up, so each hint on `Bash` sits behind a small `sh` pre-filter that exits at once unless the payload could match, such as a command holding a `git` word. Keep the hook's matcher narrow too: never `"*"`.
- **A subagent is a separate reader.** Hooks fire for a dispatched subagent's calls too, but its payload carries the parent's transcript path. The hints that dedupe find the subagent's own transcript from its `agent_id`, so a pointer the parent already got still reaches the subagent once.

## Try it in your project

Find an error message your agent keeps misreading. Add a `PostToolUseFailure` hook on `Bash` that checks the command's error for that message and prints the JSON above with one sentence that names the real cause and the fix. End the hook's command with `|| true`, so a bug in it never blocks a call.
