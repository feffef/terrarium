Some instructions keep being missed however they are worded. A blocking hook stops asking and checks instead: a `PreToolUse` hook that looks at a tool call before it runs, denies the wrong ones, and tells the agent what to do. It must also decide what happens when it breaks. A blocking hook that fails closed blocks the call when it can't do its job; one that fails open lets the call through, and a crash quietly becomes a pass.

Know PreToolUse hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A blocking hook is a `PreToolUse` [hook](/t/glassbox/guide/claude-code/hooks). Claude Code runs it before each tool call its matcher names and hands it the call as JSON on stdin, including `tool_name`, `tool_input` and the path of the session's transcript. To refuse the call, the hook exits 0 and prints a decision:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep."
  }
}
```

Claude Code blocks the call and shows Claude the reason, so the reason is the instruction the model acts on next. When several hooks decide on one call, the strictest decision wins.

A hook that fails is another matter. If it exits with any code but 0 or 2 and prints no valid JSON, or doesn't start at all, Claude Code reports a non-blocking error and the call goes ahead: by default a hook fails open. The docs' advice for a hook that enforces a policy is to exit 2 to block, rather than 1. A crash, though, picks its own exit code. Newer versions of Claude Code take `"onFailure": "block"` on a command hook, which turns a failure into a block: a hook that can't start, exits with a code other than 0 or 2, prints output that can't be parsed, or times out. It has no effect on a `Stop` hook.

Full reference: [Claude Code docs: Block the action when a hook fails](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)

## In Terrarium

Terrarium calls its blocking hooks guards. :file[docs/agents/guards.md] is the roster: each guard, what it denies, where the rule it enforces lives, and its issue. It lists the hints too, which add guidance and deny nothing. Each guard's own script header holds its reasons and the cases it can't see.

A guard is a small script in :file[scripts/hooks/]: a registry of the cases it knows, a pure check, and a message. :file[scripts/hooks/hook-io.ts] holds the plumbing they share: reading the payload and the transcript, the deny JSON, and a `--dry-run` mode. A guard's `main` shows the pattern. An empty stdin, a bare run by hand, passes; a payload it can't read is denied:

::excerpt{path="scripts/hooks/skill-inline-guard.ts" lines="98-107"}
```ts
export function main(): void {
  const result = readHookPayload()
  if (result.kind === 'none') return
  if (result.kind === 'invalid') return denyUninspectable(LABEL, REF, 'the hook payload was not valid JSON')
  if (result.kind === 'no-tool') return denyUninspectable(LABEL, REF, 'the hook payload named no tool')

  const { payload } = result
  const output = denyOutputFor(checkSkillInlineCall(payload.tool_input, readTranscript(payload.transcript_path)))
  if (output) process.stdout.write(JSON.stringify(output))
}
```
::

A transcript it can't read denies too. `denyUninspectable` says the block is a guard fault, not the agent's mistake. Every guard starts through `runGuard`, which turns a thrown error into the same kind of deny:

::excerpt{path="scripts/hooks/hook-io.ts" lines="126-135"}
```ts
  const onCrash = (err: unknown): void => {
    if (opts.failOpen) return
    denyUninspectable(opts.label, opts.ref, `the guard itself crashed (${err instanceof Error ? err.message : String(err)})`)
  }
  try {
    const done = opts.dryRun && argv.includes('--dry-run') ? opts.dryRun(argv) : opts.main()
    if (done instanceof Promise) done.catch(onCrash)
  } catch (err) {
    onCrash(err)
  }
```
::

A crash before that `try`, such as a TypeScript runner that won't start or an import that throws, prints nothing and exits nonzero. The wiring in :file[.claude/settings.json] covers that case: each guard's hook sets `onFailure`, except the ones :file[docs/agents/guards.md] lists as wired with `|| true`. The first entry here is such an exception; the second is the usual wiring:

::excerpt{path=".claude/settings.json" lines="15-33"}
```json
      {
        "matcher": "TaskCreate|Monitor",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/deferred-tool-guard.ts || true"
          }
        ]
      },
      {
        "matcher": "ScheduleWakeup",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/loop-only-tool-guard.ts",
            "onFailure": "block"
          }
        ]
      },
```
::

:file[scripts/hooks/deferred-tool-guard.ts] catches a tool called with another tool's arguments. It passes `failOpen: true` to `runGuard`, and its hook ends in `|| true`, which turns any exit into 0, with no `onFailure`. The `Stop` hook :file[scripts/hooks/harness-tag-stop.ts], which the roster lists with the guards, and every hint are wired with `|| true` too.

A test holds the wiring in place. :file[tests/unit/guards-wiring.spec.ts] finds every `scripts/hooks/*-guard.ts`, checks a `PreToolUse` hook runs it, and, for all but the fail-open list, checks the hook sets `onFailure` and holds no `|| true`:

::excerpt{path="tests/unit/guards-wiring.spec.ts" lines="8,15-24"}
```ts
const FAIL_OPEN = ['deferred-tool-guard']
// …
describe('every scripts/hooks/*-guard.ts is wired', () => {
  it.each(guards)('%s runs from a PreToolUse hook', (guard) => {
    const wired = entries.filter((h) => h.command.includes(`scripts/hooks/${guard}.`))
    expect(wired, `no PreToolUse hook runs ${guard}`).not.toHaveLength(0)
    if (FAIL_OPEN.includes(guard)) return
    for (const h of wired) {
      expect(h.onFailure, h.command).toBe('block')
      expect(h.command, 'a `|| true` exits 0, so onFailure never fires').not.toContain('|| true')
    }
  })
```
::

Each guard has its own unit test in :file[tests/unit/], such as :file[tests/unit/skill-inline-guard.spec.ts]: it calls the pure check with recorded and adversarial inputs, an unreadable transcript included, and runs the real script once through stdin and once through `--dry-run`. Most guards' `Usage:` headers show the `--dry-run` command that prints the decision for a given call, with no deny.

### Why it's built this way

- **The deny message is the rule's home.** A guard's message states the rule and its fix at the call, where a doc went unread ([Claude Code hooks](/t/glassbox/guide/claude-code/hooks#why-its-built-this-way) says why). :file[scripts/hooks/skill-inline-guard.ts].
- **A crash blocks.** Guards were once wired with `|| true`. A crash before the guard's own `try` exited nonzero, `|| true` made that a silent 0, and a guard let through a commit it should have refused. A wrapper script fixed it, until Claude Code's `onFailure` replaced the wrapper; `runGuard`'s deny stays, since it names the guard. The cost: a broken guard blocks every call of its kind until fixed. :file[docs/agents/guards.md].
- **A guard that can't tell may fail open.** The deferred-tool guard can recognize a wrong call only by the shape of its arguments, and a guard that denied what it couldn't identify would block correct calls. So it stays silent on any doubt, its own crash included. The cost: when it breaks, that mistake goes unchecked. :file[scripts/hooks/hook-io.ts].
- **A new mistake is a data row.** Each guard keeps the cases it knows in an exported array at the top of its script, so a newly seen variant of the mistake is one more row and a test case, not new logic. The cost: a new tool also needs adding to the hook's matcher in :file[.claude/settings.json], which a person merges. :file[docs/agents/guards.md].
- **Tests assert a property.** A regex once matched across a line break, so a write verb on one line denied an unrelated command on the next, and every single-line test still passed. Guard tests now cover multi-line and adversarial input, and a guard's real deny is probed live once. The cost: more cases per guard, and a manual probe no test replaces. :file[docs/agents/guards.md].

### What to watch for

- **The deny message is the instruction.** Do what it says. If it is wrong, report it on the guard's issue in the roster rather than rewording the call until it slips past.
- **Fail-closed covers crashes, not blind spots.** A guard that blocks when it breaks can still miss a call it doesn't recognize. The `Bash`, `Edit` and `Write` guards and their shell pre-filters match text, so a path built from a variable, or a payload key the harness renames, passes unchecked. Each guard's header lists its gaps.
- **`onFailure` is version-bound.** A Claude Code older than the minimum in :file[docs/agents/guards.md] ignores it, and a guard that can't start fails open again.
- **A probe can be blocked by the guard it probes.** A `Bash` call that carries a denying `--dry-run --input` in its own text can trip the guard before the dry run starts. Put the input in a file and pass `--input-file`.
- **A unit test can't see a live deny.** It checks the decision, not that the hook fires in a session, which is one reason guards are :term[Human-only] to merge ([Claude Code hooks](/t/glassbox/guide/claude-code/hooks) says why).

## Try it in your project

Add `"onFailure": "block"` to a `PreToolUse` hook you rely on, then make it crash on purpose (an import of a module that doesn't exist will do) and check that the call is blocked. Remove the setting and run it again: the call goes ahead.
