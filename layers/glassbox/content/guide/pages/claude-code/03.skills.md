A procedure written into `CLAUDE.md` costs every session its full length, even the sessions that never do that job. A Skill moves the procedure into its own folder. A session sees one line about it, and reads the rest only when the job comes up.

Know Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Skill is a folder holding a `SKILL.md` file: YAML frontmatter, then the instructions in Markdown. A project's Skills live in `.claude/skills/<name>/` and are committed, so everyone who clones the project has them. The folder can hold other files too, such as a longer reference or a script, which the instructions point to.

```md
---
name: release-notes
description: Write release notes. Use when asked for a changelog.
---

1. List the PRs merged since the last tag.
2. …
```

`name` defaults to the folder's name. `description` is what Claude reads to decide when the Skill applies, and it stays in context all session. The rest of the file loads only when the Skill runs: because Claude judged it relevant, or because you typed `/release-notes`. Once loaded, the instructions stay in the conversation for later turns. Claude Code doesn't read the file again, so write them as standing instructions, not as steps to do once.

Two fields decide who may start a Skill. `disable-model-invocation: true` means only you can: Claude can't start it on its own, and its description leaves the context. The docs suggest it for jobs with side effects, or jobs whose timing you want to control, like a deploy. `user-invocable: false` is the reverse: only Claude can start it, and it is hidden from the `/` menu.

Full reference: [Claude Code docs: Extend Claude with skills](https://code.claude.com/docs/en/skills)

## In Terrarium

Terrarium's :term[Skills]{id="skill"} are committed in :file[.agents/skills/], one folder each. :file[.claude/skills/] holds only a link to each folder, which Claude Code follows to find the Skill. Skills from an outside Skill pack sit beside Terrarium's own, kept exactly as installed.

A Skill is Platform code. It changes through a gated PR like any other code, and the :term[Gate] treats it that way. A change made only of Skill files and :term[Inert] paths skips the build and the browser tests: the build only lists which folders hold a `SKILL.md`, and no browser test reads one. The comment above `isSkillFile` in :file[scripts/gate.ts] says so.

Each Skill makes the invocation choice in its frontmatter. A Skill that sessions must reach on their own keeps a description that names its triggers, as the pack's `tdd` does:

::excerpt{path=".agents/skills/tdd/SKILL.md" lines="1-4"}
```md
---
name: tdd
description: Test-driven development. Use when the user wants to build features or fix bugs test-first, mentions "red-green-refactor", or wants integration tests.
---
```
::

A Skill that a person or a :term[Routine] starts turns model invocation off. Its description is then a one-line summary for people, and it costs a session no context:

::excerpt{path=".agents/skills/prune-trial/SKILL.md" lines="1-5"}
```md
---
name: prune-trial
description: Prune one problem's instructions down to the goal behind them, then let real sessions deliver the verdict before the prune is judged.
disable-model-invocation: true
---
```
::

:file[.agents/skills/writing-for-agents/SKILL-MECHANICS.md] sets the test: a Skill keeps model invocation only when the agent must reach it on its own, or another Skill must; one that only ever starts by hand turns it off. That keeps the jobs that open their own PRs, such as writing the day's Digest, from starting unasked. The Skills a session needs mid-task, such as `close-session`, `code-review` and `dispatch-subagents`, stay model-invoked.

How much each Skill matters, and whether it fires and does its job, is the :term[Skill Inventory]'s job.

### Why it's built this way

- **Committed Skills.** Cloud and scheduled sessions start from a fresh clone, so a Skill in someone's personal folder isn't there. Committing Skills fixes that and puts them in review with the code they change. The cost: every edit, even one word, is a PR that passes the Gate. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Schedule apart from steps.** The Skill holds what a scheduled run does; a :term[Routine] outside the repo holds when it runs. A schedule changes without a PR, and the Skill can still be started by hand. The cost: the repo alone doesn't tell you when a Skill runs. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Pack Skills untouched.** Reinstalling the pack would silently overwrite a local edit, so pack Skills are never edited. The Gate keeps a fingerprint (a hash) of their files and fails on a mismatch. Notes on fit go in the :term[Skill Inventory] entry, not the files. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **A cheaper Gate for Skills.** The Gate reran the full build and browser tests for any script change, even one only a Skill uses ([The Gate](/t/glassbox/guide/terrarium-practice/gate) tells the story). Skill-only scripts now live in their Skill's folder, so such changes skip those but still run unit tests. The cost: a script the site or a browser test uses must not live there. :file[scripts/gate.ts].
- **Who may start it.** A description stays in every session's context so Claude can start the Skill itself; turning that off saves space, but a person must remember it. Claude once could start the log Skill on a wrong guess that the session was over, committing an early log straight to `main`. So only a person could, until logs stopped committing. :file[.agents/skills/writing-for-agents/SKILL-MECHANICS.md].

### What to watch for

- **A Skill reads no file, so its rules don't load.** Terrarium adds them with a hint: [Path-scoped rules](/t/glassbox/guide/claude-code/path-scoped-rules#in-terrarium) explains how.
- **Don't start a Skill twice.** When a slash command starts a Skill, its full text arrives in the prompt. Calling the Skill tool on it again is redundant, and an error for a Skill with model invocation off, so a guard denies the call.
- **No Skill can start a user-invoked one.** With no description in context, nothing but a person can reach it. Reference that two such Skills share goes in a plain file both point to.

## Try it in your project

Find a procedure in your `CLAUDE.md` that only some sessions follow. Move it into `.claude/skills/<name>/SKILL.md`, with a description that names when it applies. If only you ever start it, add `disable-model-invocation: true`.
