A Skill tells a model what to do, and the model decides each next step. When the steps must run in order, every time, for dozens of agents, that decision is the weak point. A workflow script takes it away: the script, not the model, decides what runs next.

Know Claude Code workflows already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Claude Code workflow is a JavaScript file that starts subagents and combines their results. It opens with a `meta` object naming it, then plain JavaScript with top-level `await`. `agent()` starts one subagent with a prompt, `parallel()` runs several at once and waits for all of them, and `pipeline()` runs one per item in a list. A `schema` on `agent()` makes that subagent return JSON of a given shape instead of prose. `phase()` groups the agents that follow in the progress view, and `log()` shows a message above it. Input arrives in a global named `args`.

```js
export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const audits = await pipeline(args.files, (file) =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)
```

A runtime runs the script in the background. The script can't read files, run commands or ask the user anything: its agents do the work, and its variables hold the results, so the session's context gets only the final answer. A workflow saved in a project's `.claude/workflows/` runs by name in later sessions, and a permission rule such as `Workflow(audit-routes)` approves that one workflow by name.

Full reference: [Claude Code docs: Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows)

## In Terrarium

Terrarium's :term[Workflow] scripts sit in :file[.claude/workflows/], each run by the :term[Skill] that names it. The `clear-backlog` Skill, which works through the open-issue backlog in one run, has two: :file[.claude/workflows/clear-backlog-explore.js] triages each issue with its own agent, and :file[.claude/workflows/clear-backlog-build.js] builds and reviews each planned branch. The Skill itself keeps what a script can't do: it asks the owner its questions, waits on CI and merges.

The build script gives each branch's build agent its own worktree, and turns an agent that returned nothing into a failure the Skill can act on:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="134-138"}
```js
async function buildBranch(b) {
  // Isolated even on a re-run: if b.worktree was auto-removed, the agent starts fresh in its own.
  const r = await agent(buildPrompt(b), { label: `build ${b.name}`, phase: 'Build', schema: WORK, isolation: 'worktree', ...modelOf(b) })
  return r || { status: 'failed', reason: 'build agent returned nothing; its worktree may hold commits, and `pnpm check:worktrees` lists it', commits: [], decisions: [], worktree: b.worktree }
}
```
::

The review rounds that follow are in [The engineering loop](/t/glassbox/guide/skill-pack/engineering-loop).

A script is also where a rule can't be talked around. When a triage agent says to build an issue the owner reserved, one by a :term[Public] author, or one labelled for a human, the explore script turns its answer back into a question for the owner:

::excerpt{path=".claude/workflows/clear-backlog-explore.js" lines="108-111"}
```js
  if (r && r.outcome === 'build' && (issue.reserved || r.publicAuthor || r.readyForHuman)) {
    r.outcome = 'grill'
    r.question ||= { choice: 'Build this as briefed?', options: ['a) yes, as briefed', 'b) no'], pick: 'a', why: 'Reserved, Public-authored or ready-for-human: the owner decides.' }
  }
```
::

:file[.claude/settings.json] allows both scripts by name, and :file[tests/unit/workflow-scripts.spec.ts] checks that each one compiles and that its `meta.name` matches its file name.

### Why it's built this way

Why a script is its Skill's code, and why it lives in `.claude/workflows/` rather than in its Skill's folder: ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Nothing lints it.** A workflow script returns at the top level, so it isn't an ES module and ESLint skips it. The unit test above stands in, but only checks that it compiles and is named right.
- **The Gate counts it as Skill code.** A change of only Skill files and Inert paths skips the build and the browser tests; see [The Gate](/t/glassbox/guide/terrarium-practice/gate).
- **Plan for `null`.** A stopped or failed agent returns `null` inside `parallel()` and `pipeline()`, and the run carries on. Turn each `null` into a result that says what to check, as the build script does, rather than dropping it.
- **It can't ask.** A run takes no input once it starts. A step that needs a person, CI or a merge goes in the Skill around it, between two runs.

## Try it in your project

Pick a job you hand Claude often that fans out over many files or items. Ask Claude to use a workflow for it, then save the run to `.claude/workflows/` from `/workflows`. Add a test that compiles every script there, since your linter won't read them.
