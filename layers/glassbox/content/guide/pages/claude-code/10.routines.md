A Skill says what a job does. Something else has to say when it runs. Claude Code offers several timers, which differ in where they run and how long they last, from a cloud task that needs no open session to a loop that ends with the session it runs in. Terrarium keeps each job's steps in the repo and its timer outside it, and reads what ran back from the session logs.

Know scheduled tasks and `/loop` already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code has three ways to run a prompt later, compared side by side in the docs' [scheduling options table](https://code.claude.com/docs/en/scheduled-tasks#compare-scheduling-options):

- A **cloud scheduled task**, called a routine until the docs renamed it, runs on Anthropic's cloud and needs neither your machine nor an open session.
- A **Desktop scheduled task** runs on your own machine, with its local files.
- **`/loop`** runs inside one open session and lasts only as long as it does.

A cloud scheduled task is a saved prompt with one or more repositories and connectors, the outside services such as Slack or an issue tracker it may use. A trigger starts it: a schedule no more often than hourly, an HTTP call to its own endpoint, or a GitHub event such as a new pull request. You create one at claude.ai/code/routines, or with `/schedule` in the CLI. Each run is a new cloud session on a fresh clone of each repository, so it has the Skills committed there and nothing from your machine. The run starts in auto mode, where a classifier model allows or blocks each action instead of asking you, but some actions, such as one matching an ask rule, still stop and wait for an answer. It pushes to a branch prefixed `claude/` unless the prompt names another, and everything it does through GitHub or a connector appears as you.

[`/loop`](https://code.claude.com/docs/en/scheduled-tasks) runs a prompt again and again in the current session:

```text
/loop 5m check whether the deploy finished
/loop check whether CI passed and address any review comments
```

With an interval, the prompt runs on a fixed schedule. Without one, Claude picks a wait of one minute to one hour after each run, and ends the loop with the `ScheduleWakeup` tool once the work is done. Underneath, `CronCreate`, `CronList` and `CronDelete` manage these session tasks, and a plain request such as "remind me at 3pm to push the release branch" makes a one-off. A task fires only between turns, only while Claude Code runs, and a recurring one expires after seven days. A fire runs only Skills Claude may start on its own: a Skill with `disable-model-invocation: true` reaches Claude as plain text instead.

Full reference: [Claude Code docs: Automate work with scheduled tasks](https://code.claude.com/docs/en/routines)

## In Terrarium

Terrarium calls a cloud scheduled task that runs one of its :term[Skills]{id="skill"} a :term[Routine], the docs' former name. The Routine lives in a claude.ai account; its prompt is the Skill's slash command, and the Skill in :file[.agents/skills/] holds the steps. A scheduled Skill may say that it is scheduled, and never how often. `dependabot-sweep` opens like this:

::excerpt{path=".agents/skills/dependabot-sweep/SKILL.md" lines="7-9"}
```md
A Routine runs this Skill; its schedule lives there, not here (ADR-0005).
Its approval covers only the steps below (ADR-0003): it opens no branch and
edits no file.
```
::

:file[scripts/gate/validate-skill-cadence.ts], part of `pnpm validate:content`, enforces that for one Collection: it fails any :term[Skill Inventory] sentence that pairs "Routine" with a cadence word such as "weekly" or a phrase such as "every 2 hours".

**What ran is read back, not declared.** No file lists the Routines. When a session ends, its :term[session log] records the `entrypoint` Claude Code reported, `remote_trigger` for a Routine's run, and a `trigger` derived from the run's first turn in :file[scripts/session/transcript-trace.ts]:

::excerpt{path="scripts/session/transcript-trace.ts" lines="447-456"}
```ts
export function deriveTrigger(
  records: Record<string, unknown>[],
  entrypoint: string | undefined,
): string | undefined {
  if (entrypoint !== 'remote_trigger') return undefined
  const first = records.find((r) => r.type === 'user')
  if (!first) return undefined
  const msg = first.message as { content?: unknown } | undefined
  const [name] = commandSkillNames(msg?.content) // reuse the one slash-command extractor
  if (name) return name
```
::

The `audit-skills` Skill groups recent logs by `trigger`. It appends each run's time, tokens and cost to that Routine's file in the Journal's `routines` Collection, which the [Routine costs](/t/journal/current/routines) page charts, and grades a Skill's importance in the Skill Inventory by the same fact:

::excerpt{path=".agents/skills/audit-skills/SKILL.md" lines="125-127"}
```md
- **routine**: it *is* a scheduled Routine's job, driving whole unattended
  sessions (e.g. `digest`, `audit-docs`). Assign it on the observed fact that
  scheduled sessions run it; a Skill invoked by hand is not `routine`.
```
::

**Scheduled Skills turn model invocation off.** A Routine's prompt arrives as the run's first turn, the way a person's slash command does, and the Skill runs. A `/loop` fire of it arrives as plain text, and the Skill tool refuses it; each Skill that `/loop` may drive says what to do then, as `guest-intake` does:

::excerpt{path=".agents/skills/guest-intake/SKILL.md" lines="18-20"}
```md
**`disable-model-invocation` above is deliberate** (ADR-0023: neither Skill
starts itself). A Routine or `/loop` session cannot invoke this Skill with the
Skill tool; that refusal is expected. Follow these steps directly (issue #568).
```
::

**Inside a session, Terrarium waits without `/loop`.** A session that must check a PR's CI hours later schedules its own check-in with the cloud host's `send_later` tool, which delivers a message back into the same session (:file[docs/agents/pr-workflow.md]). `ScheduleWakeup` belongs to `/loop` alone. :file[scripts/hooks/loop-only-tool-guard.ts], a `PreToolUse` hook, denies it unless the session's transcript shows a `/loop`, and its message names what to use instead; it allows a call with `stop: true`, which only cancels a wakeup.

### Why it's built this way

- **The timer outside the Skill.** [Claude Code Skills](/t/glassbox/guide/claude-code/skills#why-its-built-this-way) gives the reason a schedule lives in the Routine and never in the Skill. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Observed, not declared.** The timers sit in an account the repo can't read, and a run's transcript names no Routine. So the log takes the Skill's name from the run's first turn, and the audit counts what actually fired. The cost: a Routine that never fires leaves no trace, and one whose prompt isn't a slash command is named by its first line. :file[scripts/session/transcript-trace.ts].
- **A check where the mistake happened.** A schedule changes with no commit, so a sentence saying how often a Routine runs goes stale without anyone noticing. A Skill Inventory entry is the one place that had happened, so the check scans only those entries. The cost: the same sentence in a Skill, doc or page passes `pnpm validate:content` and goes stale at the next schedule change. :file[scripts/gate/validate-skill-cadence.ts].
- **Each Skill states its own limits.** Nobody watches a scheduled run, so each scheduled Skill writes down what it may change, as `dependabot-sweep` does; [Human-in-the-loop agents](/t/glassbox/guide/terrarium-practice/human-in-the-loop#why-its-built-this-way) says why no central table holds it. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **A guard instead of a note.** Sessions outside `/loop` kept calling `ScheduleWakeup`, and a fired wakeup arrives as an unwanted turn that can re-run the session's whole prompt. Two fixes that wrote the rule into a doc failed ([Claude Code hooks](/t/glassbox/guide/claude-code/hooks#why-its-built-this-way) says why), so a hook now denies the call. The cost: when it can't read the transcript it denies too. :file[scripts/hooks/loop-only-tool-guard.ts].

### What to watch for

- **Session timers can vanish on resume.** :file[docs/agents/environment-caveats.md] records a `/loop` or `CronCreate` job gone after a session resumed, with no error, and the docs say a self-paced `/loop` is never restored. Check that it is still there before you rely on it.
- **A scheduled wake-up may not show as a turn.** A scheduled task that wakes an existing session can fire without a visible turn; the same caveats doc says to check the task's last run before you decide it didn't fire.
- **An unattended run can wait forever.** Auto mode still stops for some actions, and in an unattended run a subagent's call that needs approval blocks with no signal to the session that dispatched it (:file[docs/agents/environment-caveats.md]). Treat a long silence as possibly stuck.

## Try it in your project

Pick a chore you repeat, such as a dependency check. Write it as a Skill with `disable-model-invocation: true` and a first line saying a schedule runs it. Then run `/schedule` and give the new task the Skill's slash command as its prompt. Keep the timer there alone: search your repo for the Skill's name next to "daily" or "weekly", and expect no hit.
