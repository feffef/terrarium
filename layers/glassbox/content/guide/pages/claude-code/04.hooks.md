An instruction asks the model to do something, and the model may forget. A hook is a command that Claude Code itself runs at a fixed point in a session, so it happens every time, whatever the model decides.

Know hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A hook is declared in a settings file under `hooks`, in three levels: the event it answers, a matcher group that narrows when it fires, and the handlers to run. Events include `SessionStart`, `UserPromptSubmit`, `PreToolUse` and `PostToolUse` around each tool call, `Stop` when Claude finishes responding, and `SessionEnd`. For the tool events the matcher is the tool's name, such as `Bash` or `Edit|Write`; for `SessionStart` it is how the session started, such as `startup` or `resume`.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npx prettier --write ." }]
      }
    ]
  }
}
```

A command hook gets the event as JSON on stdin and answers with its exit code and what it prints. Exit 0 with nothing printed changes nothing. A `PreToolUse` hook can print a decision that denies the call, and the reason it gives goes back to Claude. A `PostToolUse` hook can print `additionalContext`, which Claude reads beside the tool's result. Every hook that matches runs, in parallel, and the strictest decision wins.

`~/.claude/settings.json` holds your own hooks for every project. A project's `.claude/settings.json` is committed, so everyone who works in it gets its hooks; `.claude/settings.local.json` is the uncommitted variant. The [hooks guide](https://code.claude.com/docs/en/hooks-guide) walks through first examples.

Full reference: [Claude Code docs: Hooks reference](https://code.claude.com/docs/en/hooks)

## In Terrarium

Every hook Terrarium uses is wired in one committed file, :file[.claude/settings.json], so each session, a cloud one included, has the same hooks as every other. Each command starts with `cd "${CLAUDE_PROJECT_DIR:-.}"`, so it runs from the project's root whatever folder the session is in. The hooks do three jobs.

**Setting up a session.** On `SessionStart`, at startup and on resume, a hook runs `pnpm install`, then :file[scripts/unshallow-on-start.ts], which fetches full git history when the clone arrived shallow. That script catches its own failures, so a fetch that fails never blocks the start.

**Landing the session log.** A session writes the judgement half of its log, then hooks land it. The `Stop` hook checks for that pending log and lands it with :file[scripts/log-session.ts]:

::excerpt{path=".claude/settings.json" lines="173-183"}
```json
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && [ -f .session-logs/pending.scratch.json ] && pnpm exec tsx scripts/log-session.ts --land || true"
          }
        ]
      }
    ],
```
::

So the log lands at the end of the turn that wrote it, not only at teardown, which can prompt no one and may have no network. `SessionEnd`, at teardown, and `SessionStart`, on resume, call the same `--land` as fallbacks. The lander never exits with an error, since a fault there must not wedge a session's end.

**Checking tool calls.** `PreToolUse` hooks are guards: each can deny one kind of mistaken call and say what to do instead. `PostToolUse`, `PostToolUseFailure` and `UserPromptSubmit` hooks are hints: each can add guidance beside a call's result or a prompt, and never blocks. :file[docs/agents/guards.md] lists both kinds.

Each tool hook's matcher names only the tools it checks, never `*`. Starting a TypeScript script costs a moment, and a hook on every call would pay it on every read and edit. So the hooks on `Bash`, `Edit` and `Write` start with a short shell filter, such as :file[scripts/workflow-edit-guard.sh], which exits at once unless the call's text could match.

### Why it's built this way

Session logs straight to `main`: ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).

Who merges the hook wiring: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **A crashed hook doesn't stop the call.** An exit code other than 0 or 2, with no valid JSON printed, is a non-blocking error, and the call goes ahead, unless the hook sets `onFailure: "block"`. That suits a hint and is a hole in a guard: [Guards that fail closed](/t/glassbox/guide/claude-code/guards) shows how Terrarium closes it.
- **Hooks see a subagent's calls too.** A subagent's tool calls fire the same hooks as the main session's. Its payload carries `agent_id` and `agent_type`, which a main session's lacks, and that pair is the only signal; `agent_type` alone also appears when a session runs under `--agent`.
- **The wiring is :term[Human-only].** An agent may edit :file[.claude/settings.json], but a person merges the change. And a session nobody is watching shouldn't try: the edit raises a permission prompt that no one is there to grant.

## Try it in your project

Add a `PostToolUse` hook with the matcher `Edit|Write` to your project's `.claude/settings.json` that runs your formatter, then ask Claude to edit a file and check that it came out formatted.
