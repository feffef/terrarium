A procedure written into `CLAUDE.md` costs every session its full length, even the sessions that never do that job. A skill moves the procedure into its own folder. A session sees one line about it, and reads the rest only when the job comes up.

Know skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

A skill is a folder holding a `SKILL.md` file: YAML frontmatter, then the instructions in Markdown. A project's skills live in `.claude/skills/<name>/` and are committed, so everyone who clones the project has them. The folder can hold other files too, such as a longer reference or a script, which the instructions point to.

```md
---
name: release-notes
description: Write release notes. Use when asked for a changelog.
---

1. List the PRs merged since the last tag.
2. …
```

`name` defaults to the folder's name. `description` is what Claude reads to decide when the skill applies, and it stays in context all session. The rest of the file loads only when the skill runs: because Claude judged it relevant, or because you typed `/release-notes`. Once loaded, the instructions stay in the conversation for later turns. Claude Code doesn't read the file again, so write them as standing instructions, not as steps to do once.

Two fields decide who may start a skill. `disable-model-invocation: true` means only you can: Claude can't start it on its own, and its description leaves the context. The docs suggest it for jobs with side effects, or jobs whose timing you want to control, like a deploy. `user-invocable: false` is the reverse: only Claude can start it, and it is hidden from the `/` menu.

Full reference: [Claude Code docs: Extend Claude with skills](https://code.claude.com/docs/en/skills)

## In Terrarium

Terrarium's :term[skills]{id="skill"} are committed in :file[.agents/skills/], one folder each. :file[.claude/skills/] holds only a link to each folder, which Claude Code follows to find the skill. A skill is Platform code: it changes through a gated PR like any other code.

A skill reads as a goal and numbered steps. `close-session`, which a session runs at session closure (the point where it judges its work complete and in an honest state), opens like this; a :term[friction] in it is one problem the session records in its log:

::excerpt{path=".agents/skills/close-session/SKILL.md" lines="6-13"}
```md
You've reached **Session closure**. Goal: the Journal holds an honest log of
this session, with its final status.

1. **Check this session against CLAUDE.md and the always-loaded rules** (already
   in your context; do not reopen the files). For every rule or step in them that
   this session broke or skipped, log a Friction that names the rule, even if you
   fixed it later. Say what impact breaking it had or could have had, and what
   would have made you read it at the time.
```
::

Each skill makes the invocation choice with `disable-model-invocation` in its frontmatter. A skill that sessions must reach on their own, such as `close-session`, `code-review` or `dispatch-subagents`, keeps a description that spells out its triggers and sets no `disable-model-invocation`. A skill that a person or a :term[routine] starts turns model invocation off: Claude no longer sees its description, which becomes a one-line summary for people only. Glass Box's own Lesson-writing skill is one:

::excerpt{path=".agents/skills/glassbox-lesson/SKILL.md" lines="1-5"}
```md
---
name: glassbox-lesson
description: Write one Glass Box Lesson, a page about one concept with Terrarium as the worked example.
disable-model-invocation: true
---
```
::

The rule for choosing comes from :file[.agents/skills/writing-for-agents/SKILL-MECHANICS.md], part of the installed `writing-for-agents` skill that ADR-0005 (:file[docs/adr/0005-skill-model.md]) names as how to write one: a skill keeps model invocation only when the agent must reach it on its own, or another skill must; one that only ever starts by hand turns it off. [Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks) shows what a scheduled skill says about its timer.

Skills installed from another repository sit beside Terrarium's own, kept exactly as installed ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)). The Journal keeps one entry per skill in use, its :term[skill inventory]. In each entry, `importance` grades how much the project needs the skill and `role` says in plain words what it is for. A :term[routine] running the `audit-skills` skill writes both, and the [skill inventory](/t/journal/current/skills) page shows them.

### Why it's built this way

- **Committed skills.** Cloud and scheduled sessions start from a fresh clone, so a skill in someone's personal folder isn't there. Committing skills fixes that and puts them in review with the code they change. The cost: every edit, even one word, is a PR that passes the gate. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Schedule apart from steps.** The skill holds what a scheduled run does; a :term[routine] outside the repo holds when it runs. A schedule changes without a PR, and the skill can still be started by hand. The cost: the repo alone doesn't tell you when a skill runs. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Turning model invocation off saves context.** A description stays in every session's context so Claude can start the skill itself. With it off, Claude can't pick it; only its name starts it, typed by a person or sent as a :term[routine]'s prompt. The skill that writes the day's :term[digest] turns it off and is scheduled (:file[.agents/skills/digest/SKILL.md]). The cost: a person must remember the skill exists. :file[.agents/skills/writing-for-agents/SKILL-MECHANICS.md].

### What to watch for

- **A skill reads no file, so its rules don't load.** Terrarium adds them with a hint: [Path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules#in-terrarium) explains how.
- **No skill can start a user-invoked one.** With no description in context, nothing but a person can reach it. Material that two such skills share goes in an ordinary file that both name in their text.
- **The description is the whole trigger.** A model-invoked skill fires on its description alone, and a weak one shows up only as a skill that should have fired and didn't. The audit in the [Self-improvement loop](/t/glassbox/guide/terrarium-practice/self-improvement-loop) looks for that.
- **A slash command already pastes the skill's text.** A guard, a hook that refuses a call, refuses a `Skill` call for a skill whose text the slash command already pasted into the session ([Claude Code hooks](/t/glassbox/guide/hooks/hooks)); follow the text you already have.

## Try it in your project

Find a procedure in your `CLAUDE.md` that only some sessions follow and move it into `.claude/skills/<name>/SKILL.md`. Write the description as the triggers, not a summary. Then ask Claude for that job without naming the skill and check that it fired; if it didn't, add the words you used to the description. If only you will ever start it, add `disable-model-invocation: true` instead and start it with `/<name>`.
