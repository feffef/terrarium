The other checks in this subject are mechanical: each passes or fails. A usability test looks from a different angle. It asks whether a visitor can get something done, which no pass or fail check can say: a site can pass every one and still leave a visitor unsure what it is for or where to go next. A usability test finds that by watching people try real tasks on it. Terrarium runs a version with agents as the visitors, as a routine rather than a gate step: a :term[skill] sends several agents through one part of the site, then checks what they report before any of it becomes work. Agents stand in for people only in part, and the page says where that stops.

Know usability testing already? Skip to [In Terrarium](#in-terrarium).

## The concept

Usability is how easily people can complete tasks with a design. Its most established method is usability testing: recruit representative users, ask them to do realistic tasks with the design, and observe what they do.

A qualitative test, one that aims to find and fix problems, often needs only about 5 users to surface many of the more important issues. The usual practice is iterative: test with a few users, fix what they hit, then test the revised design again, since the next round often finds new problems. Most tests are remote: moderated, with a facilitator watching over a video call, or unmoderated, with participants working alone while a testing platform records their screen and voice.

Anyone can run a test after learning the basics of facilitation and task writing, but a poorly run one, with leading questions or a facilitator who helps participants, gives misleading results. Testing isn't the only method either; expert reviews and analytics are other common ones.

AI brings new methods, and the Nielsen Norman Group (NN/g) is wary of them. Replacing participants with synthetic users or digital twins is still experimental, and these "should not be treated as reliable substitutes for real users". Usability is also not the same as an AI agent's ability to use a site: an agent can find a phone number by reading a page's HTML even when a person can barely see it in a low-contrast font.

Full reference: [Nielsen Norman Group: Usability 101: Introduction to Usability](https://www.nngroup.com/articles/usability-101-introduction-to-usability/)

## In Terrarium

The skill :file[.agents/skills/visitor-loop/SKILL.md] runs a visit. It builds the site and serves its production preview with `scripts/ui/preview.ts start` ([Headless browser checks](/t/glassbox/guide/verification/headless-browser-checks#why-its-built-this-way) says why a preview serves the production build). Then it sends several read-only visitor [subagents](/t/glassbox/guide/agents/subagents) through one part of the site at once, each looking through its own lens: a role with a list of what to look for. Every visitor gets the same brief, :file[.agents/skills/visitor-loop/visitor-brief.md], keeping only one of its two access blocks:

::excerpt{path=".agents/skills/visitor-loop/visitor-brief.md" lines="9-19"}
```md
**Blind access.** You know nothing about this site; someone just sent you the
link. Experience it only through the browser; the one file you may read is
`scripts/lib/chromium.ts`, which launches Chromium.

**Informed access.** The site is built from the repository you are in. What
changed in this area in the last week, the ideas already logged about it and
its open issues are in {CONTEXT_FILE}; read it first, and propose nothing it
already holds. You may read the repository (source, docs, glossaries, git
history) to check a finding or idea before you report it: is it really
broken, already built, or decided against? Read git only with `log`, `show`
and `diff`.
```
::

One visitor is blind: it gets the brief and nothing else, no context file, no hints and no past findings. The others are informed. Their context file lists the part's pages, its merged pull requests, its open issues and the ideas already logged about it, which :file[.agents/skills/visitor-loop/scripts/ideas.ts] reads from past :term[session logs]{id="session-log"}. Each visitor reports the path it took, its findings with their evidence, its ideas, and anything that took it several attempts to work out.

The run merges what the visitors reported into one tally and marks each item a bug, an idea, a learning, or dropped with a reason. A bug gets checked further. In the excerpt, *dropped (#N)* means an open issue already states it, and *amend #N* means it fits one and adds new evidence:

::excerpt{path=".agents/skills/visitor-loop/SKILL.md" lines="99-106"}
```md
- **bug**: the site breaks its own intent: a broken link or control, an error,
  a layout fault, a mobile or accessibility failure, a false statement. Check
  it yourself against the source and the rendered page before you mark it; a
  visitor can misread. Mark one you can't reproduce *dropped (not reproduced)*.
  Then match it against every open issue
  (`pnpm exec tsx scripts/github/list-open-issues.ts 5000`): mark it *dropped (#N)*
  if an issue already states it, or *amend #N* if it fits one and adds a new
  page, symptom or evidence.
```
::

The run files the confirmed bugs as issues labelled `needs-triage`, the label that marks an issue for a maintainer to evaluate, or as a comment on the open issue each one fits. Ideas and learnings go into its own session log, where the `harvest` skill, which turns logged ideas and learnings into issues that propose work, files them as :term[seedlings]{id="seedling"} ([Ideas and lessons learned](/t/glassbox/guide/self-improvement/ideas-and-lessons-learned#in-terrarium)). An idea that contradicts one of the owner's standing rulings in :file[.agents/skills/visitor-loop/decisions.md] is dropped, and `harvest` files no seedling for it. The run changes no code and opens no branch or pull request. Last, it asks each visitor about the workflow around its visit, not the site, and logs each problem with the skill as a :term[friction] whose fix names the file to change.

### Why it's built this way

- **One visitor knows nothing, the others can check.** Visitors who all knew the repo would miss how a newcomer meets the site, through a bare link; only the repo says whether a fault is already built or decided against. So one visitor gets just the link and the browser, the others recent history and the repo. The cost: the blind visitor can't check its reports. :file[.agents/skills/visitor-loop/visitor-brief.md]
- **The run reproduces each bug itself.** A visitor can misread a page ([Subagents](/t/glassbox/guide/agents/subagents#what-to-watch-for)), and filing its claims unchecked would put misreads in the tracker. So the run checks each bug against the source, the rendered page and the open issues first. The cost: a bug the run can't reproduce is dropped, not filed. :file[.agents/skills/visitor-loop/SKILL.md]
- **Visitors propose, people decide.** New work starts only once a :term[trusted user]{id="trusted"} approves it, and visitors filing ideas as work would skip that person. So the run files only bugs and logs other ideas for `harvest`. The cost: a suggested wording fix is only an idea, and waits for a person like any other. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]), :file[.agents/skills/visitor-loop/SKILL.md]
- **The owner's rulings are written down.** Some suggestions are ones the owner has already corrected or rejected. Rather than judging each such idea again by hand, the run drops any idea that contradicts a line in the rulings file. The cost: an idea in the same family as a ruling is dropped too, though no line names it. :file[.agents/skills/visitor-loop/decisions.md]

### What to watch for

- **Agents are not your users.** NN/g warns that synthetic users are not reliable substitutes for real ones, and that an agent can read what a person can't see. Agent visitors find broken links, errors and unclear wording; what real newcomers struggle with takes real people. The brief has visitors read words as text and screenshot only what must be seen, such as contrast, so a visit that skips the screenshots can miss what a person would.
- **A brief can lead the visitor.** A hint or a past finding in a brief steers what a visitor reports, as a leading question steers a participant. The blind visitor's brief holds neither; keep it that way when you change it.
- **Not every change needs one.** As general advice, not a Terrarium rule: a usability test observes people doing tasks with a design, so a change with nothing people see or use, such as a backend-only one, gains little from it, and with no representative users to recruit, it can't be run as described.

## Try it in your project

Build your site and serve the production build locally. Start an agent session in an empty folder, with a browser tool but no copy of your code, and give it only the URL and one realistic task, such as finding how to contact you, worded without hints about where to look. Ask it for the pages it visited, where it got lost, and each problem with its URL and evidence. Reproduce every problem yourself in a browser before you file it, and drop the ones you can't. Then give one person the same task, watch without helping, and compare: what only the person hit is what an agent visit can't find.
