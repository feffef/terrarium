A page can build, pass every test and send the right HTML, yet still show a blank gap, a wrong colour or a layout that breaks on a phone. Only a browser that loads the page and runs its scripts shows what a visitor sees. A headless browser does that with no window, driven by a script that screenshots the page or reads a value out of it.

Know Playwright's library API already? Skip to [In Terrarium](#in-terrarium).

## The concept

A headless browser is an ordinary browser run without a visible window; [Chromium's headless mode](https://developer.chrome.com/docs/chromium/headless) is one. A script controls it instead of a person.

Playwright gives one API for Chromium, Firefox and WebKit, in two forms. Playwright Test adds a test runner, with a fresh page for each test and assertions that wait and retry. Playwright Library is the API alone: a plain Node script picks a browser, launches it, opens a page and closes the browser itself.

A Library script follows a few calls:

- `chromium.launch()` starts the browser, headless unless you pass `headless: false`. Its `executablePath` option runs a browser binary you name instead of the one Playwright bundles; Playwright only promises to work with its bundled build.
- `browser.newPage({ viewport, colorScheme })` opens a page with that viewport size, and emulates the visitor's light or dark preference.
- `page.goto(url)` loads the page.
- `page.screenshot({ path, fullPage })` saves a PNG, of the whole scrollable page with `fullPage: true`.
- `page.evaluate(expression)` runs code inside the page and returns its result to the script. The code can be a function or a string, such as `'1 + 2'`.

Full reference: [Playwright docs: Library](https://playwright.dev/docs/library)

## In Terrarium

Terrarium's e2e tests drive a browser through Nuxt's test utilities, inside the test suite ([Testing](/t/glassbox/guide/verification/testing)). This page covers the scripts in :file[scripts/ui/] an agent runs by hand, through the `playwright-core` package.

Every one of them launches the same browser. :file[scripts/lib/chromium.ts] looks for a pre-installed Chromium in the folder `PLAYWRIGHT_BROWSERS_PATH` names, `/opt/pw-browsers` when it is unset, and throws when none is there. That is not the build Playwright bundles; [why it's built this way](#why-its-built-this-way) gives the reason and the cost. `launchChromium` starts it with Playwright, adding `--no-sandbox` and `--disable-gpu`, which its comment calls the flags every launch needs in this sandbox:

::excerpt{path="scripts/lib/chromium.ts" lines="51-53,97-99"}
```ts
export function findPreinstalledChromium(): string | undefined {
  return findChromium(process.env.PLAYWRIGHT_BROWSERS_PATH ?? '/opt/pw-browsers')
}
// …
export function launchChromium(extraArgs: string[] = []) {
  return chromium.launch({ executablePath: resolveChromiumPath(), args: ['--no-sandbox', '--disable-gpu', ...extraArgs] })
}
```
::

:file[scripts/ui/screenshot.ts] screenshots a URL that is already serving. It opens a page at the requested size, optionally in a light or dark scheme, loads the URL, waits a fixed two seconds, scrolls to the URL's `#anchor` if it has one, and saves the PNG. `preview.ts` calls the same code and adds a touch-phone mode and full-page capture. Its `--wait-for <selector>` replaces the fixed wait with two waits, in order: until the page has had no network connections for half a second, then until an element matching the selector is in the DOM, the tree of elements the browser built for the page, even if that element is hidden.

:file[scripts/ui/eval-in-page.ts] reads one value, such as a computed style or a bounding box, from an already-serving page. It passes the expression, a string, straight to `page.evaluate`, and prints the result, as JSON when it is an object:

::excerpt{path="scripts/ui/eval-in-page.ts" lines="33-43"}
```ts
async function evaluate(url: string, expression: string, waitMs: number, viewport?: { width: number; height: number }): Promise<unknown> {
  const browser = await launchChromium()
  try {
    const page = await browser.newPage({ viewport })
    await page.goto(url)
    await page.waitForTimeout(waitMs)
    return await page.evaluate(expression)
  } finally {
    await browser.close()
  }
}
```
::

:file[scripts/ui/preview.ts] runs a local server for those scripts. Its verbs:

- `shot <route> <out.png>` starts a server, takes one screenshot of the route and stops the server. `--wait-for <selector>` waits for an element rather than a fixed time.
- `review <route> <out-dir>` starts one server and takes full-page shots at a desktop and a phone size, each in light and dark.
- `start` starts a server, prints its `PID=` and `URL=`, and leaves it running.
- `stop <pid>` stops that server, and exits 0 even when it is already gone.

By default the server is the production build in `.output`, and the script refuses to start without one. `--dev` runs `nuxt dev` instead. `startPreview` asks the operating system for a free port, then starts the server on it as a detached process, in a process group of its own (a set of processes that one signal reaches together), with its output in a log file:

::excerpt{path="scripts/ui/preview.ts" lines="241-247,258-259"}
```ts
export async function startPreview(opts: { dev?: boolean } = {}): Promise<PreviewServer> {
  const dev = opts.dev ?? false
  ensureBuilt(dev)
  const port = await pickFreePort()
  const logPath = logPathFor(port)
  const child = spawnServer(port, dev, logPath)
  const pid = child.pid
  // …
  return { port, url: `http://${HOST}:${port}`, pid, logPath }
}
```
::

The lines left out poll the server until it answers HTTP. If it exits or never answers, the script prints the likely causes with the end of the server's log, stops it and throws. Stopping sends the process group `SIGTERM`, the signal that asks a process to exit. If the server outlasts a grace period, it then sends `SIGKILL`, which ends it at once. A process that is already gone counts as stopped.

Cloud sessions send their web requests through a proxy, and the proxy refuses the deployed site. Agents review a local production build instead, with `pnpm build` and then `preview.ts`. Glass Box's own lessons are checked this way: a page whose layout or diagram changed is shot with `preview.ts review` (:file[.agents/skills/glassbox-lesson/writing-pages.md]).

### Why it's built this way

- **The rendered page, not its HTML.** The server's HTML carries a serialized `useAsyncData` payload, the data the server fetched for the page, so a text search can find a string the page never shows. Terrarium checks what the browser rendered instead. :file[docs/agents/verifying-ui-changes.md].
- **Read the value, not the picture.** A downscaled or compressed screenshot can hide a style that applied, and a grey can pass for a tint. `eval-in-page.ts` reads the computed value itself. :file[docs/agents/verifying-ui-changes.md].
- **A port of its own, stopped by PID.** Several agents share one container's ports, and stopping servers with `pkill -f` matched the shell's own command, dropping the steps after it, and could kill a sibling's server. Each server gets a free port and is stopped only by its own PID. The cost: a `start`ed server runs until someone passes its PID to `stop`. :file[scripts/ui/preview.ts].
- **The production build by default.** The dev server's DevTools badge, an overlay Nuxt draws on the page, can cover real content and look like a bug, and a cold dev server can catch a half-built page. Previews serve the built app unless asked for `--dev`. The cost: a `pnpm build` first, and Vue's dev warnings don't show. :file[docs/agents/verifying-ui-changes.md].
- **One browser, found in one place.** Without a shared lookup, each ad-hoc probe re-derived by hand where the pre-installed Chromium lives. Every script launches through one shared helper and downloads no browser. The cost: Playwright only promises to work with the Chromium it bundles, not this one. :file[scripts/lib/chromium.ts].

### What to watch for

- **Wait before you capture.** Content that loads after [hydration](/t/glassbox/guide/nuxt-vue/hydration) may not be in the page yet when the shutter fires. When you know the element, pass `--wait-for <selector>` to `preview.ts shot` rather than trusting the fixed wait.
- **Visible isn't on screen.** Playwright's `isVisible()` is true for an element scrolled out of view. To prove it is in the viewport, compare its `getBoundingClientRect()` with the viewport.
- **Pass `page.evaluate` a string from a `tsx` script.** `tsx` compiles with esbuild's `keepNames`, which adds a `__name` helper that exists only in Node, so a function you pass in throws `__name is not defined` in the page.
- **Dev warnings need `--dev`.** A production build compiles out hydration-mismatch and other Vue dev warnings, so a clean production run can't show that such a warning is fixed.
- **Stop what you started.** A `preview.ts start` server outlives the command. Stop it with `preview.ts stop <pid>`.

## Try it in your project

In a Node project, run `npm i -D playwright` and `npx playwright install chromium` (Terrarium's scripts use the smaller `playwright-core` package instead, with a Chromium already on the machine). Start your dev server, then save this as `check.mjs`:

```js
import { chromium } from 'playwright'

const browser = await chromium.launch()
try {
  const page = await browser.newPage({ viewport: { width: 390, height: 844 }, colorScheme: 'dark' })
  await page.goto(process.argv[2])
  await page.waitForTimeout(1000)
  console.log(await page.evaluate('getComputedStyle(document.body).backgroundColor'))
  await page.screenshot({ path: 'shot.png', fullPage: true })
} finally {
  await browser.close()
}
```

Run `node check.mjs http://localhost:3000/`. It prints the body's background colour as the browser computed it in dark mode at a phone's width, such as `rgb(18, 18, 18)`, and saves `shot.png` in the current folder. Change that colour in your CSS and run it again: the printed value names the new colour exactly, where the screenshot only looks similar.
