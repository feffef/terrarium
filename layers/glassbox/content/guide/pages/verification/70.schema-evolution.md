Some records are written once and almost never rewritten. If their schema changes, every record already written must still pass it. So the schema grows: by optional fields, or, for a change old records would fail, by a new version beside the old one. Terrarium's session logs work this way.

Know schema evolution already? Skip to [In Terrarium](#in-terrarium).

## The concept

A schema change is safe for old records when every value that passed before still passes. Adding a field with `.optional()` is safe: old records simply lack it. Most other changes are not. A new required field fails every old record, a renamed field fails every record that has the old name, and a narrower type, such as an enum with one value fewer, fails the records that used it. On an object that rejects unknown keys ([`.strict()`](https://v3.zod.dev/?id=strict)), so does removing a field: the old records that carry it now hold an unknown key.

When a breaking change is needed anyway, add a new version beside the old one. Give each version a literal field, `z.literal(1)` and `z.literal(2)`, and accept either with [`z.union([v1, v2])`](https://v3.zod.dev/?id=unions). Old records still match the first branch, new ones the second, and code that reads them checks the version.

[`.default(value)`](https://v3.zod.dev/?id=default) fills in a missing field when a record is parsed, so it changes what code sees, not what was stored.

Full reference: [Zod 3 docs: Optionals](https://v3.zod.dev/?id=optionals)

## In Terrarium

Each Claude Code session writes a :term[session log]{id="session-log"}, and :file[scripts/session/log-session.ts] commits it straight to `main` ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs)). The :term[Gate] checks every log, current or archived, against the schema in :file[shared/schemas/session.ts] ([Content validation](/t/glassbox/guide/verification/content-validation)). One old log that fails would fail the Gate.

The schema's first field says how it may change:

::excerpt{path="shared/schemas/session.ts" lines="70-75"}
```ts
export const sessionSchema = z
  .object({
    // Absent ⇒ 1. A breaking change adds a v2 object with z.literal(2) and makes
    // this z.union([v1, v2]); never .default(1), which would blur absent ⇒ v1.
    // Readers tolerate older or unknown versions. Policy: ADR-0009.
    schemaVersion: z.literal(1).optional(),
```
::

A log without `schemaVersion` counts as version 1, and at this revision there is only version 1: the fields added over time are optional. The transcript trace fields, and the authored `learnings` and `ideas` notes, are each `.optional()`, so logs written before them still pass:

::excerpt{path="shared/schemas/session.ts" lines="100-103,177-178"}
```ts
    durationSec: z.number().int().nonnegative().optional(),
    models: z.record(z.string(), z.number().int()).optional(), // model id → assistant-turn count
    toolCounts: z.record(z.string(), z.number().int()).optional(), // tool name → call count
    filesEdited: z.array(z.string()).optional(),
    // …
    learnings: z.array(z.string()).optional(),
    ideas: z.array(z.string()).optional(),
```
::

The object is `.strict()`. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]) names one exception: a Trusted user may remove a field few logs used, rename a field, or rename or drop a value, in the schema and in every log that holds it, in one human-merged PR. Any other field that is no longer written, such as `docsReadViaShell`, stays in the schema, marked as deprecated.

The landing script checks each log against `main`'s schema as well as its branch's. When `main`'s schema rejects only top-level fields it does not know, the script lands the log without them and prints their names; any other rejection, such as a nested field, holds the whole log back:

::excerpt{path="scripts/session/log-session.ts" lines="425,770-771,774-780"}
```ts
  const strippable = issues.every((i) => i.code === 'unrecognized_keys' && i.path.length === 0)
  // …
  const rejection = mainRejection(entry, opts)
  if (!rejection) return stageAndLand(relPath, yaml, opts)
  // …
  if (!rejection.unknownKeys) return refusalOf(rejection, opts.remote)
  const dropped = rejection.unknownKeys
  const stripped = entryYaml(Object.fromEntries(Object.entries(entry).filter(([k]) => !dropped.includes(k))), opts)
  const onMain = current !== null && withoutLandedBy(current) === withoutLandedBy(stripped)
  const res: HandlerResult = onMain ? { action: 'skipped-unchanged', relPath } : stageAndLand(relPath, stripped, opts)
  // Only a log that is on main without the fields counts as stripped.
  return res.action === 'landed' || res.action === 'skipped-unchanged' ? { ...res, dropped } : res
```
::

The script records each landing in `.session-logs/last-landed.json`, a git-ignored file that :file[scripts/session/transcript-trace.ts] names, with the dropped fields as `strippedFields`. While that list is not empty, the `Stop` hook, which Claude Code runs each time the agent finishes a reply ([Claude Code docs: Hooks](https://code.claude.com/docs/en/hooks)), tries the full log again, and the full log lands once `main`'s schema accepts it.

### Why it's built this way

- **Old logs stay as written.** No session edits another's landed log, not even to fix its wording, and none is ever migrated, so every change must keep every old log valid. Terrarium adds optional fields, and a version beside the old one for a change that can't be optional. The cost: a field no longer written stays in the schema. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **One bad log fails the build.** A single invalid log fails the whole build, and an old log can't be regenerated to fix it. So a log must pass `main`'s schema before it lands, not only its branch's. The cost: a log that uses a new top-level field lands without it until the schema change merges, and one with a new nested field waits. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **Other views read the logs.** The session schema is a shared contract that the Commons Timeline reads, and renaming or dropping a field can silently empty such a view ([Cross-tenant reads](/t/glassbox/guide/terrarium-practice/cross-tenant-reads) gives that reason). ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

### What to watch for

- **Optional means every reader copes without it.** A page that shows a new field must handle logs that don't have it, which is every log written before it.
- **A version is a promise to read both.** Once a second version exists, each reader handles both shapes. That cost is why a version waits for a change that truly can't be additive.
- **`.default` hides what was written.** After `.default([])` a reader can't tell an empty list in the file from a missing one. The schema uses `.optional()` where that difference matters, such as the optional `learnings` and `ideas` notes.

## Try it in your project

Pick a schema for records you keep, such as saved settings or event logs. Before you change it, run the new schema over a sample of old records and count the failures; a change is safe only at zero:

```ts
const failures = oldRecords.filter((record) => !newSchema.safeParse(record).success)
console.log(`${failures.length} old records would no longer pass`)
```
