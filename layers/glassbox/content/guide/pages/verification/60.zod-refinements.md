A config file is data, and data can be wrong. If nothing checks it, a typo in a key is silently ignored and the mistake turns up much later, somewhere far from the file. Terrarium checks each tenant's manifest with a Zod schema before anything is built from it.

Know Zod refinements already? Skip to [In Terrarium](#in-terrarium).

## The concept

[Zod](https://v3.zod.dev/) describes the shape of data as a schema in TypeScript, then checks a value against it at runtime with `parse` or `safeParse`; a `.strict()` object also rejects keys it doesn't know. [Content validation](/t/glassbox/guide/verification/content-validation) explains both.

A shape alone can't state every rule a config needs. Two tools cover the rest:

- **`.refine` and `.superRefine`.** Some rules span several fields, such as "this field is required when that one has this value". A refinement is a function that runs after the shape has parsed. With [`.refine`](https://v3.zod.dev/?id=refine) it returns a value, and any truthy one passes. `.superRefine` also gets a context object, `ctx`, and may call `ctx.addIssue` as often as it needs. Each issue is one reported problem, with its own `path` to the field and its own message.
- **`z.custom`.** For a value Zod has no schema for, [`z.custom`](https://v3.zod.dev/?id=custom-schemas) accepts any value unless you give it a test function.

By default an object schema strips keys it doesn't know from its result; `.strict()` rejects them instead. That choice is the schema's policy for unknown keys. Two ways combine object schemas. `A.extend({ … })` adds fields to `A`. [`A.merge(B)`](https://v3.zod.dev/?id=merge) does the same with `B`'s fields, and the result also takes `B`'s policy for unknown keys.

Full reference: [Zod 3 docs: .superRefine](https://v3.zod.dev/?id=superrefine)

## In Terrarium

Each :term[tenant] declares its :term[spaces]{id="space"} and :term[collections]{id="collection"} in one :term[manifest]. [Content collections](/t/glassbox/guide/nuxt-content/content-collections) says what the checks catch; this lesson shows how they're built. :file[shared/manifest.ts] holds the schema for one collection entry. Its `schema` field must hold a Zod schema:

::excerpt{path="shared/manifest.ts" lines="77-80"}
```ts
const zodSchemaField = z.custom<ZodObject<ZodRawShape>>(
  (v) => typeof (v as { safeParse?: unknown })?.safeParse === 'function',
  'schema is not a zod schema',
)
```
::

The entry's `schema` and `kind` fields are both optional. `kind` names a :term[kind]{id="collection-kind"}, a shared shape a collection opts into. A kind's *contract* is the minimum set of fields every collection of that kind has. The entry's `type` field is `page` or `data`, and a `.superRefine` requires a `schema` or a `kind` on a `data` collection. The excerpt leaves out the kind checks between the fields and that rule:

::excerpt{path="shared/manifest.ts" lines="97-101,124-131"}
```ts
    schema: zodSchemaField.optional(),
    kind: z.string().optional(),
  })
  .strict()
  .superRefine((val, ctx) => {
    // …
    if (val.type === 'data' && val.schema === undefined && val.kind === undefined) {
      ctx.addIssue({
        code: z.ZodIssueCode.custom,
        path: ['schema'],
        message: 'data collection requires a schema (or a `kind` whose contract supplies one)',
      })
    }
  })
```
::

A `schema` in a manifest is itself a Zod schema object, and `z.custom` passes any value with a `safeParse` method. The `.superRefine` adds one issue per broken rule that spans fields: a `data` collection without a `schema` or a kind, a `kind` missing from :file[shared/kinds.ts], or a kind whose type differs from the collection's. A second `.superRefine`, on the whole set of collections, ties the `page` type to the name `pages`.

`validateManifest()` runs `safeParse` and turns every issue into one line, led by its path when it has one. `expand()` in :file[shared/expand.ts] calls it on each manifest and throws with all of that manifest's lines at once. A manifest with a misspelt `source` key on a `data` collection that has no schema stops the build with:

```text
invalid manifest "demo":
- collections.notes: Unrecognized key(s) in object: 'sorce'
- collections.notes.schema: data collection requires a schema (or a `kind` whose contract supplies one)
```

A collection that names a kind gets the kind's contract plus its own schema. `effectiveSchema()` in :file[shared/expand.ts] combines them by extending the local schema with the contract fields it lacks:

::excerpt{path="shared/expand.ts" lines="111-114"}
```ts
  const additions = Object.fromEntries(
    Object.entries(contract.shape).filter(([field]) => !(field in local.shape)),
  )
  return local.extend(additions)
```
::

`local.extend(additions)` adds only the contract fields the local schema doesn't declare: on a shared name, the local field wins.

### Why it's built this way

- **Checked before it's built.** A manifest mistake found late fails far from its cause; [Content collections](/t/glassbox/guide/nuxt-content/content-collections) gives this reason and its cost. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).
- **A kind is a minimum.** A collection that names a kind keeps its own fields on top of the kind's contract; [Cross-tenant reads](/t/glassbox/guide/terrarium-practice/cross-tenant-reads) gives the reason and its cost. ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).
- **Several problems per run.** Fixed one `safeParse` at a time, a manifest with several mistakes takes several runs. So each rule adds its own issue with a path, and `validateManifest()` returns one line for each issue a run reaches. The cost: an invalid `type` or a `schema` that isn't a Zod schema hides the later rules until it is fixed. :file[shared/manifest.ts].
- **A refinement, not a union.** A plain optional `schema` can't require a `data` collection to name a `schema` or a `kind`. A discriminated union could, but its built-in error doesn't fit the file's labelled messages, so a refinement on one object does it. :file[shared/manifest.ts].
- **Extend, don't merge.** `loadManifests()` loads every `tenant.config.ts` through a [jiti](https://github.com/unjs/jiti) instance of its own, a loader that runs TypeScript in Node, so a tenant's schema and a kind's contract can use different copies of Zod. Zod's `instanceof` check for the strip policy fails across copies, so `.merge` turns a schema that strips unknown keys into one that rejects them. Extending keeps the tenant schema's own policy. :file[shared/expand.ts].

### What to watch for

- **A refinement waits for the shape.** Zod runs a refinement only once the object it sits on has parsed, and a failed `z.custom` test stops that parse too. On an entry with an invalid `type` or a `schema` that isn't a Zod schema, that entry's own kind and schema rules don't run, and neither does the `pages` rule for any collection, so fixing it can bring new errors on the next run. An unknown key doesn't hold them back: `.strict()` reports it as an issue, but the object still counts as parsed, so its refinements run too.
- **`z.custom` checks what you test, nothing more.** The schema field passes any object with a `safeParse` method, whichever copy of Zod made it. That loose test is what lets two copies meet in `effectiveSchema()`.
- **The type repeats part of the schema.** `CollectionDef` in :file[shared/manifest.ts] is a TypeScript union that, like the schema, requires a `data` collection to name a `schema` or a `kind`, and its `kind` field accepts only a name from :file[shared/kinds.ts]. The schema's other rules, such as lowercase slug names, a kind matching its collection's type and the `pages` rule, run only at build. The schema-or-kind rule is written by hand in both, so a change to it needs the same change in both.

## Try it in your project

If your app reads a config file, give it a strict schema and check it before you use it, listing every problem it finds:

```ts
import { z } from 'zod'

const config = z
  .object({ mode: z.enum(['static', 'server']), port: z.number().optional() })
  .strict()
  .superRefine((c, ctx) => {
    if (c.mode === 'server' && c.port === undefined) {
      ctx.addIssue({ code: z.ZodIssueCode.custom, path: ['port'], message: 'a server needs a port' })
    }
  })

const result = config.safeParse(loadedConfig)
if (!result.success) {
  throw new Error(result.error.issues.map((i) => `${i.path.join('.')}: ${i.message}`).join('\n'))
}
```
