A test suite has to run on every change, so it must be fast, yet some bugs show only when the real app loads in a browser, and that is slow. When one app serves several sites, there is a second question: where each test lives, so that a site can be added or removed with its tests in one piece.

Know Vitest and Nuxt's test utilities already? Skip to [In Terrarium](#in-terrarium).

## The concept

A unit test calls a function or module directly and checks what it returns. It needs no server and runs in milliseconds. An end-to-end test, *e2e* for short, starts the built app's server and drives a real browser through it, so it catches what only the running app shows, such as a page that throws while it loads. It is far slower, so a suite holds many unit tests and fewer e2e tests.

[Vitest](https://vitest.dev/guide/projects) can run both. Its *projects* split one config into named parts, each with its own `include` globs and settings, and `vitest --project <name>` runs one of them. A [filter on the command line](https://vitest.dev/guide/filtering#filtering-by-file-name), such as `vitest run tests/unit`, keeps only the test files whose path contains that text. By default Vitest runs each test file in a fresh context; the [`isolate`](https://vitest.dev/config/isolate) setting turns that off, which is faster but lets files that run in the same worker, one of the threads or processes Vitest spreads test files across, share globals and module state. A [`globalSetup`](https://vitest.dev/config/globalsetup) file runs once before a project's tests, the place for work every file shares.

For e2e, Nuxt's `@nuxt/test-utils` gives a `setup()` call for each `describe` block. Its options decide whether it builds the app, starts a server on the result, launches a browser through [Playwright](https://playwright.dev/docs/library), or points at a server already running.

Full reference: [Nuxt docs: Testing](https://nuxt.com/docs/4.x/getting-started/testing)

## In Terrarium

A test lives with the code it tests. Platform tests sit in :file[tests/]. A :term[tenant]'s own tests sit in its layer, in `layers/<tenant>/tests/unit/` and `layers/<tenant>/tests/e2e/`. :file[tests/README.md] sets out the rule. :file[vitest.config.ts] defines a `unit` and an `e2e` project, and their globs find every tenant's folder without naming one. The `unit` project matches `layers/*/tests/unit/**/*.spec.ts` and each skill's `.agents/skills/*/tests/unit/` beside the platform's own `tests/unit/`, and turns `isolate` off. The `e2e` project in full:

::excerpt{path="vitest.config.ts" lines="49-59"}
```ts
      {
        extends: true,
        test: {
          name: 'e2e',
          include: ['tests/e2e/**/*.spec.ts', 'layers/*/tests/e2e/**/*.spec.ts'],
          globalSetup: ['tests/support/e2e-global-setup.ts'],
          // The default 1 s is shorter than a browser state change (accordion
          // toggle, route navigation) on a loaded CI or gate machine.
          expect: { poll: { timeout: 10_000 } },
        },
      },
```
::

`pnpm test` in :file[package.json] runs `nuxt prepare`, then `vitest run tests/unit`. That filter is text in a path, so it also picks up the `tests/unit/` folders inside each layer and each skill. `pnpm test:e2e` runs `vitest run tests/e2e`, which selects the e2e specs the same way.

A unit test can hold a content rule too. Glass Box's :file[layers/glassbox/tests/unit/glassbox-pages.spec.ts] runs :file[layers/glassbox/page-checks.ts] on every guide page. Each page names a commit, its `revision`, and quotes code from that commit in excerpts. A page whose excerpt no longer matches its file at that commit, or that links a page that doesn't exist, fails `pnpm test`. A lesson, a page on one concept, fails too when its title runs past four words or its *In Terrarium* section uses the word `because`. A page that is merely old passes.

The Blog holds a rule from its writing skill, :file[.agents/skills/blog-post/SKILL.md], the same way: a GitHub link to a file names a commit SHA, never `main`. :file[layers/blog/tests/unit/blog-immutable-links.spec.ts] reads every Markdown file under the Blog's content and fails on each link on a route that serves a file whose ref isn't a hex SHA, naming those links in its message:

::excerpt{path="layers/blog/tests/unit/blog-immutable-links.spec.ts" lines="23-26"}
```ts
const FILE_ROUTE_LINK = /github\.com\/[^/]+\/[^/]+\/(?:blob|tree|raw|blame|edit)\/([^/\s)]+)\//g
// An immutable pin is a hex commit SHA (7–40 chars). Anything else — `main`, a
// feature-branch name, a tag — is mutable and rejected.
const SHA = /^[0-9a-f]{7,40}$/
```
::

The skill asks for a full 40-character SHA, but the test checks only that a link is pinned: its comment counts any hex SHA of 7 to 40 characters as an immutable pin, and a short SHA passes.

The e2e tests share one build. :file[tests/support/e2e-global-setup.ts] runs once before them: it reuses the app in `.output` when that build is at least as new as every file git tracks or would add, and builds only when it isn't. The files it compares come from git:

::excerpt{path="tests/support/fresh-output.ts" lines="22-32"}
```ts
/** Every source file's mtime, plus each ancestor directory's: a deletion moves only the directory's. */
function sourceMtimes(root: string): number[] {
  const git = (...args: string[]) =>
    execFileSync('git', args, { cwd: root, encoding: 'utf8', maxBuffer: 1 << 26, stdio: ['ignore', 'pipe', 'ignore'] }).split('\0').filter(Boolean)
  const files = [...git('ls-files', '-z'), ...git('ls-files', '-z', '--others', '--exclude-standard')]
  const paths = new Set(files)
  for (const file of files) for (let dir = dirname(file); !paths.has(dir); dir = dirname(dir)) paths.add(dir)
  // CI creates the gitignored `.pw-browsers` here after the build, which bumps the root's mtime.
  paths.delete('.')
  return [...paths].flatMap((path) => mtimeOf(join(root, path)) ?? [])
}
```
::

Each spec then calls `setupL2()` from :file[tests/support/e2e.ts] (:file[tests/README.md] numbers its test levels: L0 and L3 are unit tests, L1 is content validation and L2 is e2e). The function copies the build's content database into a temporary folder and calls Nuxt's `setup()` with the build turned off and the server pointed at that copy; the lines left out launch a Chromium browser.

::excerpt{path="tests/support/e2e.ts" lines="37-47,55-56"}
```ts
export async function setupL2(): Promise<void> {
  const dbDir = mkdtempSync(join(tmpdir(), 'terrarium-e2e-'))
  afterAll(() => rmSync(dbDir, { recursive: true, force: true }))
  const builtDb = join(root, '.data/content/contents.sqlite')
  if (existsSync(builtDb)) copyFileSync(builtDb, join(dbDir, 'contents.sqlite'))
  await setup({
    rootDir: root,
    build: false,
    nuxtConfig: { nitro: { output: { dir: join(root, '.output') } } },
    env: { NUXT_CONTENT_DATABASE_FILENAME: join(dbDir, 'contents.sqlite') },
    browser: true,
    // …
  })
}
```
::

The platform's spec, :file[tests/e2e/smoke.spec.ts], loads every tenant and :term[space] entry address in the browser and fails on a console error or a broken render. It reads that list from the manifests. A tenant's own e2e spec checks what only that tenant has, and the specs run in parallel. Unit tests, the build and the e2e tests form the :term[gate]'s :term[heavy] tier, the slow steps `pnpm gate:scoped` skips only when a change provably can't affect them ([Merge gate](/t/glassbox/guide/verification/gate)).

### Why it's built this way

- **Tests travel with their tenant.** Tests once sat in shared folders, so removing a site meant hunting down its tests. Now they sit in the tenant's own folder, found by glob, so adding or deleting that folder adds or removes its tests with no other edit. The cost: a spec outside the globs never runs, and nothing warns. :file[tests/README.md].
- **One build for every e2e spec.** After the gate's `pnpm build`, Nuxt's `setup()` built the app again, once per spec. Now specs only serve the gate's build, so each tenant's e2e runs as its own spec, in parallel. The cost: reusing a stale build once hid a regression, so the freshness check now covers every file git tracks or would add. :file[tests/README.md].
- **A database per spec.** Parallel servers sharing one content database file raced to fill it, hit "database is locked" and answered errors. So each spec's server gets its own copy, seeded from the build's. The cost: a file copy per spec. :file[tests/support/e2e.ts].
- **No isolation between unit files.** Each unit file re-imported Vue, Nuxt's helpers and the scripts' imports in a fresh context, a large share of the whole run. Turning isolation off cut that, and the tests still passed in shuffled order and on a single worker. The cost: unit files on one worker share one set of globals, so each must clean up after itself. :file[vitest.config.ts].

### What to watch for

- **Unit specs share a worker's context.** A spec that changes `process.env`, `PATH` or a global must put it back itself, or a later file on that worker sees the change and fails for no reason of its own.
- **An e2e spec never builds.** Call `setupL2()`, never pass `build: true` to `setup()`, which would add a build per spec, and set `E2E_FRESH_BUILD=1` to force a fresh build.
- **Slow isn't flaky.** Use Vitest's `expect`, not [Playwright's matchers](https://playwright.dev/docs/test-assertions#auto-retrying-assertions) such as `toBeVisible`, which come with its own test runner and don't run here. For a condition that settles over time, use `expect.poll`; if an animation outlasts its timeout, raise the timeout for that call rather than re-running the test. :file[tests/README.md] has the default.
- **Heavy tiers wait their turn.** Too many e2e runs at once in one container ran it out of memory, so `pnpm gate:scoped` waits for a free slot before a heavy tier that builds; each container has a fixed number of slots. Running `pnpm test:e2e` by hand takes no slot. :file[scripts/gate/gate.ts].

## Try it in your project

Give each part of your app that could be removed on its own a `tests/` folder beside its code, and change your test config to find those folders by glob, with no part named:

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config'

export default defineConfig({
  test: { include: ['tests/**/*.spec.ts', 'parts/*/tests/**/*.spec.ts'] },
})
```

Run `npx vitest list --filesOnly` and check each part's specs are listed. Then delete one part's folder, say `parts/billing/`, and run `grep -rn 'parts/billing' --exclude-dir=node_modules --exclude-dir=.git .`: no match means no config or script still names it, and the list no longer shows its specs.
