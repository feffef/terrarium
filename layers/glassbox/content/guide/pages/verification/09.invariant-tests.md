Some rules about content must hold on every page, every day: a link into the code shows the code the author saw. A rule that only lives in a writing guide holds until someone forgets it. Written as a test, it holds on every change, and the test can say exactly which link broke it.

Know permanent links already? Skip to [In Terrarium](#in-terrarium).

## The concept

A link to a file on a branch, such as `…/blob/main/src/app.ts`, always shows the file as it is now. Months later the lines it pointed at have moved, or the file is gone. A permanent link names a commit instead of the branch, as in `…/blob/<commit-sha>/src/app.ts`, and shows that exact version for good. On GitHub, pressing `y` while viewing a file turns its address into one ([GitHub Docs: Getting permanent links to files](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)).

A rule like "links to code are permanent" is an *invariant*: something that must be true of all the content, all the time. You can check an invariant with an ordinary unit test in a runner such as Vitest: read every content file, find what breaks the rule, and fail with a message that names it. Keep the test beside the content it guards, so the two move together.

Full reference: [Vitest docs: Getting Started](https://vitest.dev/guide/)

## In Terrarium

The Blog's writing Skill, :file[.agents/skills/blog-post/SKILL.md], asks every link to a file or a line to name a full commit SHA, never `main`. The Blog checks that with a unit test in its own layer, :file[layers/blog/tests/unit/blog-immutable-links.spec.ts]. It reads every Markdown file under the Blog's content and fails on any file link whose ref is not a commit SHA:

::excerpt{path="layers/blog/tests/unit/blog-immutable-links.spec.ts" lines="21-26"}
```ts
// Only file-serving GitHub routes take a ref that can be a branch; `commit`,
// `pull`, `issues`, `compare`, … don't, so they can't rot this way.
const FILE_ROUTE_LINK = /github\.com\/[^/]+\/[^/]+\/(?:blob|tree|raw|blame|edit)\/([^/\s)]+)\//g
// An immutable pin is a hex commit SHA (7–40 chars). Anything else — `main`, a
// feature-branch name, a tag — is mutable and rejected.
const SHA = /^[0-9a-f]{7,40}$/
```
::

A first check fails if the walk finds no content at all, as it would if the content folder moved. A second rule in the same file fails on a GitHub link to another Blog post, which must use the post's own site address instead.

Like every :term[Tenant]'s unit tests, it runs in `pnpm test`, part of the :term[Gate] ([Testing](/t/glassbox/guide/verification/unit-and-e2e-tests)): a post with a branch link fails the test step.

### Why it's built this way

- **Branch links rot silently.** A `blob/main/…` link keeps loading while its line anchors drift as the file changes, and a later rename or delete turns it into a 404, so a long-published post quietly points at the wrong thing. Some of the Blog's branch links were already dead when the test was written. So the test rejects every file link not pinned to a commit. :file[layers/blog/tests/unit/blog-immutable-links.spec.ts]
- **The Skill sets the rule, the test enforces it.** The writing Skill states the convention for authors; the test is its enforcement, so a post that breaks it fails a check instead of waiting for a reader to find the dead link. The cost: the rule is written twice, and the two already differ on how long a SHA must be. :file[layers/blog/tests/unit/blog-immutable-links.spec.ts]
- **Tests travel with their Tenant.** The test sits in the Blog's own layer rather than a shared folder, for the reason [Testing](/t/glassbox/guide/verification/unit-and-e2e-tests) gives: a Tenant's tests are found by glob, so they come and go with its folder. :file[tests/README.md]

### What to watch for

- **The test is looser than the Skill.** The Skill asks for a full 40-character SHA; the test accepts any hex run of 7 to 40 characters, so a short SHA passes.
- **A pinned link can still be wrong.** The test checks the shape of the ref, not that the commit exists or holds the quoted lines. The Skill has the author copy the SHA from git output for that reason.
- **Only file links in the Blog's Markdown are checked.** The test reads only `.md` files under `layers/blog/content`, so a link in the Blog's YAML files, or anywhere outside that folder, goes unchecked. Commit, pull request and issue links name something that never changes, so the test skips them.

## Try it in your project

Pick one rule from your project's writing guide that a script could check. Write it as a test that reads every content file and fails with the offending text in its message, then break the rule once on purpose to see the message.
