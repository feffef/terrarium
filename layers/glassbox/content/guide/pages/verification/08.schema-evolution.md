Some records are written once and almost never rewritten. If their schema changes, every record already written must still pass it. So the schema grows: by optional fields, or, for a change old records would fail, by a new version beside the old one. Terrarium's session logs work this way.

Know schema evolution already? Skip to [In Terrarium](#in-terrarium).

## The concept

A schema change is safe for old records when every value that passed before still passes. Adding a field with `.optional()` is safe: old records simply lack it. Most other changes are not. A new required field fails every old record, a renamed field fails every record that has the old name, and a narrower type, such as an enum with one value fewer, fails the records that used it. On a strict object, so does removing a field: the old records that carry it now hold an unknown key.

When a breaking change is needed anyway, add a new version beside the old one. Give each version a literal field, `z.literal(1)` and `z.literal(2)`, and accept either with `z.union([v1, v2])`. Old records still match the first branch, new ones the second, and code that reads them checks the version.

`.default(value)` fills in a missing field when a record is parsed, so it changes what code sees, not what was stored.

Full reference: [Zod 3 docs: Optionals](https://v3.zod.dev/?id=optionals)

## In Terrarium

Each Claude Code session writes a :term[session log]{id="session-log"}, and :file[scripts/session/log-session.ts] commits it straight to `main` ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs)). No session edits another's landed log, ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]), and the :term[Gate] checks every one, current or archived, against the schema in :file[shared/schemas/session.ts] ([Content validation](/t/glassbox/guide/verification/content-validation)). One old log that fails would fail the Gate.

The schema's first field says how it may change:

::excerpt{path="shared/schemas/session.ts" lines="39-44"}
```ts
export const sessionSchema = z
  .object({
    // Absent ⇒ 1. A breaking change adds a v2 object with z.literal(2) and makes
    // this z.union([v1, v2]); never .default(1), which would blur absent ⇒ v1.
    // Readers tolerate older or unknown versions. Policy: ADR-0009.
    schemaVersion: z.literal(1).optional(),
```
::

At this revision there is only version 1: the fields added over time are optional. Fields the landing script derives from the transcript, such as `durationSec` and `filesEdited`, are all optional, so logs written before them still pass. The object is `.strict()`, and ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]) names the one case where a field may be removed. Any other field that is no longer written stays in the schema, marked as deprecated:

::excerpt{path="shared/schemas/session.ts" lines="90-92"}
```ts
    // DEPRECATED — no longer written; shell reads fold into `docsRead`. The key
    // stays so older logs validate (ADR-0009).
    docsReadViaShell: z.array(z.string()).optional(),
```
::

A new field has one more hurdle. A log lands on `main`, but the session that writes it may run on a branch that changed the schema. The landing script checks each log against `main`'s schema as well as the branch's. A log that `main`'s schema rejects is held back, and lands once the schema change has merged.

### Why it's built this way

- **Old logs stay as written.** No session edits another's landed log, not even to fix its wording, and none is ever migrated, so every change must keep every old log valid. Terrarium adds optional fields, and a version beside the old one for a change that can't be optional. The cost: a field no longer written stays in the schema. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **One bad log fails the build.** A single invalid log fails the whole build, and an old log can't be regenerated to fix it. So a log must pass `main`'s schema before it lands, not only its branch's. The cost: a log that uses a new field waits until the schema change merges. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **Other views read the logs.** The session schema is a shared contract that the Commons Timeline reads, and renaming or dropping a field can silently empty such a view ([Cross-tenant reads](/t/glassbox/guide/terrarium-practice/cross-tenant-reads) gives that reason). ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

### What to watch for

- **Optional means every reader copes without it.** A page that shows a new field must handle logs that don't have it, which is every log written before it.
- **A version is a promise to read both.** Once a second version exists, each reader handles both shapes. That cost is why a version waits for a change that truly can't be additive.
- **`.default` hides what was written.** After `.default([])` a reader can't tell an empty list in the file from a missing one. The schema uses `.optional()` where that difference matters, such as the optional `learnings` and `ideas` notes.

## Try it in your project

Pick a schema for records you keep, such as saved settings or event logs. Before you change it, run the new schema over a sample of old records and count the failures; a change is safe only at zero:

```ts
const failures = oldRecords.filter((record) => !newSchema.safeParse(record).success)
console.log(`${failures.length} old records would no longer pass`)
```
