When several sites share one content database, the worst bug is a page that shows another site's content. Filtering every query by a site column makes each query a chance to forget the filter. Terrarium puts each site's content in tables of its own instead, so a query can only see what its table holds.

Know how Nuxt Content stores collections already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content keeps your content in an SQLite database. When it builds, it reads each collection's files, creates one table for that collection with columns from its schema, and inserts one row per file. Nothing else shares that table.

A query starts from one collection. [`queryCollection`](https://content.nuxt.com/docs/utils/query-collection) takes the name you gave the collection in `content.config.ts` and builds SQL against that collection's table alone: `where`, `order` and the rest narrow the rows of that one table, and no method joins it to another. Two collections are as separate as two tables, so the collection is the smallest unit of content you can keep apart.

Full reference: [Nuxt Content docs: Database](https://content.nuxt.com/docs/advanced/database)

## In Terrarium

Every :term[Tenant], :term[Space] and :term[Collection] together become one collection, and so one table. Its name is a key that joins the three names:

::excerpt{path="shared/manifest.ts" lines="173-176"}
```ts
/** The collection key — also the SQLite table name and the unit of isolation (ADR-0001). */
export function collectionKey(tenant: string, space: string, collection: string): string {
  return `${tenant}_${space}_${collection}`
}
```
::

So the Blog's David Space keeps its posts under `blog_david_pages`, and Nuxt Content names the table after the key, `_content_blog_david_pages`. How the keys are produced from each manifest is in [Collections expanded from one manifest](/t/glassbox/guide/nuxt-content/manifest-collections).

A table keeps Spaces apart only if every page asks for the right key. No page builds a key itself: the page asks `useSpace` in :file[app/composables/space.ts], which hands the request's Tenant and Space to `resolveSpaceRoute` in :file[shared/routing.ts]. The resolver reads one entry of the routing map, the generated list of every Space's keys, and nothing else:

::excerpt{path="shared/routing.ts" lines="95-98"}
```ts
  const tenantSpaces = Object.hasOwn(map, tenant) ? map[tenant] : undefined
  const spaceCollections =
    tenantSpaces && Object.hasOwn(tenantSpaces, space) ? tenantSpaces[space] : undefined
  if (!spaceCollections?.pages) return null
```
::

A page gets back the keys of exactly one Space, or a 404. `Object.hasOwn` makes a name such as `__proto__` miss instead of finding something on every object. A page that reads more than one Space, like a Tenant's own front page above its Spaces, calls the same resolver once per Space.

The :term[Gate] tests both halves. :file[tests/unit/expand.spec.ts] checks that every Tenant, Space and Collection gets its own well-formed key and folder, and :file[tests/unit/routing.spec.ts] checks that a resolved route names only the requested Space's keys.

### Why it's built this way

Why each collection is its own table, inside one app: ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

Why one resolver turns the URL into one Space's keys: ADR-0006 (:file[docs/adr/0006-runtime-routing-path-prefix.md]).

Why a change to who can reach which Tenant's data waits for a person: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

A Tenant's root page above its Spaces: ADR-0016 (:file[docs/adr/0016-tenant-root-layer-routes.md]).

Reading across Tenants on purpose: ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

### What to watch for

- **Separate is not secret.** Every build holds every Space, and Nuxt Content serves each collection's dump at its own URL so the browser can load it. Anyone can fetch any Space's content; the tables only stop a page from showing it by mistake.
- **Take keys from `useSpace`, never from a string.** A key typed into a page, such as `` `blog_${space}_pages` ``, skips the resolver and its tests. Why a typed key matters is in [queryCollection patterns](/t/glassbox/guide/nuxt-content/query-collection-patterns).
- **A rename moves the content.** The key is made of the three names, so renaming a Tenant, Space or Collection gives it a new table and a new folder under `layers/<tenant>/content/`, and a Space's or Tenant's rename changes its URLs too.

## Try it in your project

Start your Nuxt Content dev server once, then list the tables in its database with Node's built-in SQLite module (Node 22.13 or later; it may print an ExperimentalWarning), by running this file with `node tables.mjs` from the project root. You should see one `_content_<name>` table per collection in your `content.config.ts`, plus Nuxt Content's own `_content_info` and `_development_cache`:

```js
// tables.mjs
import { DatabaseSync } from 'node:sqlite'

const db = new DatabaseSync('.data/content/contents.sqlite')
console.log(db.prepare("SELECT name FROM sqlite_master WHERE type = 'table'").all())
```
