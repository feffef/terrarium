A site with many sections, each in several variants, needs many content collections that differ only in a name and a folder. Written out by hand, that list grows with every section and goes wrong in ways nobody spots. Terrarium writes down only what each site holds, and lets code produce the list.

Know Nuxt Content collections already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content reads the files in your project and stores them in a database you query from your pages. A collection groups the files of one kind, such as blog posts or authors. You define collections in `content.config.ts`, at the project root, with `defineCollection`; once that file exists, only files that some collection matches are imported.

Each collection has a `type`. A **page** collection maps each file to one page of the site: Nuxt Content [generates its `path`](https://content.nuxt.com/docs/collections/types#path-generation) from the file's path and adds the fields a page needs, such as `title`, `description` and the parsed `body`. A **data** collection holds structured records that pages read but that have no URL of their own, and its schema is all yours.

[`source`](https://content.nuxt.com/docs/collections/sources#source) says which files belong: a glob, or an object with `include`, `exclude`, a `cwd` folder to search from and, for pages, a path `prefix`. `schema` is a [Zod](https://v3.zod.dev/) object for the fields you add, and it is the source of the collection's TypeScript types. [`queryCollection('<name>')`](https://content.nuxt.com/docs/utils/query-collection) reads a collection.

`content.config.ts` is TypeScript that runs, not a static list, so the collections in it can be computed.

Full reference: [Nuxt Content docs: Define Content Collections](https://content.nuxt.com/docs/collections/define)

## In Terrarium

Each :term[tenant] states what it holds in one :term[manifest], `layers/<tenant>/tenant.config.ts`. The manifest gives the tenant's name, its :term[spaces]{id="space"}, and its :term[collections]{id="collection"} with their types and schemas. Tinkerfund's manifest names its spaces, then the collections every space holds: its routed `pages` and the `data` collections those pages read, each with a schema from Tinkerfund's own `schemas.ts`:

::excerpt{path="layers/tinkerfund/tenant.config.ts" lines="10-23"}
```ts
export default defineTenant({
  name: 'tinkerfund',
  spaces: ['prod', 'qa'],
  collections: {
    pages: { type: 'page', source: '**/*.md', schema: page },
    inventors: { type: 'data', source: '*.yml', schema: inventor },
    categories: { type: 'data', source: '*.yml', schema: category },
    comments: { type: 'data', source: '*.yml', schema: commentThread },
    updates: { type: 'data', source: '*.yml', schema: updateLog },
    promotions: { type: 'data', source: '*.yml', schema: promotion },
    backer: { type: 'data', source: '*.yml', schema: backer },
    shop: { type: 'data', source: '*.yml', schema: shop },
  },
})
```
::

:file[shared/manifest.ts] checks each manifest before anything is built from it. Its Zod schema is strict ([Content validation](/t/glassbox/guide/verification/content-validation)): a misspelt key fails with a message that names the field. A `data` collection needs a schema, or a :term[kind]{id="collection-kind"}, a shared shape that code in other tenants can read ([Cross-tenant reads](/t/glassbox/guide/terrarium-practice/cross-tenant-reads)); the check refuses one with neither. Any `page` collection maps its files to pages, but Terrarium's routing serves only the collection named `pages` ([File routing](/t/glassbox/guide/nuxt-vue/file-routing)). The check ties type to name both ways: a `page` collection by any other name fails, and so does a `pages` collection that isn't a `page` one.

Then `expand()` in :file[shared/expand.ts] multiplies it out: each collection of each space becomes a Nuxt Content collection of its own ([Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation) shows what that buys). Each gets a key such as `tinkerfund_prod_pages` and a folder such as `layers/tinkerfund/content/prod/pages/`. The key joins the three names with `_`, which no name may hold: names are lowercase letters and digits only, and a key always splits back into its three parts. `expand()` still checks that no two collections share a key, and fails the build if two do.

:file[content.config.ts] holds no list of collections. It turns the expansion into `defineCollection` calls each time Nuxt Content loads it:

::excerpt{path="content.config.ts" lines="22-23,29-40"}
```ts
    expand(loadManifests()).map((c) => [
      c.key,
      // …
      c.type === 'page'
        ? defineCollection({
            type: 'page',
            source: { cwd: dir(c.cwdRel), include: c.include, prefix: '/' },
            schema: c.schema,
          })
        : defineCollection({
            type: 'data',
            source: { cwd: dir(c.cwdRel), include: c.include },
            schema: c.schema,
          }),
    ]),
```
::

`loadManifests()` reads every tenant's manifest, `dir()` turns a folder path relative to the repo root into an absolute one, and `c.include` is the collection's `source` glob from its manifest, or `**` when it gives none.

`cwd` points each collection at its own folder, and a page's `path` starts at that folder, with no tenant or space segment in it. Nuxt Content's default `prefix` is the part of `include` before its first `*`: empty for a source such as `**/*.md`, which gives `/` anyway. `prefix: '/'` keeps the path at the folder for a source that starts with a folder name too. The same expansion builds the routing map in :file[modules/routing.ts], which turns an address into one space's keys.

### Why it's built this way

- **Generated, not hand-written.** By hand, the list of collections would be one shared file every tenant edits, prone to merge conflicts, where one slip breaks every tenant. So each tenant writes a small :term[manifest] and tested code multiplies it out, one collection per space ([Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation) says why). The cost: one more layer above Nuxt Content. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).
- **Checked manifests.** Each manifest is checked before anything is built from it, so a misspelt key fails at once, naming the field. Unchecked, it could be silently ignored or fail later with a confusing Nuxt build error. The cost: a manifest can use only the keys the shared schema knows, so a new kind of setting changes that schema first. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).
- **Built at load time.** `content.config.ts` was once generated and committed, and PRs still failed when a manifest edit skipped regenerating it. Building the list when the config loads makes a stale list impossible. The cost: no file shows the expanded list, and the design relies on Nuxt Content letting the config import the manifests. ADR-0013 (:file[docs/adr/0013-content-config-built-from-manifests.md]).
- **Only `pages` has URLs.** Each space gets one set of addresses, so the URL scheme, route lookup and smoke test stay simple; everything else is data pages read. A `page` collection under another name once made the smoke test check addresses routing never served; now the check ties type to name. The cost: anything needing its own address must be a page in `pages`. ADR-0006 (:file[docs/adr/0006-runtime-routing-path-prefix.md]).

### What to watch for

- **Declare collections only in the manifest.** A collection defined anywhere else, such as in a tenant's layer, skips `expand()` and its check that every key is unique, the backstop for one table per space.
- **A page schema holds only the extras.** The `page` type [already adds](https://content.nuxt.com/docs/collections/types#schema-overrides) `title`, `description`, `body` and the rest, so a manifest's `pages` schema declares only the tenant's own fields.
- **The dev server misses manifest edits on its own.** Nuxt Content restarts when `content.config.ts` changes, not when a file it imports does. :file[modules/routing.ts] adds the manifests and `shared/expand.ts` to Nuxt's watch list, which closes that gap for existing tenants. A brand-new layer folder isn't watched, so restart the dev server after adding a tenant.

## Try it in your project

If your `content.config.ts` repeats nearly the same `defineCollection` call, say once per language, generate the calls from a list instead, so adding a language is one more entry:

```ts
// content.config.ts
import { defineCollection, defineContentConfig } from '@nuxt/content'

const locales = ['en', 'de']

export default defineContentConfig({
  collections: Object.fromEntries(locales.map((locale) => [
    `docs_${locale}`,
    defineCollection({ type: 'page', source: `${locale}/**/*.md` }),
  ])),
})
```

Run `npx nuxt prepare`, which regenerates the project's types, then check that each locale became a collection of its own:

```bash
grep -A3 'interface Collections' .nuxt/content/types.d.ts
```

You should see one key per entry in `locales`:

```ts
  interface Collections {
    docs_en: DocsEnCollectionItem
    docs_de: DocsDeCollectionItem
  }
```

Add `'fr'` to the list and run both commands again: a `docs_fr` key appears. To list the database tables these collections fill, use the script in [Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation).
