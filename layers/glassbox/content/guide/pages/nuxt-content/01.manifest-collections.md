A site with many sections, each in several variants, needs many content collections that differ only in a name and a folder. Written out by hand, that list grows with every section and goes wrong in ways nobody spots. Terrarium writes down only what each site holds, and lets code produce the list.

Know Nuxt Content collections already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content reads the files in your project and stores them in a database you query from your pages. A collection groups the files of one kind, such as blog posts or authors. You define collections in `content.config.ts`, at the project root, with `defineCollection`; once that file exists, only files that some collection matches are imported.

Each collection has a `type`. A **page** collection maps each file to one page of the site: Nuxt Content generates its `path` from the file name and adds the fields a page needs, such as `title`, `description` and the parsed `body`. A **data** collection holds structured records that pages read but that have no URL of their own, and its fields are all yours.

`source` says which files belong: a glob, or an object with `include`, `exclude`, a `cwd` folder to search from and, for pages, a path `prefix`. `schema` is a [Zod](https://v3.zod.dev/) object for the fields you add, and it is the source of the collection's TypeScript types. `queryCollection('<name>')` reads a collection.

`content.config.ts` is TypeScript that runs, not a static list, so the collections in it can be computed.

Full reference: [Nuxt Content docs: Define Content Collections](https://content.nuxt.com/docs/collections/define)

## In Terrarium

Each :term[Tenant] states what it holds in one :term[manifest], `layers/<tenant>/tenant.config.ts`: its name, its :term[Spaces]{id="space"}, and its :term[Collections]{id="collection"} with their types and schemas. The Blog's manifest declares one Space per Persona and two Collections that every Space holds, its routed `pages` and its `pingbacks` data:

::excerpt{path="layers/blog/tenant.config.ts" lines="52-57,61-64,85-87"}
```ts
export default defineTenant({
  name: 'blog',
  // Personas-as-Spaces: same content model, physically isolated content per
  // Persona. The slug is the persona's name (layers/blog/GLOSSARY.md: Persona).
  spaces: [...personaSlugs],
  collections: {
    // …
    pages: {
      type: 'page',
      kind: 'page', // opt into the cross-Tenant #catalog (ADR-0025)
      source: '**/*.md',
    // …
    pingbacks: {
      type: 'data',
      source: '**/*.yml',
```
::

:file[shared/manifest.ts] checks each manifest before anything is built from it. Its Zod schema is strict, so a misspelt key fails with a message that names the field, and it refuses a `data` Collection with neither a schema nor a `kind`. Only the Collection named `pages` gets URLs, and the check holds both ways: a `page` Collection by any other name fails, and so does a `pages` Collection that isn't a `page` one.

Then `expand()` in :file[shared/expand.ts] multiplies it out: one Nuxt Content collection for every Tenant, Space and Collection. Each gets a key such as `blog_david_pages` and a folder such as `layers/blog/content/david/pages/`. Tenant, Space and Collection names may hold only lowercase letters and digits, so a key always splits back into its three parts. `expand()` fails the build if two collections share a key.

:file[content.config.ts] holds no list of collections. It turns the expansion into `defineCollection` calls each time Nuxt Content loads it:

::excerpt{path="content.config.ts" lines="20-34"}
```ts
export default defineContentConfig({
  collections: Object.fromEntries(
    expand(loadManifests()).map((c) => [
      c.key,
      // …
      c.type === 'page'
        ? defineCollection({
            type: 'page',
            source: { cwd: dir(c.cwdRel), include: c.include, prefix: '/' },
            schema: c.schema,
          })
```
::

`cwd` points each collection at its own folder, and `prefix: '/'` keeps a page's `path` relative to its Space. The same expansion builds the routing map in :file[modules/routing.ts], which turns an address into one Space's keys.

### Why it's built this way

- **Generated, not hand-written.** By hand, the list of collections would be one shared file every Tenant edits, prone to merge conflicts, where one slip breaks every Tenant. So each Tenant writes a small :term[manifest] and tested code multiplies it out, one collection per Space ([Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation) says why). The cost: one more layer above Nuxt Content. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).
- **Checked manifests.** Each manifest is checked before anything is built from it, so a misspelt key fails at once, naming the field. Unchecked, it could be silently ignored or fail later with a confusing Nuxt build error. ADR-0002 (:file[docs/adr/0002-manifest-driven-config-generation.md]).
- **Built at load time.** `content.config.ts` was once generated and committed, and PRs still failed when a manifest edit skipped regenerating it. Building the list when the config loads makes a stale list impossible. The cost: no file shows the expanded list, and the design relies on Nuxt Content letting the config import the manifests. ADR-0013 (:file[docs/adr/0013-content-config-built-from-manifests.md]).
- **Only `pages` has URLs.** Each Space gets one set of addresses, so the URL scheme, route lookup and smoke test stay simple; everything else is data pages read. The manifest once accepted a `page` Collection under another name, and the smoke test checked addresses routing never served. Now the check ties type to name. ADR-0006 (:file[docs/adr/0006-runtime-routing-path-prefix.md]).

### What to watch for

- **Declare collections only in the manifest.** A collection defined anywhere else, such as in a Tenant's layer, skips `expand()` and its check that every key is unique, the backstop for one table per Space.
- **A page schema holds only the extras.** The `page` type already adds `title`, `description`, `body` and the rest, so a manifest's `pages` schema declares only the Tenant's own fields.
- **The dev server misses manifest edits on its own.** Nuxt Content restarts when `content.config.ts` changes, not when a file it imports does. :file[modules/routing.ts] adds the manifests and `shared/expand.ts` to Nuxt's watch list, which closes that gap for existing Tenants. A brand-new layer folder isn't watched, so restart the dev server after adding a Tenant.

## Try it in your project

If your `content.config.ts` repeats nearly the same `defineCollection` call, say once per language, generate the calls from a list instead, so adding a language is one more entry:

```ts
// content.config.ts
import { defineCollection, defineContentConfig } from '@nuxt/content'

const locales = ['en', 'de']

export default defineContentConfig({
  collections: Object.fromEntries(locales.map((locale) => [
    `docs_${locale}`,
    defineCollection({ type: 'page', source: `${locale}/**/*.md` }),
  ])),
})
```
