Once content sits in a database, every page asks it something: one :term[document] by its address, a list in date order, how many there are. Nuxt Content answers all of these with one query builder, and a few habits decide whether a page stays typed, small and inside its own space.

Know `queryCollection` already? Skip to [In Terrarium](#in-terrarium).

## The concept

`queryCollection('<name>')` starts a query on one collection, a group of content files defined in `content.config.ts`. You chain methods that become SQL, then run it:

- `path(p)` matches a page collection's generated `path`, the usual way to find the page for a route;
- `where(field, operator, value)` filters, with [SQL operators](https://content.nuxt.com/docs/utils/query-collection#wherefield-keyof-collection-string-operator-sqloperator-value-unknown) such as `=`, `<`, `IN`, `LIKE` and `IS NOT NULL`; `andWhere` and `orWhere` group conditions;
- `order(field, 'ASC' | 'DESC')`, `limit(n)` and `skip(n)` sort and page;
- `select(...fields)` returns only the fields you name;
- `all()` returns every match, `first()` the first or `null`, and `count()` the number of matches.

The builder is typed from the collection's schema, so field names and results are checked. In a page you run it inside [`useAsyncData`](https://nuxt.com/docs/4.x/api/composables/use-async-data), so the server renders the result and the browser reuses it. On the server, in an API route, you [pass the request event first](https://content.nuxt.com/docs/utils/query-collection#server-usage): `queryCollection(event, 'docs')`.

Full reference: [Nuxt Content docs: queryCollection](https://content.nuxt.com/docs/utils/query-collection)

## In Terrarium

Terrarium's pages don't write collection names. Every name is a generated key, one per :term[tenant], :term[space] and :term[collection] ([Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation) shows the scheme).

A page inside a space gets its keys from `useSpace`: `pagesKey` for the routed `pages` collection, and `collections.<name>` for each other one. A page above any space calls `resolveSpaceRoute` for each space it shows. A read across tenants takes its keys from the :term[catalog] ([Cross-tenant reads](/t/glassbox/guide/terrarium-practice/cross-tenant-reads)).

The Journal's space landing shows the usual shape: one `useAsyncData`, keyed by the route, holding every query the page needs.

::excerpt{path="layers/journal/app/pages/t/journal/[space]/index.vue" lines="33-41"}
```ts
const { data } = await useAsyncData(route.path, async () => {
  const pages = await queryCollection(pagesKey).all()
  const skills = await queryCollection(collections.skills).all()
  // Newest-first, ordered in SQL rather than re-sorted client-side.
  const sessions = await queryCollection(collections.sessions).order('endedAt', 'DESC').limit(JOURNAL_SESSIONS_LOADED).all()
  const sessionTotal = await queryCollection(collections.sessions).count()
  const routines = await queryCollection(collections.routines).select('name', 'runs').all()
  return { pages, skills, sessions, sessionTotal, routines }
})
```
::

Its `pages` query has no `select`: it fetches whole documents, parsed bodies included. The landing lists the Journal's daily :term[digests]{id="digest"}, and each one opens in place from those documents.

Sorting, capping and counting happen in SQL: the page loads only the newest sessions, and counts all of them without loading them. Filtering and trimming work the same way. Tinkerfund's search, in :file[layers/tinkerfund/app/composables/search.ts], asks for campaign pages whose title or description matches, or whose inventor's name does, and only the four fields it shows. A field that holds an object, such as `campaign`, is stored as JSON text. The inventor test is a `LIKE` on that text, looking for `"inventor":"<stem>"` inside it:

::excerpt{path="layers/tinkerfund/app/composables/search.ts" lines="14-23"}
```ts
    const hits = await queryCollection(pagesKey)
      .where('campaign', 'IS NOT NULL')
      .orWhere((q) => {
        q.where('title', 'LIKE', like).where('description', 'LIKE', like)
        // Frontmatter is stored as JSON text, and a stem is a validated slug.
        for (const { stem } of inventors) q.where('campaign', 'LIKE', `%"inventor":"${stem}"%`)
        return q
      })
      .select('path', 'title', 'description', 'campaign')
      .all()
```
::

One document by address is `queryCollection(pagesKey).path(path).first()`, where `path` is the space-relative path `useSpace` returns. `first()` gives `null` for no match, and for a missing document the page sets a 404 status itself; an unknown space never gets this far, as `useSpace` throws its 404 ([File routing](/t/glassbox/guide/nuxt-vue/file-routing)).

### Why it's built this way

- **Keys from the resolver, not names.** One resolver decides which keys every page gets, and no page writes a collection name; [Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation) says why that keeps spaces apart. ADR-0006 (:file[docs/adr/0006-runtime-routing-path-prefix.md]).
- **Return only what the page reads.** Everything a page's `useAsyncData` returns travels in its payload ([Data fetching](/t/glassbox/guide/nuxt-vue/data-fetching)), so a list `select`s only the fields it shows. The Journal's landing is the deliberate exception: it returns whole pages, so a digest opens in place with no further request. The cost: every digest body ships in the landing's payload. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).
- **Cap and count in SQL.** Every session a Journal landing loads ships in its HTML, and uncapped the page grew to megabytes. The cost: the landing can't list sessions past the cap. :file[layers/journal/app/utils/dashboard.ts].

### What to watch for

- **A key typed as `string` loses its fields.** `queryCollection` takes its result type from the exact type of its key, so a key typed as plain `string` widens the result to every collection's item type (:file[shared/routing.ts]); [File routing](/t/glassbox/guide/nuxt-vue/file-routing) says how a page keeps its keys precise.

## Try it in your project

Write a list page that asks the database for exactly what it shows:

```vue
<script setup lang="ts">
const { data: posts } = await useAsyncData('posts', () =>
  queryCollection('blog')
    .order('date', 'DESC')
    .select('path', 'title', 'date')
    .limit(10)
    .all(),
)
</script>
```

Start the dev server and measure the payload script Nuxt puts in the page's HTML, the one with `id="__NUXT_DATA__"`:

```bash
curl -s http://localhost:3000/ | grep -o '<script[^>]*__NUXT_DATA__[^<]*' | wc -c
```

Delete the `.select(…)` line and run it again. In a test project with twenty short posts, the number grew more than fivefold without `select`, because each post's parsed body came along. A page prerendered with `nuxt generate` keeps that data in a `_payload.json` file beside its HTML instead, so measure that file there.

`queryCollection` returns a flat list of matches, the wrong shape for three jobs that Nuxt Content has helpers for: a collection's navigation tree is [`queryCollectionNavigation`](https://content.nuxt.com/docs/utils/query-collection-navigation), the previous and next items around one page are [`queryCollectionItemSurroundings`](https://content.nuxt.com/docs/utils/query-collection-item-surroundings), and pages split into sections at their headings, for a search index, are [`queryCollectionSearchSections`](https://content.nuxt.com/docs/utils/query-collection-search-sections). Data that sits in no collection, such as another service's API, is out of `queryCollection`'s reach: serve it from a server route instead.
