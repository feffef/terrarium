Content written as Markdown and YAML files has to become something a page can query quickly. Nuxt Content parses the files once, when the site is built, and ships the result; a server that starts later only loads that result, never the files. Knowing where that result lives, on the server and sometimes in the browser, explains what a page costs to load and how it can fail.

Know how Nuxt Content's database works already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content moves content through three places.

**At build time,** it parses every collection's files, creates a table per collection from its schema, inserts the parsed rows and saves the result as a dump: the SQL that rebuilds that table.

**On the server,** nothing is parsed while the site runs. The [first query](https://content.nuxt.com/docs/advanced/database#restoring-dump-on-cold-start) for a collection after the server starts loads that collection's dump into the server's database: SQLite unless the [`database` option](https://content.nuxt.com/docs/getting-started/configuration#database) names another adapter. How each collection gets its own table there is in [Multi-tenant isolation](/t/glassbox/guide/nuxt-content/multi-tenant-isolation). A checksum stored with each table tells Nuxt Content whether the table already matches the build, so a restart with unchanged content doesn't import it again. Which SQLite library runs it is a setting, [`experimental.sqliteConnector`](https://content.nuxt.com/docs/getting-started/configuration#experimentalsqliteconnector); `native` uses the module built into Node 22.5 and later (available without a flag from 22.13), [`node:sqlite`](https://nodejs.org/api/sqlite.html), so no native package has to be compiled.

**In the browser,** a query that runs after the page has loaded, such as one during client-side navigation, doesn't call the server. The [first one](https://content.nuxt.com/docs/advanced/database#wasm-sqlite-in-browser) downloads an SQLite build compiled to WebAssembly and the collection's dump, builds a local database, and answers that query and later ones from it.

Full reference: [Nuxt Content docs: Database](https://content.nuxt.com/docs/advanced/database)

## In Terrarium

Terrarium uses Node's own SQLite:

::excerpt{path="nuxt.config.ts" lines="35-38"}
```ts
  content: {
    // Native node:sqlite (unflagged from Node 22.13) — no better-sqlite3 native build in CI.
    experimental: { sqliteConnector: 'native' },
  },
```
::

The live server runs on the Node 22.16 image that :file[deploy/Dockerfile] pins. That container builds `main` itself and serves the build's output, dumps included.

On the server, Nuxt Content answers queries inside :term[Nitro] ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro)), including each query a page makes while the server renders it. After the server starts, the first query for each :term[collection] compares its table's checksum with the build and restores the table from its dump if they differ.

The browser side is mostly avoided. A link inside the app reads the next page's payload, the data the server rendered for that page, and a typical navigation runs no query in the browser. When the browser database still loads is in [Data fetching](/t/glassbox/guide/nuxt-vue/data-fetching).

When the browser database fails to load, the page doesn't go blank. Space pages mount :file[app/components/ContentLoadErrorDialog.vue] with their `useAsyncData` status, and it hands a failure to :file[app/composables/contentLoadRecovery.ts]: a failed download, of a code chunk or of the database, reloads the page by itself unless that path was reloaded a few seconds ago; a repeat failure, or any other kind, shows a dialog that offers a reload.

### Why it's built this way

- **Reload, not retry.** Pages mostly skip the browser database, but when it fails to load, Nuxt Content remembers the failure and a section stays empty. A patch to Nuxt Content that retries the download was rejected: it must be redone on every upgrade. A full reload always recovers. The cost: a flash and lost unsaved in-page state. ADR-0019 (:file[docs/adr/0019-content-load-error-recovery.md]).
- **Node's own SQLite.** The `native` connector uses the SQLite (a one-file database) built into Node, so CI never compiles a separate package. The cost: the site relies on a feature Node still marks experimental, and every machine that builds or serves it, the live server too ([Continuous deployment](/t/glassbox/guide/deploy/continuous-deployment)), needs a Node that has it. :file[docs/research/nuxt-content-review-grounding.md].

### What to watch for

- **The browser loads a whole collection.** Its first query in the browser downloads the WebAssembly runtime and that collection's entire dump, however few rows it wants. Check the dump's size before you send a page's queries to the browser.
- **The browser keeps dumps in `localStorage`.** In a production build, Nuxt Content caches each downloaded dump there under a `content_` key, on the one origin every tenant shares. A tenant that calls `localStorage.clear()` throws them away; :file[.claude/rules/tenant-layers.md] says to remove only your own keys.
- **Editing a file on the server changes nothing.** The live site reads the dumps of its last build. Content changes reach visitors through `main` and a new build, never through the running server.

## Try it in your project

Build your site and start it with `node .output/server/index.mjs`. Open a fresh private window, or clear the site's storage, since a production build may answer from a dump it cached in `localStorage` and skip the request. Open the browser's network tab, load one page, then follow a link to another page that queries content. Look for a `sql_dump.txt` request under `/__nuxt_content/` and a `.wasm` file: that is the browser database loading, and their sizes are what the first query in the browser costs.
