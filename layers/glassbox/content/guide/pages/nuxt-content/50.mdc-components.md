Markdown covers prose, but now and then a page needs a block that prose can't express: a callout, an interactive dial, an embedded record. MDC lets a writer place a Vue component right in the Markdown file. It is easy to reach for, and a field in frontmatter, the YAML header at the top of the file, often does the same job more safely. Even the plain elements, such as links and code blocks, are drawn by Vue components you can replace, for the whole app or for one render.

Know MDC already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content parses the body of each Markdown file into a tree, stores it with the :term[document] in its database, and `<ContentRenderer>` turns that tree into Vue when the page renders. MDC, short for Markdown Components, is the syntax that adds components to that tree.

A block component opens with `::name` and closes with `::`. What sits between, in ordinary Markdown, fills its default slot: a slot is where a Vue component places content passed in by whoever uses it. A line starting with `#`, such as `#description`, opens a named slot, a second place for content.

Props go in braces after the name, as in `::alert{type="warning"}`, or as YAML between two `---` lines at the top of the block. A component inside a sentence takes one colon, `:name`.

A block can hold another block. Giving the inner one more colons, as in `:::card`, is optional, but it makes each opening easy to pair with its closing line.

The name is kebab-case and finds its component by name: `::phase-note` renders `PhaseNote`. Components in a `content/` folder inside the app's `components/` folder, `app/components/content/` in a Nuxt 4 app or layer, are available to Markdown; any other component must be registered as global first.

Each element plain Markdown produces is drawn by a prose component: a paragraph by `ProseP`, a link by `ProseA`, a fenced code block by `ProsePre`. The stock ones come from `@nuxtjs/mdc`, which Nuxt Content builds on, and a component with the same name in `components/content/` replaces one wherever Markdown renders. For one render only, `<ContentRenderer>` takes a `components` prop, a map from an element such as `table` to the component that draws it; that map wins over a replacement registered for the whole app.

A collection's schema describes frontmatter, the fields Nuxt Content stores as columns you can query. Props inside the body are part of the body tree. They get no column, so you can't query them, and no schema describes them.

Full reference: [Nuxt Content docs: Markdown](https://content.nuxt.com/docs/files/markdown)

## In Terrarium

Atlas and Midden, two :term[tenants]{id="tenant"}, use MDC where a block's place in the prose is the point. An Atlas :term[specimen]'s field note wraps each phase of the creature's year in a `:::phase-note` and cites dated sightings inside it:

::excerpt{path="layers/atlas/content/pool/pages/luciola-mersa.md" lines="141,144-145,148"}
```md
:::phase-note{of="few-lights"}
<!-- … -->
::sighting{date="2026-04-26"}
::
<!-- … -->
:::
```
::

The same page seats its almanac dial above the phase notes with `::almanac`. The Atlas components live in :file[layers/atlas/app/components/content/]. A Midden dig report embeds each catalogued find with `::midden-artifact{slug="…"}`, which :file[layers/midden/app/components/content/MiddenArtifact.vue] looks up in its own :term[space]'s collection. The Journal's routine chart blocks, :file[layers/journal/app/components/content/RoutineChart.vue] among them, are a third use: they read data their page provides.

:file[scripts/gate/validate-content-schema.ts] checks only a Markdown page's frontmatter against its schema. :file[scripts/gate/validate-content-refs.ts] reads these blocks from the body: a `phase-note` must name a phase the page declares, a `sighting` a real entry in the space's ledger, and a `midden-artifact` a real :term[document] in the same space. On an Atlas specimen page, a block left without its closing line fails the check too.

When MDC isn't the answer, Terrarium uses frontmatter. :file[docs/agents/mdc-when-to-use.md] holds the checklist, and its worked example is the Journal's "New here?" cards. Each page a card opens declares that card in frontmatter, and the Journal's :term[collection] schema checks it:

::excerpt{path="layers/journal/tenant.config.ts" lines="154-161"}
```ts
        // Dashboard on-ramp opt-in (the "New here?" cards on the Space landing).
        // A page surfaces itself as a card by setting `onramp` to its sort order
        // (lowest first); `onrampLabel`/`onrampBlurb` carry the card's teaser copy,
        // kept distinct from the page's own title/description. Ordinary pages omit
        // all three. Consumed in app/pages/t/journal/[space]/index.vue.
        onramp: z.number().int().positive().optional(),
        onrampLabel: z.string().optional(),
        onrampBlurb: z.string().optional(),
```
::

:file[.claude/rules/mdc-when-to-use.md] points an agent at the checklist whenever it edits a content component or a manifest.

### Replacing prose components

Terrarium replaces one prose component. :file[app/components/content/ProsePre.vue] sends a `mermaid` code block to the diagram component that [Mermaid pre-rendering](/t/glassbox/guide/nuxt-content/mermaid-pre-rendering) explains, and draws every other block as a plain `<pre>` with its class and content:

::excerpt{path="app/components/content/ProsePre.vue" lines="1-4,11-18"}
```vue
<template>
  <MermaidDiagram v-if="props.language === 'mermaid'" :code="props.code" />
  <pre v-else :class="props.class"><slot /></pre>
</template>
// …
const props = withDefaults(defineProps<{
  code?: string
  language?: string | null
  filename?: string | null
  highlights?: unknown[]
  meta?: string | null
  class?: string | null
}>(), { code: '', language: null, filename: null, highlights: () => [], meta: null, class: null })
```
::

It declares all of the stock component's props and keeps its one style rule; other code blocks render unchanged. It sits in the platform's own `app/`, not in a tenant's layer: Nuxt merges every layer's components into one registry ([Nuxt layers](/t/glassbox/guide/nuxt-vue/layers)), so a prose component in any layer changes that element for every tenant (:file[docs/agents/tenant-layers.md]).

When one tenant wants a different element, it passes `components` to its own `ContentRenderer`. A Journal document page wraps each table in a scrolling box that way:

::excerpt{path="layers/journal/app/pages/t/journal/[space]/[...slug].vue" lines="66-67"}
```vue
    <article v-if="page" class="jd-prose">
      <ContentRenderer :value="page" :components="{ table: JournalScrollTable }" />
```
::

Most tenants need neither. They restyle the rendered elements with CSS scoped under their wrapper class, as the Blog's :file[layers/blog/app/assets/theme.css] does for paragraphs, headings and links.

### Why it's built this way

- **MDC where the prose decides the place.** Writers, mostly agents, compose a page from ready-made blocks without writing Vue, and a block's place in the text is its place on the page. Terrarium uses MDC for such blocks, like the Atlas phase notes. The cost: a typo in a prop shows only when the page renders. :file[docs/agents/mdc-when-to-use.md]
- **Frontmatter where the layout decides.** The Journal's "New here?" cards sit between a space's intro and its daily digests, a place the page layout owns, and a card shows only when its page exists. A body block can't leave the Markdown, so each page declares its card in frontmatter, which the schema checks and the layout reads. :file[docs/agents/mdc-when-to-use.md]

### What to watch for

- **A typo in a prop passes the build.** A misspelt prop renders nothing or the wrong thing. Terrarium's body check covers only the blocks it names; a new component gets none until someone adds it to :file[scripts/gate/validate-content-refs.ts].
- **A missing closing `::` raises no error outside specimen pages.** The block can quietly run on and swallow the text after it, and the page still renders.
- **The block renders where it sits.** A page layout can't move a body block into a sidebar or between sections it draws itself. If the layout decides the place, use a field the layout reads.
- **A prose override is a copy.** If a release of `@nuxtjs/mdc` changes its stock component, the replacement doesn't follow. Compare the two when you upgrade.
- **A component the Markdown never names isn't bundled for it.** Nuxt Content's build lists only the components the content names. The Midden's dig report adds gloss elements, buttons that show what a jargon word means, to the body in code, so it passes `MiddenGloss` through `components` by hand.

## Try it in your project

Find HTML you repeat by hand in your Markdown, such as a warning box. Move it into a component with a slot, then write `::callout{type="warning"}` and a closing `::` around the text instead:

```vue
<!-- components/content/Callout.vue -->
<script setup lang="ts">
defineProps<{ type?: 'note' | 'warning' }>()
</script>

<template>
  <aside :class="['callout', type]"><slot /></aside>
</template>
```

Start the dev server and view the page's source, or inspect it in the browser's developer tools: the block arrives as `<aside class="callout warning">` around a `<p>` holding your text. Misspell the prop as `tpye` and the page still renders, now with `<aside class="callout" tpye="warning">`: the unknown prop became a plain attribute and the warning class is gone. Delete the closing `::` and, in a test, the box ran on to the end of the file, taking in the paragraphs after it. Neither mistake printed a warning in the dev server's log.

Then ask whether the block's data would be safer as a frontmatter field that your schema checks.

To change an element Markdown already produces, such as making external links open in a new tab, copy the stock `ProseA` into `components/content/ProseA.vue` and edit it instead. To change it on one page only, pass it as `:components="{ a: ExternalLink }"` to that page's `ContentRenderer`.
