When several sites share one content database, the worst bug is a page that shows another site's content. Filtering every query by a site column makes each query a chance to forget the filter. Terrarium puts each site's content in tables of its own instead, and hands every page its tables through one lookup, so a page can only see what it was given.

Know how Nuxt Content stores collections already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content keeps your content in an SQLite database. When it builds, it reads each collection's files, creates one table for that collection with columns from its schema, and inserts one row per file. Nothing else shares that table.

A query starts from one collection. [`queryCollection`](https://content.nuxt.com/docs/utils/query-collection) takes the name you gave the collection in `content.config.ts` and builds SQL against that collection's table alone: `where`, `order` and the rest narrow the rows of that one table, and no method joins it to another. Two collections are as separate as two tables, so the collection is the smallest unit of content you can keep apart.

Separate tables keep content apart only if each page asks for the right one. A Vue [composable](https://vuejs.org/guide/reusability/composables.html), a function a component calls from `<script setup>` to reuse logic, can be the one door to them: it does the check and hands back only what passed, so pages that never do the check themselves can't do it differently.

Full reference: [Nuxt Content docs: Database](https://content.nuxt.com/docs/advanced/database)

## In Terrarium

Every :term[Tenant], :term[Space] and :term[Collection] together become one collection, and so one table. Its name is a key that joins the three names:

::excerpt{path="shared/manifest.ts" lines="173-176"}
```ts
/** The collection key — also the SQLite table name and the unit of isolation (ADR-0001). */
export function collectionKey(tenant: string, space: string, collection: string): string {
  return `${tenant}_${space}_${collection}`
}
```
::

So the Blog's David Space keeps its posts under `blog_david_pages`, and Nuxt Content names the table after the key, `_content_blog_david_pages`. How the keys are produced from each manifest is in [Content collections](/t/glassbox/guide/nuxt-content/manifest-collections).

No page builds a key itself. Every page inside a Space, at `/t/<tenant>/<space>/…`, starts by calling `useSpace` in :file[app/composables/space.ts]:

::excerpt{path="app/composables/space.ts" lines="22-30"}
```ts
export function useSpace<T extends string>(tenant: T): SpaceContext<T> {
  const route = useRoute()
  const space = String(route.params.space)
  const resolved = resolveSpaceRoute(tenant, space, route.params.slug)
  if (!resolved) {
    throw createError({ statusCode: 404, statusMessage: `Unknown Tenant/Space: ${tenant}/${space}` })
  }
  return { ...resolved, space }
}
```
::

The composable does only the Nuxt part: it reads the route and turns a failed lookup into a 404. The lookup is `resolveSpaceRoute` in :file[shared/routing.ts], a plain function with no Nuxt in it. It reads only the requested Space's entry in the routing map, which the build writes from the manifests, and returns the keys of that Space's Collections: `pagesKey` for its pages and `collections` for the rest, with the page's `path` inside the Space. A page gets back the keys of exactly one Space, or a 404.

The Platform's catch-all page calls it with whatever Tenant the URL holds; a Tenant's own pages pass their name as a literal, such as `useSpace('journal')`, and get keys typed for that Tenant. Pages above a Space don't use it: a Tenant's root page at `/t/<tenant>`, such as :file[layers/blog/app/pages/t/blog/index.vue], names each Space it shows and calls `resolveSpaceRoute` for it directly.

The :term[Gate] tests both halves. :file[tests/unit/expand.spec.ts] checks that every Tenant, Space and Collection gets its own well-formed key and folder, and :file[tests/unit/routing.spec.ts] checks that a resolved route names only the requested Space's keys. The resolver is on the :term[Human-only]{id="human-only"} list; the composable, which only calls it, is not.

### Why it's built this way

- **One door, no copies.** Pages copied the same steps (read the address, look up the Space, 404 if none), and the copies drifted: one hid a type error, one showed a missing Space a landing page. `useSpace` now holds the steps, so there is one place to get right and one test that no Space reaches another's tables. The cost: every Space page must use it. ADR-0006 (:file[docs/adr/0006-runtime-routing-path-prefix.md]).
- **Isolation without a filter.** Nuxt Content gives each collection its own table, so making every Tenant, Space and Collection one collection builds the wall with no filter to forget. It holds only if pages ask for the right key, which the bullet above covers. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).
- **One repo, one container.** The owner wanted one repo and one container for every Tenant; a database or container per Space was rejected as more to deploy, for isolation not needed. Cost: every build holds every Space, so a Space that must never ship beside another needs its own build. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).
- **Testable resolver.** The lookup first lived in the catch-all page, where no test reached it and a type bug was found only by luck. It became a plain function that a unit test runs without Nuxt. It also serves a Tenant's root page, which can't use `useSpace` ([File routing](/t/glassbox/guide/nuxt-vue/file-routing) says why). :file[tests/unit/routing.spec.ts].
- **Small reviewed core.** A resolver bug could show one Space's Documents in another, so a person merges any change to it ([Protected files](/t/glassbox/guide/terrarium-practice/human-only-list)). The composable decides nothing and keeps the Nuxt glue out of the resolver, so it merges like other code and the reviewed part stays small. The cost: even a type fix in the resolver waits for a human. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **Separate is not secret.** Every build holds every Space, and Nuxt Content serves each collection's dump at its own URL so the browser can load it. Anyone can fetch any Space's content; the tables only stop a page from showing it by mistake.
- **Take keys from `useSpace`, never from a string.** A key typed into a page, such as `` `blog_${space}_pages` ``, skips the resolver and its tests. A page that reads another Space calls `resolveSpaceRoute` once per Space, as the Blog's network footer does in :file[layers/blog/app/components/blog/Network.vue]. A key built by hand or read off the routing map skips the one check the tests cover.
- **A plain string widens the types.** The catch-all passes a `string`, so its keys are a union over every Tenant. In a Tenant's own page, pass the literal name, or the fields its template reads won't type-check.
- **The 404 covers the Space, not the Document.** `useSpace` throws only for an unknown Tenant or Space. A path with no Document in a known Space resolves fine, and the page decides what to show.
- **A rename moves the content.** The key is made of the three names, so renaming a Tenant, Space or Collection gives it a new table and a new folder under `layers/<tenant>/content/`, and a Space's or Tenant's rename changes its URLs too.
- **Reads across Tenants are opt-in.** A Collection opts in by naming a shared :term[kind]{id="collection-kind"}, and such reads go only through the :term[Catalog] (ADR-0025, :file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

## Try it in your project

Start your Nuxt Content dev server once, then list the tables in its database with Node's built-in SQLite module (Node 22.13 or later; it may print an ExperimentalWarning), by running this file with `node tables.mjs` from the project root. You should see one `_content_<name>` table per collection in your `content.config.ts`, plus Nuxt Content's own `_content_info` and `_development_cache`:

```js
// tables.mjs
import { DatabaseSync } from 'node:sqlite'

const db = new DatabaseSync('.data/content/contents.sqlite')
console.log(db.prepare("SELECT name FROM sqlite_master WHERE type = 'table'").all())
```

Then put the step every page repeats, such as picking the collection from the route, in one composable, and check that a page with an unknown route gets a 404.
