When several sites share one content database, the worst bug is a page that shows another site's content. Filtering every query by a site column makes each query a chance to forget the filter. Terrarium puts each site's content in tables of its own instead, so a query for one site has nothing else to return.

Know how Nuxt Content stores collections already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content keeps your content in an SQLite database. When it builds, it reads each collection's files, creates one table for that collection with columns from its schema, and inserts one row per file. Nothing else shares that table.

A query starts from one collection. [`queryCollection`](https://content.nuxt.com/docs/utils/query-collection) takes the name you gave the collection in `content.config.ts` and builds SQL against that collection's table alone: `where`, `order` and the rest narrow the rows of that one table, and no method joins it to another. Two collections are as separate as two tables, so the collection is the smallest unit of content you can keep apart.

Full reference: [Nuxt Content docs: Database](https://content.nuxt.com/docs/advanced/database)

## In Terrarium

Every :term[Tenant], :term[Space] and :term[Collection] together become one collection, and so one table. Its name is a key that joins the three names:

::excerpt{path="shared/manifest.ts" lines="173-176"}
```ts
/** The collection key — also the SQLite table name and the unit of isolation (ADR-0001). */
export function collectionKey(tenant: string, space: string, collection: string): string {
  return `${tenant}_${space}_${collection}`
}
```
::

So the Blog's David Space keeps its posts under `blog_david_pages`, and Nuxt Content names the table after the key, `_content_blog_david_pages`. Each row is one :term[Document]. How the keys are produced from each manifest is in [Content collections](/t/glassbox/guide/nuxt-content/manifest-collections).

A page queries only the keys it is handed for its Space. No page builds a key itself: it calls `useSpace`, which reads the Space from the address and returns that Space's keys, or a 404 ([File routing](/t/glassbox/guide/nuxt-vue/file-routing) shows it). :file[tests/unit/expand.spec.ts] checks that every Tenant, Space and Collection gets its own well-formed key and folder.

### Why it's built this way

- **Isolation without a filter.** A shared table needs a site filter in every query, and one forgotten filter leaks a site. Making every Tenant, Space and Collection one collection, so one table, builds the wall with no filter to forget. The cost: it holds only if pages ask for the right key, so one lookup hands keys out. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).
- **One repo, one container.** The owner wanted one repo and one container for every Tenant; a database or container per Space was rejected as more to deploy, for isolation not needed. The cost: every build holds every Space, so a Space that must never ship beside another needs its own build. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

### What to watch for

- **Separate is not secret.** Every build holds every Space, and Nuxt Content serves each collection's dump at its own URL so the browser can load it. Anyone can fetch any Space's content; the tables only stop a page from showing it by mistake.
- **Take keys from the lookup, never from a string.** A key typed into a page, such as `` `blog_${space}_pages` ``, skips the lookup and its tests. A page that reads another Space calls `resolveSpaceRoute` once per Space, as the Blog's network footer does in :file[layers/blog/app/components/blog/Network.vue].
- **A rename moves the content.** The key is made of the three names, so renaming a Tenant, Space or Collection gives it a new table and a new folder under `layers/<tenant>/content/`, and a Space's or Tenant's rename changes its URLs too.
- **Reads across Tenants are opt-in.** A Collection opts in by naming a shared :term[kind]{id="collection-kind"}, and such reads go only through the :term[Catalog] (ADR-0025, :file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

## Try it in your project

Start your Nuxt Content dev server once, then list the tables in its database with Node's built-in SQLite module (Node 22.13 or later; it may print an ExperimentalWarning), by running this file with `node tables.mjs` from the project root. You should see one `_content_<name>` table per collection in your `content.config.ts`, plus Nuxt Content's own `_content_info` and `_development_cache`:

```js
// tables.mjs
import { DatabaseSync } from 'node:sqlite'

const db = new DatabaseSync('.data/content/contents.sqlite')
console.log(db.prepare("SELECT name FROM sqlite_master WHERE type = 'table'").all())
```
