Content written as Markdown and YAML files has to become something a page can query quickly. Nuxt Content does that work once, when the site is built, and ships the result. Knowing where that result lives, on the server and sometimes in the browser, explains what a page costs to load and how it can fail.

Know how Nuxt Content's database works already? Skip to [In Terrarium](#in-terrarium).

## The concept

Nuxt Content moves content through three places.

**At build time,** it parses every collection's files, creates a table per collection from its schema, inserts the parsed rows and saves the result as a dump: the SQL that rebuilds that table.

**On the server,** nothing is parsed while the site runs. The first query for a collection after the server starts loads that collection's dump into the server's SQLite database. A checksum stored with each table tells Nuxt Content whether the table already matches the build, so a restart with unchanged content doesn't import it again. Which SQLite library runs it is a setting, `experimental.sqliteConnector`; `native` uses the module built into Node 22.5 and later (unflagged from 22.13), [`node:sqlite`](https://nodejs.org/api/sqlite.html), so no native package has to be compiled.

**In the browser,** a query that runs after the page has loaded, such as one during client-side navigation, doesn't call the server. The first one downloads an SQLite build compiled to WebAssembly and the collection's dump, builds a local database, and answers that query and later ones from it.

Full reference: [Nuxt Content docs: Database](https://content.nuxt.com/docs/advanced/database)

## In Terrarium

Terrarium uses Node's own SQLite:

::excerpt{path="nuxt.config.ts" lines="30-33"}
```ts
  content: {
    // Native node:sqlite (unflagged from Node 22.13) — no better-sqlite3 native build in CI.
    experimental: { sqliteConnector: 'native' },
  },
```
::

The live server runs on a Node 22 image, pinned in :file[deploy/Dockerfile]. That container builds `main` itself and serves the build's output, dumps included, so content changes only when a new build goes live.

The server side runs inside :term[Nitro] whenever a page renders there. After the server starts, the first query for each Collection compares its table's checksum with the build and restores the table from its dump if they differ.

The browser side is mostly avoided. A link inside the app reads a payload the server rendered for that route, the data its `useAsyncData` returned, so a typical navigation runs no query in the browser. The browser database loads only where that payload doesn't exist or doesn't hold the data: a route that opts out of the server's page cache, such as Tinkerfund's search ([Nitro: the server under Nuxt](/t/glassbox/guide/nuxt-vue/nitro) shows the rule), a query that re-runs after the page has mounted, and a payload that fails to download.

When the browser database fails to load, the page doesn't go blank. Space pages mount :file[app/components/ContentLoadErrorDialog.vue] with their `useAsyncData` status, and it hands a failure to :file[app/composables/contentLoadRecovery.ts]: a failed download reloads the page once; a second failure, or any other kind, shows a dialog that offers a reload.

### Why it's built this way

Nuxt Content reads files when the site is built and has no supported way to add collections or switch databases while it runs. Terrarium works with that instead of around it: every Tenant's content is built into one database, and adding a page or a Tenant is a file edit that goes through the same PR and gate as code. The cost is that content can't change while the site runs, and every build holds every Space. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

Because content is baked in, keeping the site current means building again after every merge. Running that build inside the serving container avoids a pipeline that publishes an image and a redeploy for each content edit. It builds beside the live copy and switches only when the build succeeds, so a bad commit can't take the site down. The price is a full rebuild for every update, which needs a lot of memory. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).

The owner wants pages to keep building in the browser, so view transitions and in-memory state such as Tinkerfund's cart survive a click. But a query in the browser downloads the WebAssembly runtime and a whole dump, which is heavy and is where content loads fail, and Nuxt Content has no setting to send those queries to the server. Server payloads need only documented Nuxt settings and made measured navigations several to dozens of times lighter; full page loads were rejected because they lose transitions and state. The cost is a server page cache, so a page that reads a request header must say so. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md]).

When the browser database fails to load, for example because the server restarted mid-navigation, Nuxt Content remembers the failure for the rest of the page's life, and a section stays empty. Terrarium once patched the library to retry, but the patch was tied to one version's compiled code and had to be redone on every upgrade, so it was dropped. A full reload always recovers, because the server renders a fresh page; the cost is a flash and the loss of unsaved in-page state. ADR-0019 (:file[docs/adr/0019-patched-nuxt-content-client-db-loading.md]).

The `native` connector uses the SQLite built into Node, so CI never has to compile the `better-sqlite3` package. In exchange the site depends on a feature Node still marks experimental, and every machine that builds or serves it must run a Node version that has it. :file[docs/research/nuxt-content-review-grounding.md]

### What to watch for

- **The browser loads a whole Collection.** Its first query in the browser downloads the WebAssembly runtime and that Collection's entire dump, however few rows it wants. Check the dump's size before you send a page's queries to the browser.
- **The browser keeps dumps in `localStorage`.** In a production build, Nuxt Content caches each downloaded dump there under a `content_` key, on the one origin every Tenant shares. A Tenant that calls `localStorage.clear()` throws them away; :file[.claude/rules/tenant-layers.md] says to remove only your own keys.
- **Editing a file on the server changes nothing.** The live site reads the dumps of its last build. Content changes reach visitors through `main` and a new build, never through the running server.

## Try it in your project

Build your site and start it with `node .output/server/index.mjs`. Open the browser's network tab, load one page, then follow a link to another page that queries content. Look for a `sql_dump.txt` request under `/__nuxt_content/` and a `.wasm` file: that is the browser database loading, and their sizes are what the first query in the browser costs.
