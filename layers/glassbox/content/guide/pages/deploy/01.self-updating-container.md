A merge to `main` should reach the live site without anyone running a deploy, and a commit that fails to build should never take the site down. Terrarium gets both from one container that watches `main`, builds each new commit itself, and swaps only a build that worked.

Know Docker Compose and Nuxt's server build already? Skip to [In Terrarium](#in-terrarium).

## The concept

`nuxt build` with the default Node server preset has :term[Nitro] write a standalone server to `.output/`. You start it with `node .output/server/index.mjs`; it reads its port and host from the `PORT` and `HOST` environment variables. The [Nuxt deployment guide](https://nuxt.com/docs/4.x/getting-started/deployment) has the details.

The usual way to ship that server is an image per release: CI builds the app into a container image, and the server pulls and runs the new image. The other way round is an image that holds only tools. The container clones the repo itself, builds it, serves the result, and checks the branch for new commits. Building into a separate folder and copying over the served one only when the build succeeds keeps a broken commit away from visitors.

Docker Compose describes such a container in one YAML file: its image, its restart policy, a volume that keeps its files across restarts, the networks it joins and a health check. `docker compose up` starts it. A reverse proxy such as [Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy) usually sits in front, takes the HTTPS traffic for a domain and passes it to the container.

Full reference: [Docker Compose overview](https://docs.docker.com/compose/)

## In Terrarium

Terrarium's image, :file[deploy/Dockerfile], holds Node, git, rsync and one script; no Terrarium source is copied in. The script, :file[deploy/entrypoint.sh], clones `main` into a volume, installs and builds it, copies `.output` into a separate serve folder and starts Node from there. Then it loops: it fetches `main`, and when a new commit has arrived it resets the checkout, reinstalls only if the lockfile changed, and builds while the old server keeps answering. Only a build that succeeds replaces the served copy:

::excerpt{path="deploy/entrypoint.sh" lines="153-159"}
```bash
  if build; then
    publish
    restart_server
    log "update applied — now serving $remote_rev"
  else
    log "build FAILED for $remote_rev — keeping previous build live (will retry on next commit)"
  fi
```
::

The script deliberately leaves out `set -e`, so one failing command can't end the loop and the site with it. A failed install also keeps the last good build live, and if Node itself dies, the next pass of the loop starts it again from that build.

:file[deploy/docker-compose.yml] runs the one service. It publishes no port on the host; it only exposes Node's port on a shared Docker network, `web`, where the host's existing Caddy proxy forwards Terrarium's domain to it:

::excerpt{path="deploy/docker-compose.yml" lines="27-35"}
```yaml
    expose:
      # Internal only. The shared Caddy proxies `terrarium.feffef.de` -> terrarium:3000.
      - "3000"
    volumes:
      # …
      - terrarium_app:/app
    networks:
      - web
```
::

The volume keeps the checkout, the pnpm store and the served build, so a restarted container picks up where it left off. The repo token reaches git through `GIT_ASKPASS` and is never written into the checkout's config. :file[deploy/README.md] covers setting it up on the server.

### Why it's built this way

All content is baked into the build, so keeping the site current means building again after every merge. The only question was where that build runs. The usual answer, CI building a new image for each release and the server redeploying it, would need a publish pipeline and a redeploy for every one-word edit. Building inside the serving container needs neither. The cost is that no fixed image pins what is live, so there is nothing to roll back to, and every update is a full build that needs a lot of memory. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).

With no step between a merge and the server, a broken commit would otherwise reach visitors at once. Building beside the live copy and swapping only on success means the site only ever moves between builds that worked, and a bad commit fixes itself when a good one follows. The same rule had to cover installs too: a reviewer once found that after a failed install the script would skip installing on the next commit and build against old packages, so it now records the last install that worked. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).

The site lives on one server that already hosts other apps behind a shared Caddy proxy, and their host ports were already taken. Joining Caddy's network and publishing no port fits Terrarium in the way those apps are reached, with nothing new opened on the host. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).

The container needs a token to clone a private repo, and its checkout lives on a volume that outlasts the container. Handing the token to git only when git asks for it keeps it out of the checkout's config, so a copied or inspected volume doesn't leak it. The token is also read-only and limited to this one repo, so even a leaked one can't push. :file[deploy/entrypoint.sh]

One app and one image serve every :term[Tenant]{id="tenant"}, because the owner wants one thing to run, not a container per Tenant or :term[Space]{id="space"}. So one build updates every Tenant at once, and the cost is that each build carries every Space's content, even one a visitor never opens. ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

### What to watch for

- **Merging is deploying.** No step sits between a merge and the live site, so the checks before the merge are the only ones. See [The Gate](/t/glassbox/guide/terrarium-practice/gate).
- **A change to `deploy/` doesn't deploy itself.** The container runs the image the operator built; a merged change to the Dockerfile or the script waits until they rebuild it by hand, as :file[deploy/README.md] says.
- **The swap is a copy and a restart.** The new build is copied over the served folder and Node restarts, so each update has a short gap while the new server starts.
- **`NODE_ENV` is set in one place.** The script starts the server with `NODE_ENV=production` beside `HOST` and `PORT`; a server started some other way, such as by hand in the container, needs it too.
- **Every update is a full build.** Content is baked into the build, so even a one-word edit rebuilds the whole site, and a build needs a lot of memory. A build killed for lack of memory just doesn't swap.

## Try it in your project

Run your app's production build twice in a row, the second time after breaking one file on purpose. Check that whatever serves your site would still be serving the first build, and if it wouldn't, build into a separate folder and copy only on success.
