`package.json` names version ranges, so two installs a week apart can get different packages. A lockfile records the exact version of every package, direct or indirect, and an install that follows it gets the same tree each time. Terrarium commits `pnpm-lock.yaml`, and both the gate in CI (continuous integration, the checks a server runs on each pushed change) and the live container refuse to install when it disagrees with `package.json`.

Know pnpm and lockfiles already? Skip to [In Terrarium](#in-terrarium).

## The concept

A package manager reads each range in `package.json`, such as `^3.25.76`, picks one version, and does the same for every package those depend on. The lockfile writes the result down: every package's exact version and an integrity hash, a checksum of the package's contents. Committed, it lets each install repeat the tree you tested instead of resolving again ([pnpm: Working with Git](https://pnpm.io/10.x/git)).

A frozen install is the strict form. With [`pnpm install --frozen-lockfile`](https://pnpm.io/10.x/cli/install#--frozen-lockfile), pnpm never writes the lockfile and fails if it doesn't match `package.json`. In CI, pnpm installs frozen by default; a plain `pnpm install` anywhere else updates the lockfile to match instead.

Which pnpm a project expects is the `packageManager` field of `package.json`, and pnpm reads it. So does [Corepack](https://github.com/nodejs/corepack#readme), a tool that fetches and runs the package manager a project names, without your installing it.

Full reference: [pnpm docs: Settings](https://pnpm.io/10.x/settings)

## In Terrarium

:file[package.json] pins pnpm itself:

::excerpt{path="package.json" lines="5"}
```json
  "packageManager": "pnpm@10.33.0",
```
::

In CI, [pnpm/action-setup](https://github.com/pnpm/action-setup), the GitHub Action that installs pnpm, reads that field when it is given no version. The live container starts from an image, the packaged file that holds its tools, and that image turns on Corepack, which reads the field too (:file[deploy/Dockerfile]). Each range in `package.json` resolves to one exact version in :file[pnpm-lock.yaml]:

::excerpt{path="pnpm-lock.yaml" lines="17-19"}
```yaml
      zod:
        specifier: ^3.25.76
        version: 3.25.76
```
::

Terrarium installs in three places: CI, the live container and a contributor's own checkout. Two of the three installs are frozen and refuse a lockfile that disagrees. The first is the install step in :file[.github/actions/gate/action.yml], where CI runs the :term[gate]:

::excerpt{path=".github/actions/gate/action.yml" lines="24-26"}
```yaml
    - name: Install
      shell: bash
      run: pnpm install --frozen-lockfile
```
::

The second is the live container's install in :file[deploy/entrypoint.sh], into a pnpm store, the folder where pnpm saves downloaded packages, on its volume:

::excerpt{path="deploy/entrypoint.sh" lines="57-62"}
```bash
install_deps() {
  rm -f "$INSTALLED_HASH"
  log "pnpm install (frozen lockfile)…"
  ( cd "$REPO_DIR" && pnpm install --frozen-lockfile --store-dir "$STORE_DIR" ) &&
    lockhash > "$INSTALLED_HASH"
}
```
::

It runs at first boot, and after a new commit only when the lockfile's hash differs from the one saved by the last good install ([Continuous deployment](/t/glassbox/guide/deploy/continuous-deployment) follows that loop).

The third, a contributor's local install, is plain: it updates the lockfile rather than fail. Each Claude Code session starts with `pnpm install` (:file[.claude/settings.json]). `pnpm gate:scoped`, the command that runs the gate's checks locally, also runs `pnpm install` before its first check when `package.json` or the lockfile has changed since the last install. It tells by comparing their file times with that of `node_modules/.pnpm`, the folder pnpm's last install wrote (:file[scripts/gate/gate.ts]).

The repo has no `pnpm-workspace.yaml` or `.npmrc`, and `package.json` has no `pnpm` field: pnpm runs on its defaults. Since pnpm 10, those skip every dependency's install scripts, the commands a package may run as it is installed. pnpm's docs give the reason: most compromised packages have used such a script to run their code the moment they are installed ([pnpm: Supply chain security](https://pnpm.io/10.x/supply-chain-security)). [`pnpm ignored-builds`](https://pnpm.io/10.x/cli/ignored-builds) prints the packages whose scripts it skipped.

A person must merge any PR that changes `package.json`: the file is on the human-only list ([Protected paths](/t/glassbox/guide/terrarium-practice/protected-paths)). `pnpm-lock.yaml` is not on it.

### Why it's built this way

- **Install what the gate tested.** A rewritten lockfile is a tree nobody committed, so the gate and the container both install frozen. CI defaults to that, so the gate's flag only states it; in the container, which isn't CI, a plain install would rewrite the lockfile instead of failing. The cost: a `package.json` edit without a matching lockfile fails the gate at its install step. :file[.github/actions/gate/action.yml] and :file[deploy/entrypoint.sh].
- **A new package is new code on the server.** Every merge runs on the server, its install and build included. The gate checks only that the app builds and passes its tests; it can't tell what a package's code sets out to do. So a person merges a PR that adds a dependency. The cost: even a dev-only tool waits for a person. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).
- **A stale install looks like a real break.** Agents took type errors from an old `node_modules` for a broken `main`. `pnpm gate:scoped` now installs first when the manifest or lockfile is newer than the install. The cost: that install isn't frozen, so it can rewrite the lockfile. :file[scripts/gate/gate.ts].

### What to watch for

- **Commit `package.json` and the lockfile together.** A range changed by hand, with no `pnpm install` after it, stops the gate's install with `ERR_PNPM_OUTDATED_LOCKFILE`. `pnpm add` and `pnpm remove` change both files at once.
- **Don't fix the lockfile by hand.** After a merge conflict in `pnpm-lock.yaml`, run `pnpm install` and pnpm resolves it; read the diff before you commit, since it may not choose the side you meant ([pnpm: Merge conflicts](https://pnpm.io/10.x/git#merge-conflicts)).
- **Import only what you declare.** pnpm puts only a project's direct dependencies at the top of `node_modules` ([pnpm: Motivation](https://pnpm.io/10.x/motivation)), so a package that only a dependency brings in isn't there to import. :file[shared/expand.ts] imports jiti, a TypeScript loader that Nuxt Content also uses, and `package.json` declares it. Adding one with `pnpm add -D` changes `package.json`, so a person merges the PR.
- **Two commands write `pnpm-workspace.yaml`.** `pnpm patch-commit` records a patched package there, and [`pnpm approve-builds`](https://pnpm.io/10.x/cli/approve-builds) records the dependencies allowed to run install scripts. The file isn't on the human-only list of paths that the merge script checks, so a PR that changes only that file isn't refused ([Protected paths](/t/glassbox/guide/terrarium-practice/protected-paths#what-to-watch-for)).
- **A `pnpm patch` must be redone at every upgrade.** It edits one version's built code; [Content database](/t/glassbox/guide/nuxt-content/content-database) says why Terrarium dropped its patch of Nuxt Content.
- **pnpm.io's unversioned pages describe a newer major.** Its settings can differ, so read the versioned pages for the major that `packageManager` names, such as `/10.x/`.

## Try it in your project

In a project with a committed `pnpm-lock.yaml`, change one dependency's range in `package.json` without installing, then run `pnpm install --frozen-lockfile`. It should stop with `ERR_PNPM_OUTDATED_LOCKFILE` and name the package, with the lockfile's range and yours. Undo the edit, then run `pnpm ignored-builds` to see which dependencies' install scripts pnpm skipped.
