A merge should reach the live site without anyone running a deploy, and a commit that fails to build should never replace the live copy. Continuous deployment gives both. Terrarium does it with one container that watches `main` and keeps two folders: a checkout, where it builds each new commit, and a serve folder, which holds the live copy. A new build replaces the live copy only after it succeeds.

Know continuous deployment already? Skip to [In Terrarium](#in-terrarium).

## The concept

Continuous deployment ships every change merged to the main branch to the live site automatically, with no release step a person runs. It is only safe if a change that fails to build can't take the site down: build the new version beside the running one, and switch over only when the build succeeds.

A container starts from an image, the packaged file that holds everything the container runs. Terrarium uses an image that holds only tools: the container clones the repo itself, builds it, serves the result, and checks the branch for new commits. The more usual way is an image per release: CI (continuous integration, the automation a server runs on each pushed change) builds the app into a new image, and the server pulls and runs it. For a Nuxt app, the build is one server folder, `.output/`, started with `NODE_ENV=production node .output/server/index.mjs` ([Nitro server engine](/t/glassbox/guide/nuxt-vue/nitro) shows what it holds; the [Nuxt deployment guide](https://nuxt.com/docs/4.x/getting-started/deployment#entry-point) has the details).

[Docker Compose](https://docs.docker.com/compose/) describes such a container in one YAML file, with the [volume](https://docs.docker.com/reference/compose-file/volumes/) that keeps its files across restarts, and [`docker compose up`](https://docs.docker.com/reference/cli/docker/compose/up/) starts it. A reverse proxy, a web server that routes each request to the right app, such as [Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy), usually sits in front and [passes a domain's HTTPS traffic](https://caddyserver.com/docs/quick-starts/reverse-proxy#https-from-client-to-proxy) to it.

Full reference: [Wikipedia: Continuous deployment](https://en.wikipedia.org/wiki/Continuous_deployment)

## In Terrarium

Terrarium's image, :file[deploy/Dockerfile], holds Node, git, rsync and one script; no Terrarium source is copied in. It also turns on [Corepack](https://github.com/nodejs/corepack#readme), a Node tool that supplies the pnpm version `package.json` names. The script, :file[deploy/entrypoint.sh], clones `main` into a volume, a folder on the host that Docker manages and that outlasts the container, installs and builds it in the checkout, copies `.output` into the serve folder and starts Node from there.

Then it loops. It fetches `main`, which downloads new commits without touching the checkout's files. When `main` has moved, it resets the checkout to the newest commit (`git reset --hard`, which makes every file match that commit); commits merged between two fetches are built together, not one by one. It reinstalls only if the lockfile changed since the last good install ([pnpm and the lockfile](/t/glassbox/guide/deploy/pnpm-lockfile) shows how), and builds while the old server keeps answering. Only a build that succeeds replaces the served copy:

::excerpt{path="deploy/entrypoint.sh" lines="153-159"}
```bash
  if build; then
    publish
    restart_server
    log "update applied — now serving $remote_rev"
  else
    log "build FAILED for $remote_rev — keeping previous build live (will retry on next commit)"
  fi
```
::

A failed build sends `if build; then` to its `else` branch, which only logs the failure: the serve folder and the running server stay as they were, and the loop goes on to the next pass. The script leaves out `set -e`, the bash option that stops a script at its first failing command, and checks the critical steps itself instead. A failed install also keeps the last good build live. Each pass of the loop first checks that the Node it started is still running, and if it has died, starts it again from the serve folder.

:file[deploy/docker-compose.yml] runs the one service. It publishes no port on the host, the machine the containers run on. Its `expose` entry opens Node's port 3000 only to other containers on a shared Docker network called `web`.

The host already runs Caddy, and Caddy sits on that network too. The comment in the excerpt states Caddy's rule: requests for Terrarium's domain, `terrarium.feffef.de`, go to port 3000 of the `terrarium` service:

::excerpt{path="deploy/docker-compose.yml" lines="27-35"}
```yaml
    expose:
      # Internal only. The shared Caddy proxies `terrarium.feffef.de` -> terrarium:3000.
      - "3000"
    volumes:
      # …
      - terrarium_app:/app
    networks:
      - web
```
::

The volume keeps the checkout, the pnpm store and the served build, so a restarted container picks up where it left off. The repo token reaches git through `GIT_ASKPASS`, a program git runs when it needs a password, and is never written into the checkout's config. :file[deploy/README.md] covers setting it up on the server.

### Why it's built this way

- **Build in the container.** Content is built in ([Content database](/t/glassbox/guide/nuxt-content/content-database)), so every merge needs a new build. CI building an image per release would add a publishing pipeline and redeploy to every edit; building in the container needs neither. The cost: no saved image to roll back to, and a full build for every update (below). ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).
- **Swap only good builds.** A broken commit would reach visitors at once, so a failed build leaves the live copy alone (above); the next good commit cures a bad one. Installs follow suit: one failed install once left the next build on old packages, so the script records the last good install. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).
- **Shared server, no new port.** Other apps on the server already hold the host ports and sit behind a shared Caddy proxy. Terrarium joins Caddy's network and publishes no port, so nothing new opens on the host. ADR-0011 (:file[docs/adr/0011-poc-self-updating-deploy-container.md]).
- **Token kept out of the checkout.** Cloning a private repo needs a token, and the checkout sits on a volume that outlasts the container. Handing the token to git only when asked keeps it out of the checkout's settings, so a copied volume doesn't leak it. The setup also asks for a read-only token limited to this repo, so a leak can't push. :file[deploy/entrypoint.sh] and :file[deploy/README.md].

### What to watch for

- **Merging is deploying.** No person or review sits between a merge and the live site. After the merge, the container checks only that the install and build succeed; every other check has to run before the merge. See [Merge gate](/t/glassbox/guide/verification/gate).
- **The container's own files are the exception.** Merges to the app go live by themselves, but the container runs the image the operator, the person who runs the host, built by hand. A merged change to the Dockerfile or the script waits until they rebuild that image, as :file[deploy/README.md] says.
- **The swap is a copy and a restart.** The new build is copied over the served folder and Node restarts, so each update has a short gap while the new server starts.
- **Every update is a full build.** Content is baked into the build, so even a one-word edit rebuilds the whole site, and a build needs a lot of memory. A build killed for lack of memory just doesn't swap.

## Try it in your project

Save this as `deploy.sh` next to your `package.json`. It builds into `.output/`, a Nuxt app's build folder (use your framework's), and copies that into `serve/` only when the build succeeds:

```sh
#!/bin/sh
npm run build && rsync -a --delete .output/ serve/
```

Run it, then start your server from `serve/` (for Nuxt, `node serve/server/index.mjs`). Break one file on purpose and run the script again: the build fails and prints its error, `&&` skips the copy, and `ls -l serve/` shows the same file times as before, so the running server still holds the first build. Fix the file and run it once more: `serve/` now holds the new build, which the server shows once you restart it.
