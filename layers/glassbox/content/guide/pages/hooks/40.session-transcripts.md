Claude Code writes each session to a file as it runs: every prompt, reply, tool call and tool result. Every hook is handed that file's path, so it can check what the session has already done instead of relying on what the model remembers.

Know session transcripts already? Skip to [In Terrarium](#in-terrarium).

## The concept

A session transcript is a JSON Lines file, one JSON object per line, at `~/.claude/projects/<project>/<session>.jsonl`. It holds the conversation's messages, tool calls and tool results, and also the system prompt, tool definitions and request parameters Claude Code sent the model. A subagent's transcript sits in that session's `subagents/` folder, in the same format.

Every hook gets the path as `transcript_path` in its JSON on stdin, beside `session_id`, `cwd` and `hook_event_name` ([Common input fields](https://code.claude.com/docs/en/hooks#common-input-fields)). A hook that fires inside a subagent also gets `agent_id` and `agent_type`.

Each line is one record with a `type`, such as `user`, `assistant` or `attachment`. A `user` or `assistant` record carries its `timestamp`, `sessionId`, `cwd`, `gitBranch` and Claude Code `version`, and a `message` whose `content` is a list of blocks. A tool call is a `tool_use` block, with an `id`, in an assistant message; its result is a `tool_result` block in a later user record that names the same `tool_use_id`, sometimes several records later.

The docs warn that the file is written asynchronously and may lag the conversation, so when a hook fires it may not yet hold the current turn's latest messages. A `Stop` hook that needs the turn's final reply should read `last_assistant_message` from its payload instead.

Full reference: [Claude Code docs: Application data](https://code.claude.com/docs/en/claude-directory#application-data)

## In Terrarium

Terrarium's hooks read the transcript through `readTranscript` in :file[scripts/hooks/hook-io.ts], except :file[scripts/hooks/github-provenance-guard.ts], which reads the file itself and parses it with the same `parseTranscript`. That parser skips any line that isn't valid JSON, such as a half-written last line, and `readTranscript` returns `null` when the file is missing or unreadable:

::excerpt{path="scripts/hooks/hook-io.ts" lines="84-93"}
```ts
/** The session transcript at `path`, parsed. `null` for a missing path or an
 *  unreadable file — which a fail-closed guard denies on. */
export function readTranscript(path: string | undefined): Record<string, unknown>[] | null {
  if (!path) return null
  try {
    return parseTranscript(readFileSync(path, 'utf8'))
  } catch {
    return null
  }
}
```
::

What `null` leads to depends on the reader. A guard such as :file[scripts/hooks/skill-inline-guard.ts] denies the call ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks)). Hints differ: :file[scripts/hooks/adr-read-hint.ts], and :file[scripts/hooks/read-first-hint.ts] in the main agent, stay silent, while `read-first-hint` in a subagent and :file[scripts/hooks/bash-rules-hint.ts] turn `null` into an empty list and still fire, as if nothing had been read.

**Hints.** :file[scripts/hooks/read-first-hint.ts] and :file[scripts/hooks/adr-read-hint.ts] point to a doc only if the transcript shows no read of it and no earlier `hook_additional_context` attachment, the record that holds what a hook added, with the same pointer ([Hook-added context](/t/glassbox/guide/hooks/hook-added-context)). In a [subagent](/t/glassbox/guide/agents/subagents), `transcript_path` still names the parent's file, which holds none of the subagent's records, so the hint opens the subagent's own file by its `agent_id`:

::excerpt{path="scripts/hooks/read-first-hint.ts" lines="111-112,119-123"}
```ts
  const parent = prop(payload, 'transcript_path')
  const agent = prop(payload, 'agent_id')
  // …
  let records: Record<string, unknown>[] | null
  if (typeof parent !== 'string') records = dryRun && parent === undefined ? [] : null
  else if (agent === undefined) records = readTranscript(parent)
  else records = readTranscript(agentTranscript(parent, String(agent))) ?? []
  if (!records) return null
```
::

**The `Stop` hook.** :file[scripts/hooks/harness-tag-stop.ts] takes this turn's records, from the last user record that isn't only tool results, skips subagent and meta records, and searches the assistant's text for a tag only the harness delivers ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#in-terrarium)).

**Session logs.** :file[scripts/session/log-session.ts] takes `transcript_path` from its hook's payload, and `extractTrace` in :file[scripts/session/transcript-trace.ts] derives the log's mechanical half from the records ([A session log lands on main](/t/glassbox/guide/walkthroughs/session-log-lands-on-main) follows it; [Session logs](/t/glassbox/guide/terrarium-practice/session-logs) says why). A scheduled run's first turn also gives its `trigger` ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks#in-terrarium)).

**Attribution.** The guard that checks each GitHub write for its session's mark ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution)) takes the session id from the environment first, and from the transcript only when the environment has none:

::excerpt{path="scripts/session/transcript-trace.ts" lines="490-495"}
```ts
export function resolveGroundTruthSessionId(
  transcriptSessionId: string | undefined,
  env: SessionIdEnv = process.env,
): string | undefined {
  return normalizeRemoteSessionId(env.CLAUDE_CODE_REMOTE_SESSION_ID) ?? transcriptSessionId
}
```
::

With an unreadable transcript, it still finds the id in the environment.

### Why it's built this way

- **One reading for every reader.** A hint that judged "read" differently from the session log would point to a doc the log counts as read. So the ADR hint builds the session log's own index of doc lines, and the hooks that read the transcript parse it with the same `parseTranscript`. The cost: a change to that code moves every hook at once. :file[scripts/hooks/adr-read-hint.ts].
- **The environment before the transcript.** A cloud session's link, `claude.ai/code/session_<id>`, comes from its `CLAUDE_CODE_REMOTE_SESSION_ID` with the prefix swapped; the transcript's `sessionId` is the id only for a local CLI session. So the code asks the environment first. The cost: a local session's id is a bare UUID with no link. :file[docs/agents/environment-caveats.md].

### What to watch for

- **It's plaintext.** Anything a tool reads or prints, a credential included, is written to the transcript, which isn't encrypted at rest ([Plaintext storage](https://code.claude.com/docs/en/claude-directory#plaintext-storage)).
- **A large result is a preview.** A large tool output is saved to its own file, and :file[scripts/session/transcript-trace.ts] finds only a 2KB preview and a "Full output saved to:" pointer in the transcript, so it opens that file to see the whole output.
- **An unreadable transcript means something different to each reader.** Decide it per reader, as the guard, the hints and attribution above do, not once for all.

## Try it in your project

Find your project's folder under `~/.claude/projects/`, open the newest `.jsonl` file there, and run `jq -r '.type' <file> | sort | uniq -c` to see which record types it holds. Then pick one `tool_use` block's `id` and find the `tool_result` that answers it.
