A hook is code, and it can break: its script crashes, its path is wrong, or it never answers. Claude Code then has to decide what happens to the action the hook was checking. A hook that fails closed blocks the call when it can't do its job; one that fails open lets the call through, and a crash quietly becomes a pass.

Know hook exit codes already? Skip to [In Terrarium](#in-terrarium).

## The concept

A [hook](/t/glassbox/guide/hooks/hooks) answers with its exit code and what it prints. If it exits with any code but 0 or 2 and prints no valid JSON, or doesn't start at all, Claude Code reports a non-blocking error and the call goes ahead: by default a hook fails open. Exit 2 blocks the call ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#the-concept)), but a script that crashes doesn't exit 2 (Node exits 1), so its crash still fails open.

Claude Code v2.1.295 and later take `"onFailure": "block"` on a command, HTTP or (from v2.1.328) `mcp_tool` hook, which turns a failure into a block: a hook that can't start, exits with a code other than 0 or 2, gets an HTTP or MCP error, prints output that can't be parsed, or times out. It has no effect on `Stop` and the other events where a block sends Claude back to keep working ([Stop hooks](/t/glassbox/guide/hooks/stop-hooks)), since Claude can't repair a hook that won't run, nor on a command hook set to run in the background. A command that ends in `|| true` exits 0 whatever happened, so `onFailure` never fires on it.

Failing open suits a hook that only adds advice the agent can work without; a check that must hold every time should fail closed.

Full reference: [Claude Code docs: Block the action when a hook fails](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)

## In Terrarium

Terrarium calls a hook that can deny a call or block a stop a guard; this page covers the `PreToolUse` ones ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#in-terrarium)); a hint or a recorder only adds context or keeps a record. A guard can fail after it starts or before. After it starts, `runGuard` in :file[scripts/hooks/hook-io.ts], which runs every guard's `main`, catches a thrown error and prints the same guard-fault deny that `denyUninspectable` prints for unreadable input, unless the guard passes `failOpen`:

::excerpt{path="scripts/hooks/hook-io.ts" lines="126-135"}
```ts
  const onCrash = (err: unknown): void => {
    if (opts.failOpen) return
    denyUninspectable(opts.label, opts.ref, `the guard itself crashed (${err instanceof Error ? err.message : String(err)})`)
  }
  try {
    const done = opts.dryRun && argv.includes('--dry-run') ? opts.dryRun(argv) : opts.main()
    if (done instanceof Promise) done.catch(onCrash)
  } catch (err) {
    onCrash(err)
  }
```
::

A crash before that `try`, such as `tsx`, the TypeScript runner each guard's command starts, failing to start, or an import that throws, prints nothing and exits nonzero. The wiring in :file[.claude/settings.json] covers that case: each guard's hook sets `onFailure`, except the ones :file[docs/agents/guards.md] lists as wired with `|| true`. The excerpt shows two separate hooks, one of each kind: the deferred-tool guard's ends in `|| true`, and the loop-only-tool guard's sets `onFailure`:

::excerpt{path=".claude/settings.json" lines="20,29-30"}
```json
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/deferred-tool-guard.ts || true"
            // …
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/loop-only-tool-guard.ts",
            "onFailure": "block"
```
::

:file[scripts/hooks/deferred-tool-guard.ts] and :file[scripts/hooks/tenant-glossary-guard.ts] fail open. The first catches a deferred tool (one Claude loads on demand through `ToolSearch`) called with another tool's arguments. The second blocks an edit under a :term[tenant]'s folder before that tenant's glossary has been read, and passes when it can't find the transcript or the glossary. Both pass `failOpen: true` to `runGuard`, and both are wired with `|| true`. The guards, Stop hooks and hints that let the action go ahead when they crash are listed in *Conventions every guard follows* in :file[docs/agents/guards.md]. The test's `FAIL_OPEN` list repeats only the guards on it. The `Stop` hooks that file lists with the guards, such as :file[scripts/hooks/harness-tag-stop.ts] and :file[scripts/hooks/merge-close-stop.ts], and every hint and recorder are wired with `|| true` too ([Stop hooks](/t/glassbox/guide/hooks/stop-hooks#in-terrarium), [Hook-added context](/t/glassbox/guide/hooks/hook-added-context#in-terrarium)).

A test holds the wiring in place. :file[tests/unit/guards-wiring.spec.ts] collects every `PreToolUse` hook in :file[.claude/settings.json] as `entries` and every `scripts/hooks/*-guard.ts` as `guards`, checks a hook runs each guard, and, for all but the guards the test's `FAIL_OPEN` list names, checks the hook sets `onFailure` and holds no `|| true`:

::excerpt{path="tests/unit/guards-wiring.spec.ts" lines="8,12-24"}
```ts
const FAIL_OPEN = ['deferred-tool-guard', 'tenant-glossary-guard']
// …
const entries: Hook[] = settings.hooks.PreToolUse.flatMap((h: { hooks: Hook[] }) => h.hooks)
const guards = globSync('scripts/hooks/*-guard.ts', { cwd: root }).map((f) => basename(f, '.ts'))

describe('every scripts/hooks/*-guard.ts is wired', () => {
  it.each(guards)('%s runs from a PreToolUse hook', (guard) => {
    const wired = entries.filter((h) => h.command.includes(`scripts/hooks/${guard}.`))
    expect(wired, `no PreToolUse hook runs ${guard}`).not.toHaveLength(0)
    if (FAIL_OPEN.includes(guard)) return
    for (const h of wired) {
      expect(h.onFailure, h.command).toBe('block')
      expect(h.command, 'a `|| true` exits 0, so onFailure never fires').not.toContain('|| true')
    }
  })
```
::

### Why it's built this way

- **A crash blocks.** A crash before the guard's own `try` exits nonzero, and a `|| true` would make that a silent 0 that lets the call through. Guard hooks set `onFailure` instead, and `runGuard` still denies a thrown error itself, because its deny names the guard and its issue. The cost: a broken guard blocks every call of its kind until fixed. :file[docs/agents/guards.md].
- **A guard that can't tell may fail open.** The deferred-tool guard has one signal for a wrong call, its arguments' shape, and fails open. Both it and the tenant-glossary guard pass `failOpen: true`, so a crash lets the call through; the latter's header says a wrong block costs more than a missed nit. The cost: when either breaks, its mistake goes unchecked. :file[scripts/hooks/tenant-glossary-guard.ts].

### What to watch for

- **Fail-closed covers crashes, not blind spots.** `onFailure` and `runGuard` turn a broken guard into a block; a guard that runs fine still lets through a call it doesn't recognize ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#what-to-watch-for)).
- **`onFailure` is version-bound.** A Claude Code older than v2.1.295 ignores it, and a guard that can't start fails open again.

## Try it in your project

With Claude Code v2.1.295 or later, add this matcher group under `hooks.PreToolUse` in `.claude/settings.json`: a guard whose code is missing, so Node exits 1 on every `Bash` call. Don't end its command with `|| true`, which exits 0, so `onFailure` never fires.

```json
{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "node -e \"require('missing-guard')\"", "onFailure": "block" }] }
```

Ask Claude to run `ls`. The call is blocked, and the transcript shows a `PreToolUse:Bash hook error` notice saying `failed; blocking because onFailure is "block"`, followed by Node's `Cannot find module` error. Remove `"onFailure": "block"` and ask again: the notice says `Failed with non-blocking status code:` instead, and `ls` runs.
