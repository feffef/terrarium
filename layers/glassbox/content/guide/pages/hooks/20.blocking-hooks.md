Some instructions keep being missed however they are worded. A blocking hook stops asking and checks instead: a `PreToolUse` hook that looks at a tool call before it runs, denies the wrong ones, and tells the agent what to do. It must also decide what happens when it breaks. A blocking hook that fails closed blocks the call when it can't do its job; one that fails open lets the call through, and a crash quietly becomes a pass.

Know PreToolUse hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A blocking hook is a `PreToolUse` [hook](/t/glassbox/guide/hooks/hooks). Claude Code runs it before each tool call its matcher names and hands it the call as JSON on stdin, including `tool_name`, `tool_input` and the path of the session's transcript. To refuse the call, the hook exits 0 and prints a decision:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep."
  }
}
```

Claude Code blocks the call and shows Claude the reason, so the reason is the instruction the model acts on next. When several `PreToolUse` hooks decide on one call, the strictest decision wins: `deny`, then `defer`, which in a non-interactive run (`claude -p`) ends the turn so the call can be resumed later, then `ask`, which prompts the user to confirm, then `allow`.

A hook that fails is another matter. If it exits with any code but 0 or 2 and prints no valid JSON, or doesn't start at all, Claude Code reports a non-blocking error and the call goes ahead: by default a hook fails open. Exit 2 is the other way to block: the call stops and Claude receives the hook's stderr as the reason, and the docs advise it over exit 1 for a hook that enforces a policy. A script that crashes doesn't exit 2, though (Node exits 1), so its crash still fails open. Claude Code v2.1.295 and later take `"onFailure": "block"` on a command or HTTP hook, which turns a failure into a block: a hook that can't start, exits with a code other than 0 or 2, gets an HTTP error, prints output that can't be parsed, or times out. It has no effect on `Stop` and the other events where a block sends Claude back to keep working, since Claude can't repair a hook that won't run, nor on a command hook set to run in the background with `async` or `asyncRewake`.

Full reference: [Claude Code docs: Block the action when a hook fails](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails)

## In Terrarium

Terrarium calls its blocking hooks guards. :file[docs/agents/guards.md] is the roster: each guard, what it denies, where the rule it enforces lives, and its issue. It lists the hints and recorders too, which add guidance or keep a record and deny nothing. Each guard's own script header holds its reasons and the cases it can't see.

A guard is a small script in :file[scripts/hooks/]: a registry of the cases it knows, a pure check, and a message. :file[scripts/hooks/hook-io.ts] holds the plumbing they share: reading the payload and the transcript, the deny JSON, and a `--dry-run` mode. A guard's `main` shows the pattern. An empty stdin, a bare run by hand, passes; a payload it can't read is denied:

::excerpt{path="scripts/hooks/skill-inline-guard.ts" lines="98-107"}
```ts
export function main(): void {
  const result = readHookPayload()
  if (result.kind === 'none') return
  if (result.kind === 'invalid') return denyUninspectable(LABEL, REF, 'the hook payload was not valid JSON')
  if (result.kind === 'no-tool') return denyUninspectable(LABEL, REF, 'the hook payload named no tool')

  const { payload } = result
  const output = denyOutputFor(checkSkillInlineCall(payload.tool_input, readTranscript(payload.transcript_path)))
  if (output) process.stdout.write(JSON.stringify(output))
}
```
::

A transcript it can't read denies too. `denyUninspectable` says the block is a guard fault, not the agent's mistake. Every guard starts through `runGuard`, which turns a thrown error into the same kind of deny unless the guard passes `failOpen`:

::excerpt{path="scripts/hooks/hook-io.ts" lines="126-135"}
```ts
  const onCrash = (err: unknown): void => {
    if (opts.failOpen) return
    denyUninspectable(opts.label, opts.ref, `the guard itself crashed (${err instanceof Error ? err.message : String(err)})`)
  }
  try {
    const done = opts.dryRun && argv.includes('--dry-run') ? opts.dryRun(argv) : opts.main()
    if (done instanceof Promise) done.catch(onCrash)
  } catch (err) {
    onCrash(err)
  }
```
::

A crash before that `try`, such as `tsx`, the TypeScript runner each guard's command starts, failing to start, or an import that throws, prints nothing and exits nonzero. The wiring in :file[.claude/settings.json] covers that case: each guard's hook sets `onFailure`, except the ones :file[docs/agents/guards.md] lists as wired with `|| true`, which makes the command exit 0 whatever happened. The excerpt shows one hook of each kind: the deferred-tool guard's ends in `|| true`, and the loop-only-tool guard's sets `onFailure`:

::excerpt{path=".claude/settings.json" lines="20,29-30"}
```json
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/deferred-tool-guard.ts || true"
            // …
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/loop-only-tool-guard.ts",
            "onFailure": "block"
```
::

:file[scripts/hooks/deferred-tool-guard.ts] catches a tool called with another tool's arguments. It passes `failOpen: true` to `runGuard`, as the hints that use it do, and its hook ends in `|| true` with no `onFailure`. The `Stop` hooks the roster lists with the guards, such as :file[scripts/hooks/harness-tag-stop.ts] and :file[scripts/hooks/merge-close-stop.ts], and every hint and recorder are wired with `|| true` too.

A test holds the wiring in place. :file[tests/unit/guards-wiring.spec.ts] finds every `scripts/hooks/*-guard.ts`, checks a `PreToolUse` hook runs it, and, for all but the fail-open list, checks the hook sets `onFailure` and holds no `|| true`:

::excerpt{path="tests/unit/guards-wiring.spec.ts" lines="8,15-24"}
```ts
const FAIL_OPEN = ['deferred-tool-guard']
// …
describe('every scripts/hooks/*-guard.ts is wired', () => {
  it.each(guards)('%s runs from a PreToolUse hook', (guard) => {
    const wired = entries.filter((h) => h.command.includes(`scripts/hooks/${guard}.`))
    expect(wired, `no PreToolUse hook runs ${guard}`).not.toHaveLength(0)
    if (FAIL_OPEN.includes(guard)) return
    for (const h of wired) {
      expect(h.onFailure, h.command).toBe('block')
      expect(h.command, 'a `|| true` exits 0, so onFailure never fires').not.toContain('|| true')
    }
  })
```
::

Each guard has its own unit test in :file[tests/unit/], such as :file[tests/unit/skill-inline-guard.spec.ts]: it calls the pure check with recorded and adversarial inputs, an unreadable transcript included, and runs the real script once through stdin and once through `--dry-run`. Most guards' `Usage:` headers show the `--dry-run` command that prints the decision for a given call, with no deny.

### Why it's built this way

- **The deny message is the rule's home.** A guard's message states the rule and its fix at the call, where a doc went unread ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#why-its-built-this-way) says why). :file[scripts/hooks/skill-inline-guard.ts].
- **A crash blocks.** Guards were once wired with `|| true`. A crash before the guard's own `try` exited nonzero, `|| true` made that a silent 0, so the guard let the call through. Now guard hooks set `onFailure`, and `runGuard` still denies a thrown error itself, because its deny names the guard and its issue. The cost: a broken guard blocks every call of its kind until fixed. :file[docs/agents/guards.md].
- **A guard that can't tell may fail open.** The deferred-tool guard can recognize a wrong call only by the shape of its arguments, and a guard that denied what it couldn't identify would block correct calls. So it stays silent on any doubt, its own crash included. The cost: when it breaks, that mistake goes unchecked. :file[scripts/hooks/hook-io.ts].
- **A new mistake is a data row.** Each guard keeps its known cases in an exported array at the top of its script, so a new variant is one more row and a test case, not new logic. The cost: a variant passes until its row exists, and a new tool needs adding to the hook's matcher in :file[.claude/settings.json], which a person merges. :file[docs/agents/guards.md].
- **Tests assert a property.** A regex once matched across a line break, so a write verb on one line denied an unrelated command on the next, and every single-line test still passed. Guard tests now cover multi-line and adversarial input, and a guard's real deny is probed live once. The cost: more cases per guard, and a manual probe no test replaces. :file[docs/agents/guards.md].

### What to watch for

- **The deny message is the instruction.** Do what it says. If it is wrong, report it on the guard's issue in the roster rather than rewording the call until it slips past.
- **Fail-closed covers crashes, not blind spots.** A guard that blocks when it breaks can still miss a call it doesn't recognize. The `Bash`, `Edit` and `Write` guards and their shell pre-filters match text, so a path built from a variable, or a payload key the harness renames, passes unchecked. Each guard's header lists its gaps.
- **`onFailure` is version-bound.** A Claude Code older than the minimum in :file[docs/agents/guards.md] ignores it, and a guard that can't start fails open again.
- **A probe can be blocked by the guard it probes.** `--dry-run` takes the call's input as JSON in `--input`, or from a file named by `--input-file`. A `Bash` call that carries a denying `--input` in its own text can trip the guard before the dry run starts, so use `--input-file`.
- **A unit test can't see a live deny.** It checks the decision, not that the hook fires in a session, which is one reason guards are :term[human-only] to merge ([Claude Code hooks](/t/glassbox/guide/hooks/hooks) says why).

## Try it in your project

With Claude Code v2.1.295 or later, add this matcher group under `hooks.PreToolUse` in `.claude/settings.json`: a guard whose code is missing, so Node exits 1 on every `Bash` call. Don't end its command with `|| true`, which exits 0, so `onFailure` never fires.

```json
{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "node -e \"require('missing-guard')\"", "onFailure": "block" }] }
```

Ask Claude to run `ls`. The call is blocked, and the transcript shows a `PreToolUse:Bash hook error` notice saying `failed; blocking because onFailure is "block"`, followed by Node's `Cannot find module` error. Remove `"onFailure": "block"` and ask again: the notice says `Failed with non-blocking status code:` instead, and `ls` runs.
