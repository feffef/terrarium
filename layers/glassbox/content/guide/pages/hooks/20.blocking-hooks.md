Some instructions keep being missed however they are worded. A blocking hook stops asking and checks instead: a `PreToolUse` hook that looks at a tool call before it runs, denies the wrong ones, and tells the agent what to do. What happens when the hook itself breaks is in [Hook failure modes](/t/glassbox/guide/hooks/hook-failure-modes).

Know PreToolUse hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A blocking hook is a `PreToolUse` [hook](/t/glassbox/guide/hooks/hooks). Claude Code runs it before each tool call its matcher, the pattern of tool names the hook answers, names, and hands it the call as JSON on stdin, including `tool_name`, `tool_input` and the path of the session's transcript, the file that holds the conversation so far. To refuse the call, the hook exits 0 and prints a decision:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "Use rg instead of grep."
  }
}
```

Claude Code blocks the call and shows Claude the reason, so the reason is the instruction the model acts on next. When several `PreToolUse` hooks decide on one call, the strictest decision wins: `deny`, then `defer`, which ends the turn for a later resume and is honoured only in a `claude -p` run whose turn makes a single tool call, then `ask`, which prompts the user, then `allow`. A blocking hook is for a rule that must hold every time; a judgement call belongs in an instruction ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#the-concept)).

Exit 2 is the other way to block: the call stops and Claude receives the hook's stderr as the reason, and the docs advise it over exit 1 for a hook that enforces a policy. Exit codes alone can only block or stay silent; the JSON decision gives the finer control above.

Full reference: [Claude Code docs: PreToolUse decision control](https://code.claude.com/docs/en/hooks#pretooluse-decision-control)

## In Terrarium

Terrarium calls its blocking hooks guards. :file[docs/agents/guards.md] lists them: each guard, what it denies, where the rule it enforces lives, and its issue. It lists the hints and recorders too, hooks that only add guidance or keep a record. Each guard's own script header holds its reasons and the cases it can't see.

A guard is a small script in :file[scripts/hooks/]: a registry of the cases it knows, a check with no side effects, and a message. :file[scripts/hooks/hook-io.ts] holds the plumbing they share: reading the payload and the transcript, the deny JSON, and a `--dry-run` mode. A guard's `main` shows the pattern. An empty stdin, a bare run by hand, passes; a payload it can't read is denied:

::excerpt{path="scripts/hooks/skill-inline-guard.ts" lines="98-107"}
```ts
export function main(): void {
  const result = readHookPayload()
  if (result.kind === 'none') return
  if (result.kind === 'invalid') return denyUninspectable(LABEL, REF, 'the hook payload was not valid JSON')
  if (result.kind === 'no-tool') return denyUninspectable(LABEL, REF, 'the hook payload named no tool')

  const { payload } = result
  const output = denyOutputFor(checkSkillInlineCall(payload.tool_input, readTranscript(payload.transcript_path)))
  if (output) process.stdout.write(JSON.stringify(output))
}
```
::

A transcript it can't read denies too. `denyUninspectable` words that deny as a guard fault, not the agent's mistake: the guard ran to the end and denied an input it could not read; `runGuard` prints the same deny when a guard throws. Every guard starts through `runGuard` in :file[scripts/hooks/hook-io.ts], which runs the guard's `main` and catches what it throws; what it does with a throw is in [Hook failure modes](/t/glassbox/guide/hooks/hook-failure-modes#in-terrarium).

Each guard has its own unit test in :file[tests/unit/], such as :file[tests/unit/skill-inline-guard.spec.ts]: it calls the pure check with recorded and adversarial inputs, an unreadable transcript included, and runs the real script once through stdin and once through `--dry-run`. Most guards' `Usage:` headers show the `--dry-run` command that prints the decision for a given call, with no deny.

### Why it's built this way

- **The deny message is the rule's home.** A guard's message states the rule and its fix at the call, where a doc went unread ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#why-its-built-this-way) says why). :file[scripts/hooks/skill-inline-guard.ts].
- **A new mistake is a data row.** Each guard keeps its known cases in an exported array at the top of its script, so a new variant is one more row and a test case, not new logic. The cost: a variant passes until its row exists, and a new tool needs adding to the hook's matcher in :file[.claude/settings.json], which a person merges. :file[docs/agents/guards.md].
- **Tests assert a property.** A regex once matched across a line break, so a write verb on one line denied an unrelated command on the next, and every single-line test still passed. Guard tests now cover multi-line and adversarial input, and a guard's real deny is probed live once. The cost: more cases per guard, and a manual probe no test replaces. :file[docs/agents/guards.md].

### What to watch for

- **The deny message is the instruction.** Do what it says. If it is wrong, report it on the guard's issue in :file[docs/agents/guards.md] rather than rewording the call until it slips past.
- **A guard misses what it doesn't recognize.** The `Bash`, `Edit` and `Write` guards and their shell pre-filters match text, so a path built from a variable, or a payload key the harness renames, passes unchecked. Each guard's header lists its gaps; a guard that breaks is another matter ([Hook failure modes](/t/glassbox/guide/hooks/hook-failure-modes#what-to-watch-for)).
- **A probe can be blocked by the guard it probes.** `--dry-run` takes the call's input as JSON in `--input`, or from a file named by `--input-file`. A `Bash` call that carries a denying `--input` in its own text can trip the guard before the dry run starts, so use `--input-file`.
- **A unit test can't see a live deny.** It checks the decision, not that the hook fires in a session, which is one reason guards are :term[human-only] to merge ([Claude Code hooks](/t/glassbox/guide/hooks/hooks) says why).

## Try it in your project

This hook denies any `Bash` call whose command runs `grep`. Save it as `.claude/hooks/no-grep.sh` and make it executable (`chmod +x`); it needs `jq`:

```sh
#!/bin/sh
jq -c 'select(.tool_input.command // "" | test("\\bgrep\\b")) | {hookSpecificOutput: {hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason: "Use rg instead of grep."}}'
```

Test it by hand first: `echo '{"tool_name":"Bash","tool_input":{"command":"grep -r TODO src"}}' | .claude/hooks/no-grep.sh` prints the deny decision, and the same payload with `ls` as the command prints nothing. Then add this matcher group under `hooks.PreToolUse` in `.claude/settings.json`:

```json
{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/no-grep.sh" }] }
```

Type `/hooks` and check that the hook is listed. Then ask Claude to run `grep -r TODO` in the shell; this matcher doesn't catch Claude's own Grep tool. Claude Code blocks the call and shows Claude the reason.
