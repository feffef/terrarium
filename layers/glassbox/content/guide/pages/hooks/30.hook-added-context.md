Some advice only makes sense at the moment it applies: right after a push is rejected, or the first time an agent runs `git`. A hook can add that advice beside the result of the call that needed it, and then get out of the way.

Know hooks that add context already? Skip to [In Terrarium](#in-terrarium).

## The concept

A `PostToolUse` [hook](/t/glassbox/guide/hooks/hooks), a command Claude Code runs at a fixed point in a session, runs after a tool call succeeds, and a `PostToolUseFailure` hook runs after one fails. By then the tool has already run, so the hook can't stop it. What it can do is talk to Claude: if it prints JSON with an `additionalContext` string, Claude Code puts that string into the conversation beside the tool's result, as a system reminder Claude reads on its next step. A `UserPromptSubmit` hook can do the same beside the prompt a person just sent.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "This file is generated. Edit src/schema.ts instead."
  }
}
```

How hooks are wired, and what their exit codes do: [Claude Code hooks](/t/glassbox/guide/hooks/hooks).

Full reference: [Claude Code docs: Add context for Claude](https://code.claude.com/docs/en/hooks#add-context-for-claude)

## In Terrarium

Besides the hooks that set up a session and land its log, Terrarium's hooks are guards and hints, and one recorder of rule loads. A guard can block: it denies a call before it runs, or blocks a stop. A hint runs after a call, or after a prompt, and only adds context (a few run at a session or subagent start). The roster in :file[docs/agents/guards.md] lists every hint and the recorder beside the guards, and :file[.claude/settings.json] wires each one in.

Each hint watches for one situation. For example:

- :file[scripts/hooks/stale-push-hint.ts] waits for a `git push` that git rejects as "stale info", and adds that the remote branch was probably deleted when its PR merged, with the fix.
- :file[scripts/hooks/read-first-hint.ts] waits for the first call of a kind that `CLAUDE.md` or a :term[rule] ties to a doc. Examples are a session's first GitHub call, or its first git command other than `status`, `diff`, `show`, `ls-tree`, `cat-file`, `grep`, `ls-files`, `rev-parse` or a listing-only `branch`. It names that doc, and adds that a late read which clears the call is not a :term[friction]. After the main session (the top-level session, not a subagent it dispatched) opens a PR, or runs `merge-pr.ts` and the script reports the PR merged, it also says to invoke the `close-session` :term[skill].
- :file[scripts/hooks/adr-read-hint.ts] runs after an `Edit`, a `Write` or a Bash `git commit` and points to each :term[ADR] whose rule matches a file written, or that the change names, unless the agent has already read it in full.

The stale-push hint makes its decision in one function: a Bash `git push`, then git's own rejection line anywhere in the output.

::excerpt{path="scripts/hooks/stale-push-hint.ts" lines="32-40"}
```ts
export function staleInfoHint(payload: unknown): string | null {
  const command = field(field(payload, 'tool_input'), 'command')
  if (field(payload, 'tool_name') !== 'Bash') return null
  if (typeof command !== 'string' || !GIT_PUSH.test(command)) return null
  // PostToolUse carries `tool_response`; PostToolUseFailure carries `error`.
  const response = field(payload, 'tool_response')
  const output = [field(response, 'stdout'), field(response, 'stderr'), field(payload, 'error')]
  return output.some((s) => typeof s === 'string' && STALE_REJECTION.test(s)) ? HINT : null
}
```
::

The hint is wired on both `PostToolUse` and `PostToolUseFailure`, and prints JSON like the example above, with whichever event called it as `hookEventName`.

A hint fails open: no hint's entry sets `onFailure: "block"`, and each hint that starts through `runGuard` in :file[scripts/hooks/hook-io.ts] passes `failOpen: true`, with which `runGuard` returns silently when the hint crashes. Each is also wired as `… || true` ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#in-terrarium)).

A hint that points to a doc also says each thing once: it checks the agent's transcript and stays silent once the doc was read or the pointer already given ([Session transcripts](/t/glassbox/guide/hooks/session-transcripts#in-terrarium) shows how). The stale-push hint checks no transcript and adds its fix after every stale push.

### Why it's built this way

- **Advice where it applies.** Agents read git's "stale info" rejection as someone else pushing at the same time and retried, when the remote branch had usually been deleted after its PR merged. The hint puts the real cause and the fix into that same tool result. The cost: it arrives after the rejected push, so it corrects the next step, not this one. :file[scripts/hooks/stale-push-hint.ts].
- **Hints back read-first instructions.** A read-first trigger in `CLAUDE.md` is prose, and sessions read its doc after the action it guards. The read-first hint points to that doc at the first matching call, and the ADR hint backs a :term[rule] the same way ([Path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules#why-its-built-this-way) says why). The cost: that call still runs first, which the owner accepts. :file[scripts/hooks/read-first-hint.ts].
- **Fail open.** A hint only adds advice the agent can work without, so a crashing hint should add nothing rather than block ([In Terrarium](#in-terrarium)). A `PreToolUse` guard is the opposite case ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#why-its-built-this-way) says why). The cost: a broken hint just goes quiet, and nothing reports that its advice stopped. :file[scripts/hooks/hook-io.ts].
- **Say it once.** A pointer added on every matching call would repeat the same text in the context, so a hint that points to a doc says it once ([In Terrarium](#in-terrarium)). The cost: with no readable transcript, the ADR hint and the main session's read-first hint add nothing, while the read-first hint in a subagent and the Bash-rules hint still fire ([Session transcripts](/t/glassbox/guide/hooks/session-transcripts#in-terrarium)). :file[scripts/hooks/read-first-hint.ts].

### What to watch for

- **A hint comes after the call.** It can't stop a mistake, only correct the next step. When the first wrong call is itself costly, a hint is the wrong tool; a guard, which runs before the call, is the right one.
- **Every matching call pays for the hook.** Each hint on `Bash` sits behind a short shell filter, as [Claude Code hooks](/t/glassbox/guide/hooks/hooks#in-terrarium) explains.
- **A subagent is a separate reader.** Hooks fire for a dispatched subagent's calls too, and a pointer the parent already got still reaches the subagent once, because the hints that dedupe read the subagent's own transcript ([Session transcripts](/t/glassbox/guide/hooks/session-transcripts#in-terrarium)).

## Try it in your project

Find an error message your agent keeps misreading; this example uses Node's `Cannot find module`. A `PostToolUseFailure` hook gets the failure text in the payload's `error` field, so save this as `.claude/hooks/missing-module.sh` and make it executable (`chmod +x`). It prints the context only when the error matches, and nothing otherwise:

```sh
#!/bin/sh
jq -c 'select((.error // "") | test("Cannot find module")) | {hookSpecificOutput: {hookEventName: "PostToolUseFailure", additionalContext: "A dependency is missing: run npm install, then retry."}}'
```

Test it by hand first: `echo '{"error":"Error: Cannot find module x"}' | .claude/hooks/missing-module.sh` prints the JSON. Then add this matcher group under `hooks.PostToolUseFailure` in `.claude/settings.json`:

```json
{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/missing-module.sh" }] }
```

Ask Claude to run `node -e "require('missing-module')"`. The context isn't shown as a chat message, so ask Claude to quote any system reminder beside that result, or find it in the session's transcript ([Session transcripts](/t/glassbox/guide/hooks/session-transcripts#try-it-in-your-project) shows where) with `jq -c 'select(.attachment.type == "hook_additional_context") | .attachment.content' <file>`. Leave `|| true` off while you debug: a bug can't block anything, since the call has already run and with `onFailure` unset a failing hook is a non-blocking error, and the hook-error notice shows what went wrong. Add `|| true` once the hook works, if you want a later failure to stay silent.
