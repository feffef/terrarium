An instruction asks the model to do something, and the model may forget. A hook is a command that Claude Code itself runs at a fixed point in a session, so wherever it is loaded, it happens every time, whatever the model decides.

Know hooks already? Skip to [In Terrarium](#in-terrarium).

## The concept

A hook is declared in a settings file under `hooks`, in three levels: the event it answers, a matcher group that narrows when it fires, and the handlers to run. Events include `SessionStart`, `UserPromptSubmit`, `PreToolUse` and `PostToolUse` around each tool call, `PostToolUseFailure` after one fails, `SubagentStart` when a subagent is spawned, `Stop` when Claude finishes responding, and `SessionEnd`. For the tool events the matcher is the tool's name, such as `Bash` or `Edit|Write`; for `SessionStart` it is how the session started, such as `startup` or `resume`.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }]
      }
    ]
  }
}
```

A command hook gets the event as JSON on stdin, which is where the example reads the edited file's path, and answers with its exit code and what it prints. Exit 0 with nothing printed changes nothing. A `PreToolUse` hook can print a decision that denies the call, and the reason it gives goes back to Claude. A `PostToolUse` hook can print `additionalContext`, which Claude reads beside the tool's result. A `Stop` hook can print a decision that blocks the stop, and Claude keeps working. Every hook that matches runs, in parallel; [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks) says which decision wins when several `PreToolUse` hooks decide on one call.

A hook is for what must hold every time; a judgement call belongs in an instruction, and a hook that only adds advice after a call is the wrong tool when that first call is costly ([Hook-added context](/t/glassbox/guide/hooks/hook-added-context#what-to-watch-for)). Every matching call starts the hook's command, so scope the matcher to the tools it checks, and the command runs with your [full user permissions](https://code.claude.com/docs/en/hooks#security-considerations).

`~/.claude/settings.json` holds your own hooks for every project. A project's `.claude/settings.json` is committed, so everyone who works in it gets its hooks; `.claude/settings.local.json` is the uncommitted variant. The [hooks guide](https://code.claude.com/docs/en/hooks-guide) walks through first examples.

Full reference: [Claude Code docs: Hooks reference](https://code.claude.com/docs/en/hooks)

## In Terrarium

Every hook Terrarium uses is wired in one committed file, :file[.claude/settings.json]. A cloud session on this one repository loads it; one on several repositories, or a thread in a project, runs none of its hooks ([Cloud sessions](/t/glassbox/guide/agents/cloud-sessions#in-terrarium)). Each command starts with `cd "${CLAUDE_PROJECT_DIR:-.}"`, which moves it to the project's root. Terrarium calls a hook a guard when it can block, by denying a tool call (`PreToolUse`) or by blocking the stop (`Stop`), and a hint when it only adds advice. The hooks do three jobs.

**Setting up a session.** On `SessionStart`, at startup and on resume, a hook runs `pnpm install`, then :file[scripts/hooks/unshallow-on-start.ts], which fetches full git history when the clone arrived shallow. That script catches its own failures: a fetch that fails never blocks the start. Another, :file[scripts/hooks/network-start.ts], probes a set of hosts through the network proxy and prints which are readable or blocked, and prints nothing when no proxy is set.

**Landing the session log.** The first `Stop` hook lands the session's pending log, its Journal record, with the log script, :file[scripts/session/log-session.ts]; a `SessionStart` hook on resume and the `SessionEnd` hook at teardown run it again as fallbacks. The second `Stop` hook, :file[scripts/hooks/harness-tag-stop.ts], blocks the stop once if the agent's reply contains a `<task-notification>` or `<agent-message>` block. Only the harness delivers those, so one in the reply means the agent wrote a subagent's report itself. The third, :file[scripts/hooks/merge-close-stop.ts], blocks the stop once if the session merged a PR and has not run `close-session`, the skill that closes a session and records its log, since. The fourth, :file[scripts/hooks/pr-subscribe-stop.ts], blocks the stop once if the session opened a PR and never subscribed to its activity. An `InstructionsLoaded` hook, :file[scripts/hooks/rule-load-ledger.ts], also records each path-scoped rule load for the log to read back. The `Stop` wiring, showing the first and fourth hooks:

::excerpt{path=".claude/settings.json" lines="224-231,242-246"}
```json
    "Stop": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && [ -f .session-logs/pending.scratch.json ] && node_modules/.bin/tsx scripts/session/log-session.ts --land || true"
          },
      // …
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/pr-subscribe-stop.ts || true"
          }
        ]
      }
    ],
```
::

The empty matcher matches every stop. The `Stop` hooks and the hints end in `|| true`, and `|| true` turns any exit code into 0, so a failing command neither blocks the action nor raises a hook-error notice. `|| true` changes only the exit code: a `Stop` hook that prints a decision to block the stop still blocks it. A guard fails closed unless :file[docs/agents/guards.md] lists it as letting the action go ahead: its hook sets `onFailure: "block"` and holds no `|| true`, which :file[tests/unit/guards-wiring.spec.ts] checks for each `PreToolUse` guard ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#in-terrarium)).

At `SessionEnd`, `log-session.ts --land` never exits with an error. [A session log lands on main](/t/glassbox/guide/walkthroughs/session-log-lands-on-main) follows the log from these hooks to its commit on `main`.

**Checking tool calls.** `PreToolUse` hooks are guards that check tool calls: each can deny one kind of mistaken call and say what to do instead (the `Stop` guards above block a stop instead). `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit` and `SubagentStart` hooks are hints: each can add guidance beside a call's result, a prompt or a subagent's start, and never blocks ([Hook-added context](/t/glassbox/guide/hooks/hook-added-context) shows how). :file[docs/agents/guards.md] lists both kinds. This guard denies a `Skill` call for a skill whose text the session already received inline, and its `onFailure` makes Claude Code block the call when the hook itself fails, where by default the call goes ahead:

::excerpt{path=".claude/settings.json" lines="44-53"}
```json
      {
        "matcher": "Skill",
        "hooks": [
          {
            "type": "command",
            "command": "cd \"${CLAUDE_PROJECT_DIR:-.}\" && node_modules/.bin/tsx scripts/hooks/skill-inline-guard.ts",
            "onFailure": "block"
          }
        ]
      },
```
::

Each tool hook's matcher names only the tools it checks, never `*`. Most hooks on `Bash`, `Edit` and `Write` start with a short shell filter, such as :file[scripts/hooks/workflow-edit-guard.sh], which exits at once unless the call's text could match.

### Why it's built this way

- **Hooks over prose.** Some rules failed as instructions: agents kept skipping a full-history check, and a fix written into a doc never reached sessions with no reason to open it. So a `SessionStart` hook fetches the history, and a guard's deny message states the rule and its fix at the call. The cost: code that runs in every session with hooks and needs its own tests. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).
- **Broken guards refuse.** A crashed hook lets its call through by default, but most Terrarium guards block it when they crash; [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks#why-its-built-this-way) tells the crash that led there, its cost and the exceptions. :file[docs/agents/guards.md].
- **A filter before each guard.** A `tsx` start on each matching call would pause every read and edit. So each hook names only the tools it checks, and most `Bash`, `Edit` and `Write` hooks start their guard only when a shell filter finds text that could match. The cost: a call the filter doesn't recognise, such as a re-encoded payload, never reaches the guard. :file[docs/agents/guards.md].
- **Wiring under human review.** No test or build sees a hook act in a session, so a careless wiring change could quietly disable a guard while every check passed. So :file[.claude/settings.json] and the guards are on the :term[human-only] list ([Protected paths](/t/glassbox/guide/terrarium-practice/protected-paths)). The cost: fixing a hook waits for a person. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **By default a crashed hook doesn't stop the call.** An entry that sets `onFailure: "block"`, as most of Terrarium's guards do, makes it stop; [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks) covers both, and :file[docs/agents/guards.md] lists the hooks wired to fail open.
- **Hooks see a subagent's calls too.** A subagent's tool calls fire the same hooks as the main session's, and the payload carries `agent_id` and `agent_type`, which identify the subagent; `agent_type` also appears when a session runs under `--agent` (a session started as a named agent).
- **An unattended session can't change the wiring.** Editing the hooks in :file[.claude/settings.json] raises a permission prompt that no one is there to grant (:file[docs/agents/guards.md]).

## Try it in your project

Save the example under [The concept](#the-concept) as `.claude/settings.json` in your project, creating the file if it is missing, or add its `hooks` key to the file you have; its command needs `jq` and `npx`. A running session normally picks up the change through Claude Code's file watcher: type `/hooks` and check that the hook is listed under `PostToolUse` as coming from project settings, and if it isn't there after a few seconds, restart the session.

Then write a JavaScript file with single-quoted strings yourself, so it starts out unformatted, ask Claude to add a line to it, and open it. If your own lines now use double quotes, Prettier's default, the hook ran. A hook that succeeds shows nothing in the conversation, so the reformatted file is the proof.
