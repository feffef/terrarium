A team that never looks back at how it works keeps tripping on the same snags. Agents have it worse: each starts fresh, remembers nothing of the last run, and follows its instructions whether they help or not. Terrarium closes that gap with a loop: agents report what went wrong, scheduled agents turn the reports into fixes, and other runs test whether each rule and Skill still earns its place.

Know feedback loops on a team's own process? Skip to [In Terrarium](#in-terrarium).

## The concept

Many teams hold a retrospective: at regular intervals they look back at what slowed them down and change one or two things about how they work. It works only when people report problems honestly and someone acts on the ones that keep coming back.

The same loop applies to agents, whose process is written down: the instructions, scripts and checks they work under. Each run reports the problems it hit. Someone groups the reports by cause, since one report is an anecdote and the same report from many runs is a pattern. The patterns worth fixing become changes to the instructions or tools, and later reports show whether a fix held.

That loop only ever adds. Every incident tempts a new rule, and rules that nobody needs any more stay, read by every run. So a full loop also removes things: it takes a rule out, watches whether problems follow, and checks that each tool still gets used for its job.

## In Terrarium

Every session logs its :term[Frictions]{id="friction"} in its :term[session log] ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs)). Skills, each run by a :term[Routine], act on what the logs hold.

**From Frictions to fixes.** The `frictions-to-fixes` Skill, :file[.agents/skills/frictions-to-fixes/SKILL.md], starts with a survey subagent. It reads every log that ended in a window starting shortly before the last update of the :term[Friction Ledger], through :file[scripts/session/extract-frictions.ts], and files each Friction under a Ledger entry: one YAML file per root cause in :file[layers/journal/content/current/frictions/], listing every session that hit it and every PR meant to fix it. It then screens each candidate. One that a merged change already fixed, that an open issue or PR tracks, that only an edit to an outside pack Skill could fix, or whose fix would restore text an open :term[Prune Trial] cut, is dropped. One that came back after its fix merged is a regression: the run files an issue naming the fix that failed and never retries it.

The run picks a few fixes, weighing recurrence and severity together, and a design subagent designs each one and judges its risk. A fix that touches a :term[Human-only] file, a guard or the hook wiring, or that turns on a choice a person should make, becomes an issue. The rest go to helper agents, each in its own worktree: all doc fixes on one branch, each code or config fix on its own. The run reviews each branch, posts its verdict on the PR, and merges or leaves it for a human. Its updates to the Ledger land in a PR of their own every run, fixes or none.

Whether a fix worked is never written down by hand. The Ledger page derives each entry's state from the dates of its fixes and its later occurrences, in :file[layers/journal/app/utils/ledger.ts]:

::excerpt{path="layers/journal/app/utils/ledger.ts" lines="12-13"}
```ts
export type FixState = 'fix landed' | 'likely fixed' | 'still recurring'
export type LedgerState = FixState | 'open' | 'tracked' | 'on trial' | 'accepted'
```
::

**Prune Trials.** The `prune-trial` Skill, :file[.agents/skills/prune-trial/SKILL.md], cuts one problem's instructions down to the goal behind them, or rewrites one Skill or doc in plain words, and records the cut in :file[.agents/prune-trials.yml] with its territory and a check: how a later run would tell it broke. Before shipping, a subagent on a smaller model reads only the cut text and must answer a real case correctly. Once the cut has stood on `main` past its window, a later run reads the Frictions logged since and judges it:

::excerpt{path=".agents/skills/prune-trial/SKILL.md" lines="34-37"}
```md
- `major` or `blocker` damage that traces to the trial → restore the
  **minimum**: the one goal-shaped line that would have prevented it, never the
  wall that was there before.
- `nit`, `minor`, `moderate`, silence → the prune holds.
```
::

**Skill audits.** The `audit-skills` Skill, :file[.agents/skills/audit-skills/SKILL.md], starts from a scorecard that :file[scripts/session/audit-skills.ts] builds from recent logs: which Skills each session used, and which sessions shipped a merged PR but never logged. Subagents check whether our own often-used Skills did what their `SKILL.md` promises. A finding that did real damage, or repeats an earlier one, becomes an issue; any other is kept as an observation on the Skill's entry in the :term[Skill Inventory]. The run grades each Skill's importance by how much its absence was felt, and records an idea, never an action, when the evidence suggests retiring or splitting one.

### Why it's built this way

- **One complaint, or a pattern.** A cause that came back every few days hid inside each run's short reading window, and "already tracked" items were dropped run after run with nobody on them. The Ledger keeps one entry per cause, counting recurrence over weeks and keeping status between runs. The cost: every run must file each Friction under the right cause.
- **Facts by script, judgement by agent.** The scripts only gather and sort the logs; grouping, ranking and every fix are the session's call. A fixed script gives the same input every run, at a low token cost, instead of a parser improvised each time. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **A fix that failed goes to a person.** When a Friction comes back after its fix merged, that change has already failed once and needs a person's eyes. So the run files an issue that names the failed fix instead of trying again. The cost: regressions wait for a person. :file[.agents/skills/frictions-to-fixes/SKILL.md].
- **Remove to find out.** Reading a rule can't show what it still prevents, so rules only piled up; one was reworded sharper several times and still not followed. A trial removes the text and lets later Frictions decide; damage brings back one line stating the goal, not the old text. The cost: a failure nobody notices logs no Friction, so a trial can miss it. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).
- **A window from the real landing.** A trial was once judged a day early, against a landing commit that didn't exist. So a script finds when each cut actually reached `main`, and a trial whose landing can't be found isn't judged at all. :file[.agents/skills/prune-trial/SKILL.md].
- **The failures Frictions miss.** A Skill that runs and quietly doesn't deliver, or one that should have run and never did, leaves no Friction behind. The audit looks for both. It grades a Skill by need, not use: a rare Skill that is the right tool for its job keeps its grade. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).

### What to watch for

- **Leave open trials alone.** If an instruction you expected is missing, check :file[.agents/prune-trials.yml] before restoring it: inside an open trial's territory, log a Friction and work around it, as ADR-0027 (:file[docs/adr/0027-prune-trials.md]) asks.
- **A Friction you don't log never reaches the loop.** Nothing else feeds it, so a problem you fixed yourself mid-session still belongs in your log.
- **A merged fix isn't a working fix.** An entry reads `likely fixed` only after a quiet spell with no new occurrence, and `still recurring` when Frictions come back.
- **Retiring a Skill is a person's call.** The audit only records the idea and a trial run only files an issue; a :term[Trusted] user approves removing a Skill or a Routine.

## Try it in your project

Keep a shared file where each agent session appends the problems it hit, with a possible fix. Once a week, group them by cause, fix the cause that appears most, and delete one instruction you suspect nobody needs; check the next week's problems before you decide whether it comes back.
