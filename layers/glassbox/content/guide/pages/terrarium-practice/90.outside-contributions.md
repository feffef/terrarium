Once agents build a project, someone without write access can contribute in two ways: ask for a change and let the maintainer's agents build it, or send a change their own agent made. Either way their text is an idea, never an order, and a person with write access merges the result.

Know how your project takes outside work already? Skip to [In Terrarium](#in-terrarium).

## The concept

An outside contributor's issues and pull requests are input, and input can carry instructions aimed at any agent that reads it; [Author trust](/t/glassbox/guide/git-github/author-trust) covers who may direct one.

A maintainer can still let agents take an outsider's request all the way to a pull request without approving each one. The approval then comes from the maintainer starting the agents' job, and lasts only while it runs. Three limits keep it contained: the agent interviews the requester and builds only what they confirm; a written screen sends any request that looks dangerous to a person instead; and a person merges every pull request the job opens. When requests are few enough for a maintainer to approve each one, skip the job: it spends build time on every request, and each result still waits for a person.

An outsider's own agent, on another tool or model, can also open a pull request from a fork. It knows nothing of your project's habits, so write them where it will look: GitHub links a repository's contribution guidelines whenever someone opens an issue or pull request ([GitHub Docs: Setting guidelines for repository contributors](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors)). Say there what the change must carry with it, and that a person merges it.

## In Terrarium

:file[docs/agents/guest-contributions.md] names Terrarium's two modes and keeps them apart: the guest pipeline, where Terrarium's own agents build what a :term[Public] user asked for on an issue they filed, and an outside agent's fork PR.

Two :term[Skills]{id="skill"} run the guest pipeline, `guest-intake` and `guest-build`, and only while the owner starts them, by hand, on a :term[Routine] or with `/loop`. Both set `disable-model-invocation: true`, so neither starts itself.

`guest-intake` reads each open issue's newest comment, or its body when it has none, and `classifyActivity` in :file[.agents/skills/guest-intake/scripts/guest-intake-scan.ts] sorts it:

::excerpt{path=".agents/skills/guest-intake/scripts/guest-intake-scan.ts" lines="149-157"}
```ts
export function classifyActivity(activity: Activity, issue: Pick<RawIssueRecord, 'user' | 'author_association'>): Stage {
  if (isAiAuthored(activity.body)) return 'agent-authored-skip'
  if (PUBLIC_ASSOCIATIONS.has(activity.authorAssociation)) {
    const ownIssue = PUBLIC_ASSOCIATIONS.has(issue.author_association) && issue.user?.login === activity.author
    return ownIssue ? 'guest-activity' : 'bystander-comment'
  }
  if (TRUSTED_ASSOCIATIONS.has(activity.authorAssociation)) return 'owner-steering'
  return 'unrecognized-association'
}
```
::

A comment that opens with an agent's session header is the pipeline's own reply, whatever its association ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution) says how the header is read), and the issue waits until the guest writes again. A Public user counts as a guest only on an issue they filed. A :term[Trusted] comment without the header is the owner steering, and :file[.agents/skills/guest-intake/SKILL.md] has the agent obey it.

With a guest, `guest-intake` holds a short interview in comments: a few questions per comment, over a capped number of rounds, then a summary of what the site will do for a visitor, in the :term[Tenant]'s own words, which the guest confirms. The issue carries `needs-info` throughout. When the guest confirms, the agent screens the work against ADR-0023 (:file[docs/adr/0023-guest-driven-demo-pipeline.md]):

::excerpt{path="docs/adr/0023-guest-driven-demo-pipeline.md" lines="20-28"}
```md
- **What goes to the owner.** At confirmation and again before building, the
  agent labels the issue `ready-for-human`, with the reason, if the work would:
  - break or deface the site on purpose;
  - raise a major security concern: it touches secrets, credentials or
    environment variables, looks like XSS or injection, asks to run code or
    reach a shell, or weakens what keeps Tenants apart. Being ambitious is not
    a concern;
  - add a dependency;
  - touch a Human-only file (ADR-0004).
```
::

A request that passes gets `ready-for-agent` ([Issue triage labels](/t/glassbox/guide/git-github/issue-triage-labels)). :file[.agents/skills/guest-build/SKILL.md] picks it up, runs the screen again on the actual work, has an agent build it in its own worktree, reviews it on a different model, and opens a PR that closes the issue and carries the `guest-pipeline` label. It never merges; the owner does ([Author trust](/t/glassbox/guide/git-github/author-trust)).

Each Skill runs on its own schedule. Before acting on an issue, each adds a `guest-in-flight` label, and it removes the label in the same write that sets the resulting state label. The scans skip an issue whose label is fresh and treat an old one as abandoned, after a window set in :file[scripts/github/guest-label.ts].

An outside agent finds the second mode's rules through the Contributing section of :file[README.md], which points it to :file[CLAUDE.md] and :file[docs/agents/guest-contributions.md]. That doc's house rules ask its PR to carry the agent's own :term[session log], marked `external: true`, with one honest log per unit of work, revisions included; to open every GitHub post with a session header; and to expect a Trusted user to merge it by hand. Agents that reply to such a PR thank its author and turn each unmet rule into a concrete next step, with the rule named and linked.

### Why it's built this way

- **The guest exception runs only while the owner runs it.** Letting guests watch agents build their idea automates an approval kept for people. The owner's merge contains guest text that steers an agent: a guest reaches a PR, never `main`. Tying the exception to the owner running the Skills turns it off without code. The cost: every guest issue costs build time and an owner's review. ADR-0023 (:file[docs/adr/0023-guest-driven-demo-pipeline.md]).
- **An interview in rounds.** A design interview usually asks one question at a time, but a guest answers a GitHub thread on their own time, and one question per comment would stall it. So each comment asks a few, over capped rounds, and a clear idea goes straight to its summary. The cost: after the last round the summary goes out anyway. :file[.agents/skills/guest-intake/SKILL.md].
- **Screened twice.** Guest text can steer an agent towards code the owner never wanted. The screen runs when the guest confirms a summary, and `guest-build` runs it again on the work itself before anything is built. The cost: an escalated idea waits for the owner, and the guest is told so. :file[.agents/skills/guest-build/SKILL.md].
- **A claim label between Skills.** Intake and build each run on their own interval, with no view of each other's work in flight, so both could act on one issue at once. A label both add before acting keeps one at a time. The cost: with no heartbeat, a dead session's label blocks the issue until it ages out. :file[scripts/github/guest-label.ts].
- **An outside log rides its PR.** An outside agent has no hook that lands its log and can't push to `main`, so the log commits with its change. Its Frictions describe tools Terrarium's fixes can't reach, so Friction mining and the Skill audit skip an `external` log and use only its ideas. The cost: the log lands only if the PR merges. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).

### What to watch for

- **Only the filer's comments count.** A Public comment on someone else's issue is a bystander's, and the pipeline does nothing with it, however it is worded.
- **Nothing answers while the Skills are stopped.** Guests can still file issues, but no agent replies until the owner starts the Skills again ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks)).
- **An unbuildable idea gets alternatives, not a refusal.** The site is built from committed files and stores nothing visitors write, so an idea such as a login or visitor comments is offered buildable alternatives instead. The alternative the guest picks is what gets confirmed and screened, not their first ask (:file[.agents/skills/guest-intake/SKILL.md]).

## Try it in your project

Write the rules an outside agent must follow into your contributing guidelines file: where its record of the work goes, how it marks its posts, and who merges. If you run an agent that builds outsiders' requests, write its screen as a short list of what goes to a person, run it when the requester confirms and again before the build, and leave every PR it opens for a person to merge.
