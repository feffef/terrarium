Code shows what a project does, but not why it does it that way, or which other ways were tried and ruled out. An architecture decision record, or ADR, writes that down: one short file per decision, kept in the repository beside the code it explains.

Know ADRs already? Skip to [In Terrarium](#in-terrarium).

## The concept

An ADR records one decision that matters to the shape of a system: its context, what was decided, and why. A team numbers its ADRs and keeps them in a folder of the repository, such as `docs/adr/`, so they are versioned and reviewed like code. A future reader who wonders why the code looks the way it does finds the answer there, and writing one makes a group argue its way to an agreement before it commits.

Not every choice deserves one. A good test asks three things: the decision is hard to reverse, it would surprise a reader who lacks the context, and it came from a real trade-off between options. A record of an obvious choice adds nothing.

The classic practice treats an accepted ADR as fixed. When the decision changes, you don't edit the old record; you write a new one that supersedes it, and link the two. Martin Fowler's [Architecture Decision Record](https://www.martinfowler.com/bliki/ArchitectureDecisionRecord.html) describes it that way. The folder then reads as a history of decisions, and to learn what holds today you follow the chain to its end.

## In Terrarium

Terrarium's ADRs live in :file[docs/adr/], one numbered file each, and every one follows :file[docs/adr/TEMPLATE.md]: a `# ADR-NNNN:` heading, a short summary that covers the whole decision, then *Scope*, *Why* and *Rejected alternatives*, with optional sections left out rather than filled. The template's required part:

::excerpt{path="docs/adr/TEMPLATE.md" lines="1-9,11,15"}
```md
# ADR-NNNN: <title: a short reminder of what the ADR is about, the same heading its summary rule uses>

<A summary of 2–3 sentences covering the whole decision. A reader who stops
here knows what we decided.>

## Scope

<What the decision covers, who may do what, and the exceptions that change
that.>
<!-- … -->
## Why
<!-- … -->
## Rejected alternatives
```
::

Terrarium breaks with the classic practice on one point: when a decision changes, its ADR is rewritten in place, and git keeps the old versions. ADR-0030 says what that rules in and out.

The :term[Gate] enforces the shape. :file[scripts/gate/validate-adr-rules.ts] runs in `pnpm validate:content`, with its checks in :file[scripts/lib/adr-rules.ts], and fails any ADR that doesn't open with its heading, or that holds one of these:

::excerpt{path="scripts/lib/adr-rules.ts" lines="126-131"}
```ts
/** History an ADR must not carry: git holds it (ADR-0030). */
const HISTORY: [RegExp, string][] = [
  [/\b\d{4}-\d{2}-\d{2}\b/, 'a date'],
  [/^(Status|Date):/m, 'a status line'],
  [/^>\s*\**(Amended|Superseded)\b/im, 'an amendment banner'],
]
```
::

Each ADR also has a summary :term[Rule], which [Path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules) covers. The same script fails the Gate when an ADR changed since its rules were last checked, or when its summary has no line that points to the ADR, says when to read it in full and gives a current token estimate.

### Why it's built this way

- **An ADR states only the decision as it stands.** Dated amendments piled up, some reversing others, and one ADR's main text contradicted its own amendment, so an agent had to rebuild today's rule from the layers. Each ADR is now rewritten in place. The cost: the same PR must also rewrite its summary rule and repoint what cites it. ADR-0030 (:file[docs/adr/0030-adrs-document-a-decision-not-its-history.md]).
- **Git keeps history.** Git already keeps every version with its change and reason, so history in the ADR was a second copy that made the first harder to read. The cost: a reader who wants a decision's path must run `git log` on the file. Rejected alternatives stay, to stop the same idea being proposed again. ADR-0030 (:file[docs/adr/0030-adrs-document-a-decision-not-its-history.md]).
- **One home per fact.** ADRs repeated numbers and steps that a script or Skill also held; the copies came apart and agents trusted the stale one. Now a number or command lives where it is enforced and the ADR points there, leaving it the reasoning no code comment or Skill records. The cost: a reader who wants the number follows the ADR's pointer to it. ADR-0030 (:file[docs/adr/0030-adrs-document-a-decision-not-its-history.md]).
- **Agents read a summary Rule first.** An agent gets a short summary Rule and reads the full ADR for the why; [Path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules#why-its-built-this-way) says why. The cost: two texts that can drift, which the Gate's check above catches. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).

### What to watch for

- **Any date fails the check.** The pattern above matches a date anywhere in an ADR's text, even in an example.
- **An ADR change waits for a person.** Every file in `docs/adr/` is on the :term[Human-only] list, so an agent may rewrite an ADR but not merge the change.
- **Ignore domain-modeling's ADR template.** The installed `domain-modeling` Skill in :file[.agents/skills/domain-modeling/] has its own ADR template, with a `Status` field. Terrarium's template replaces that layout.

## Try it in your project

Pick one decision in your code that a newcomer keeps questioning. Write it as an ADR of a summary, *Why* and *Rejected alternatives*, in a numbered file under `docs/adr/`. When the decision changes, decide once whether your team edits the record or supersedes it, and write that choice down as your first ADR.
