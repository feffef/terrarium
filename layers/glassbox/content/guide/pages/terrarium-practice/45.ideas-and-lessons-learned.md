A review that asks only "what went wrong?" teaches a team to avoid its mistakes, and loses what went well and what was worth trying next. Those thoughts are clearest in the middle of the work and gone by the next meeting. Capture them where they happen, then harvest them into proposals a person decides on.

Know retrospectives that collect ideas? Skip to [In Terrarium](#in-terrarium).

## The concept

Many retrospective formats ask three questions, not one: what went wrong, what went well, and what to try. The first yields fixes. The other two yield lessons to keep and ideas for new work, and they are the easiest to drop: a problem demands attention, an idea doesn't.

Two things decide whether such notes are worth anything. The first is when they are written. A lesson noted while the work is fresh carries its context; one reconstructed later is vaguer, or gone. For agents this is sharper still, since an agent's context ends with its session: what it noticed is written then or never. The second is what happens next. Notes nobody reads cost effort and change nothing, so someone has to collect them, drop what is already built, filed or rejected, and turn the rest into proposals that carry enough context for a person to decide on each without digging.

That decision stays with a person: an agent is good at noticing what could be built, but whether it should exist is a product choice. Capturing ideas is the wrong choice where nobody will ever harvest them, or where one person already reads every session as it happens.

## In Terrarium

A :term[session log] holds two optional lists beside its required :term[frictions]{id="friction"}: `learnings`, knowledge the session worked out rather than read, and `ideas`, concrete proposals for the platform's or a :term[tenant]'s future, specific enough to become an issue. Both are lists of plain strings in :file[shared/schemas/session.ts]. The `close-session` :term[skill] asks for them in the agent's last look back at the work: a fact found late by inference is also a learning, and a proposal reaching well past one friction's fix is an idea (:file[.agents/skills/close-session/SKILL.md]). `log-session` adds that each is written only when the session produced one: a fact read from a file is not a learning, and an idea names the thing to build and why, in words a later reader could file as an issue (:file[.agents/skills/log-session/SKILL.md]). [Session logs](/t/glassbox/guide/terrarium-practice/session-logs) covers the rest of the log.

The Journal lists every note on its "Ideas & learnings" page, newest first. Some skills write ideas on purpose: a `visitor-loop` run records each unbuilt idea its visitors raised in its log's `ideas` (:file[.agents/skills/visitor-loop/SKILL.md]).

The `harvest` skill, :file[.agents/skills/harvest/SKILL.md], turns notes into issues. It starts by name, from a person's command or a routine's prompt; an agent can't invoke it on its own. Its helper, :file[.agents/skills/harvest/scripts/harvest.ts], lists the notes in recent logs that no issue has taken yet, skipping the logs of the `harvest` and `audit-skills` runs (`SKIPPED_TRIGGERS` in that file). It ranks them by recency alone and alternates the two kinds, which only sets the order the agent reads them in:

::excerpt{path=".agents/skills/harvest/scripts/harvest.ts" lines="117-121,161-168"}
```ts
/** Unharvested entries from logs that ended in the window, newest first within a
 *  kind. Recency is the only signal: ranking by a session's Friction would bury the
 *  positive and creative ideas of a smooth session. The two kinds alternate (idea
 *  first) and one that runs out lets the other continue. */
export function buildEntries(
  // …
  const rank = (a: Draft, b: Draft) => b.endedAt.localeCompare(a.endedAt) || a.key.localeCompare(b.key)
  const ideas = all.filter((e) => e.kind === 'idea').sort(rank)
  const learnings = all.filter((e) => e.kind === 'learning').sort(rank)
  const ordered: Draft[] = []
  for (let i = 0; i < Math.max(ideas.length, learnings.length); i++) {
    if (ideas[i]) ordered.push(ideas[i]!)
    if (learnings[i]) ordered.push(learnings[i]!)
  }
```
::

The agent then merges near-duplicates into clusters and labels each one **product** (a tenant, its content, the UI) or **workflow** (instructions, skills, hooks, the gate), checking every product cluster before the first workflow one. A cluster passes only when its change is unbuilt, unfiled and unrejected, no :term[friction ledger] entry already names its problem, its own session didn't already do it, and a workflow cluster's idea retires as much as it adds, while a learning is a fact its home doc lacks. The agent writes each cluster's evidence for every test into a record file, and no issue is filed until `harvest check-clusters` accepts that record.

Each passing cluster becomes a :term[seedling], up to a small cap per run with a smaller one for workflow clusters: an issue titled `Seedling: …`, labelled `ready-for-human`, written to :file[.agents/skills/harvest/body-template.md]. Its banner says it is not approved. Under it, a block of `Harvested:` key lines names each entry it took, by session, kind and a hash of the note's text; a retro entry's key ends in `retro` in place of the kind and hash:

::excerpt{path=".agents/skills/harvest/scripts/harvest.ts" lines="38,65-68"}
```ts
export const KEY_RE = /^Harvested: (\S+ (?:(?:idea|learning) [0-9a-f]{8}|retro))$/
// …
export function entryKey(session: string, kind: Kind, text: string): string {
  const hash = createHash('sha1').update(flattenText(text)).digest('hex').slice(0, 8)
  return `${session} ${kind} ${hash}`
}
```
::

`harvest extract` reads every issue, open or closed, and skips each entry whose key it finds there. A run's retro step adds one more seedling, a retro on the skill itself, keyed that way. `check-body` checks a body before it is posted, and `check-posted` checks that the stored issue holds the same keys.

A seedling then waits for a :term[trusted] user. `auto-triage` skips it until a trusted user relabels it or says to build it (:file[.agents/skills/auto-triage/SKILL.md]), and the owner's `clear-backlog` run only ever asks about one, never building or closing it itself (:file[.claude/workflows/clear-backlog-explore.js]). Approving it works like approving any new work: [Human-in-the-loop agents](/t/glassbox/guide/terrarium-practice/human-in-the-loop).

### Why it's built this way

- **A learning lives only in the session that inferred it.** A fact read from a file can be read again; one the agent worked out cannot. So `close-session` asks for learnings and ideas in the agent's last look back, before the session ends. The cost: they come from memory, with no transcript read. :file[.agents/skills/close-session/SKILL.md].
- **Recency, not pain, ranks the notes.** Ranking by a session's frictions would bury the positive, creative ideas of a smooth session. So the helper orders notes by when their session ended and nothing else. The cost: a note from a log older than the helper's window of recent logs is never harvested, however good it was. :file[.agents/skills/harvest/scripts/harvest.ts].
- **The issues themselves hold the state.** A rerun, or a run after a gap, must not file an entry twice. So a key line on any issue, open or closed, marks its entry as taken, and no separate list exists. The cost: every run reads the whole tracker, and each posted body is checked to still hold its keys. :file[.agents/skills/harvest/SKILL.md].
- **Pains go to the ledger, ideas to seedlings.** `frictions-to-fixes` owns the pains. So `harvest` files only the ideas and learnings the ledger doesn't carry, and leaves every problem a friction ledger entry names to it. The cost: a cluster the ledger covers in part shrinks to the part it misses. :file[.agents/skills/harvest/SKILL.md].
- **A person green-lights each seedling.** Whether something should exist is a product choice, a reason [Human-in-the-loop agents](/t/glassbox/guide/terrarium-practice/human-in-the-loop) explains. So a seedling skips triage: `harvest` is the one skill outside it that files an issue as `ready-for-human`, not `needs-triage`. The cost: nothing is built until a trusted user approves. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).

### What to watch for

- **An idea in a log is not a plan.** It is noted, not planned, and nothing builds it until a trusted user approves its seedling. Only `harvest` files seedlings; anyone else's proposal is a plain issue ([Issue triage labels](/t/glassbox/guide/git-github/issue-triage-labels)).
- **Unharvested notes age out.** `harvest` reads only recent logs, so a note no run took in time stays only on the Journal page.
- **An outside agent's learnings are dropped.** `harvest` keeps the ideas of a log written by an outside agent ([Outside contributions](/t/glassbox/guide/terrarium-practice/outside-contributions)) and skips its learnings; the schema's comment says a good idea is toolchain-agnostic.
- **Vague notes are noise.** "Someone should look into X" can't become an issue; `log-session` asks for the thing to build and why, and for no note at all when the session produced none.

## Try it in your project

Add two optional lists to the record your agents write at the end of a session: `learnings` (things worked out, not read) and `ideas` (something to build, and why). Keep the records in one file such as `sessions.json`:

```json
[
  {"session": "s-101", "learnings": ["The test runner skips files without .spec in their name"],
   "ideas": ["Cache dependencies in CI: every run reinstalls them"]},
  {"session": "s-102", "learnings": [],
   "ideas": ["Add a search box to the docs site: readers ask where pages are"]}
]
```

When you file a note as an issue, add its line to `filed.txt`. This lists every note not filed yet; `grep -vxFf` drops each line that matches a whole line of `filed.txt`:

```sh
jq -r '.[] | (.ideas[] | "idea: \(.)"), (.learnings[] | "learning: \(.)")' sessions.json | grep -vxFf filed.txt
```

With the caching idea in `filed.txt`, it prints:

```text
learning: The test runner skips files without .spec in their name
idea: Add a search box to the docs site: readers ask where pages are
```

Read what is left, drop what is already done or rejected, and file the rest as issues under a label only a person removes.
