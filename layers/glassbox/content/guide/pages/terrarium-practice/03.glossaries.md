When people and agents use different words for one thing, or one word for different things, every conversation about the code drifts. A glossary fixes the words. In a project with several distinct parts, one glossary per part keeps each list short enough to read.

Know ubiquitous language already? Skip to [In Terrarium](#in-terrarium).

## The concept

Eric Evans's domain-driven design calls it a [ubiquitous language](https://martinfowler.com/bliki/UbiquitousLanguage.html): one shared vocabulary that developers and the people who know the domain both use, in conversation, in documents and in the code itself. Each term has one definition and one preferred word. A synonym in a pull request is a hint that two people mean different things, so a team that keeps a glossary challenges it.

One language rarely fits a large system. The same word can mean different things in two parts of it: an "account" in billing is not an "account" in sign-in. Domain-driven design draws a boundary, a bounded context, around each part, and each context gets its own language. A map says which contexts exist and how they relate.

For an agent, the glossary is also context it reads. A short glossary costs every session little, while words from parts of the system the session never touches only crowd out the ones it needs.

## In Terrarium

Terrarium splits its vocabulary by who needs it, as :file[GLOSSARY-MAP.md] opens:

::excerpt{path="GLOSSARY-MAP.md" lines="3-5"}
```md
Domain vocabulary is split (ADR-0021) between a shared **Platform glossary** at
the root and one glossary per Tenant, beside that Tenant's code. Read the
Platform glossary always; read a Tenant's glossary when you work on that Tenant.
```
::

The Platform glossary, :file[GLOSSARY.md], holds the words every agent needs whatever its task, such as :term[Tenant], :term[Space] and :term[Friction]. It is a glossary only, with no implementation details, plus two lists: the Tenants, each linking its own glossary, and the terms Terrarium stopped using, so older text stays readable. :file[CLAUDE.md] has every session read the map and then this glossary at the start, and use a glossary's term rather than a synonym.

Each Tenant's own words live in `layers/<tenant>/GLOSSARY.md`, beside its code. The Blog's, :file[layers/blog/GLOSSARY.md], defines a Persona; the Atlas's defines a Biome. Both are the root glossary's Space under a Tenant-specific name and meaning, and the root entry says so and points there. A Tenant's glossary holds more than words: why the Tenant exists, who it's for and its product decisions, which have no other home, because only decisions about the Platform get an ADR.

Each term is defined once, in one glossary; anywhere else may point to it. Two rules in :file[docs/agents/domain.md] keep the lists from growing. A concept earns a term only at its second instance: before that, describe it in plain words where it lives. A concept missing from the glossary means either the writer is inventing language or there is a real gap to record. `CLAUDE.md` sends an agent to that doc before it adds or changes a term.

### Why it's built this way

The split, what goes in each glossary, and why a demo Tenant's purpose lives in its glossary rather than an ADR: ADR-0021 (:file[docs/adr/0021-multi-context-domain-docs.md]). Its *Why*: when the root glossary held every Tenant's words, an agent looking up a Platform term read past another Tenant's fictional species.

### What to watch for

- **Define once, point elsewhere.** A second definition of a term will drift from the first. Write a pointer to the glossary that owns it instead.
- **A coined term costs every session.** Every session reads the Platform glossary, so a term there is paid for on every task. Hold back until the second instance, and prefer a plain phrase.
- **The Skill's templates differ.** The `domain-modeling` Skill in :file[.agents/skills/domain-modeling/] supports several glossaries tied together by a map, which is the shape Terrarium uses. Its entry layout differs from Terrarium's, and `domain.md` lists where Terrarium departs from it.
- **ADRs are not glossaries.** A decision with reasons belongs in an ADR, and a word with its meaning in a glossary: [ADRs: one decision, no history](/t/glassbox/guide/terrarium-practice/adrs).

## Try it in your project

List the five nouns your team argues about most. Write each with a one-sentence definition in a `GLOSSARY.md` at the root, and add one line to your `CLAUDE.md` telling agents to read it and use its words. When one part of the system starts using a word differently, give that part its own glossary and add a map.
