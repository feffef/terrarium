A project that gives its agents many Skills, folders of instructions each written for one kind of job, soon can't say which ones it has, which still earn their place, or where to write down how it uses a Skill it didn't write. An inventory is one record of them all, graded by how much each is needed and kept honest by evidence from real sessions.

Know inventories of tools or services? Skip to [In Terrarium](#in-terrarium).

## The concept

A Skill costs something after it is written. A Skill an agent may start on its own keeps its description in every session's context, and someone must keep its steps true. Skills pile up, and nobody remembers which exist, which a newer one replaced, or which a kind of work depends on.

An inventory has one entry per Skill and does three jobs:

- **A map.** One plain sentence on what the Skill is for on this project. A Skill's own description is written for the model that decides whether to start it, not for a person deciding whether to keep it.
- **A home for notes.** A Skill installed from another repository can't be edited, so a caveat about how your project uses it has nowhere to sit in its file. The entry can hold it.
- **A grade.** How much the project needs the Skill, with the evidence kept beside it.

An entry for a Skill that reviews a diff might read: *Checks a change against the repo's standards before a pull request opens. Grade: essential. Note: installed from another repository, never edited.*

A grade is only worth trusting when it comes from evidence nobody has to remember. Sessions leave logs, and a periodic review reads them: which Skills ran, which a problem names, which a person reached for. Good evidence is a session where skipping a Skill cost a rework, not a tally of how often it ran, because a rarely used Skill can be the only tool for its job.

An inventory is the wrong tool for a handful of Skills that one person knows well: a line in the README does the job. It starts to pay when Skills are many, some come from outside, and agents rather than people choose which to run.

## In Terrarium

The Skill Inventory is one YAML file per Skill in the Journal :term[Tenant], in :file[layers/journal/content/current/skills/]. A Skill gets its file when the `audit-skills` Skill, described below, first sees it in use. An entry's fields come from one schema, :file[layers/journal/tenant.config.ts]:

::excerpt{path="layers/journal/tenant.config.ts" lines="20-22,32,38"}
```ts
    name: z.string(),
    category: z.enum(['platform-operation', 'general-engineering']),
    importance: z.enum(['essential', 'routine', 'specialist', 'supporting', 'peripheral']),
    // …
    role: z.string(),
    // …
    installedSha256: z.string().optional(),
```
::

An entry also has a short `gist` for the top grades and `observations`: the audit's own dated notes of evidence. The site doesn't show them; later audit runs and `audit-docs` read them. Data moves through an entry in three steps. `installedSha256` is a hash of an installed Skill's file, which the Gate recomputes.

**Evidence in.** Each :term[session log] lists the Skills the session used in `skillsUsed`: the agent's own picks plus the ones its transcript shows. :file[scripts/session/audit-skills.ts] reads a recent window of logs into one scorecard row per Skill: the sessions that used it, the sessions whose Frictions or learnings name it, and the sessions whose logged reason says a person asked for it.

**A Routine grades.** A :term[Routine] runs the `audit-skills` Skill, :file[.agents/skills/audit-skills/SKILL.md]. The grades are `essential` (its absence would be felt across many kinds of session), `routine` (scheduled sessions run it), `specialist` (essential within one kind of work, even a rare one), `supporting` and `peripheral`. A grade moves only on cited evidence: at least two sessions in the window where the Skill caught something or where skipping it cost something. Bare use counts don't move it. It writes only Inventory entries, Routine run costs and issues, never a Skill. A script deletes observations once they pass a fixed window, and `role` stays a short plain description with no PR, issue or session ids. Its other jobs are in the [Self-improvement loop](/t/glassbox/guide/terrarium-practice/self-improvement-loop).

**Entries are read.** Four readers use them:

- **People** read the Journal's [Skills page](/t/journal/current/skills): Skills grouped by grade, each with the number of sessions that used it beside the grade. Installed Skills are listed apart.
- **Agents** read the notes an installed Skill can't hold. The installed `triage` Skill's file is never edited, so the rule that a Public author's issue is checked by reading only sits in its entry, and `auto-triage`, the unattended triage sweep, points there:

::excerpt{path="layers/journal/content/current/skills/triage.yml" lines="1-10"}
```yaml
name: triage
category: general-engineering
importance: supporting
installedSha256: 917b0baf74be583e74f110857ed45df2766617f75c00baf61fd136d7af515edf
role: >-
  Moves an issue or external PR through the triage state machine (categorise,
  verify, grill, write an agent-ready brief, set readiness); the manual
  counterpart to `auto-triage` (ADR-0022). Verify Public-authored items by
  reading only: never check out, install, build, test or run them, since hooks
  would run their code with the session's GitHub credentials (ADR-0020).
```
::

- **Other Skills.** `audit-docs`, a scheduled Skill that finds docs that no longer match the code, checks entries like any doc, leaves the grade alone, and uses a Skill's `observations` as evidence for a drift finding.
- **Checks.** The :term[Gate] fails when an installed Skill's file no longer matches its pin ([Installed skills](/t/glassbox/guide/skill-pack/skill-packs)) and rejects an entry that says when a Routine runs ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks#why-its-built-this-way)). A unit test, :file[layers/journal/tests/unit/importance-consistency.spec.ts], fails when the grades in the schema and the order the page groups them in drift apart.

### Why it's built this way

- **A grade says need, not use.** Grading by uses would punish a rare Skill that is the right tool for its job, and grading by Frictions per use would mislead, since hard sessions use more Skills and log more problems. So a grade follows how much a Skill matters when its kind of work comes up. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **A project note on an installed Skill goes in its entry.** Reinstalling overwrites an edit to the Skill's own file without notice, so nobody edits it. The entry is where the audit and the Journal read a note, and the pin turns an edit to the file into a failed check. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Readers get prose, the audit keeps the ids.** Entries that cited pull requests and sessions turned into an audit log and crowded out the sentence a reader came for. So `role` stays plain and the dated evidence goes in `observations`. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).

### What to watch for

- **A grade is not a usage count.** The page prints use beside the grade as a separate fact, and a Skill with no recent sessions can keep a high grade. Read its `role` and `observations` before you act on how often it ran.
- **A note expires.** Observations are pruned after a fixed window, so anything a later run must keep belongs in `role`.
- **A new grade touches three places.** Change the schema, the page's grouping order and the grade count in the consistency test, or the test fails.
- **A scheduled Skill's entry can go stale unseen.** A Routine's timer can stop with no commit. When the audit finds none of its runs in the window, it notes the possible stop, rewords a `role` that says the Skill is scheduled and regrades it by the grade definitions.

## Try it in your project

Keep one file per Skill: a sentence on what it is for here and a grade from a short fixed list. Count which Skills your session records show running, and read those sessions before you change a grade. Put dated notes in a separate field and delete the old ones. Then look for the first Skill you would cut.
