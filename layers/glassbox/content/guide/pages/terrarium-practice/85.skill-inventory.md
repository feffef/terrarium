A team that adds automated helpers without recording them soon can't say which ones exist, what each is for, or which it could do without. The answer lives in people's heads, and agents have no head to keep it in. An inventory writes it down, with a grade for how much each part is needed.

Know inventories of tools or services? Skip to [In Terrarium](#in-terrarium).

## The concept

An inventory has one entry per part, so a reader can see the whole set at once. Each entry says what the part is for on this project in plain words, which is not a copy of the part's own description, and gives it a grade of need. A grade answers how much its absence would hurt, not how often it runs: a rarely used part can be the only tool for its job.

Facts that change go in the evidence, not in the prose. The grade moves only when evidence supports it, and the evidence is kept beside the entry where the next review can read it. Without that discipline the entry becomes a log that nobody reads.

Full reference: [Claude Code docs: Extend Claude with skills](https://code.claude.com/docs/en/skills)

## In Terrarium

The Skill Inventory is one YAML file per Skill in :file[layers/journal/content/current/skills/], in the Journal :term[Tenant]. A Skill gets its file when it is first seen in use. The Journal page at [/t/journal/current/skills](/t/journal/current/skills) groups the Skills Terrarium wrote by grade and lists the installed ones apart, each with the number of sessions that used it.

An entry's fields come from one schema, :file[layers/journal/tenant.config.ts]:

::excerpt{path="layers/journal/tenant.config.ts" lines="20-22,32,38"}
```ts
    name: z.string(),
    category: z.enum(['platform-operation', 'general-engineering']),
    importance: z.enum(['essential', 'routine', 'specialist', 'supporting', 'peripheral']),
    // …
    role: z.string(),
    // …
    installedSha256: z.string().optional(),
```
::

`role` is plain prose with no pull request, issue or session ids. A short `gist` is written for the top grades. The ids go in `observations`: dated notes of the evidence behind a finding or a grade, which the site doesn't show and which keep only recent history.

The grades are `essential` (its absence would be felt across many kinds of session), `routine` (a scheduled :term[Routine] runs it), `specialist` (essential within one kind of work, even a rare one), `supporting` and `peripheral`. The `audit-skills` Skill, :file[.agents/skills/audit-skills/SKILL.md], keeps them current. It checks that Skills fire when they should and deliver what they promise, moves a grade only on cited session evidence, and edits only Inventory entries, Routine run costs and issues, never a Skill.

Two :term[Gate] checks protect the data. For an installed Skill, the entry's `installedSha256` pins a hash of its `SKILL.md`: :file[scripts/gate/validate-skills-lock.ts] fails on any difference, and `pnpm verify:skills-lock --write` records a new pin after a legitimate install. :file[scripts/gate/validate-skill-cadence.ts], part of `pnpm validate:content`, fails a sentence in an entry that pairs "Routine" with a word such as "weekly".

### Why it's built this way

- **Importance is need, not frequency.** Grading by how often a Skill runs would punish a rare Skill that is the right tool for its job. So a grade says how much a Skill matters when its kind of work comes up, and disuse alone never lowers it. The cost: a grade needs a judgement from evidence, which a run can get wrong. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Notes on an installed Skill go in its entry.** Nobody edits an installed Skill, so its problems and fit are recorded in the Inventory instead; [Installed skills](/t/glassbox/guide/skill-pack/skill-packs#why-its-built-this-way) gives the reasons. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **Ids stay out of `role`.** Entries that cited pull requests and sessions turned into an audit log and crowded out the prose readers came for. So the evidence goes in `observations`, which the site hides. ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).
- **No schedule in an entry.** A Routine's schedule is set outside the repository and can change with no commit, so a sentence naming it would go stale unseen. An entry says that a Skill is scheduled, never when, and the cadence check enforces it. :file[scripts/gate/validate-skill-cadence.ts].

### What to watch for

- **A grade is not a usage count.** `peripheral` means little pull even where the Skill applied, not that it rarely runs; the session count on the page shows use separately.
- **Pins are machine-managed.** Never hand-edit `installedSha256`; regenerate it with `pnpm verify:skills-lock --write`.

## Try it in your project

List every automated helper your agents can call, in one file each. For every one write a plain sentence on what it is for and a grade of how much its kind of work needs it. Put dates and evidence in a separate field. Review the list on a schedule, and change a grade only when you can cite what you saw.
