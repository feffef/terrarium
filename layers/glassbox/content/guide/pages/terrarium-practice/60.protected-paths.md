Some changes need a person to merge them, and a list of protected paths says which. If that list lives in the same repository as the changes it judges, a change can edit the list and let itself through. Terrarium reads the list from `main`, which an open pull request can't change.

Know protected-path lists already? Skip to [In Terrarium](#in-terrarium).

## The concept

A check that decides whether a change may merge reads some settings: which files are sensitive, who may approve them. If it reads them from the branch under review, the branch is judging itself. A pull request that removes a file from the sensitive list and changes that file at the same time passes, because the check sees the shortened list.

The fix is to read the settings from the branch the change merges into. That copy already went through review, and no open pull request can alter it. A change to the list itself then waits for review like any other, and takes effect only once it merges.

Two more habits keep such a check honest. It fails closed: if it can't read the list, it refuses rather than treating an empty list as "nothing is sensitive". And it counts every path the change touches, including the old path of a renamed file, so moving a file out of a protected folder still counts as touching it.

A list like this earns its place only where some changes merge with no second person, such as authors or agents allowed to merge their own work. Where every change already waits for a reviewer, a list that only marks files as needing a person adds nothing. And it costs upkeep: each new sensitive file must be added by hand, and one left off passes unchecked, since the check sees paths, not what a change does.

## In Terrarium

Terrarium calls its protected paths the :term[human-only] list. It is the `paths` field of one file, :file[.claude/rules/adr-0004-human-merge.md]:

::excerpt{path=".claude/rules/adr-0004-human-merge.md" lines="3-4,17,22,25-26"}
```md
paths:
  - "content.config.ts"
  # …
  - ".claude/rules/**"
  # …
  - "scripts/github/merge-pr.ts"
  # …
---
# Human-only files (ADR-0004)
```
::

That file does two jobs. It is a [path-specific rule](/t/glassbox/guide/claude-code/path-scoped-rules), so when an agent reads or edits a listed file, Claude Code loads its text, which tells the agent that a person will normally merge the PR. And it is the list the merge script enforces. One list serves both, so the warning and the refusal can't disagree.

Agents merge their own PRs with :file[scripts/github/merge-pr.ts]. Before it waits for CI, it compares every file the PR touches, a rename's old path included, with the list as it stands on `main`:

::excerpt{path="scripts/github/merge-pr.ts" lines="456-463,549-554"}
```ts
function readHumanMergeGlobsFromMain(cwd: string): string[] {
  try {
    git(['fetch', 'origin', 'main'], cwd, { stdio: 'ignore' })
    return rulePaths(git(['show', `origin/main:${HUMAN_MERGE_RULE}`], cwd))
  } catch {
    return []
  }
}
// …
    const globs = readHumanMergeGlobsFromMain(cwd)
    const humanRefusal = humanMergeRefusal(prFilePaths(files), globs)
    if (humanRefusal !== null) {
      waiver = humanMergeWaiver(prFilePaths(files), globs, opts.ownerApproved, opts.mergeMethod)
      if (waiver === null) return { pr: prNumber, verdict: 'human-merge', merged: false, message: humanRefusal }
    }
```
::

The script fetches `main` first, then reads the rule with `git show`, so neither the branch's copy nor a stale local one counts. Any failure along the way returns an empty list, and `humanMergeRefusal` refuses the merge on an empty list. The globs are matched with Node's [`path.matchesGlob`](https://nodejs.org/api/path.html#pathmatchesglobpath-pattern). The rule file sits under `.claude/rules/`, which the list covers, so a PR that edits the list is itself refused unless the owner waives it (below). :file[tests/unit/merge-pr.spec.ts] covers the refusals and the waiver below.

The refusal has one waiver, which ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]) records: the owner's word, passed as `--owner-approved "<quote>"`. `humanMergeWaiver` turns it into the merge commit message:

::excerpt{path="scripts/github/merge-pr.ts" lines="211-215"}
```ts
export function humanMergeWaiver(files: string[], globs: string[], quote: string | undefined, method: MergeMethod): string | null {
  const hits = humanOnlyFiles(files, globs)
  if (!quote || hits.length === 0 || method === 'rebase') return null
  return `Human-only merge waived on the owner's word (ADR-0004): "${quote}"\nHuman-only files: ${hits.join(', ')}`
}
```
::

With no quote, an unreadable list or a rebase merge, which drops the commit message, it returns `null` and the refusal stands. It lifts only the human-only refusal: the checks after it, and CI, still run before the merge.

The same reading serves one more caller: :file[.agents/skills/clear-backlog/scripts/list-human-only-paths.ts] prints the human-only paths a branch touches, also read from `origin/main` and also failing on an empty list, so a backlog run can say in its PR description that the PR waits for a person.

### Why it's built this way

- **Code enforces which files need a person.** A person used to merge every PR, so risky files were named only in prose. Once agents merged on a green :term[gate] ([Merge gate](/t/glassbox/guide/verification/gate) says why), code had to enforce that line. The cost: the list must also cover what keeps self-merging safe, such as the merge script, trust tiers, the gate and the list's own file. ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).
- **The list exists once, as a rule's paths.** :term[ADR] text repeated the list, and the copies went stale at each change. Now it exists once, as the `paths` of a :term[rule], which Claude Code already reads to decide when to show that rule ([Path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules)). The cost: it is the one ADR summary rule that holds a fact of its own. ADR-0029 (:file[docs/adr/0029-instructions-load-with-the-files-they-govern.md]).
- **A rename counts both its paths.** A security review found the gate checked only a renamed file's new path, so renaming a test into a docs folder skipped the tests. Now every file list feeding a decision counts both paths, and the merge script adds the old name GitHub reports. The cost: even a harmless rename out of a protected folder waits for a person. :file[docs/agents/git-conventions.md].
- **A script, not the agent, finds human-only files.** An agent reported no human-only files for a branch that edited rules, so its PR description was wrong. Matching paths to patterns is a job for code, so a script works them out from the branch's changes and `main`'s list. The cost: it reads the local `origin/main` without fetching, so a stale clone can give an old answer. :file[.agents/skills/clear-backlog/scripts/list-human-only-paths.ts].

### What to watch for

- **A new entry protects nothing until it merges.** A PR that adds a path to the list is judged by `main`'s list, and so is every other open PR until it lands.
- **Only some reasons are enforced.** The script sees which files a PR touches, who opened it, from where, and its labels; other reasons a person merges, such as a change no test can observe, or a PR built from a public request ([Author trust](/t/glassbox/guide/git-github/author-trust) says why it looks trusted), are the agent's to notice ([Merge gate](/t/glassbox/guide/verification/gate)).
- **The check sees paths, not effects.** `pnpm-lock.yaml` and a new `pnpm-workspace.yaml` aren't on the list, so a PR that changes only them passes the path check, though it can add a package or patch one ([pnpm and the lockfile](/t/glassbox/guide/deploy/pnpm-lockfile) says what writes them). The agent must notice and leave that PR to a person; ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]) lists the reasons.
- **One kind of PR skips the list.** A same-repo Dependabot PR that changes only `package.json` and its lockfile, and moves each version within its major (a 0.x minor counts as a major), is checked by `dependabotBumpRefusal` instead; one from a fork, or with any other change, still goes to a person.
- **The script takes the owner's word on trust.** It checks only that `--owner-approved` holds some text, not that the owner said it; the merge commit records the quote and the human-only files it waived.
- **The refusal lives in the script.** It holds for merges that go through `merge-pr.ts`, the one merge path agents are told to use.

## Try it in your project

Keep your list in a file such as `.github/protected-paths`, one shell pattern per line, the file itself among them. This script reads the list from the target branch with `git show`, never the change's own copy, and exits 1 when it can't read it or when a changed path matches. `--no-renames` lists a rename's old path too, and a shell `*` in `case` also matches `/`, so `deploy/*` covers every file below `deploy/`:

```bash
#!/usr/bin/env bash
git fetch -q origin main || exit 1
list=$(git show origin/main:.github/protected-paths) || exit 1
[ -n "$list" ] || { echo "refused: protected-paths list is empty"; exit 1; }
hits=$(git diff --name-only --no-renames origin/main...HEAD | while read -r path; do
  while read -r glob; do
    case "$path" in $glob) echo "$path" ;; esac
  done <<< "$list"
done)
[ -z "$hits" ] || { echo "needs a person:" $hits; exit 1; }
```

With `deploy/*` on the list, a branch that drops that line and edits `deploy/run.sh` is still caught, since `main`'s list counts:

```text
needs a person: .github/protected-paths deploy/run.sh
```

Delete the list on `main`, and it fails closed with a `fatal:` line such as:

```text
fatal: path '.github/protected-paths' does not exist in 'origin/main'
```
