An agent's session is seen only by the people in it. When it ends, its transcript is gone from view, and with it every wrong turn, confusing doc and wasted step. A session log keeps what only the session knew, so the project can learn from work nobody watched.

Know agent session logs already? Skip to [In Terrarium](#in-terrarium).

## The concept

Observability, for agents, means being able to tell from records what an agent did and where it struggled, without having watched it. Git shows what changed; it can't show what the agent read, which instruction misled it or which step it had to repeat.

A session log fills that gap. It has two halves. The judgement half only the agent can write: what it set out to do, how far it got, and every problem it hit, each with a possible fix. The mechanical half, such as timings, tools used and files read, comes from the recorded transcript, because an agent misremembers facts that the transcript holds exactly.

The problems are the point. One log's complaint is an anecdote; the same complaint in many logs is a pattern worth fixing. That only works if agents report every problem, small ones too, and report them honestly, so a log is a self-report to learn from, never a performance review. Logs are the wrong choice for a single short-lived agent a person watches end to end, and logs nobody reads or mines only cost tokens.

## In Terrarium

Each session writes a :term[session log] into the Journal, the tenant where Terrarium documents itself. When its work reaches a coherent state, such as a PR opened or a question answered, the agent runs the `close-session` skill, which calls `log-session`. The agent writes the judgement half into a scratch file: its goal, a status, an outcome, a summary, the skills it used, the rules that steered or backed what it did and the docs that helped, and every :term[friction]. The schema in :file[shared/schemas/session.ts] makes the list of frictions required, even when it is empty:

::excerpt{path="shared/schemas/session.ts" lines="165-173"}
```ts
    // List EVERY friction — not just one or two. No `tag`: the Friction Ledger
    // groups frictions by cause instead (GLOSSARY.md).
    frictions: z.array(
      z.object({
        description: z.string(), // ~20 words — honest description
        solution: z.string(), // possible fix / what would have helped
        severity: z.enum(['nit', 'minor', 'moderate', 'major', 'blocker']),
      }),
    ),
```
::

The `log-session` skill defines each severity grade. A log may also hold optional `ideas` and `learnings`, which [Ideas and lessons learned](/t/glassbox/guide/terrarium-practice/ideas-and-lessons-learned) follows.

A log's optional `ruleUse` list holds an entry for each agent, the main agent or a subagent, that loaded a rule or reported something; a subagent also gets one once asked. It says how each rule in `.claude/rules/` ([path-specific rules](/t/glassbox/guide/claude-code/path-scoped-rules)) loaded for that agent (`via`: `start` at session start, `native` when the harness loaded it for a path, `hint` when a hint hook added it, `read` when the agent read the file itself) and the rules and docs the agent reported. A reported rule is `steered` when it made the agent do or decide something differently, or `backed` when it matched what the agent was already doing; a rule the agent leaves out counts as neither. A subagent is asked by a note at its start: a hook answers its bare `echo rule-use:` call with the question, and a second call names its rules and docs. The main agent is asked by `log-session.ts --pending` and answers in the `reported` list of the log it writes.

At the end of that turn, a `Stop` [hook](/t/glassbox/guide/hooks/hooks) derives the mechanical half from the transcript, joins the two, checks the result against the schema, and commits that one file to `main` without a PR; [A session log lands on main](/t/glassbox/guide/walkthroughs/session-log-lands-on-main) follows each step. If the work continues, say the PR merges, the session logs again and replaces its earlier log. Only that session re-logs; no other session edits its log.

:file[scripts/session/log-session.ts] won't author a log from a linked [git worktree](/t/glassbox/guide/git-github/git-worktrees), where a dispatched [subagent](/t/glassbox/guide/agents/subagents) works. It tells one by git's two directories:

::excerpt{path="scripts/session/log-session.ts" lines="211-219"}
```ts
export function isLinkedWorktree(cwd: string): boolean {
  try {
    const gitDir = git(['rev-parse', '--git-dir'], cwd).trim()
    const commonDir = git(['rev-parse', '--git-common-dir'], cwd).trim()
    return resolve(cwd, gitDir) !== resolve(cwd, commonDir)
  } catch {
    return false
  }
}
```
::

A session moved into a worktree on purpose, with Claude Code's `EnterWorktree`, passes `--allow-worktree`.

Later sessions read the logs. One :term[skill] groups frictions by root cause in the :term[friction ledger], with every session that hit each cause and every PR meant to fix it, and turns the ones worth fixing into PRs or issues. Another reads which skills sessions used, :file[scripts/session/rule-use-report.ts] reports, for each rule with enough data, the share of answering loads in which it steered or backed the agent, and a :term[prune trial] takes the frictions logged while it stands as its verdict. Logs from outside agents are marked `external`, and both skills skip them.

### Why it's built this way

- **Logs are first-hand, never rebuilt.** Nobody can see an ended session's transcript, and the repository shows what changed, not what was hard. The skills that improve Terrarium need that record, so nothing rebuilds them from the repository; a status dashboard built that way was rejected. The cost: this part of the Journal can't be regenerated. ADR-0008 (:file[docs/adr/0008-self-documentation-tenant-is-a-journal.md]).
- **Straight to `main`.** A PR for a log is ceremony that makes agents skip or thin their logs, and no PR fits every session: some open none, some several, and a rejected PR's frictions still happened. So a log skips the :term[gate] and goes straight to `main`. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **A log can't break the build.** A log is data checked against a fixed format and touches no code or page; one gated script limits the shortcut to that one file. The cost: unreviewed commits on `main`, pushed with the owner's credential, which on its own could push anything. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **A script takes the facts from the transcript.** When the agent reported everything, its claims about reads, skills and start time didn't match the transcript. Now it writes only the judgement. Whether a shell command "read" a doc is a guess, so the script lists the reads it didn't count, and the agent logs a friction if one was real. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).
- **A subagent shouldn't author a log.** A subagent shares its parent's session id and the script's scratch path, so a log it wrote would silently replace the parent's. The script refuses to author one from a linked worktree. The cost: it can't tell a subagent's worktree from one a session entered on purpose, which needs `--allow-worktree`. :file[scripts/session/log-session.ts].
- **The agent logs at closure, not session end.** A hook at session end couldn't ask the agent or tell a pause from an end, and a paused web session can lose its network, so logs were lost. Now the agent writes at closure and the `Stop` hook lands the log at turn end, network up. The cost: no closure, no log, which beats a partial one. ADR-0009 (:file[docs/adr/0009-session-logs-commit-directly-to-main.md]).

### What to watch for

- **A flattering log is worse than none.** The value is in the frictions, nits included, so the skills tell agents to be honest about what went wrong, even when they fixed it themselves.
- **Don't inflate severity.** A mistake caught before it landed stays a `nit` or `minor`. Recurrence shows up in the ledger's count, not in a louder grade.
- **A lost log is gone.** Logs are never rebuilt from the repository, so a session that never writes one leaves no record of what it hit.
- **Old logs never change.** So the schema only grows; ADR-0009 says how a field may be added, and the one case where a person may remove or rename one.

## Try it in your project

At the end of each agent session, have the agent append three YAML lines to `sessions.yml`: what it tried to do, how far it got, and every problem it hit, each as a short cause label, reused when the cause is the same, then a possible fix:

```yaml
- goal: add CSV export to the reports page
  outcome: done, tests pass
  problems: ["no-test-command: name it in the README", "slow-build: cache dependencies"]
```

After a week, count the labels across every session:

```bash
grep -o '"[a-z-]*:' sessions.yml | tr -d '":' | sort | uniq -c | sort -rn
```

If three sessions hit the same missing test command, the top of the list reads:

```text
      3 no-test-command
      1 unclear-owner
      1 slow-build
```

The top line is the problem to fix first; read its sessions' fixes and pick one.
