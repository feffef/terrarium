When people and agents use different words for one thing, or one word for different things, every conversation about the code drifts. A glossary fixes the words. In a project with several distinct parts, one glossary per part keeps each list short enough to read.

Know ubiquitous language already? Skip to [In Terrarium](#in-terrarium).

## The concept

Eric Evans's domain-driven design calls it a [ubiquitous language](https://martinfowler.com/bliki/UbiquitousLanguage.html): one shared vocabulary that developers and the people who know the domain both use, in conversation, in documents and in the code itself. Each term has one definition and one preferred word.

One language rarely fits a large system. The same word can mean different things in two parts of it: an "account" in billing is not an "account" in sign-in. Domain-driven design draws a boundary, a bounded context, around each part, and each context gets its own language. A map says which contexts exist and how they relate. A project with one context needs one glossary and no map, and a glossary that nobody reads, or checks against the code, only adds cost.

For an agent, the glossary is also context it reads. A short glossary costs every session little, while words from parts of the system the session never touches only crowd out the ones it needs.

Full reference: [Ubiquitous Language (Martin Fowler)](https://martinfowler.com/bliki/UbiquitousLanguage.html)

## In Terrarium

Terrarium splits its vocabulary by who needs it. The map, :file[GLOSSARY-MAP.md], lists every glossary, which is also the list of Tenants, with a line on what each Tenant is:

::excerpt{path="GLOSSARY-MAP.md" lines="1-10"}
```md
# Glossary Map

Every glossary, which is also the list of Tenants (ADR-0021).

## Glossaries

- **Platform**: [`GLOSSARY.md`](./GLOSSARY.md).
- **Journal**: the Platform's self-documentation; Platform infrastructure, not a
  demo (ADR-0008).
  [`layers/journal/GLOSSARY.md`](./layers/journal/GLOSSARY.md)
```
::

The Platform glossary, :file[GLOSSARY.md], holds the words every agent needs whatever its task, such as :term[Tenant], :term[Space] and :term[Friction]. An entry defines its word and may say which word to use, as the Tenant entry does:

::excerpt{path="GLOSSARY.md" lines="14-20"}
```md
### Tenant
A distinct product/site within the Platform, with its own components (its
"fit-out") and content model; that code is what sets it apart from a Space.
Tenants are isolated from each other (ADR-0025). "Multi-tenant" means this
architecture, not paying customers. A Tenant is implemented as a
Nuxt layer: say "Tenant" for the domain concept and "layer" only for the Nuxt
mechanism.
```
::

The file has two sections, `## Glossary` and `## Retired terms`; ADR-0021 (:file[docs/adr/0021-multi-context-domain-docs.md]) sets where a term goes and what each section may hold. :file[CLAUDE.md] imports the map and then this glossary, and tells agents to use a glossary's term rather than a synonym.

Each Tenant's own words live in `layers/<tenant>/GLOSSARY.md`, beside its code. The Blog's glossary, :file[layers/blog/GLOSSARY.md], defines a :term[Persona] as a Space of the Blog, and the Atlas's glossary defines a :term[Biome] as a Space of the Atlas. A rule, :file[.claude/rules/tenant-glossary.md], has an agent read a Tenant's glossary before it works on that Tenant. Besides its terms, a Tenant's glossary holds why the Tenant exists, who it is for and its product decisions.

Each term is defined once, in one glossary; anywhere else may point to it. The rule of two in :file[docs/agents/domain.md] gives a concept a term only once its second instance exists or is concretely scheduled; before that it is described in plain words where it lives. It also says a concept missing from the glossary means either the writer is inventing language or there is a real gap to record. A rule, :file[.claude/rules/glossary-terms.md], sends an agent to that doc before it adds or changes a term.

### Why it's built this way

- **Split by who needs a word.** When the root glossary held every Tenant's words, an agent looking up a Platform term read past another Tenant's fictional species. Terrarium keeps the root to words every agent needs, and a Tenant's words beside its code. The cost: more files than one flat glossary, which was simpler. ADR-0021 (:file[docs/adr/0021-multi-context-domain-docs.md]).
- **A home for a Tenant's purpose.** A demo Tenant's reason to exist is a product choice. The definitions-only root can't hold it, and an ADR per Tenant would mix product choices with architecture, so the Tenant's glossary holds it. The cost: an agent may merge a change to those decisions in an ordinary PR, while an ADR change waits for a human merge. ADR-0021 (:file[docs/adr/0021-multi-context-domain-docs.md]).
- **Coin a word on its second instance.** Every session reads the glossary and checks its words against it, so each coined term costs every session. A second instance proves a term worth that cost. The cost: the first instance is described in plain words until a second one arrives. :file[docs/agents/domain.md]

### What to watch for

- **domain-modeling's entry layout isn't Terrarium's.** The `domain-modeling` Skill in :file[.agents/skills/domain-modeling/] supports several glossaries tied together by a map, which is the shape Terrarium uses. Its entry layout differs from Terrarium's, and `domain.md` lists where Terrarium departs from it.
- **A synonym reads as another concept.** Some glossary words also name something else: bare "closure" is a JavaScript closure, so the root glossary says "Session closure", and it keeps "layer" for the Nuxt mechanism and "Tenant" for the concept. Terrarium's entries have no `_Avoid_` list, so the word to use sits in the entry's own text, and :file[CLAUDE.md] tells agents to use the term, not a synonym. A page that says "layer" for a Tenant points the reader at the wrong thing.
- **An old entry is no precedent.** The rule of two brakes only new coinage and leaves terms already built, so a glossary entry with one instance is no reason to coin another.

## Try it in your project

List the five nouns your team argues about most. Write each with a one-sentence definition in a `GLOSSARY.md` at the root, and add one line to your `CLAUDE.md` that imports it with `@GLOSSARY.md` and tells agents to use its words. When one part of the system starts using a word differently, give that part its own glossary and add a map.
