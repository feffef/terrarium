Instructions for agents grow with every incident and almost never shrink: adding a line feels safe, and removing one feels risky. A trial removes an instruction on purpose, then lets the problems that later work runs into decide whether it was needed.

Know instruction trials already? Skip to [In Terrarium](#in-terrarium).

## The concept

Reading a rule can't tell you what it still prevents. It may guard against a mistake nobody makes any more, or one a later check already catches. The only way to find out is to take it away and watch.

A fair trial needs four things. A record of what was cut and why, kept where the judge will find it. A signal that reports damage, such as the problems people or agents log as they work. A test for damage, written when the cut is made, while you still remember what the text was for. And a window during which nobody puts the text back, or no verdict is possible.

When the verdict finds damage, put back the least that would have prevented it: one line stating the goal, not the old paragraph. When a rule has failed again and again as prose, the cut has shown something else too: the behaviour may need a check that runs, not more words.

## In Terrarium

A :term[prune trial] is the work of the `prune-trial` skill, :file[.agents/skills/prune-trial/SKILL.md], which a scheduled run starts; a trial that cuts an ADR runs only when a :term[trusted] user starts it. Each run first judges the open trials whose window has passed, then opens at most one new trial: it picks one problem, cuts every instruction about it down to the goal behind them, and ships the cut as one PR. A run may also, or instead, rewrite one skill or doc in plain words; that rewrite is a trial too.

The open trials live in a ledger, :file[.agents/prune-trials.yml]. Each entry ships in the same commit as its cut; git keeps what was removed there. An entry names the `problem` the cut text tried to prevent, its `territory`, the date it was `opened`, and a `check`: how to tell the cut broke something, written while the reason for the text is still remembered. The `check` should tell real damage from a session simply using the pruned topic's tools correctly.

`territory` is the area the trial owns; no new trial may touch an open trial's territory. The ADR-0027 summary :term[rule], :file[.claude/rules/adr-0027.md], loads when a session touches the ledger, a skill or a doc, and tells it not to restore or reword text an open trial covers, but to log a :term[friction] and work around it.

Before shipping, the run commits the cut and asks a subagent pinned to that exact commit what it would do in a real situation the cut text used to cover, reading only that commit. If the answer is wrong, the run rewrites the goal and asks again, or drops the cut. `proven: false` marks a trial whose run had no subagent to ask.

The window starts when the cut lands on `main`, not on the `opened:` date. :file[.agents/skills/prune-trial/scripts/find-trial-window.ts] finds the landing commit with `git log -S`, and its `isJudgeable` decides whether a trial may be judged yet: only from the landing time plus the window, less a short grace.

::excerpt{path=".agents/skills/prune-trial/scripts/find-trial-window.ts" lines="39,45,107-109"}
```ts
const WINDOW_MS = 3 * 24 * 60 * 60 * 1000 // the trial window (ADR-0027); this constant is its home
// …
const GRACE_MS = 60 * 60 * 1000
// …
export function isJudgeable(landingIsoUtc: string, now: Date): boolean {
  return now.getTime() >= Date.parse(landingIsoUtc) + WINDOW_MS - GRACE_MS
}
```
::

If it finds no landing, the trial is not judged. Once the window has passed, the judging run applies the entry's `check`, reads the frictions logged since the landing, and compares each covered friction's share of sessions before and after it. A `major` or `blocker` friction caused by the cut puts back one goal-shaped line, or the whole cut text when the trial cut an ADR. `moderate` damage, or a clear rise in a share, keeps the cut and files an issue for a person to decide on; anything milder keeps the cut with no issue. Either way the entry is deleted, and git keeps its history.

The ledger is part of the :term[gate]: `pnpm validate:content` runs :file[scripts/gate/validate-prune-trials.ts], which fails when the file doesn't parse (a duplicate key included), or a trial's `territory` lacks a `paths` or `keywords` list or lists a non-string item.

### Why it's built this way

- **Reading can't show what a rule prevents.** Adding a rule felt safe and removing one felt risky, so nothing was removed, and rereading a rule can't tell whether it still matters. A trial settles that with evidence, and a cut is easy to undo. A cut that causes damage makes the case for a hook, as [Claude Code hooks](/t/glassbox/guide/hooks/hooks#why-its-built-this-way) explains. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).
- **Others leave the cut alone.** If sessions restored missing text as soon as they noticed the gap, no trial would ever reach a clean verdict. So every session logs a friction and works around an open trial's cut instead of rewording it. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).
- **Silent failures go unseen.** A session that fails without noticing logs no friction, and severity alone misses a cut that makes a small mistake more common. So each trial carries its own check, a probe on a weaker model and a comparison of friction rates. The cost: a trial can still miss damage, and small samples make the rate a judgement. ADR-0027 (:file[docs/adr/0027-prune-trials.md]).

### What to watch for

- **Log it even if you recovered.** A problem a cut caused you counts only once it is a logged friction ([Why it's built this way](#why-its-built-this-way)).
- **A keyword hit is not damage.** A friction that mentions the pruned topic may come from a session using it correctly. Read each one in full before counting it.
- **Not everything can be trialled.** What a trial may never cut is listed in ADR-0027's Scope.

## Try it in your project

Pick the longest passage in your agent instructions that exists because of past incidents, and cut it to one line that states its goal. In the same commit, add an entry to a ledger file such as `trials.yml`, with the check written now, while you remember what the text was for:

```yaml
trials:
  - problem: commits that fail the linter
    territory:
      paths: [CLAUDE.md]
    opened: 2026-01-15
    check: a session pushes a commit the linter rejects, and its log says it did not know to lint
```

The window starts when the cut lands, not on `opened`. `git log -S` finds the newest commit that changed how often the entry's text appears in the ledger:

```sh
git log -1 --format='%h %cI %s' -S'commits that fail the linter' -- trials.yml
```

```text
abc1234 2026-01-15T10:00:00+00:00 Cut the lint paragraph to its goal
```

Where changes reach `main` through merges, add `main --first-parent` after `git log`, since a branch commit's own time is earlier than its merge. Leave the cut alone until the window you set has passed, then judge it with the `check` and the problems your agents reported.
