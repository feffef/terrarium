A platform that keeps each tenant's data apart still wants a few views that look across all of them: a search box, an activity feed. Let any code read any tenant and the separation is gone. Copy each tenant's schema into the view and the copies drift. Terrarium takes a middle way: a tenant offers a Collection by naming a shared shape, and readers see only what was offered.

Know this pattern already? Skip to [In Terrarium](#in-terrarium).

## The concept

Give each shape that more than one reader needs a name and one home, as a contract: the fields every reader may rely on. A tenant offers a data set by naming the contract in its own config. The contract is a minimum, so the tenant keeps any fields of its own on top.

At build time, collect every data set that named a contract into one list, grouped by contract. Readers go through one function that reads that list and nothing else, and tags every row with the tenant it came from. A data set that names no contract is on no list, so no reader outside its tenant finds it. The separation stays the default, and every exception is written down in the tenant's own config.

## In Terrarium

The shared shapes are the :term[Collection kinds]{id="collection-kind"} in :file[shared/kinds.ts]. The `page` kind adds two optional fields to Nuxt Content's own page fields, and the `session` kind's contract is the whole session-log schema:

::excerpt{path="shared/kinds.ts" lines="50-66"}
```ts
export const KINDS = {
  page: {
    type: 'page',
    contract: z.object({
      /** Publish instant — what the Commons Timeline orders dated pages by. */
      publishedAt: utcTimestamp.optional(),
      /** One-line headline (e.g. a Journal digest's day-summary) an aggregator
       *  prefers over the title. */
      summary: z.string().optional(),
    }),
  },
  // …
  session: { type: 'data', contract: sessionSchema },
} satisfies Record<string, KindDef>
```
::

A :term[Collection] opts in with `kind` in its :term[Tenant]'s manifest, as the Blog's and the Journal's `pages` do. `expand()` in :file[shared/expand.ts] builds the Collection's schema from the contract plus the manifest's own schema, so `validate:content` checks the contract's fields in every Document that opts in. `catalogFrom()` in the same file lists every opted-in Collection under its kind, and :file[modules/catalog.ts] writes that list at build time as the `#catalog` module: the :term[Catalog].

The one read function is `queryAcrossTenants` in :file[app/composables/catalog.ts]. It runs Nuxt Content's [`queryCollection`](https://content.nuxt.com/docs/utils/query-collection) on each Collection the Catalog lists for a kind, lets the caller's `project` pick the fields it needs, and tags each row with its Tenant, Space and Collection:

::excerpt{path="app/composables/catalog.ts" lines="46-65"}
```ts
export async function queryAcrossTenants<T>(
  kind: KindName,
  project: (item: CatalogItem) => T,
): Promise<Array<T & CatalogProvenance>> {
  const perCollection = await Promise.all(
    catalogByKind(kind).map(async (entry) => {
      // …
      const items = await queryCollection(entry.key as keyof Collections).all()
      return items.map((item) => ({
        ...project(item as unknown as CatalogItem),
        tenant: entry.tenant,
        space: entry.space,
        collection: entry.collection,
      }))
    }),
  )
  return perCollection.flat()
}
```
::

`queryPages()` in the same file reads the `page` kind and adds each page's own URL. The Commons Tenant's Search and Timeline are built on these two functions, and a Blog post finds the Journal digest of the day it was published through `queryPages()`. :file[layers/commons/tenant.config.ts] gives its `pages` no `kind`, so the Catalog doesn't list them.

### Why it's built this way

Reads across Tenants through opted-in kinds: ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

Each Collection as its own table: ADR-0001 (:file[docs/adr/0001-single-container-baked-multitenancy.md]).

Which catalog files a person merges: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **No test stops a direct read.** Each Collection is its own table, but `queryCollection` takes any key, so a layer that names another Tenant's key reads it. The one read path holds by review, not by a check.
- **Opting in shows the reader the whole Document.** The contract says which fields a reader can count on, not which it can see: `project` receives every field. Keep a field out of an opted-in Collection if no other Tenant should read it.
- **The projector is a cast.** Rows arrive as plain records, and `project` asserts their types. The fields are there because `validate:content` checked the contract, not because TypeScript knows them.
- **The kinds and the read path wait for a person.** :file[shared/kinds.ts], :file[modules/catalog.ts] and :file[app/composables/catalog.ts] are :term[Human-only], so a change to any of them waits for a person to merge it.

## Try it in your project

If your app keeps tenants apart and one view needs to read across them, name the shape that view needs and put it in one shared file. Let each tenant's config name the shapes it offers, build the list of offered data sets at build time, and route every cross-tenant read through one function that reads only that list.
