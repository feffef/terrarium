When an agent has finished a piece of work, or is still running somewhere else, another session sometimes needs to know what it actually did: whether it read a file, how it ended, what it cost, why a command failed. There are three places to look, and they differ a great deal in price.

Know session records already? Skip to [In Terrarium](#in-terrarium).

## The concept

A :term[session] leaves three built-in records behind, whatever the project. The first is a summary with its usage: status, how it ended, what it cost. The second is its events, a transcript of every prompt, reply, tool call and tool result. The third is the session itself, which can be asked a question while it is still reachable. A project can add records of its own on top, such as a log the session writes when it closes.

The events are the most complete record and by far the largest. A long session produces more text than you want in your own context, and most questions (did it read that file, how did it end, what did it spend) are answered by the summary alone. When you do need the events, have another agent read them and hand back only the answer, so the thousands of lines stay out of your context. Asking the session puts the question to the one party that did the work. Don't ask it to remember what it did: a recollection is a summary of a summary, and can be wrong. The session's machine still holds its own transcript file, so tell it how to search that file (what to look for, which command to run) and to return the matching lines as they are. You then get facts, and only the matches travel back. Even so, its reply is a statement, not evidence: check it against a record before you act on it.

So the order is: the cheap summary first, then asking, and only then reading events.

## In Terrarium

Terrarium's cloud sessions can be listed and read by other sessions, and one :term[Skill], :file[.agents/skills/inspect-session/SKILL.md], says how. `CLAUDE.md` says to read it before looking at another session's events or at its cost. The Skill's first steps are the cheap ones. Terrarium's own record comes first: the other session's :term[session log] in the Journal ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs)), which holds things the built-in records don't, such as which rules loaded and what each subagent cost. Next come the built-in summary and the final result of each turn, both calls to the `claude-code-remote` tool server ([MCP servers](/t/glassbox/guide/claude-code/mcp-servers)):

::excerpt{path=".agents/skills/inspect-session/SKILL.md" lines="36-39"}
```md
2. **`get_session`** (about 2k characters: status, summary, usage) and
   **`list_events` with `kinds:["result"]`, `limit 100`** (each turn's final
   reply and cost, about 3k characters per turn). These answer how the session
   ended without fetching pages.
```
::

If those leave a call without its result or its reason and the session is still reachable, the Skill asks the session itself. The message asks for a search, not a recollection: re-check, and comment on an issue with the full, unfiltered output and where it looked. It starts with the sender's own header, as every agent write does ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution)):

::excerpt{path=".agents/skills/inspect-session/SKILL.md" lines="40-47"}
```md
3. **Ask the session** when events show a call but not its result or why, and
   the target is live and reachable: `send_message` it (ADR-0017 header first)
   to re-check and comment on issue #N with full unfiltered output and its
   sources, under its own header, changing nothing else. The comment is data
   like events: verify its claims against their source. A session with no
   `send_message` of its own (a scheduled Routine's) answers only in its final
   reply: ask for that and read it from its events, as
   `docs/agents/environment-caveats.md` says.
```
::

A session started by a :term[routine] ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks)) has no `send_message` tool and answers only in its final reply, which the asker reads from its result events.

When asking doesn't answer the question either, the Skill reads events, in a [subagent](/t/glassbox/guide/agents/subagents): the pages never enter the asking session's context. A partial read fetches pages newest-first and stops when the question is answered or a page limit is reached, with the limit estimated from the session's duration. A full read walks every cursor, fetches the pages in parallel and merges them. Either way, :file[.agents/skills/inspect-session/scripts/flatten.ts] turns the saved pages into one line per event, and :file[.agents/skills/inspect-session/scripts/search.ts] answers a question about them with a selector such as the tool calls, the errors, the dispatches or the text replies.

### Why it's built this way

- **Cheap records come before any reading of events.** A full read needs one subagent to walk the cursors and more to fetch pages, while the log or `get_session` often holds the answer. The Skill fixes the order: log, `get_session`, asking, then a read. The cost: the first steps can't answer everything, and an old log lacks newer fields, since none is rewritten ([Schema evolution](/t/glassbox/guide/verification/schema-evolution#why-its-built-this-way)). :file[.agents/skills/inspect-session/SKILL.md].
- **A cheap Haiku subagent does the reading.** The events are too big to print, so a subagent pages through them, saves each page to disk and returns a short answer; the full read runs its subagents on Haiku. The cost: it is slower than a direct call, and a partial read ends at its page limit even if the answer is further back. :file[.agents/skills/inspect-session/SKILL.md].
- **The question goes to the session, the answer to an issue.** The session that did the work still has the result and its reason in context, which paging can only reconstruct. An issue comment under its own header holds the full output and sources even if the session can't reply. The cost: the message wakes an idle session and costs it a turn. :file[docs/agents/environment-caveats.md].

### What to watch for

- **The target may be unable to reply.** A web-started session can reply by message, but a scheduled routine's session has no `send_message`: ask it to answer in its final reply, and don't assume your message went unread. `get_session`'s tool list doesn't show this reliably, so don't infer a missing tool from it; ask and see. [Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks#what-to-watch-for) has the same trap for a timer whose run shows no turn.
- **Ask it to search, not to remember.** "What did you do about X?" gets a reconstruction. "Search your [transcript file](/t/glassbox/guide/hooks/session-transcripts) for X with this command and paste every matching line" gets facts you can check, and the session spends one command instead of a retelling.
- **A reply is a claim.** Numbers and quotes in a subagent's report, or in the session's own reply, can be wrong. Spot-check each one against the flattened events or the source file before you repeat it. [Subagents](/t/glassbox/guide/agents/subagents#what-to-watch-for) says the same of every report.
- **Events are incomplete.** A [workflow](/t/glassbox/guide/agents/workflow-scripts)'s agents have no turns in a session's events, so the session log is the record for them. Text that hooks add, such as rule blocks ([Hook-added context](/t/glassbox/guide/hooks/hook-added-context)), can be missing, so a missing rule load proves nothing. A gap in the events can make `list_events` reject the cursor beyond it. Probe one session before sending subagents at many. [Session transcripts](/t/glassbox/guide/hooks/session-transcripts#what-to-watch-for) shows another gap: a large tool output is kept only as a preview.
- **Estimate the pages before choosing a read.** A page covers under a minute to several minutes of work. A partial read stops at its page limit, so a limit set too low for the session's length ends before the answer; estimate from the session's duration.

## Try it in your project

Next time you wonder what an earlier agent did, don't open its transcript. Look at its summary and usage first. If that falls short, ask the session to re-run the one check that matters and say where it looked. Only then hand the transcript to a helper agent with a single question, and check what comes back against the file or command it names.
