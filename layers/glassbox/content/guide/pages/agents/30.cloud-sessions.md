A session on your laptop has your tools, your sign-ins and your settings. A cloud session starts on a fresh machine with a clone of the repository and what its cloud environment sets, the network it can reach included. Whatever a project needs in every session must therefore be committed. Some kinds of cloud session skip the committed settings file, and for those the environment's setup script is the place.

Know cloud sessions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A cloud session is a Claude Code session that runs on a virtual machine Anthropic manages, started from claude.ai/code, the Claude app, the Desktop app or `claude --cloud`. It clones your repository fresh. In a session with one repository, committed files arrive: `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`, `.mcp.json` and `.claude/settings.json`; other sessions get less of that settings file, as [In Terrarium](#in-terrarium) shows. Nothing from your own machine arrives, such as `~/.claude/settings.json`, `.claude/settings.local.json` or a server you added only for yourself, and of an organization's managed settings only the [server-managed](https://code.claude.com/docs/en/settings#settings-in-cloud-sessions) ones can reach it. [Claude Code permissions](/t/glassbox/guide/claude-code/permissions) shows how the settings that do arrive decide which tool calls run unasked. Each session runs in a [cloud environment](https://code.claude.com/docs/en/cloud-environments), which sets its network access, its environment variables and a setup script. GitHub goes through a proxy that holds your credentials outside the machine, and that proxy refuses GitHub's GraphQL API.

Full reference: [Claude Code docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)

## In Terrarium

Every :term[routine] runs as a cloud session, and so does any session started from claude.ai. Terrarium commits what its sessions need to the repo.

The committed :file[.claude/settings.json] holds `env` variables, a short `permissions.allow` list and the hooks, among them a `SessionStart` hook that installs dependencies and fetches full git history when the clone is shallow, as [Claude Code hooks](/t/glassbox/guide/hooks/hooks) shows. Which of those a cloud session uses depends on how it starts ([settings docs](https://code.claude.com/docs/en/settings#settings-in-cloud-sessions)):

- **One repository.** A session started on the Terrarium repository alone reads the whole file, though it may still skip the allow list (below).
- **Several repositories.** In an Anthropic-hosted environment, a session started on several repositories at once reads only `enabledPlugins` and `extraKnownMarketplaces` from the file and installs none of the plugins or marketplaces those two keys declare. Terrarium's file sets neither: such a session reads nothing Terrarium sets in that file. :file[docs/agents/environment-caveats.md] records Terrarium meeting this case.
- **A thread in a project.** A [project](https://code.claude.com/docs/en/claude-projects) is one conversation in which Claude starts parallel cloud sessions, its threads, on your repositories and tracks what they report back. A cloud thread applies none of the file's permission rules, hooks or `env`, however many repositories the project has. Those three are the only keys Terrarium's file sets, so a thread reads nothing Terrarium sets in that file.

Reading the file is not applying all of it. An untrusted workspace drops `permissions.allow` rules and `additionalDirectories` before matching any rule, and a cloud session can be such a workspace ([Claude Code permissions](/t/glassbox/guide/claude-code/permissions#in-terrarium)); its hooks and `env` still apply. Terrarium's guards, hooks that refuse a tool call, are among them, and :file[docs/agents/guards.md] records a live test in which they fired in a cloud session, for a dispatched subagent's calls too.

The cloud also fences what a session can reach, and Terrarium has met a few of its limits. The session's GitHub token lacks the `workflow` scope that a push to `.github/workflows/` needs; [GitHub Actions](/t/glassbox/guide/git-github/composite-actions) says what Terrarium does instead. What :file[docs/agents/environment-caveats.md] calls the agent proxy refuses writes to repository settings, and it blocks some hosts, docs sites among them; the blocked set varies by environment.

:file[scripts/hooks/workflow-edit-guard.ts], a `PreToolUse` hook, denies an edit or a write-shaped command aimed at `.github/workflows/`. It acts only in a cloud session, which `isCloudSession` tells by the `CLAUDE_CODE_REMOTE_SESSION_ID` variable the cloud sets:

::excerpt{path="scripts/hooks/workflow-edit-guard.ts" lines="142-152"}
```ts
/** Always exits 0 — the deny travels in stdout, not the exit code. */
export function main(): void {
  if (!isCloudSession()) return
  const result = readHookPayload()
  if (result.kind === 'none') return
  if (result.kind === 'invalid') return denyUninspectable(LABEL, REF, 'the hook payload was not valid JSON')
  if (result.kind === 'no-tool') return denyUninspectable(LABEL, REF, 'the hook payload named no tool')

  const output = denyOutputFor(checkWorkflowEdit(result.payload.tool_name, result.payload.tool_input))
  if (output) process.stdout.write(JSON.stringify(output))
}
```
::

Outside the cloud it returns at once. In the cloud, a payload it can't read is denied, and a write it spots gets a deny decision on stdout whose reason says to leave the change in `docs/proposals/` for a person to apply.

### Why it's built this way

- **Stop a workflow edit before it is committed.** A cloud session's token can't push `.github/workflows/`, and the refusal covers every commit in the push, so one workflow edit strands the work beside it. So the guard denies the edit at the tool call, before any commit exists. The cost: it matches command text, so a path held in a variable slips past to the refused push. :file[scripts/hooks/workflow-edit-guard.ts].

### What to watch for

- **A 403 is often the environment.** A GraphQL `gh` command, a blocked docs site or a refused settings call fails the same way every time. Read :file[docs/agents/environment-caveats.md], which holds the current list, before you diagnose it as a bug in your change.
- **Your own settings never reach the cloud.** Put a hook or permission every session needs in the project file, not your own `~/.claude/settings.json`; for the sessions that skip the project file ([In Terrarium](#in-terrarium) lists them), use the environment's setup script.

## Try it in your project

Commit a `SessionStart` hook to your project's `.claude/settings.json` that installs your dependencies and then prints one line, such as `dependencies installed`. Push it, then start a cloud session on the repository with `claude --cloud "What did the SessionStart hook print?"`. The hook's plain output reaches Claude as context, so the answer should quote your line. If it doesn't, check how the session started against the list above.
