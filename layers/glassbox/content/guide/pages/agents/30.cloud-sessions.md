A session on your laptop has your tools, your sign-ins and your settings. A cloud session starts on a fresh machine with what the repository holds plus what its cloud environment sets. Whatever a project needs in every session must therefore be committed or set there, and the cloud's own network limits what the session can reach.

Know cloud sessions already? Skip to [In Terrarium](#in-terrarium).

## The concept

A cloud session is a Claude Code session that runs on a virtual machine Anthropic manages, started from claude.ai/code, the Claude app, the Desktop app or `claude --cloud`. It clones your repository fresh. In a session with one repository, committed files arrive: `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`, `.mcp.json` and `.claude/settings.json`. Nothing from your own machine does, such as `~/.claude/settings.json`, `.claude/settings.local.json` or a server you added only for yourself, and of an organization's managed settings only the [server-managed](https://code.claude.com/docs/en/settings#settings-in-cloud-sessions) ones can reach it. [Claude Code permissions](/t/glassbox/guide/claude-code/permissions) shows how the settings that do arrive decide which tool calls run unasked. Each session runs in a [cloud environment](https://code.claude.com/docs/en/cloud-environments), which sets its network access, its environment variables and a setup script. GitHub goes through a proxy that holds your credentials outside the machine, and that proxy refuses GitHub's GraphQL API.

Full reference: [Claude Code docs: Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)

## In Terrarium

Every :term[Routine] runs as a cloud session, and so does any session started from claude.ai. Terrarium commits what its sessions need to the repo, and a session that reads the repo's settings file gets all of it: a `SessionStart` hook installs dependencies and fetches full git history when the clone is shallow, as [Claude Code hooks](/t/glassbox/guide/hooks/hooks) shows.

The committed :file[.claude/settings.json] holds `env` variables, a short `permissions.allow` list and the hooks. Which of those a cloud session uses depends on how it starts ([settings docs](https://code.claude.com/docs/en/settings#settings-in-cloud-sessions)):

- **One repository.** A session started on the Terrarium repository alone reads the whole file.
- **Several repositories.** In an Anthropic-hosted environment, a session started on several repositories at once reads only `enabledPlugins` and `extraKnownMarketplaces` from it, not its hooks, `env` or permission rules, and the plugins those keys declare still don't load. Terrarium's file sets neither key: such a session gets nothing from it. :file[docs/agents/environment-caveats.md] records Terrarium meeting this case.
- **A thread in a project.** A [project](https://code.claude.com/docs/en/claude-projects) is one conversation in which Claude starts parallel cloud sessions, its threads, on your repositories and tracks what they report back. A cloud thread applies none of the file's permission rules, hooks or `env`, however many repositories the project has.

Even a session that reads the file may not apply its allow list: [Claude Code permissions](/t/glassbox/guide/claude-code/permissions#in-terrarium) says when. Terrarium's guards are hooks, and :file[docs/agents/guards.md] records them firing in a cloud session, a dispatched subagent's calls included, when probed.

The cloud also fences what a session can reach. A few of the limits Terrarium has met: the token can't push `.github/workflows/`, and [Composite actions](/t/glassbox/guide/git-github/composite-actions) says why and what Terrarium does instead; the proxy refuses writes to repository settings; and some docs sites are blocked. For the first, :file[scripts/hooks/workflow-edit-guard.ts], a `PreToolUse` hook, denies an edit or a write-shaped command aimed at `.github/workflows/`, and only in a cloud session, which `isCloudSession` tells by the `CLAUDE_CODE_REMOTE_SESSION_ID` variable the cloud sets:

::excerpt{path="scripts/hooks/workflow-edit-guard.ts" lines="142-152"}
```ts
/** Always exits 0 — the deny travels in stdout, not the exit code. */
export function main(): void {
  if (!isCloudSession()) return
  const result = readHookPayload()
  if (result.kind === 'none') return
  if (result.kind === 'invalid') return denyUninspectable(LABEL, REF, 'the hook payload was not valid JSON')
  if (result.kind === 'no-tool') return denyUninspectable(LABEL, REF, 'the hook payload named no tool')

  const output = denyOutputFor(checkWorkflowEdit(result.payload.tool_name, result.payload.tool_input))
  if (output) process.stdout.write(JSON.stringify(output))
}
```
::

Outside the cloud it returns before reading anything. In the cloud, a payload it can't read is denied, and a write it spots gets a deny decision on stdout whose reason says to leave the change in `docs/proposals/` for a person to apply.

:file[docs/agents/environment-caveats.md] holds the current list.

### Why it's built this way

- **Stop a workflow edit before it is committed.** A cloud session's token can't push `.github/workflows/`, and the refusal covers every commit in the push, so one workflow edit strands the work beside it. So the guard denies the edit at the tool call, before any commit exists. The cost: it matches command text, so a path held in a variable slips past to the refused push. :file[scripts/hooks/workflow-edit-guard.ts].

### What to watch for

- **A 403 is often the environment.** A GraphQL `gh` command, a blocked docs site or a refused settings call fails the same way every time. Read the caveats before you diagnose it as a bug in your change.
- **Your own settings never reach the cloud.** A hook or permission you set in your own `~/.claude/settings.json` never reaches a cloud session. Put what every session needs in the project file, but know where it stops: a session with several repositories, and a thread in a project, skip its hooks ([In Terrarium](#in-terrarium) has the cases), so give them a setup script on the environment instead.

## Try it in your project

Commit a `SessionStart` hook to your project's `.claude/settings.json` that installs your dependencies. Start a cloud session on the repository and check that the install ran before Claude's first answer.
