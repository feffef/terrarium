Some timers live inside one running session: Claude runs a prompt again on an interval, or wakes itself later, for as long as that session stays open. Terrarium lets a session use its own wake-up tool only inside `/loop`, and waits on a pull request's checks another way.

Know `/loop` already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code can schedule prompts that belong to the current :term[session]. They fire only while Claude Code is running and idle: a due prompt waits for the current turn to end, never interrupting a reply. A timer that needs no open session is a different tool ([Scheduled tasks](/t/glassbox/guide/agents/scheduled-tasks)).

[`/loop`](https://code.claude.com/docs/en/scheduled-tasks) runs a prompt again and again in the current session:

```text
/loop 5m check whether the deploy finished
/loop check whether CI passed and address any review comments
```

With an interval, the prompt runs on a fixed schedule. Without one, Claude picks the wait after each run with the `ScheduleWakeup` tool, which sets when the next run comes, and calls it with `stop: true` to end the loop once the work is done. Underneath, Claude manages these session timers with tools it calls itself, such as `CronCreate`, which schedules a recurring or one-shot prompt in the current session. A fire runs only skills Claude may start on its own: a skill with `disable-model-invocation: true` reaches Claude as plain text instead, though a person who types that skill's slash command still starts it.

Resuming the session with `--resume` or `--continue` restores the tasks `CronCreate` scheduled, except a recurring task that has expired (30 days after it was created, 7 for a task created before v2.1.330), a one-shot task whose time has passed and a task lost by exiting with `Exit and stop tasks`. A self-paced `/loop` is never restored: run `/loop` again to restart it.

Full reference: [Claude Code docs: Run prompts on a schedule](https://code.claude.com/docs/en/scheduled-tasks)

## In Terrarium

A Terrarium :term[skill]{id="skill"} that `/loop` may drive, such as :file[.agents/skills/guest-intake/SKILL.md], sets `disable-model-invocation: true`. A `/loop` fire that names it gives Claude only the command's text, and Claude can't start the skill with its `Skill` tool. The `guest-intake` skill expects that refusal and says to follow its steps directly.

Inside a session, Terrarium waits without `/loop`. A session that must check a PR's CI hours later schedules its own check-in with `send_later`, a tool of `claude-code-remote`, the MCP server cloud sessions get for working with sessions, which delivers a message back into the same session (:file[docs/agents/pr-workflow.md]). When a `send_later` call fails with a closed permission stream and its one retry fails too, :file[docs/agents/environment-caveats.md] says to schedule the check-in with that server's `create_trigger` and `run_once_at` instead.

:file[scripts/hooks/loop-only-tool-guard.ts], a `PreToolUse` hook (one that runs before each tool call and can deny it), denies `ScheduleWakeup` unless the session's transcript shows a `/loop`, and its message names what to use instead; it allows a call with `stop: true`, which only cancels a wakeup. Terrarium calls such a hook a guard: one that holds a rule by blocking ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks)). The guard keeps the tool's alternatives and its exemption in one registry entry, which its deny message quotes:

::excerpt{path="scripts/hooks/loop-only-tool-guard.ts" lines="56-68"}
```ts
export const LOOP_ONLY_TOOLS: readonly LoopOnlyTool[] = [
  {
    tool: 'ScheduleWakeup',
    instead: [
      'Waiting on a dispatched Agent-tool subagent → no wait/poll tool at all. It self-notifies on completion (#425).',
      'Waiting on a backgrounded Bash command → end the turn. The harness delivers a task notification when it exits.',
      'Polling non-webhook-delivered external state (CI/gate completion) → `mcp__Claude_Code_Remote__send_later` to schedule your own check-in (#241).',
    ],
    // A cancel only removes a pending wakeup; denying it would strand a spurious one.
    exempt: (input) => input.stop === true,
    exemptNote: 'Cancelling an already-scheduled wakeup (`stop: true`) is allowed in any mode.',
  },
]
```
::

### Why it's built this way

- **A hook denies ScheduleWakeup outside `/loop`.** Sessions outside `/loop` kept calling `ScheduleWakeup`, and a fired wakeup arrives as an unwanted turn that can re-run the session's whole prompt. Two fixes that wrote the rule into a doc failed ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#why-its-built-this-way) says why), so a hook now denies the call. The cost: when it can't read the transcript it denies too. :file[scripts/hooks/loop-only-tool-guard.ts].
- **Any `/loop` counts, whatever its pacing.** A fixed-interval loop is paced by the harness and would not call `ScheduleWakeup` anyway, and telling the two apart would need the command's arguments, which the transcript does not reliably carry. So the guard treats every `/loop` session alike, which avoids false denials. :file[scripts/hooks/loop-only-tool-guard.ts].

### What to watch for

- **Session timers can vanish on resume.** The restore rule above isn't the whole story: :file[docs/agents/environment-caveats.md] records cases of a `/loop` or `CronCreate` job gone after a session resumed, with no error. Check that it is still there before you rely on it.
- **A scheduled wake-up may not show as a turn.** The caveats doc says a fired self-bind routine's output may not show as a turn, and to check its last run with `list_triggers` before you decide it didn't fire.

## Try it in your project

In an open session, start a fixed-interval loop, then ask for the list of timers:

```text
/loop 1m say what time it is
what scheduled tasks do I have?
```

The docs say Claude turns the interval into a cron schedule and confirms the cadence and the job's ID, and that the second line lists the task with its next run time. Each run should arrive between your turns, never in the middle of a reply. `Esc` doesn't stop a fixed-interval loop: ask Claude to cancel it, and list the tasks again to check that it is gone.
