One session can hand parts of its work to other agents and keep only their answers. Those agents start knowing nothing, so everything they need has to be in the message that starts each one, its brief.

Know subagents already? Skip to [In Terrarium](#in-terrarium).

## The concept

A subagent is a helper Claude starts inside a session. It runs in its own context window, with its own system prompt and tools. It doesn't see the conversation that started it, the Skills already run or the files already read: it gets a message describing the task and works from that. When it finishes, only its final report comes back, so the searching and reading it did stays out of the main conversation. By default a subagent can start subagents of its own, up to three layers below the main conversation.

Keep a quick, targeted change, or work that needs back-and-forth, in the main conversation, and keep it there when the steps share a lot of context or when latency matters: a subagent starts blank and has to gather what the session already knows.

A subagent that edits files needs a checkout of its own, or parallel helpers overwrite each other's work. Claude Code can give each one a fresh [git worktree](/t/glassbox/guide/git-github/git-worktrees): ask Claude to "use worktrees for your agents", or add `isolation: worktree` to a custom subagent's frontmatter.

```md
---
name: refactorer
description: Applies one mechanical refactor across many files
isolation: worktree
---

Apply the refactor across every affected file, run the tests,
and report the results.
```

Full reference: [Claude Code docs: Create custom subagents](https://code.claude.com/docs/en/sub-agents)

## In Terrarium

Terrarium dispatches subagents for reviews, research, screenshots and whole branches of work. How to dispatch them is one :term[Skill], :file[.agents/skills/dispatch-subagents/SKILL.md], which `CLAUDE.md` says to read before writing a subagent brief or resuming a stopped subagent. A [guard](/t/glassbox/guide/hooks/blocking-hooks), :file[scripts/hooks/dispatch-read-guard.ts], denies the main session's first dispatch until it has read the Skill. Its goal is that every subagent's work lands, is right, and is never stranded: finished but uncommitted, or never seen by the session that asked for it.

Most of the Skill is a checklist for the brief. Two of its choices, in its own words:

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="18-20,51"}
```md
- **A dispatched subagent that touches git:** pass `isolation: 'worktree'` on the
  Agent call. Without it, parallel agents share one checkout and race on
  branches.
<!-- … -->
- Commit before stopping, even mid-gate: an agent can end at any time.
```
::

The brief:

- sets up the agent's checkout: the commit to start from and the install ([Git worktrees](/t/glassbox/guide/git-github/git-worktrees) has the details);
- says to commit before stopping, even halfway through a check;
- gives every file the agent writes, scripts included, a name of its own in a folder made for it.

The Skill also says who reviews. A subagent building a branch, which the Skill calls an impl agent, hands it back committed and unpushed. The session that dispatched it reviews the branch and sends every fix back to the same agent. Once a review comes back clean, the dispatching session pushes the branch, opens the PR and lands it itself.

Claude Code would let an impl agent start subagents of its own, but the Skill tells the dispatching session that it can't, and to run its review and any nested dispatch itself:

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="78-79"}
```md
- Impl agents do not run `close-session` and cannot spawn subagents: run
  `/code-review` and any nested dispatch yourself.
```
::

The limit comes from the environment Terrarium's sessions run in, not from a file in the repo: no file sets it. The one place that names it is the prompt :file[.claude/workflows/clear-backlog-build.js] gives its reviewer subagents: "you can't spawn subagents (the environment sets `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`)". That variable is the docs' setting for the nesting depth.

A building subagent writes no session log ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs) says how the log script refuses one from a worktree). And a guard, :file[scripts/hooks/subagent-background-guard.ts], denies it any background shell command. Hooks run for a subagent's tool calls too, and only a subagent's payload carries an agent id. The guard denies a backgrounded call from any caller it can't place as the main session:

::excerpt{path="scripts/hooks/subagent-background-guard.ts" lines="23-29,56-59"}
```ts
export function detectAgentContext(payload: unknown): AgentContext {
  if (payload === null || typeof payload !== 'object') return 'undeterminable'
  const p = payload as Record<string, unknown>
  if (typeof p.agent_id === 'string' || typeof p.agent_type === 'string') return 'subagent'
  if (typeof p.session_id === 'string' || typeof p.transcript_path === 'string') return 'main'
  return 'undeterminable'
}
// …
  if (toolName !== 'Bash') return null
  if (context === 'main') return null
  const input = toolInput !== null && typeof toolInput === 'object' ? (toolInput as Record<string, unknown>) : {}
  if (input.run_in_background === true) return { context, signal: 'run_in_background' }
```
::

The rest of the check also denies a bare `&` in the command text, and a `Monitor` call. How a hook is wired to deny a call: [Claude Code hooks](/t/glassbox/guide/hooks/hooks) and [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks).

A stopped subagent is resumed with `SendMessage` to its agent id, never dispatched again. A new dispatch gets a new checkout and no memory, so it can start a second copy of a branch or leave the first one's commits behind.

### Why it's built this way

- **One checklist, read each time.** A subagent's mistakes are often silent: agents shared one check log, each reading another's overwrite, and the dispatching session published a wrong diagnosis. So the brief's rules, down to git run as `git -C <root>` and the shared scratch folder, sit in one Skill read before each brief. The cost: a long brief for a small task. :file[.agents/skills/dispatch-subagents/SKILL.md].
- **No background commands.** A subagent's turn ends when it stops to wait, and nothing wakes it when a background command ends, even when the brief said how to check. So a guard refuses the command outright. The cost: a long check runs in the foreground, and one outlasting a single call needs a resume. :file[scripts/hooks/subagent-background-guard.ts].
- **Review by the dispatcher.** A branch beyond a simple change is reviewed before its PR opens. The Skill says a building subagent can't start a reviewer, so the dispatching session reviews while the subagent waits unpushed. Fixes go back to the same agent, which still holds the worktree. The cost: a round trip per review. :file[.agents/skills/dispatch-subagents/SKILL.md].

### What to watch for

- **The brief is all it knows.** A rule, a count or a source the dispatching session already holds has to be in the brief, or the subagent derives it again or misses it.
- **Its report is a claim.** A subagent's prose is checked against the source it cites before anything ships on it.

## Try it in your project

Next time you hand Claude a task with parallel parts, write the brief as if to a stranger: the commit to start from, the setup command, what to commit, and what to report back. Compare its report with the files it names before you act on it.
