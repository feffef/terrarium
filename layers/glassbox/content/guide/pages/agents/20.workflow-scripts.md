A Skill tells a model what to do, and the model decides each next step. When the steps must run in order, every time, for many agents, that decision is the weak point. A workflow script takes it away: the script, not the model, decides which agent runs next.

Know Claude Code workflows already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Claude Code workflow is a JavaScript file that starts subagents and combines their results. It opens with a `meta` object naming it, then plain JavaScript with top-level `await`. `agent()` starts one subagent with a prompt, `parallel()` runs several at once and waits for all of them, and `pipeline()` runs one per item in a list. A `schema` on `agent()` makes that subagent return JSON of a given shape instead of prose. `phase()` groups the agents that follow in the progress view, and `log()` shows a message above it. Input arrives in a global named `args`.

```js
export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const audits = await pipeline(args.files, (file) =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)
```

A runtime runs the script in the background. The script itself has no file system or shell access and takes no input from the user mid-run: its agents read, write and run commands, and its variables hold the results, so the session's context gets only the final answer. A workflow saved in a project's `.claude/workflows/` runs by name in later sessions, and a permission rule such as `Workflow(audit-routes)` approves that one workflow by name.

Full reference: [Claude Code docs: Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows)

## In Terrarium

Terrarium's :term[Workflow] scripts sit in :file[.claude/workflows/], each run by the :term[Skill] that names it. The `clear-backlog` Skill, which works through the open issues its sweep picks up in one run, runs workflows such as :file[.claude/workflows/clear-backlog-explore.js], which triages each issue with its own agent, and :file[.claude/workflows/clear-backlog-build.js], which builds each planned branch and runs a first review round on it. The Skill itself keeps what a script can't do: it asks the owner its questions, waits on CI and merges.

The build script fixes the order in code. Its closing lines have `pipeline()` send each branch through `buildBranch`, then `reviewBranch`. `reviewBranch` runs a fresh Standards and a Spec reviewer in parallel, each giving every finding a `kind`, and returns them with the status `reviewed`. The script stops there. The Skill resumes the builder and the reviewers by agent id to fix, re-check and gate, and runs the workflow again with `review: true` for a further review round:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="123,130-136"}
```js
async function reviewBranch(built, b) {
  // …
  const reviews = await parallel(AXES.map(axis => () =>
    agent(reviewPrompt(b, axis, out.worktree, round), { label: `${axis} ${b.name} r${round}`, phase: 'Review', schema: REVIEW })))
  if (reviews.some(r => !r)) return { ...out, status: 'failed', reason: `round ${round}: a reviewer returned nothing` }
  return { ...out, status: 'reviewed', reviews: Object.fromEntries(AXES.map((axis, i) => [axis, reviews[i]])) }
}

const results = await pipeline(args.branches, buildBranch, reviewBranch)
```
::

`buildBranch` gives each branch's build agent its own worktree, and turns an agent that returned nothing into a failed result whose reason names where its commits may be:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="116,118-121"}
```js
async function buildBranch(b) {
  // …
  // Isolated even on a re-run: if b.worktree was auto-removed, the agent starts fresh in its own.
  const r = await agent(buildPrompt(b), { label: `build ${b.name}`, phase: 'Build', schema: WORK, isolation: 'worktree', ...SONNET })
  return r || { status: 'failed', reason: 'build agent returned nothing; its worktree may hold commits, and `pnpm check:worktrees` lists it', worktree: b.worktree }
}
```
::

When a triage agent answers a seedling issue with anything but a question, or says to build an issue the owner reserved, one by a :term[Public] author, or one labelled for a human, the explore script turns its answer back into a question for the owner:

::excerpt{path=".claude/workflows/clear-backlog-explore.js" lines="168-172"}
```js
  const seedling = /^\s*seedling\b/i.test(r?.title || '')
  if (r && r.outcome !== 'grill' && (seedling || (r.outcome === 'build' && (issue.reserved || r.publicAuthor || r.readyForHuman)))) {
    r.outcome = 'grill'
    r.question ||= { choice: 'Go ahead as the summary says?', options: ['yes', 'no'], pick: 'yes', why: 'Reserved, seedling, Public-authored or ready-for-human: the owner decides.' }
```

::

Each workflow script is approved by name, the permission rule The concept shows: :file[.claude/settings.json] allows each one. :file[tests/unit/workflow-scripts.spec.ts] checks that each one compiles and that its `meta.name` matches its file name.

### Why it's built this way

- **A script is its Skill's code.** A fixed run of agent steps needs an owner. Each script belongs to its Skill, and the :term[Gate] treats it as that Skill's file. The cost: a script change gets a Skill change's checks, not the app's. A change of only Skill files and :term[Inert] paths skips the build and the browser tests ([Merge gate](/t/glassbox/guide/verification/gate)). ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **A real file in `.claude/workflows/`.** Terrarium keeps each Skill in `.agents/skills/<name>/` with only a link in `.claude/skills/`, but Claude Code loads a workflow from `.claude/workflows/` by name and refuses to save one through a link. The script is a real file there instead. The cost: a Skill's code sits in two folders, joined only by the script's name. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Steps the model can't skip.** The `clear-backlog` Skill sends many agents through triage, build and review, and a Skill's steps are only what the model decides to do next. Its triage, build and first review run in saved workflows, so the model can't skip one of their steps. The cost: a restart kills a running workflow. :file[.agents/skills/clear-backlog/SKILL.md].

### What to watch for

- **Nothing lints it.** Each of Terrarium's workflow scripts ends with a top-level `return`. No ES module may hold one, so ESLint skips their folder. The unit test stands in: it compiles each script as the body of an async function. [Linting](/t/glassbox/guide/verification/linting) explains why.
- **Plan for `null`.** `agent()` returns `null` when you stop it or it hits an unrecoverable API error, and `pipeline()` keeps each `null` in its results. Turn each `null` into a result that says what to check, rather than dropping it.
- **It can't ask.** A step that needs a person, CI or a merge goes in the Skill around it, between two runs, and so does the fix-and-re-check loop, which resumes the run's agents.

## Try it in your project

Pick a job you hand Claude often that fans out over many files or items. Ask Claude to use a workflow for it, then save the run to `.claude/workflows/` from `/workflows`. Add a test that compiles every script there, since your linter won't read them.
