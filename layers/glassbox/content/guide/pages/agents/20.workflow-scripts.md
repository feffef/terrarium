A skill tells a model what to do, and the model decides each next step. When the steps must run in order, every time, for many agents, that decision is the weak point. A workflow script takes it away: the script, not the model, decides which agent runs next.

Know Claude Code workflows already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Claude Code workflow is a JavaScript file that starts subagents and combines their results. It opens with a `meta` object naming it, then plain JavaScript with top-level `await`. `agent()` starts one subagent with a prompt, `parallel()` runs several at once and waits for all of them, and `pipeline()` runs one per item in a list. A `schema` on `agent()` makes that subagent return JSON of a given shape instead of prose. `phase()` groups the agents that follow in the progress view, and `log()` shows a message above it. Input arrives in a global named `args`.

```js
export const meta = {
  name: 'audit-routes',
  description: 'Audit every route handler for missing auth checks',
}

const audits = await pipeline(args.files, (file) =>
  agent(`Audit ${file} for missing authentication checks.`, { label: file }),
)

return audits.filter(Boolean)
```

The workflow runtime runs the script in the background, in an isolated environment separate from the conversation. The script itself has no file system or shell access and takes no input from the user mid-run: its agents read, write and run commands, and its variables hold the results, so the session's context gets only the final answer. A workflow saved in a project's `.claude/workflows/` runs by name in later sessions, and a permission rule such as `Workflow(audit-routes)` approves that one workflow by name.

Full reference: [Claude Code docs: Orchestrate subagents at scale with dynamic workflows](https://code.claude.com/docs/en/workflows)

## In Terrarium

Terrarium's :term[workflow] scripts sit in :file[.claude/workflows/], each run by the :term[skill] that names it. The `clear-backlog` skill takes each issue it selects to a merged PR, a closed issue or a decision for the owner, the person who started the run. It runs workflows such as :file[.claude/workflows/clear-backlog-explore.js], which triages each issue with its own agent, and :file[.claude/workflows/clear-backlog-build.js], which builds each planned branch and runs a first review round on it. The skill itself keeps what a script can't do: it asks the owner its questions, waits on CI and merges. CI runs the :term[gate] on GitHub, and its result decides the merge.

The build script fixes the order in code. Near its end, it passes `pipeline()` the branches and one function per stage: `buildBranch(b)` builds a branch, and `reviewBranch(built, b)` gets that build's result and the branch. `reviewBranch` runs two fresh reviewers in parallel: a Standards reviewer, who checks the change against the repo's documented standards and reads only §3 of the `code-review` skill, and a Spec reviewer, who checks it against the brief and the owner's picks. A branch given `small: true`, one under the simple-change bar of :file[docs/agents/pr-workflow.md], gets one `Both` reviewer in their place. Each gives every finding a `kind`, such as `defect` or `nit`, which decides how the builder treats it: a defect is always fixed, a nit only when cheap. `reviewBranch` returns the findings with the status `reviewed`, and the script stops there. The skill resumes the builder and reviewers by agent id to fix, re-check and gate. It reruns the workflow with `review: true` for a further round after a `defect` or `spec-mismatch`, a missing test on a larger branch, or a branch it judges hard or large; a small branch only when its `Both` reviewer reports the diff above the bar, and then with a full pair:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="63,128,135-142"}
```js
const axesOf = b => (b.small ? ['Both'] : AXES)
// …
async function reviewBranch(built, b) {
  // …
  const axes = axesOf(b)
  const reviews = await parallel(axes.map(axis => () =>
    agent(reviewPrompt(b, axis, out.worktree, round), { label: `${axis} ${b.name} r${round}`, phase: 'Review', schema: REVIEW })))
  if (reviews.some(r => !r)) return { ...out, status: 'failed', reason: `round ${round}: a reviewer returned nothing` }
  return { ...out, status: 'reviewed', reviews: Object.fromEntries(axes.map((axis, i) => [axis, reviews[i]])) }
}

const results = await pipeline(args.branches, buildBranch, reviewBranch)
```
::

`buildBranch` gives each branch's build agent its own git worktree (a separate checkout) through `isolation: 'worktree'`, and turns an agent that returned nothing into a failed result whose reason names where its commits may be:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="121,123-126"}
```js
async function buildBranch(b) {
  // …
  // Isolated even on a re-run: if b.worktree was auto-removed, the agent starts fresh in its own.
  const r = await agent(buildPrompt(b), { label: `build ${b.name}`, phase: 'Build', schema: WORK, isolation: 'worktree', ...SONNET })
  return r || { status: 'failed', reason: 'build agent returned nothing; its worktree may hold commits, and `pnpm check:worktrees` lists it', worktree: b.worktree }
}
```
::

The explore script has the last word on some triage answers. A triage agent's outcome is `build`, `grill` (a question for the owner), or a close or a block. A :term[seedling], an issue proposing an idea that waits for a trusted user's go-ahead, always ends as a question: the script turns any other outcome for it into `grill`. It also turns a `build` answer into `grill` when:

- the owner reserved the issue;
- a :term[public] author opened it;
- it is labelled `ready-for-human`.

::excerpt{path=".claude/workflows/clear-backlog-explore.js" lines="168-172"}
```js
  const seedling = /^\s*seedling\b/i.test(r?.title || '')
  if (r && r.outcome !== 'grill' && (seedling || (r.outcome === 'build' && (issue.reserved || r.publicAuthor || r.readyForHuman)))) {
    r.outcome = 'grill'
    r.question ||= { choice: 'Go ahead as the summary says?', options: ['yes', 'no'], pick: 'yes', why: 'Reserved, seedling, Public-authored or ready-for-human: the owner decides.' }
  }
```
::

The allow list in :file[.claude/settings.json] approves each workflow script by name, as `Workflow(clear-backlog-build)`. :file[tests/unit/workflow-scripts.spec.ts] checks that each script's `meta.name` matches its file name.

### Why it's built this way

- **A script is its skill's code.** A fixed run of agent steps needs an owner. Each script belongs to its skill, and the gate treats it as that skill's file. The cost: a script change gets a skill change's checks, not the app's. A change of only skill files and :term[inert] paths skips the build and the browser tests ([Merge gate](/t/glassbox/guide/verification/gate)). ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **A real file in `.claude/workflows/`.** Terrarium keeps each skill in `.agents/skills/<name>/` with only a symlink in `.claude/skills/`, but Claude Code loads a workflow from `.claude/workflows/` by name and refuses to save one through a symlink. The script is a real file there instead. The cost: a skill's code sits in two folders, joined only by the script's name. ADR-0005 (:file[docs/adr/0005-skill-model.md]).
- **Steps the model can't skip.** The `clear-backlog` skill sends many agents through triage, build and review, and a skill's steps are only what the model decides to do next. Its triage, build and first review run in saved workflows, so the model can't skip one of their steps. The cost: a restart kills a running workflow. :file[.agents/skills/clear-backlog/SKILL.md].

### What to watch for

- **Nothing lints it.** Each of Terrarium's workflow scripts ends with a top-level `return`. No ES module may hold one, so ESLint skips their folder. A unit test, `workflow-scripts.spec.ts`, stands in: it compiles each script as the body of an async function. [Linting](/t/glassbox/guide/verification/linting) explains why.
- **Plan for `null`.** `agent()` returns `null` when you stop it or it hits an unrecoverable API error, and `pipeline()` keeps each `null` in its results. The docs' example above drops them with `.filter(Boolean)`; Terrarium's build script instead turns each `null` into a failed result that says what to check.
- **It can't ask.** A step that needs a person, CI or a merge goes in the skill around it, between two runs, and so does the fix-and-re-check loop, which resumes the run's agents.

## Try it in your project

Pick a repeated job that fans out over many files or items, and ask Claude to write a workflow for it. Run `/workflows`: the run's progress view lists each phase with its agent count, and opening a phase shows its agents. When a run does what you wanted, select it and press `s` to save it to `.claude/workflows/`; in a new session it appears as `/<name>` in the `/` menu. Add a test that compiles every script there, since your linter won't read them.
