A skill says what a job does. Something else has to say when it runs. Claude Code offers three timers, which differ in where they run and how long they last, from a cloud task that needs no open session to a loop that fires only while its session runs. Terrarium keeps each job's steps in the repo and its timer outside it, and learns which runs fired from each session's log, the record a session commits to the Journal, the site where Terrarium documents itself.

Know scheduled tasks and `/loop` already? Skip to [In Terrarium](#in-terrarium).

## The concept

Claude Code has three ways to run a prompt later, compared side by side in the Claude Code docs' [scheduling options table](https://code.claude.com/docs/en/scheduled-tasks#compare-scheduling-options):

- A **cloud scheduled task**, called a routine until the docs renamed it, runs on Anthropic's cloud and needs neither your machine nor an open session.
- A **Desktop scheduled task** runs on your own machine, with its local files.
- **`/loop`** runs inside one open session and fires only while it runs; resuming the session restores a fixed-interval loop that hasn't expired (a recurring task expires seven days after it was created), but never a self-paced one.

A cloud scheduled task is a saved prompt you create at claude.ai/code/routines, or with `/schedule` in the CLI. Each run is a new cloud session on a fresh clone of each repository it names, so it has the skills committed there and nothing from your machine. The exception is a [project](https://code.claude.com/docs/en/claude-projects), one conversation that runs each task as a thread, usually its own cloud session: there a run can continue an existing thread instead of starting a new session. The run starts in auto mode, where a classifier model allows or blocks each action instead of asking you, but some actions still stop and wait for an answer. The table and each option's docs cover the rest, such as what can start a run and how often it may fire.

[`/loop`](https://code.claude.com/docs/en/scheduled-tasks) runs a prompt again and again in the current session:

```text
/loop 5m check whether the deploy finished
/loop check whether CI passed and address any review comments
```

With an interval, the prompt runs on a fixed schedule. Without one, Claude picks the wait after each run with the `ScheduleWakeup` tool, which sets when the next run comes, and calls it with `stop: true` to end the loop once the work is done. Underneath, Claude manages these session timers with tools it calls itself, such as `CronCreate`, which schedules a recurring or one-shot prompt in the current session. A fire runs only skills Claude may start on its own: a skill with `disable-model-invocation: true` reaches Claude as plain text instead, though a person who types that skill's slash command still starts it.

Full reference: [Claude Code docs: Automate work with scheduled tasks](https://code.claude.com/docs/en/routines)

## In Terrarium

Terrarium calls a cloud scheduled task that runs one of its :term[skills]{id="skill"} a :term[routine], the docs' former name. The routine lives in a claude.ai account; its prompt is the skill's slash command, and the skill in :file[.agents/skills/] holds the steps. The skill never says how often it runs, or that a routine runs it: the repo can't read the timer, so such a sentence would be a guess.

:file[scripts/gate/validate-skill-cadence.ts], part of `pnpm validate:content`, fails any :term[skill inventory] sentence that pairs the word "routine" with a cadence word such as "weekly" or a phrase such as "every 2 hours".

No file declares the routines or their timers: a routine's run shows only in its :term[session log]. :file[scripts/session/transcript-trace.ts] sets the log's `trigger` from the run's first turn, and only for a session with the entrypoint `remote_trigger`, which the harness gives a scheduled run. The excerpt shows what it picks: the skill that the first turn's slash command names, or else that turn's first line:

::excerpt{path="scripts/session/transcript-trace.ts" lines="457-466"}
```ts
  if (entrypoint !== 'remote_trigger') return undefined
  const first = records.find((r) => r.type === 'user')
  if (!first) return undefined
  const msg = first.message as { content?: unknown } | undefined
  const [name] = commandSkillNames(msg?.content) // reuse the one slash-command extractor
  if (name) return name
  const text = userText(msg?.content).join('\n').trim()
  if (!text) return undefined
  const firstLine = (text.split('\n')[0] ?? '').trim()
  return firstLine ? firstLine.slice(0, 200) : undefined
```
::

The `audit-skills` skill adds each run's cost to the [Routine costs](/t/journal/current/routines) page, the Journal's charts of every recorded routine run. It also grades how much each skill matters, and gives a skill the grade `routine` only when scheduled sessions run it.

The routines at this page's `revision`, by the skill each runs. The list can't say when each one runs:

- `frictions-to-fixes`, `audit-docs`, `audit-skills` and `prune-trial`: parts of the [Self-improvement loop](/t/glassbox/guide/terrarium-practice/self-improvement-loop), described there.
- `visitor-loop` sends first-time visitor agents, each on a different model, through a preview of the site, fixes what more than one of them hit and builds one idea they raised.
- `digest` writes up each finished day for the Journal and moves older entries to its archive.
- `blog-post` has one Blog :term[persona] tell the best recent story.
- `glassbox-update` brings every Glass Box guide page up to date with `main`, re-pins it and claim-checks flagged pages plus a daily rotation.
- `glassbox-curate` makes the guide easier to learn from and fills gaps in it: one focus per run, one pull request, which waits for the owner's merge when it adds a lesson or a subject or changes the skill, its docs or the page checks.
- `harvest` turns the ideas and learnings that recent session logs record into issues, each waiting for a person's green light ([Ideas and lessons learned](/t/glassbox/guide/terrarium-practice/ideas-and-lessons-learned)).
- `dependabot-sweep` reviews every open Dependabot pull request: it merges the safe minor and patch bumps, leaves the rest for a person with a reason, and turns each major into an issue ([Dependabot grouping](/t/glassbox/guide/git-github/dependabot-grouping)).

A scheduled skill sets `disable-model-invocation: true`, which keeps Claude from starting it on its own while a typed slash command still does ([Claude Code skills](/t/glassbox/guide/claude-code/skills#in-terrarium)). The two ways to fire it then differ. A routine's prompt arrives as the run's first turn, the way a person's typed slash command does, and the skill runs. A `/loop` fire that names the same skill gives Claude only the command's text, and Claude can't start the skill with its `Skill` tool. Each skill that `/loop` may drive, such as :file[.agents/skills/guest-intake/SKILL.md], expects that refusal and says to follow its steps directly.

A routine starts a new session; waiting inside a session that is already running works differently. **Inside a session, Terrarium waits without `/loop`.** A session that must check a PR's CI hours later schedules its own check-in with `send_later`, a tool of `claude-code-remote`, the MCP server cloud sessions get for working with sessions, which delivers a message back into the same session (:file[docs/agents/pr-workflow.md]). :file[scripts/hooks/loop-only-tool-guard.ts], a `PreToolUse` hook (one that runs before each tool call and can deny it), denies `ScheduleWakeup` unless the session's transcript shows a `/loop`, and its message names what to use instead; it allows a call with `stop: true`, which only cancels a wakeup.

### Why it's built this way

- **The timer outside the skill.** ADR-0005 (:file[docs/adr/0005-skill-model.md]) splits a scheduled run in two: the skill holds what the run does, and the routine holds only when. [Claude Code skills](/t/glassbox/guide/claude-code/skills#why-its-built-this-way) gives the reason.
- **Logs show which routines ran.** The timers sit in an account the repo can't read, and a run's transcript names no routine. So the log takes the skill's name from the run's first turn, and the audit counts what actually fired. The cost: a routine that never fires leaves no trace, and one whose prompt isn't a slash command is named by its first line. :file[scripts/session/transcript-trace.ts].
- **The cadence check scans only the inventory.** A schedule changes with no commit, so a sentence saying how often a routine runs goes stale without anyone noticing. The skill inventory is where that had happened, so the check scans only its entries. The cost: the same sentence in a skill, doc or page passes `pnpm validate:content`. :file[scripts/gate/validate-skill-cadence.ts].
- **Each skill states its own limits.** Nobody watches a scheduled run, so each scheduled skill writes down what it may change, as `dependabot-sweep` does; [Human-in-the-loop agents](/t/glassbox/guide/terrarium-practice/human-in-the-loop#why-its-built-this-way) says why no central table holds it. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).
- **A hook denies ScheduleWakeup outside `/loop`.** Sessions outside `/loop` kept calling `ScheduleWakeup`, and a fired wakeup arrives as an unwanted turn that can re-run the session's whole prompt. Two fixes that wrote the rule into a doc failed ([Claude Code hooks](/t/glassbox/guide/hooks/hooks#why-its-built-this-way) says why), so a hook now denies the call. The cost: when it can't read the transcript it denies too. :file[scripts/hooks/loop-only-tool-guard.ts].

### What to watch for

- **Session timers can vanish on resume.** The restore rule above isn't the whole story: :file[docs/agents/environment-caveats.md] records cases of a `/loop` or `CronCreate` job gone after a session resumed, with no error. Check that it is still there before you rely on it.
- **A scheduled wake-up may not show as a turn.** A scheduled task that wakes an existing session can fire without a visible turn; the same caveats doc says to check the task's last run before you decide it didn't fire.
- **An unattended run can wait forever.** Auto mode still stops for some actions, and in an unattended run a subagent's call that needs approval blocks with no signal to the session that dispatched it (:file[docs/agents/environment-caveats.md]). Treat a long silence as possibly stuck.

## Try it in your project

Pick a chore you repeat, such as a dependency check, and write it as a skill with `disable-model-invocation: true` that says nothing about when it runs. Run `/schedule` and give the new task the skill's slash command as its prompt. Run `/schedule run` to start it at once, then open the task at claude.ai/code/routines: its list of past runs should show the run, and opening the run should show the skill's steps. Search your repo for the skill's name next to "daily" or "weekly" and expect no hit: the schedule lives only in the task.
