One session, a single continuous Claude Code conversation, can hand parts of its work to other agents and keep only what they return. A new agent starts knowing nothing, so everything it needs has to be in the message that starts it, its brief.

Know subagents already? Skip to [In Terrarium](#in-terrarium).

## The concept

A subagent is a helper Claude starts inside a session. It runs in its own context window, with its own system prompt and tools. It doesn't see the conversation that started it, the skills already run or the files already read: it gets a message describing the task and works from that. When it finishes, only its final report comes back, so the searching and reading it did stays out of the dispatching session. By default a subagent can start subagents of its own, up to three layers below the main session; the variable `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` sets that limit, and at `1` a subagent can start none.

Keep a quick, targeted change, or work that needs back-and-forth, in the session itself. Keep it there too when the steps share a lot of context or when latency matters: a subagent starts blank and has to gather what the session already knows.

A subagent that edits files needs a checkout of its own, or parallel helpers overwrite each other's work. Claude Code can give each one a fresh [git worktree](/t/glassbox/guide/git-github/git-worktrees), a second working folder of the same repository with its own checked-out branch: ask Claude to "use worktrees for your agents", or add `isolation: worktree` to the frontmatter, the YAML block between `---` lines that opens a custom subagent's file in `.claude/agents/`.

```md
---
name: refactorer
description: Applies one mechanical refactor across many files
isolation: worktree
---

Apply the refactor across every affected file, run the tests,
and report the results.
```

Full reference: [Claude Code docs: Create custom subagents](https://code.claude.com/docs/en/sub-agents)

## In Terrarium

Terrarium dispatches subagents for reviews, research, screenshots and whole branches of work. How to dispatch them is one :term[skill], :file[.agents/skills/dispatch-subagents/SKILL.md], which `CLAUDE.md` says to read before writing a subagent brief or resuming a stopped subagent. A guard, Terrarium's name for a hook that refuses a tool call ([Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks)), holds sessions to that: :file[scripts/hooks/dispatch-read-guard.ts] refuses the main session's `Agent`, `Workflow` and `SendMessage` calls until that session has read the skill. The same guard refuses any brief that still holds an unfilled placeholder such as `{NAME}`. The skill's goal is that every subagent's work lands, is right, and is never stranded: finished but uncommitted, or never seen by the session that asked for it.

Most of the skill is a checklist for the brief. Two of its choices, in its own words (the harness is the program the agent runs in, here Claude Code):

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="20-22,56-58"}
```md
- **A dispatched subagent that touches git:** pass `isolation: 'worktree'` on the
  Agent call. Without it, parallel agents share one checkout and race on
  branches.
<!-- … -->
- Commit before stopping, even mid-gate: an agent can end at any time. Bank
  progress to logs after each step. The harness refuses a subagent's Write of
  report files, so it returns structured results in its final message.
```
::

By the rules of the skill and `CLAUDE.md`, a brief includes each of these that applies:

- set up the agent's checkout: the commit to start from and the install ([Git worktrees](/t/glassbox/guide/git-github/git-worktrees) has the details);
- say to commit before stopping, even in the middle of the :term[gate], the checks a change must pass before it merges;
- give every file the agent writes, scripts included, a scratch folder named for that agent (`CLAUDE.md` asks this of every brief); its report goes back in its final message instead.

The skill also says who reviews and lands a branch. It calls a subagent that builds a branch an impl agent, one that implements the change. An impl agent hands its branch back committed but unpushed:

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="74-80"}
```md
- Impl agents never call `merge-pr.ts`, whatever the brief says. They hand back
  a committed, green, unpushed branch. You run `/code-review` on its worktree
  (`pr-workflow.md`, "Review before opening the PR"), resume the agent for every
  fix, later ones included, and review again; once clean, you push
  (`git -C <worktree> push origin HEAD:<branch>`), open and land the PR. They do
  not run `close-session` and cannot spawn subagents: run any nested dispatch
  yourself.
```
::

Terrarium's cloud sessions start with `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` at `1`: there, an impl agent can't start subagents of its own. No file in the repo sets it: the cloud launcher passes it in, as the research note :file[docs/research/subagent-spawn-depth.md] records.

An impl agent writes no session log ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs) says how the log script refuses one from a worktree). And a guard, :file[scripts/hooks/subagent-background-guard.ts], refuses it any background command. Hooks run for a subagent's tool calls too, and the payload, the JSON a hook receives, carries an `agent_id` and `agent_type` that identify the subagent. The guard refuses `run_in_background`, a bare `&` in the command text and a `Monitor` call from any caller it can't place as the main session. The excerpt shows how it places the caller, and its first check on a `Bash` call:

::excerpt{path="scripts/hooks/subagent-background-guard.ts" lines="23-29,56-59"}
```ts
export function detectAgentContext(payload: unknown): AgentContext {
  if (payload === null || typeof payload !== 'object') return 'undeterminable'
  const p = payload as Record<string, unknown>
  if (typeof p.agent_id === 'string' || typeof p.agent_type === 'string') return 'subagent'
  if (typeof p.session_id === 'string' || typeof p.transcript_path === 'string') return 'main'
  return 'undeterminable'
}
// …
  if (toolName !== 'Bash') return null
  if (context === 'main') return null
  const input = toolInput !== null && typeof toolInput === 'object' ? (toolInput as Record<string, unknown>) : {}
  if (input.run_in_background === true) return { context, signal: 'run_in_background' }
```
::

How a hook is wired to deny a call: [Claude Code hooks](/t/glassbox/guide/hooks/hooks) and [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks).

A stopped subagent is resumed with `SendMessage` to its agent id, never dispatched again. A new dispatch gets a new checkout and no memory, so it can start a second copy of a branch or leave the first one's commits behind.

### Why it's built this way

- **One skill holds the brief's rules.** A subagent's mistakes are often silent: two agents given one scratch folder collide without an error. So the brief's rules sit in one skill read before each brief. The cost: more than three agents from one improvised brief wait for a pilot, one agent run and checked first; a brief defined in the repo needs none. :file[.agents/skills/dispatch-subagents/SKILL.md].
- **No background commands.** A subagent's turn ends when it stops to wait, and nothing wakes it when a background command ends, even when the brief said how to check. So a guard refuses the command outright. The cost: a long check runs in the foreground, and one outlasting a single call needs a resume. :file[scripts/hooks/subagent-background-guard.ts].
- **Review by the dispatcher.** A branch beyond a simple change is reviewed before its PR opens, and an impl agent can't start a reviewer. So the dispatching session reviews while the impl agent waits unpushed, still holding the worktree for the fixes. The cost: a round trip per review. :file[.agents/skills/dispatch-subagents/SKILL.md].

### What to watch for

- **The brief is all it knows.** A rule, a count or a source the dispatching session already holds has to be in the brief, or the subagent derives it again or misses it.
- **Its report is a claim.** A subagent's prose is checked against the source it cites before anything ships on it, a subagent that reads another session's events included ([Inspecting past sessions](/t/glassbox/guide/agents/inspecting-past-sessions#what-to-watch-for)).

## Try it in your project

Save the `refactorer` example above as `.claude/agents/refactorer.md`, then hand Claude a task with parallel parts for it, and write the brief as if to a stranger: the commit to start from, the setup command, what to commit, and what to report back. While the helpers run, `git worktree list` shows one extra worktree for each. A worktree whose helper changed files stays on disk afterwards: compare the helper's report with the changes there before you act on it.
