One session can hand parts of its work to other agents and keep only what they return. A new one starts knowing nothing, so everything it needs has to be in the message that starts it, its brief.

Know subagents already? Skip to [In Terrarium](#in-terrarium).

## The concept

A subagent is a helper Claude starts inside a session. It runs in its own context window, with its own system prompt and tools. It doesn't see the conversation that started it, the Skills already run or the files already read: it gets a message describing the task and works from that. When it finishes, only its final report comes back, so the searching and reading it did stays out of the dispatching session. By default a subagent can start subagents of its own, up to three layers below the dispatching session.

Keep a quick, targeted change, or work that needs back-and-forth, in the session itself. Keep it there too when the steps share a lot of context or when latency matters: a subagent starts blank and has to gather what the session already knows.

A subagent that edits files needs a checkout of its own, or parallel helpers overwrite each other's work. Claude Code can give each one a fresh [git worktree](/t/glassbox/guide/git-github/git-worktrees): ask Claude to "use worktrees for your agents", or add `isolation: worktree` to a custom subagent's frontmatter.

```md
---
name: refactorer
description: Applies one mechanical refactor across many files
isolation: worktree
---

Apply the refactor across every affected file, run the tests,
and report the results.
```

Full reference: [Claude Code docs: Create custom subagents](https://code.claude.com/docs/en/sub-agents)

## In Terrarium

Terrarium dispatches subagents for reviews, research, screenshots and whole branches of work. How to dispatch them is one :term[Skill], :file[.agents/skills/dispatch-subagents/SKILL.md], which `CLAUDE.md` says to read before writing a subagent brief or resuming a stopped subagent. A [guard](/t/glassbox/guide/hooks/blocking-hooks), :file[scripts/hooks/dispatch-read-guard.ts], denies a session's first dispatch until it has read the Skill, and any brief that still holds an unfilled placeholder such as `{NAME}`. Its goal is that every subagent's work lands, is right, and is never stranded: finished but uncommitted, or never seen by the session that asked for it.

Most of the Skill is a checklist for the brief. Two of its choices, in its own words:

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="20-22,56-58"}
```md
- **A dispatched subagent that touches git:** pass `isolation: 'worktree'` on the
  Agent call. Without it, parallel agents share one checkout and race on
  branches.
<!-- … -->
- Commit before stopping, even mid-gate: an agent can end at any time. Bank
  progress to logs after each step. The harness refuses a subagent's Write of
  report files, so it returns structured results in its final message.
```
::

The brief:

- sets up the agent's checkout: the commit to start from and the install ([Git worktrees](/t/glassbox/guide/git-github/git-worktrees) has the details);
- says to commit before stopping, even mid-gate;
- gives every scratch file the agent writes, scripts included, a folder made for it; its report goes back in its final message instead.

The Skill also says who reviews and lands a branch. A building subagent, which the Skill calls an impl agent, hands it back unpushed:

::excerpt{path=".agents/skills/dispatch-subagents/SKILL.md" lines="74-80"}
```md
- Impl agents never call `merge-pr.ts`, whatever the brief says. They hand back
  a committed, green, unpushed branch. You run `/code-review` on its worktree
  (`pr-workflow.md`, "Review before opening the PR"), resume the agent for every
  fix, later ones included, and review again; once clean, you push
  (`git -C <worktree> push origin HEAD:<branch>`), open and land the PR. They do
  not run `close-session` and cannot spawn subagents: run any nested dispatch
  yourself.
```
::

Claude Code's default would let a building subagent start subagents of its own, but the environment Terrarium's sessions run in sets `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`, which stops that. No settings file in the repo sets it: the cloud launcher passes it in, as the research note :file[docs/research/subagent-spawn-depth.md] records, and the prompt :file[.claude/workflows/clear-backlog-build.js] gives its reviewer subagents says only "you can't spawn subagents". That variable is the docs' setting for the nesting depth.

A building subagent writes no session log ([Session logs](/t/glassbox/guide/terrarium-practice/session-logs) says how the log script refuses one from a worktree). And a guard, :file[scripts/hooks/subagent-background-guard.ts], denies it any background shell command. Hooks run for a subagent's tool calls too, and the payload carries an `agent_id` and `agent_type` that identify the subagent. The guard denies `run_in_background`, a bare `&` in the command text and a `Monitor` call from any caller it can't place as the dispatching session:

::excerpt{path="scripts/hooks/subagent-background-guard.ts" lines="23-29,56-59"}
```ts
export function detectAgentContext(payload: unknown): AgentContext {
  if (payload === null || typeof payload !== 'object') return 'undeterminable'
  const p = payload as Record<string, unknown>
  if (typeof p.agent_id === 'string' || typeof p.agent_type === 'string') return 'subagent'
  if (typeof p.session_id === 'string' || typeof p.transcript_path === 'string') return 'main'
  return 'undeterminable'
}
// …
  if (toolName !== 'Bash') return null
  if (context === 'main') return null
  const input = toolInput !== null && typeof toolInput === 'object' ? (toolInput as Record<string, unknown>) : {}
  if (input.run_in_background === true) return { context, signal: 'run_in_background' }
```
::

How a hook is wired to deny a call: [Claude Code hooks](/t/glassbox/guide/hooks/hooks) and [Blocking hooks](/t/glassbox/guide/hooks/blocking-hooks).

A stopped subagent is resumed with `SendMessage` to its agent id, never dispatched again. A new dispatch gets a new checkout and no memory, so it can start a second copy of a branch or leave the first one's commits behind.

### Why it's built this way

- **One Skill holds the brief's rules.** A subagent's mistakes are often silent: agents shared one check log, each reading another's overwrite, and the dispatching session published a wrong diagnosis. So the brief's rules, down to git run as `git -C <root>` and the shared scratch folder, sit in one Skill read before each brief. The cost: a long brief for a small task. :file[.agents/skills/dispatch-subagents/SKILL.md].
- **No background commands.** A subagent's turn ends when it stops to wait, and nothing wakes it when a background command ends, even when the brief said how to check. So a guard refuses the command outright. The cost: a long check runs in the foreground, and one outlasting a single call needs a resume. :file[scripts/hooks/subagent-background-guard.ts].
- **Review by the dispatcher.** A branch beyond a simple change is reviewed before its PR opens, and a building subagent can't start a reviewer. So the dispatching session reviews while the subagent waits unpushed, still holding the worktree for the fixes. The cost: a round trip per review. :file[.agents/skills/dispatch-subagents/SKILL.md].

### What to watch for

- **The brief is all it knows.** A rule, a count or a source the dispatching session already holds has to be in the brief, or the subagent derives it again or misses it.
- **Its report is a claim.** A subagent's prose is checked against the source it cites before anything ships on it.

## Try it in your project

Next time you hand Claude a task with parallel parts, write the brief as if to a stranger: the commit to start from, the setup command, what to commit, and what to report back. Compare its report with the files it names before you act on it.
