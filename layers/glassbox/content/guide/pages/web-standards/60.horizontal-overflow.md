A page scrolls sideways on a phone when something in it sticks out past the right edge of the screen. The usual culprits are few: a long string that can't break, a flex or grid box that refuses to shrink below its content, and a table or code block that is simply wider than a phone. Each has a short CSS fix, and one number read in the browser tells you whether the page scrolls sideways.

Know why a flex item won't shrink already? Skip to [In Terrarium](#in-terrarium).

## The concept

The [viewport](https://developer.mozilla.org/en-US/docs/Glossary/Viewport) is the part of the page the browser window shows. When content is too big for its box, [CSS shows it rather than hide it](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Overflow): a hidden button would be lost without anyone noticing. Content that runs past the viewport's right edge widens the page, and the reader can scroll sideways to it.

Three things usually cause it.

**A string that can't break.** By default a line breaks only at normal break points, such as a space. A long word, a URL or a piece of inline code has none, so it runs out of its box. [`overflow-wrap`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap) lets the browser break such a string at any point when the line has no other break. It has two values for that. `anywhere` counts those breaks when the browser works out the box's min-content width, the narrowest the box can be with every possible line break taken. `break-word` doesn't, and that matters for the next cause.

**A flex or grid item that won't shrink.** A [flex item](https://developer.mozilla.org/en-US/docs/Glossary/Flex_Item) is a direct child of a box with `display: flex`; a grid item is the same for `display: grid`. Its [`min-width`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-width) defaults to `auto`, and for flex and grid items that usually means the [min-content](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/min-content) width: the item never gets narrower than its longest word or its longest line that may not wrap. `min-width: 0` lets it shrink. A grid column sized in `fr` takes a share of the space left over, but [`1fr` alone means `minmax(auto, 1fr)`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/grid-template-columns), with the same automatic minimum; [`minmax(0, 1fr)`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/minmax) lets the column shrink. An item that scrolls its own content has an automatic minimum of 0 already.

**An element that is wider than a phone.** A table with many columns, a code block whose lines must not wrap, or a diagram can't fit in a phone's width. Give it a frame of its own with [`overflow-x: auto`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-x): the content is clipped at the frame's edge and can be scrolled into view, with a scroll bar only when there is more to see. Then the frame scrolls and the page doesn't. Or show less on a narrow screen, with a media query that hides some columns.

To find out whether a page overflows, read [`scrollWidth`](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollWidth) of `document.documentElement` with the viewport at a phone width such as 390 pixels. It is the width the page needs to show all its content without a horizontal scroll bar, so a value above 390 means something is wider than the viewport. When the content fits, `scrollWidth` equals `clientWidth`, the visible width.

Full reference: [MDN: Overflowing content](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Overflow)

## In Terrarium

Each :term[tenant] styles its own pages, and the fixes above appear across them.

A Blog post ends with links to the older and newer posts by the same :term[persona], side by side. In :file[layers/blog/app/assets/theme.css], each link is a flex item with `flex: 1` and `min-width: 0`, and is itself a flex column of two lines: a direction label and the post's title. The title rule clips its one unwrapped line with an ellipsis. Below 30rem the links stack:

::excerpt{path="layers/blog/app/assets/theme.css" lines="154-166"}
```css
.bl .post-nav-title {
  font-family: var(--bl-serif);
  font-size: 0.98rem;
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}
.bl .post-nav-spacer { flex: 1; }
@media (max-width: 30rem) {
  .bl .post-nav { flex-direction: column; }
  .bl .post-nav-newer { text-align: left; align-items: stretch; }
  .bl .post-nav-spacer { display: none; }
}
```
::

Since each link is a flex column, its `align-items` sets how wide its two lines are. With `stretch` the title is as wide as the content box of the link to the newer post, and a long title is clipped and ends in "…". The rule used to be `flex-start`; the commit that changed it explains that the title then took the width of its unwrapped text, and the ellipsis never applied.

A Blog post's inline code may break at any point. A code block scrolls in its own frame instead, and the code inside it sets `overflow-wrap` back to `normal`:

::excerpt{path="layers/blog/app/assets/theme.css" lines="453,460-462,467,470-471"}
```css
.bl .prose code {
  /* … */
  overflow-wrap: anywhere;
}
.bl .prose pre {
  /* … */
  overflow-x: auto;
  /* … */
}
.bl .prose pre code { background: none; border: 0; padding: 0; font-size: 0.86rem; line-height: 1.55; overflow-wrap: normal; }
```
::

The Journal gives its wide tables and its diagrams the same kind of frame in :file[layers/journal/app/assets/theme.css].

Its grids use the other fixes. A campaign page's sections are grid items with `min-width: 0`, and on wide screens its main column is `minmax(0, 1fr)` beside a fixed 360-pixel column (:file[layers/tinkerfund/app/components/tinkerfund/campaign/Campaign.vue]). The home page has a row of cards that scrolls on its own, and card grids whose columns are `minmax(min(100%, 280px), 1fr)`, never wider than the grid itself (:file[layers/tinkerfund/app/components/tinkerfund/browse/Home.vue]).

Browser tests in the Blog and Tinkerfund layers set the viewport to 390 pixels and assert that `document.documentElement.scrollWidth` is at most 390. The Blog's spec checks one post with a long title and one with a long code string, then a sample: for each persona, the post with the longest title, the post before it, which links to that title as its newer post, and the post with the longest inline code span. It loads each in one reused page, without waiting for hydration, the step where Vue takes over the server's HTML, and collects every route that is too wide:

::excerpt{path="layers/blog/tests/e2e/blog.spec.ts" lines="291-298"}
```ts
      await page.setViewportSize({ width: 390, height: 800 })
      const wide: string[] = []
      for (const route of routes) {
        await page.goto(url(route), { waitUntil: 'load' })
        const width = (await page.evaluate('document.documentElement.scrollWidth')) as number
        if (width > 390) wide.push(`${route} (${width}px)`)
      }
      expect(wide).toEqual([])
```
::

These specs run in `pnpm test:e2e`.

### Why it's built this way

- **Wide content scrolls in its own frame, never the page.** A table or diagram wider than a phone would otherwise widen the whole page. The Journal's stylesheet says it, and Tinkerfund's browser test (:file[layers/tinkerfund/tests/e2e/tinkerfund-flows.spec.ts]) requires it: wide content scrolls inside its own frame instead of widening the page. :file[layers/journal/app/assets/theme.css]
- **A phone keeps the columns that tell campaigns apart.** Tinkerfund's index hides the rest on a narrow screen, as its stylesheet's comment says, and the table no longer needs its 820-pixel minimum there. Their details stay on each campaign's own page. :file[layers/tinkerfund/app/components/tinkerfund/browse/IndexTable.vue]
- **A long title is cut, not allowed to widen the post.** A long title in the link to the newer post made Blog posts scroll sideways at phone width. Stretching the title to its link's width lets the ellipsis cut it, and a test loads such a post. :file[layers/blog/tests/e2e/blog.spec.ts]
- **Inline code breaks; code blocks scroll.** Inline code in a Blog post could also run past the page, so it now breaks anywhere, while code blocks keep their own scroll. A test loads a post with a long code string at phone width. :file[layers/blog/tests/e2e/blog.spec.ts]
- **The Blog's sweep is a sample, not every post.** Loading every post is slow enough that the test samples instead. Overflow comes from the HTML and CSS, so one reused page loads only the kinds of post that have overflowed, without waiting for hydration. :file[layers/blog/tests/e2e/blog.spec.ts]

### What to watch for

- **`min-width: 0` alone can still widen the page.** It lets the item shrink, but a string that can't break then spills out of it. Let it wrap with `overflow-wrap: anywhere`, or clip it as the Blog's title does, with `overflow: hidden`, `white-space: nowrap` and [`text-overflow: ellipsis`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-overflow).
- **`break-word` doesn't help inside a flex item.** Its breaks don't count toward the min-content width, so the item's automatic minimum stays as wide as the long string. Use `anywhere` there.
- **`overflow-wrap` on code in a block matters only if the block wraps.** A `pre` keeps its lines as written, and `overflow-wrap` on the `code` inside has no effect; with `white-space: pre-wrap` it does. The Blog resets it to `normal` inside blocks anyway.
- **Hiding overflow on the page root hides the symptom, not the cause.** `overflow-x: hidden` clips what sticks out, and no scroll bar leads to it. In Chromium, set on `html` alone or `body` alone, `document.documentElement.scrollWidth` still reads wider than 390; set on both, it reads 390 and only `document.body.scrollWidth` still shows the overflow.
- **The page-wide number misses what a box clips.** Content cut off inside an element with `overflow: hidden` doesn't widen the page, so `document.documentElement.scrollWidth` stays at 390. To find clipped text, compare an element's own `scrollWidth` with its `clientWidth`.
- **A sample checks only what it samples.** The Blog's sweep finds a title's older neighbour by sorting filenames, assuming date-prefixed names sort as the page orders posts. A post that overflows for another reason is caught only if it happens to be in the sample.
- **A test browser can hide or invent the problem.** A desktop Chromium ignores the page's `<meta name="viewport">`, so set the width through the driver's viewport, not a window-size flag. Terrarium's screenshot guide warns that its Linux build's fallback fonts are narrow, which can hide text that a wider font pushes past its box (:file[docs/agents/verifying-ui-changes.md]).

## Try it in your project

In an empty folder, install [Playwright](https://playwright.dev/docs/library) and its Chromium:

```sh
npm i playwright
npx playwright install chromium
```

Save this as `page.html`. It has two of the causes: a flex item with a long title that may not wrap, and a long URL:

```html
<!doctype html>
<style>
  body { margin: 0; font: 16px sans-serif; }
  .row { display: flex; gap: 8px; }
  .row a { flex: 1; }
  .title { white-space: nowrap; overflow: hidden; text-overflow: ellipsis; }
</style>
<div class="row">
  <a><div class="title">A post title far too long to fit on one line of a phone</div></a>
  <a><div class="title">Older</div></a>
</div>
<p>See https://example.com/a/very/long/address/with/no/spaces/in/it/at/all</p>
```

Save this beside it as `check.cjs`; it uses `require`, so the `.cjs` ending keeps Node from reading it as an ES module. It sets the width through Playwright's `viewport`, since a desktop browser ignores the page's viewport tag:

```js
const { chromium } = require('playwright')

;(async () => {
  const browser = await chromium.launch()
  const page = await browser.newPage({ viewport: { width: 390, height: 800 } })
  await page.goto('file://' + __dirname + '/page.html')
  const width = () => page.evaluate(() => document.documentElement.scrollWidth)
  console.log('as written:', await width())
  await page.addStyleTag({ content: 'p { overflow-wrap: anywhere }' })
  console.log('overflow-wrap:', await width())
  await page.addStyleTag({ content: '.row a { min-width: 0 }' })
  console.log('min-width: 0:', await width())
  await browser.close()
})()
```

Run `node check.cjs`. It prints `as written: 465`, `overflow-wrap: 403` and `min-width: 0: 390`; the first two depend on the fonts installed. At first the URL is the widest thing on the page. Once it breaks, the title's link is still as wide as its unwrapped title, and the page still scrolls. With `min-width: 0` the link shrinks, the ellipsis cuts the title, and the page fits.

To turn the measurement into a check, save this as `fits.cjs`. It loads each URL it is given and exits with 1 if any is wider than 390:

```js
const { chromium } = require('playwright')

;(async () => {
  const browser = await chromium.launch()
  const page = await browser.newPage({ viewport: { width: 390, height: 800 } })
  let failed = false
  for (const url of process.argv.slice(2)) {
    await page.goto(url)
    const width = await page.evaluate(() => document.documentElement.scrollWidth)
    if (width > 390) { console.log(`${url}: ${width}px`); failed = true }
  }
  await browser.close()
  process.exit(failed ? 1 : 0)
})()
```

Run `node fits.cjs "file://$PWD/page.html"`. It prints the page's address with `465px` and exits with 1. Add both fixes to `page.html`, `min-width: 0` on `.row a` and `overflow-wrap: anywhere` on `p`, and it prints nothing and exits with 0. Pass it your own pages' URLs, and run it wherever a failing command stops a change.
