A page can keep a few strings in the visitor's browser and find them again on the next page or the next visit, with no server involved. The browser gives every site two such stores: one that lasts until it is cleared, and one that lasts only as long as the tab. Both are simple to call and easy to misuse, since every script on the site shares them and the browser may refuse them.

Know `localStorage` and `sessionStorage` already? Skip to [In Terrarium](#in-terrarium).

## The concept

The Web Storage API has two stores, reached as `window.localStorage` and `window.sessionStorage`. Each is a `Storage` object, and each :term[origin] gets its own of each kind. `localStorage` is shared by every tab on the origin and [persists even when the browser is closed and reopened](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API). `sessionStorage` is also split by tab: it lasts for the page session, which survives reloads and restores, and closing the tab clears it. A page opened in a new tab starts a new session.

Both have the same methods. `setItem(key, value)` creates or updates an item, `getItem(key)` returns its value, or `null` when the key does not exist, `removeItem(key)` deletes one item, and `clear()` empties the whole store for that origin. `key(i)` and `length` list what is there. Keys and values are always strings: a number is converted, and an object is stored as `"[object Object]"`. Store objects and arrays with `JSON.stringify` and read them back with `JSON.parse`.

Every call is synchronous and blocks other script until it finishes, so a large read or write can stall the page. Browsers keep up to 5 MiB of local storage and 5 MiB of session storage per origin ([quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)); past that, `setItem` throws a `QuotaExceededError`.

A browser can support storage and still not make it available. Reading `localStorage` or `sessionStorage` throws a `SecurityError` when the visitor has set the browser to stop sites persisting data, which blocking cookies probably triggers. Some private windows give a store with a quota of zero, and in private mode `localStorage` is deleted when the private tabs close. Wrap each access in `try`/`catch`.

Storage lives only in the browser. The [HTML standard](https://html.spec.whatwg.org/multipage/webstorage.html) sets it against cookies, which are transmitted with every request. A page the server renders has none: browser-only globals throw on the server, and the usual approach is to read them in `onMounted`, as [Hydration](/t/glassbox/guide/nuxt-vue/hydration) shows.

Storage is no place for a secret. It has no path restriction, so every page on the origin can read and overwrite every key, and [OWASP warns](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) that a single :term[cross-site scripting] flaw can steal all of it. It advises keeping session identifiers out of storage, which script can always read; a cookie's `httpOnly` flag mitigates that risk. For large or structured data, [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) is asynchronous and suits larger datasets; for data the server needs on each request, use a cookie or the server.

Full reference: [MDN: Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)

## In Terrarium

Every :term[tenant] is served from one origin and shares its two stores. Glass Box keeps a visitor's reading progress in `localStorage` under the key `glassbox:read`, as a JSON array of lesson paths:

::excerpt{path="layers/glassbox/app/utils/reading.ts" lines="9-20"}
```ts
// Storage can be missing or throw (private window, blocked site data), so every access is guarded.
const browserStorage = (): GlassboxStorage | undefined => {
  try { return globalThis.localStorage } catch { return undefined }
}

/** The paths of the Lessons this browser has opened. */
export function readGlassboxProgress(storage: GlassboxStorage | undefined = browserStorage()): string[] {
  try {
    const parsed: unknown = JSON.parse(storage?.getItem(glassboxReadKey) ?? '[]')
    return Array.isArray(parsed) ? parsed.filter((p): p is string => typeof p === 'string') : []
  } catch { return [] }
}
```
::

A missing key reads as `'[]'`, a value that is not an array reads as nothing read, and an array keeps only its strings. `markGlassboxRead` writes the new list inside its own `try` and still returns it when the write fails. `resetGlassboxProgress` removes only `glassbox:read`. Each function takes the store as an optional argument, defaulting to `browserStorage()`, and the unit tests pass an in-memory one and one whose every call throws (:file[layers/glassbox/tests/unit/reading.spec.ts]). The composable `useGlassboxRead` holds the list in `useState`, empty on the server, and Glass Box's page component calls its `load` in `onMounted` (:file[layers/glassbox/app/composables/useGlassboxRead.ts]). An end-to-end test scrolls a lesson's Where next into view, reads `glassbox:read` straight from `localStorage`, presses the reset button and expects `null` (:file[layers/glassbox/tests/e2e/glassbox.spec.ts]).

The Journal's maintainer view keeps one flag in `localStorage` under `terrarium:maintainer`. A `?maintainer` query sets it, `?maintainer=0` removes it, and with neither the stored flag decides:

::excerpt{path="layers/journal/app/utils/maintainerView.ts" lines="20-31"}
```ts
export function resolveMaintainerView(search: string, storage: () => MaintainerStorage): boolean {
  const flag = new URLSearchParams(search).get(PARAM)
  try {
    const store = storage()
    if (flag === null) return store.getItem(KEY) === '1'
    if (flag === '0') store.removeItem(KEY)
    else store.setItem(KEY, '1')
  } catch {
    // Storage blocked (private mode, embedded frame): the URL flag still holds for this load.
  }
  return flag !== null && flag !== '0'
}
```
::

The store arrives as a getter, `() => localStorage`, called inside the `try`. How the Journal applies the answer after hydration is in [Hydration](/t/glassbox/guide/nuxt-vue/hydration#in-terrarium).

Tinkerfund keeps its demo state in `sessionStorage`. The demo backer's actions in a space sit under `tinkerfund:<space>:actions`, and :file[layers/tinkerfund/app/utils/backer.ts] reads them back through a Zod schema, returning an empty list for anything that fails it. `useTinkerfundActions` reads them in `onMounted`, inside a `try`, and each new action is written the same way (:file[layers/tinkerfund/app/composables/cart.ts]). The "Reset demo" button removes every key with the prefix, then reloads the page (:file[layers/tinkerfund/app/components/tinkerfund/shell/ResetDemo.vue]):

::excerpt{path="layers/tinkerfund/app/utils/demo.ts" lines="5,20-23"}
```ts
export const TINKERFUND_KEY_PREFIX = 'tinkerfund:'
// …
export function resetTinkerfundDemo(storage: Storage): void {
  const keys = [...Array(storage.length).keys()].map((i) => storage.key(i))
  for (const key of keys) if (key?.startsWith(TINKERFUND_KEY_PREFIX)) storage.removeItem(key)
}
```
::

The theme pick sits under `tinkerfund-theme`, outside the prefix, and survives a reset; a unit test seeds another tenant's key and checks that both stay (:file[layers/tinkerfund/tests/unit/demo-storage.spec.ts]). How the theme is applied before the first paint is in [Colour and motion settings](/t/glassbox/guide/web-standards/colour-and-motion-settings#in-terrarium).

The framework writes to the same stores. Nuxt keeps a reload-loop guard in `sessionStorage` under `nuxt:reload`, which :file[app/composables/contentLoadRecovery.ts] reads inside a `try` and treats as absent when storage is unavailable. Nuxt Content caches its database dumps in `localStorage` under `content_` keys ([Content database](/t/glassbox/guide/nuxt-content/content-database#what-to-watch-for)).

### Why it's built this way

- **Every key belongs to one owner.** All tenants share one origin, so one `clear()` would wipe other tenants' state and the framework's. Each tenant prefixes its keys and deletes only its own, never calling `clear()`. :file[.claude/rules/tenant-layers.md]
- **The page works without storage.** Storage can be missing or throw in a private window, with blocked site data or in an embedded frame. Every read and write sits in `try`/`catch` and falls back to an empty or in-memory value. The cost: with storage blocked, the demo backer's actions last only until the next page load. :file[layers/tinkerfund/app/composables/cart.ts]
- **Even reading the global is guarded.** Merely reading `localStorage` can throw when it is blocked, and that read must sit inside the `try`. The maintainer view takes the store as a getter and calls it there. :file[layers/journal/app/utils/maintainerView.ts]
- **Stored state waits for mount.** One cached server render serves every visitor, and the server has no storage. Reading progress starts empty and loads after mount, keeping that render the same for everyone. ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md])
- **Demo state ends with the tab.** A visitor's Tinkerfund actions should change the shop only until the tab closes or they press "Reset demo", which `sessionStorage` gives. The theme is a preference, not demo state, and the reset leaves it. :file[layers/tinkerfund/GLOSSARY.md]
- **Stored values are checked when read.** A stored value can be corrupt, foreign or tampered with. Reading progress keeps only an array's strings, and a tampered theme reads as System, with unit tests for both. :file[layers/glassbox/tests/unit/reading.spec.ts]
- **The store is passed in.** Functions that take the store as an argument need no browser in a test. The maintainer view's logic stays pure over its query string and store, and its unit test drives it with a fake store. :file[layers/journal/app/utils/maintainerView.ts]

### What to watch for

- **A new demo key needs the prefix.** "Reset demo" removes only keys that start with `tinkerfund:`, so a key without it outlives every reset, and a key with it is deleted even if it was meant to stay.
- **The maintainer view is not a lock.** Anyone can add `?maintainer` or set the flag in their own browser. Its file's comment says every session id it reveals is already public and claude.ai gates the page it links; anything it shows must stay that way.
- **A new tab starts a fresh demo.** Tinkerfund's state lives in the tab's own `sessionStorage`, and a tab opened on its own starts empty, at the shop's baked baseline.

## Try it in your project

Open any page of your site, then its developer tools console, and run:

```js
localStorage.setItem('demo:prefs', JSON.stringify({ theme: 'dark' }))
sessionStorage.setItem('demo:tab', 'this tab only')
localStorage.setItem('demo:count', 3)
console.log(localStorage.getItem('demo:prefs'))
console.log(JSON.parse(localStorage.getItem('demo:prefs')).theme)
console.log(typeof localStorage.getItem('demo:count'))
console.log(localStorage.getItem('demo:missing'))
```

It prints `{"theme":"dark"}`, then `dark`, then `string` for the number you stored, then `null` for the missing key. Now open the same page in a new tab and run:

```js
console.log(localStorage.getItem('demo:prefs'))
console.log(sessionStorage.getItem('demo:tab'))
for (const key of Object.keys(localStorage)) if (key.startsWith('demo:')) localStorage.removeItem(key)
console.log(localStorage.getItem('demo:prefs'))
```

The new tab prints `{"theme":"dark"}`, then `null`: it shares `localStorage` but has its own `sessionStorage`. The loop removes only the `demo:` keys, and the last line prints `null`.
