A page can keep a few strings in the visitor's browser and find them again on the next page or the next visit, with no server involved. The browser gives every site two such stores: one that lasts until it is cleared, and one that lasts only as long as the tab. Both are simple to call and easy to misuse, since every script on the site shares them and the browser may refuse them.

Know `localStorage` and `sessionStorage` already? Skip to [In Terrarium](#in-terrarium).

## The concept

The Web Storage API has two stores, reached as `window.localStorage` and `window.sessionStorage`. Each is a `Storage` object, and each :term[origin] gets its own of each kind. `localStorage` is shared by every tab on the origin and [persists even when the browser is closed and reopened](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API). `sessionStorage` is separate for each tab: it survives a reload, and closing the tab clears it. A new tab begins with an empty one, unless a script opened that tab with `window.open` (without `noopener`), in which case it starts as a copy. Use `sessionStorage` when the data need not outlive the tab, and `localStorage` when it should come back on the next visit.

Both have the same methods. `setItem(key, value)` creates or updates an item, `getItem(key)` returns its value, or `null` when the key does not exist, `removeItem(key)` deletes one item, and `clear()` empties the whole store for that origin. `key(i)` and `length` list what is there. Keys and values are always strings: a number is converted, and an object is stored as `"[object Object]"`. Store objects and arrays with `JSON.stringify` and read them back with `JSON.parse`.

Every call is synchronous and blocks other script until it finishes, so a large read or write can stall the page. Each store has a size limit, its quota: browsers keep up to 5 MiB of local storage and 5 MiB of session storage per origin ([quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)); past that, `setItem` throws a `QuotaExceededError`.

A browser can support storage and still not make it available. Reading `localStorage` or `sessionStorage` throws a `SecurityError` when the visitor has set the browser to stop sites persisting data, which blocking cookies probably triggers. Some browsers' private windows give a store with a quota of zero, and in private mode `localStorage` is deleted when the private tabs close. Wrap each access in `try`/`catch`.

Storage lives only in the browser. The [HTML standard](https://html.spec.whatwg.org/multipage/webstorage.html) sets it against cookies, which are transmitted with every request. When a server renders a page, it runs the page's code to build the HTML, and browser-only globals are missing there. Vue's advice is to read them in `onMounted`, a hook that runs only in the browser, after it has taken over the server's HTML; [Hydration](/t/glassbox/guide/nuxt-vue/hydration) covers that step.

Storage is no place for a secret. It has no path restriction, so every page on the origin can read and overwrite every key, and [OWASP warns](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) that a single :term[cross-site scripting] flaw can steal all of it. It advises keeping session identifiers out of storage, which script can always read; a cookie flagged [`HttpOnly`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) cannot be read by script, which mitigates that risk.

Pick something else for three kinds of data. Large amounts of structured data go in [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), the browser's built-in database. Data the server needs on each request goes in a cookie. Secrets stay out of Web Storage and IndexedDB alike, as OWASP advises.

Full reference: [MDN: Using the Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API/Using_the_Web_Storage_API)

## In Terrarium

Every :term[tenant] is served from one origin and shares its two stores. Glass Box keeps a visitor's reading progress in `localStorage` under the key `glassbox:read`, as a JSON array of lesson paths:

::excerpt{path="layers/glassbox/app/utils/reading.ts" lines="9-20"}
```ts
// Storage can be missing or throw (private window, blocked site data), so every access is guarded.
const browserStorage = (): GlassboxStorage | undefined => {
  try { return globalThis.localStorage } catch { return undefined }
}

/** The paths of the Lessons this browser has opened. */
export function readGlassboxProgress(storage: GlassboxStorage | undefined = browserStorage()): string[] {
  try {
    const parsed: unknown = JSON.parse(storage?.getItem(glassboxReadKey) ?? '[]')
    return Array.isArray(parsed) ? parsed.filter((p): p is string => typeof p === 'string') : []
  } catch { return [] }
}
```
::

A missing key reads as `'[]'`, a value that is not an array reads as nothing read, and an array keeps only its strings. `markGlassboxRead` writes inside its own `try` and still returns the new list when the write fails, and `resetGlassboxProgress` removes only `glassbox:read`.

Each function takes the store as an optional argument, which the unit tests fill with an in-memory or a throwing store (:file[layers/glassbox/tests/unit/reading.spec.ts]). The list starts empty in `useState` (:file[layers/glassbox/app/composables/useGlassboxRead.ts]), and Glass Box's page component loads it in `onMounted` (:file[layers/glassbox/app/pages/t/glassbox/]).

The Journal's maintainer view keeps one flag in `localStorage` under `terrarium:maintainer`. A `?maintainer` query sets it, `?maintainer=0` removes it, and with neither the stored flag decides:

::excerpt{path="layers/journal/app/utils/maintainerView.ts" lines="20-31"}
```ts
export function resolveMaintainerView(search: string, storage: () => MaintainerStorage): boolean {
  const flag = new URLSearchParams(search).get(PARAM)
  try {
    const store = storage()
    if (flag === null) return store.getItem(KEY) === '1'
    if (flag === '0') store.removeItem(KEY)
    else store.setItem(KEY, '1')
  } catch {
    // Storage blocked (private mode, embedded frame): the URL flag still holds for this load.
  }
  return flag !== null && flag !== '0'
}
```
::

The store arrives as a getter, `() => localStorage`, called inside the `try`. The Journal resolves the flag only after the page mounts, and its session cards share one answer, as [Hydration](/t/glassbox/guide/nuxt-vue/hydration#in-terrarium) shows.

Tinkerfund keeps its demo state in `sessionStorage`. The demo backer's actions in a space sit under `tinkerfund:<space>:actions`, and :file[layers/tinkerfund/app/utils/backer.ts] reads them back through a [Zod](https://v3.zod.dev/) schema, returning an empty list for anything that fails it. `useTinkerfundActions` reads them in `onMounted`, inside a `try`, and each new action is written the same way (:file[layers/tinkerfund/app/composables/cart.ts]). The "Reset demo" button runs the loop below, removing every key with the prefix, and then reloads the page (:file[layers/tinkerfund/app/components/tinkerfund/shell/ResetDemo.vue]).

::excerpt{path="layers/tinkerfund/app/utils/demo.ts" lines="5,20-23"}
```ts
export const TINKERFUND_KEY_PREFIX = 'tinkerfund:'
// …
export function resetTinkerfundDemo(storage: Storage): void {
  const keys = [...Array(storage.length).keys()].map((i) => storage.key(i))
  for (const key of keys) if (key?.startsWith(TINKERFUND_KEY_PREFIX)) storage.removeItem(key)
}
```
::

The theme pick sits under `tinkerfund-theme`, outside the prefix, and survives a reset; a unit test seeds it beside another tenant's key and checks that both stay (:file[layers/tinkerfund/tests/unit/demo-storage.spec.ts]). A script in `<head>` reads that key before the first paint, as [Colour and motion settings](/t/glassbox/guide/web-standards/colour-and-motion-settings#in-terrarium) shows.

Nuxt keeps a reload-loop guard under `nuxt:reload` in `sessionStorage` (:file[app/composables/contentLoadRecovery.ts]), and Nuxt Content caches its database dumps in `localStorage` under `content_` keys ([Content database](/t/glassbox/guide/nuxt-content/content-database#what-to-watch-for)).

### Why it's built this way

- **Every key belongs to one owner.** All tenants share one origin, so one `clear()` would wipe other tenants' state and the framework's. Each tenant prefixes its keys, removes only its own and never calls `clear()`. :file[.claude/rules/tenant-layers.md]
- **The page works without storage.** Storage can be missing or throw in a private window, with blocked site data or in an embedded frame, and even reading the global can throw. Every access sits in `try`/`catch`, the maintainer view's getter included, and falls back to an empty or in-memory value. The cost: with storage blocked, the demo backer's actions last only until the next page load. :file[layers/journal/app/utils/maintainerView.ts] :file[layers/tinkerfund/app/composables/cart.ts]
- **Stored state waits for mount.** One cached server render serves every visitor, and the server has no storage. Reading progress starts empty and loads after mount, keeping that render the same for everyone. :file[layers/glassbox/app/composables/useGlassboxRead.ts] ADR-0028 (:file[docs/adr/0028-navigation-reads-server-payloads.md])
- **Demo state ends with the tab.** A visitor's Tinkerfund actions should change the shop only until the tab closes or they press "Reset demo", which `sessionStorage` gives. The theme is a preference, not demo state, and the reset leaves it. :file[layers/tinkerfund/GLOSSARY.md] :file[layers/tinkerfund/app/utils/demo.ts]
- **Stored values are checked when read.** A stored value can be corrupt, foreign or tampered with. Reading progress keeps only an array's strings, and a tampered theme reads as System, with unit tests for both. :file[layers/glassbox/tests/unit/reading.spec.ts] :file[layers/tinkerfund/tests/unit/demo-storage.spec.ts]
- **The store is passed in.** Functions that take the store as an argument need no browser in a test. The maintainer view's logic stays pure over its query string and store, and its unit test drives it with a fake store. :file[layers/journal/app/utils/maintainerView.ts] :file[layers/journal/tests/unit/maintainer-view.spec.ts]

### What to watch for

- **A new demo key needs the prefix.** "Reset demo" removes only keys that start with `tinkerfund:`, so a key without it outlives every reset, and a key with it is deleted even if it was meant to stay.
- **The maintainer view is not a lock.** Anyone can add `?maintainer` or set the flag in their own browser. Its file's comment says every session id it reveals is already public and claude.ai gates the page it links; anything it shows must stay that way.
- **A tab opened on its own starts a fresh demo.** Tinkerfund's state lives in the tab's own `sessionStorage`; a tab you open directly starts empty, at the shop's baked baseline, though one a script opens with `window.open` starts with a copy.

## Try it in your project

Open any page of your site, then its developer tools console, and run:

```js
localStorage.setItem('demo:prefs', JSON.stringify({ theme: 'dark' }))
sessionStorage.setItem('demo:tab', 'this tab only')
localStorage.setItem('demo:count', 3)
console.log(localStorage.getItem('demo:prefs'))
console.log(JSON.parse(localStorage.getItem('demo:prefs')).theme)
console.log(typeof localStorage.getItem('demo:count'))
console.log(localStorage.getItem('demo:missing'))
```

It prints `{"theme":"dark"}`, then `dark`, then `string`, then `null`. Now type or paste the same address into a new tab and run:

```js
console.log(localStorage.getItem('demo:prefs'))
console.log(sessionStorage.getItem('demo:tab'))
for (const key of Object.keys(localStorage)) if (key.startsWith('demo:')) localStorage.removeItem(key)
console.log(localStorage.getItem('demo:prefs'))
```

The new tab prints `{"theme":"dark"}`, then `null`: it shares `localStorage` but has its own `sessionStorage`. The loop removes only the `demo:` keys, and the last line prints `null`.
