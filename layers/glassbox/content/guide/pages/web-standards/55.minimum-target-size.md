A link or button is easier to hit when it is big enough, or far enough from its neighbours. WCAG, the web's accessibility guidelines, asks that a target for a pointer be at least 24 by 24 CSS pixels, and names the cases that are exempt, such as a link inside a sentence. In CSS, padding grows a small link's box, and an equal negative margin cancels the room that padding would take, so nothing around it moves.

Know the 24-pixel rule already? Skip to [In Terrarium](#in-terrarium).

## The concept

Success criterion 2.5.8 Target Size (Minimum), at level AA of WCAG 2.2, asks that the target for pointer inputs be at least 24 by 24 CSS pixels. A CSS pixel is the unit CSS measures all lengths in, not a pixel of the screen's hardware. Pointer inputs cover a mouse, a trackpad, a stylus and a finger. A target is big enough when a 24 by 24 square, aligned with the page, fits wholly inside it. Zoom doesn't count: zooming in leaves an element's size in CSS pixels the same.

It helps people with hand tremors, people whose specialised input devices are less accurate than a mouse, and anyone on a touchscreen. Touch research suggests larger sizes, but this criterion covers every pointer, so its minimum is smaller. The stricter [2.5.5 Target Size (Enhanced)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html), at level AAA, asks for 44 by 44.

There are five exceptions:

- **Spacing.** A target smaller than 24 by 24 passes if a circle 24 pixels across, centred on its bounding box (the smallest upright rectangle around it), doesn't touch another target or the circle of another small target.
- **Equivalent.** Another control on the same page does the same thing and meets the criterion.
- **Inline.** A link in a sentence is exempt, as is any target whose size is held by the line height of the text around it. Text reflows with the window, so an author can't know where such links will fall.
- **User agent control.** The browser draws the control and the author hasn't resized it, such as the calendar of an `<input type="date">`.
- **Essential.** The size or position carries the information, such as pins on a map.

A box's hit area includes its padding. Where the growth goes depends on `display`. On a plain inline link, vertical padding [changes the size of the box without moving the content around it](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Box_model), and can overlap the lines above and below. An [`inline-block`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/display-legacy) element sits in a line of text like a word but is laid out as a block, so its padding does push what follows down. A [negative margin](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/margin) of the same size cancels that room: the box is taller, and its place in the layout stays the same. In headless Chromium, with 13-pixel text at line-height 1.4, 5 pixels of padding took a 15-pixel link to 25 pixels inline, with nothing moved, and to 28 as an `inline-block`: its 18-pixel line height plus the padding. That pushed the next line down 10 pixels until the negative margin was added.

Where the layout has room, a `min-height` of 24 pixels on an `inline-block` or block reaches the size with no margin to work out, but it takes that room: in the same test it moved the next line down about 6 pixels.

To measure a target, read [`getBoundingClientRect()`](https://developer.mozilla.org/en-US/docs/Web/API/Element/getBoundingClientRect) in the browser: the smallest rectangle around the element, padding and border included. Read it at a phone's width, such as 390 pixels.

Full reference: [W3C: Understanding SC 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## In Terrarium

Small links in several :term[tenants]{id="tenant"} and the site footer (:file[app/components/SiteFooter.vue]) get `display: inline-block`, a vertical padding, and an equal negative vertical margin. The Blog's Back link is one:

::excerpt{path="layers/blog/app/assets/theme.css" lines="168-173"}
```css
.bl .post-nav-back {
  margin: 0.9rem 0 0;
  font-family: var(--bl-mono);
  font-size: 0.78rem;
}
.bl .post-nav-back a { display: inline-block; padding-block: 5px; margin-block: -5px; color: var(--bl-muted); text-decoration: none; }
```
::

The Blog's breadcrumb links carry the same three declarations with 5 pixels, and the Blog's comments call it a 24px tap target with no layout shift. Tinkerfund's heading links in long text (:file[layers/tinkerfund/app/assets/theme.css]) and inventor names use 4 pixels, and Tinkerfund's comments and the footer's say the negative margin keeps the layout.

An element that already has a margin takes the padding out of it. A dig report's jump link on the Midden had margins of its own, and the pager's links sit in a flex row, whose children the browser turns into blocks ([CSS Flexbox: flex items](https://www.w3.org/TR/css-flexbox-1/#flex-items)):

::excerpt{path="layers/midden/app/pages/t/midden/[space]/[...slug].vue" lines="232-236"}
```css
/* 24px tap targets (WCAG 2.5.8): padding makes up the height, the negative margin
   takes it back so nothing moves (as the breadcrumb does, theme.css). The jump
   link's margins are the old 0.6rem / 0.2rem less that 0.25rem each. */
.midden-report__jump { display: inline-block; padding: 0.25rem 0; margin: 0.35rem 0 -0.05rem; }
.midden-report__pager a { padding: 0.25rem 0; margin: -0.25rem 0; }
```
::

The Blog's tag label does the same in :file[layers/blog/app/assets/theme.css]: 4 pixels of padding, and a bottom margin of `calc(0.6rem - 4px)`, 0.6rem less the padding. On a narrow screen, where the label opens a disclosure, `.net-tags[open] summary` restores that margin while it is open. The button below it that shows the tags' meanings uses 6 pixels the same way. The Journal's select for the friction ledger's window takes `min-height: 1.5rem` instead (:file[layers/journal/app/pages/t/journal/]).

End-to-end tests load a page at 390 by 844 pixels and read the matching controls' heights:

::excerpt{path="layers/blog/tests/e2e/blog.spec.ts" lines="435,438,440-444"}
```ts
  it('keeps the breadcrumb and Back links at least 24px tall on a phone', async () => {
    // …
      await page.setViewportSize({ width: 390, height: 844 })
      // …
      const heights = await page
        .locator('.crumb a, .post-nav-back a')
        .evaluateAll((els) => els.map((el) => el.getBoundingClientRect().height))
      expect(heights.length).toBeGreaterThanOrEqual(3)
      for (const h of heights) expect(h).toBeGreaterThanOrEqual(24)
```
::

The Midden's jump and pager links (:file[layers/midden/tests/e2e/midden.spec.ts]) and Tinkerfund's campaign links in its index table (:file[layers/tinkerfund/tests/e2e/tinkerfund-flows.spec.ts]) have the same kind of test. The Journal's test reads the first matching select and pull-request link with Playwright's `boundingBox()` (:file[layers/journal/tests/e2e/journal.spec.ts]).

### Why it's built this way

- **A taller target must not move the page.** Padding alone makes a link taller, and on an `inline-block` it pushes everything below it down. Terrarium pairs the padding with an equal negative margin. :file[layers/blog/app/assets/theme.css]
- **A margin the element already has absorbs the padding.** An element has one margin per side; the Midden's jump link folds the padding into its old margins, and the Blog's tag label writes `calc(0.6rem - 4px)`. Each margin is the old value less the padding, and the Midden's comment names the old values and the padding. :file[layers/midden/app/pages/t/midden/]

### What to watch for

- **Nothing measures a new control.** No :term[ADR], rule or agent doc sets a target-size practice, and no lint rule or :term[gate] step measures targets. Only the e2e tests above do, each for the selectors it names: a new small link passes `pnpm gate:scoped` unmeasured.
- **Keep the two numbers equal.** A padding of 5 pixels with a margin of -4 pixels moves everything below by 2 pixels. Change both together, and redo the sum when the element has a margin of its own.
- **A big box is not always the target.** The padding reaches over its neighbours. Where two padded links overlap, the later one in the page takes the tap, and an element drawn on top takes it from both. `document.elementFromPoint(x, y)` names what a tap at a point would hit.
- **The tests read height only.** A link of one or two characters can be narrower than 24 pixels. Measure the width too.
- **Passing is not the same as easy to use.** A very small target can pass on spacing alone and still be hard to activate; the Understanding page adds that larger targets help many people. 2.5.8 is a minimum.

## Try it in your project

Save this as `target.html` and open it in a browser:

```html
<!doctype html>
<meta name="viewport" content="width=device-width">
<body style="font: 14px/1.4 sans-serif">
  <nav><a href="#">Back to the list</a></nav>
  <p id="next">The next paragraph</p>
  <script>
    const a = document.querySelector('a')
    const next = document.querySelector('#next')
    console.log('before', a.getBoundingClientRect().height, next.getBoundingClientRect().top)
    Object.assign(a.style, { display: 'inline-block', paddingBlock: '4px', marginBlock: '-4px' })
    console.log('after', a.getBoundingClientRect().height, next.getBoundingClientRect().top)
  </script>
</body>
```

In headless Chromium at 390 pixels wide they read `before 16 41.59375` and `after 27.59375 41.59375`. The first height depends on the font; the second, as in The concept, is the line height, 19.6 pixels, plus 8 of padding. The paragraph's top is the same in both. Then remove the `marginBlock` and reload: the height stays, and the paragraph moves down.
