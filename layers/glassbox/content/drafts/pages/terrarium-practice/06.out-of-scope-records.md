A rejected idea comes back. A closed issue hides why it was turned down, so the next person or agent to ask for the same thing starts the argument from scratch. An out-of-scope record writes the no down once, where the next request will meet it.

Know out-of-scope records already? Skip to [In Terrarium](#in-terrarium).

## The concept

Keep one short file per rejected idea in a folder of the repository. Each file says what the project won't do, why, in reasons that will still hold next year, and which requests asked for it. A file is about a concept, not an issue: every later request for the same thing joins the same file.

Whoever triages a new request reads the folder first and matches by meaning, not by keyword: "night theme" matches a file about dark mode. On a match, the old reasons go to the person deciding, who confirms the no or changes their mind. Changing your mind means deleting or rewriting the file.

Only a rejected idea gets a file. A request closed because the feature already exists is not a rejection, and a file for it would make the next triage turn down something the project has.

## In Terrarium

The records live in :file[.out-of-scope/]. The format and the triage steps come from the pack's `triage` Skill, whose :file[.agents/skills/triage/OUT-OF-SCOPE.md] describes them; Terrarium keeps it as installed ([The Skill pack](/t/glassbox/drafts/skill-pack/skill-pack)). A record opens with the decision in one sentence:

::excerpt{path=".out-of-scope/ci-enforced-doc-invariants.md" lines="1-5"}
```md
# CI-Enforced Documentation Invariants

This project does not add gate/CI checks that block a change because a
documentation or metadata invariant is unsatisfied — a doc mentioning a retired
term, a commit missing its authorship stamp, and their relatives.
```
::

`triage` reads every record before it recommends anything for a request, and writes one when a maintainer rejects an enhancement as `wontfix`. Terrarium's own unattended sweep, :file[.agents/skills/auto-triage/SKILL.md], closes only what it can check in the repo: a duplicate, or a request already built. A rejection is a judgement call, so the sweep labels the issue `ready-for-human`, and a record is written only once a :term[Trusted] user confirms the no.

### Why it's built this way

Which issues the unattended sweep may close, and why a rejection waits for a person: ADR-0022 (:file[docs/adr/0022-autonomous-triage-sweep.md]).

Why rejected ideas get a record, from the pack's `triage` Skill: :file[.agents/skills/triage/OUT-OF-SCOPE.md].

### What to watch for

- **A record is not an instruction.** The Skills that audit or prune agent instructions skip :file[.out-of-scope/], so no audit checks a record against the code. Its reasons are as of when it was written; reread them before you lean on one.
- **A record is not an ADR.** An ADR states how the Platform works and binds every agent; a record only says no to one idea, for whoever triages the next request for it.

## Try it in your project

Next time you close a feature request as "won't do", create `.out-of-scope/<idea>.md` with the decision in one sentence, the reasons, and a link to the request. Before you triage the next one, read the folder.
