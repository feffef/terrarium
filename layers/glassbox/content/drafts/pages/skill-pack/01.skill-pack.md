You don't have to write every :term[Skill] your agents use. A Skill pack is a set of Skills someone else wrote and published, which you install into your project. The catch is that the files are then in your repo, where anyone can edit them, and the next install would undo that edit without a word.

Know Skill packs already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Skill is a folder with a `SKILL.md` file of instructions for one kind of job. A pack publishes many of them in one GitHub repository. The pack Terrarium uses, Matt Pocock's `skills`, holds Skills such as `tdd`, `diagnosing-bugs` and `grill-me`. It can be installed as a plugin, which updates itself, or with the [`skills` command-line tool](https://github.com/vercel-labs/skills), which copies the Skills into your project as ordinary files that you update by hand:

```bash
npx skills@latest add mattpocock/skills
```

The command-line tool installs into the project by default, so the Skills are committed with your code and every clone has them. When one install serves several agents, it can link each agent's Skill folder to a single copy. `npx skills update` brings the copies up to date with the pack.

Some packs also ship a setup Skill that writes a project's own configuration from templates. This pack's `setup-matt-pocock-skills` asks which issue tracker the project uses, whether to keep its default triage labels, and where its docs live, then writes docs that the other Skills read.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

The pack's Skills sit in :file[.agents/skills/] beside Terrarium's own, and :file[.claude/skills/] holds a link to each folder so Claude Code finds it. The installer's :file[skills-lock.json] records each pack Skill: its source repository, its path there, and a hash of that upstream file.

::excerpt{path="skills-lock.json" lines="112-116"}
```json
    "tdd": {
      "source": "mattpocock/skills",
      "sourceType": "github",
      "skillPath": "skills/engineering/tdd/SKILL.md",
      "computedHash": "daf55026f456af104a72fa43247f7bcec89e5127316dc5b1b8d675d6a9d8ce94"
```
::

Being listed there is what makes a Skill a pack Skill, and nobody in Terrarium edits a pack Skill's files. The lock's hash can't check them: as :file[scripts/gate/validate-skills-lock.ts] explains, it is a hash of the upstream source, not of the file as installed, and can't be checked offline. So each pack Skill's entry in the :term[Skill Inventory] pins a hash of its installed `SKILL.md`:

::excerpt{path="layers/journal/content/current/skills/tdd.yml" lines="1-4"}
```yaml
name: tdd
category: general-engineering
importance: supporting
installedSha256: 5505d25bbaa8fc14a79e4d20163936958992a2995b7f1dd1d6197edc9ed722e0
```
::

:file[scripts/gate/validate-skills-lock.ts] is a step of the :term[Gate]'s :term[Floor]. It reads the lock only to learn which Skills are the pack's, hashes each one's installed `SKILL.md`, and fails on a file that is missing, has no pin, or differs from its pin. After a real update from the pack, `pnpm verify:skills-lock --write` re-pins in the same PR. Notes on how a pack Skill fits Terrarium, and problems with its text, go in its Inventory entry, not in its files.

The setup Skill seeded three docs: :file[docs/agents/issue-tracker.md], :file[docs/agents/triage-labels.md] and :file[docs/agents/domain.md]. Those are Terrarium's own now. Each opens with a note not to re-sync it against the pack's template.

### Why it's built this way

Pack Skills and their pins: ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).

Docs copied from a pack template: ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Only pack Skills in the Inventory are checked for edits.** A Skill gets its entry when it is first seen in use, so one installed but never used goes unchecked until then.
- **A fix to a pack Skill can't land here.** If a pack Skill's text is wrong, record the problem in its Inventory entry; the fix belongs upstream.
- **Re-pin only after a real install.** `--write` makes any edited file pass, so run it only when the new content came from the pack.

## Try it in your project

Pick one Skill you installed from a pack, record the sha256 of its `SKILL.md` in a file you own, and add a CI step that fails when the installed file's hash differs.
