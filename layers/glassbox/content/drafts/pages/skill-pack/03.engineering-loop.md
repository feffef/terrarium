An agent writes code faster than anyone can read it, so the useful question is what tells it, and you, that the code is right. The Skill pack's engineering Skills each answer part of that: a test that fails first, a bug caught by a check that goes red, a review that compares the change with both the repo's rules and the request, and cheap answers to design questions before any of it.

Know these Skills already? Skip to [In Terrarium](#in-terrarium).

## The concept

Five :term[Skills]{id="skill"} from the pack shape how a change gets built and checked. The agent can reach for any of them on its own when the task fits.

**`tdd`** is the red-then-green loop: write one failing test, then only enough code to pass it, one slice at a time. Tests sit at *seams*, the public boundaries where behaviour can be seen without reaching inside, and the seams are agreed with the person before any test is written. The Skill names three traps: tests coupled to the implementation, tests that recompute the expected value the way the code does, and writing every test before any code. Refactoring is left out of the loop on purpose; it belongs to review.

**`diagnosing-bugs`** starts from the same idea. Its first phase, the one it calls "the skill", is a feedback loop: one command, already run, that goes red on this exact bug, gives the same verdict every run and takes seconds. Only then does it reproduce and shrink the case, rank several falsifiable hypotheses, test them one variable at a time, write the regression test before the fix, and remove its tagged debug logs. Where no seam lets a regression test catch the real bug, it records that as a finding rather than write a shallow test that gives false confidence.

**`code-review`** reviews the diff from a fixed point, such as a branch or commit, on two axes. *Standards* asks whether the change follows the repo's documented rules, plus a baseline of code smells from Martin Fowler's *Refactoring* that a documented rule always overrides. *Spec* asks whether it does what the originating issue asked, no more and no less. Each axis runs in its own sub-agent, and the two reports stay separate, so a change that passes one can't hide that it fails the other.

**`prototype`** builds throwaway code to answer one design question: a single HTML file for "does this logic feel right", or several switchable variants on one route for "what should this look like". When it is done, the decision goes into the real code and the prototype is kept on a branch outside `main`, linked from the issue.

**`research`** sends a background agent to answer a question from primary sources, such as official docs, source code and specs, and writes the findings with their sources to one Markdown file where the repo keeps such notes.

Full reference: [mattpocock/skills on GitHub](https://github.com/mattpocock/skills)

## In Terrarium

All five are pack Skills in :file[.agents/skills/], kept exactly as installed ([The Skill pack](/t/glassbox/drafts/skill-pack/skill-pack)). Terrarium leaves most of them optional and makes one a fixed step.

That step is `code-review`. Before a branch's first push, a session runs `code-review` against `origin/main`, fixes what it finds, and then runs `pnpm gate:scoped` on the final head, as :file[docs/agents/pr-workflow.md] sets out. A simple change gets the author's own read of its diff instead, and the same file says what counts as simple. An integration PR that stacks several reviewed stories gets one more review of its whole diff, since separate reviews can't see how the stories interact. The Standards axis has no single standards file to read here: Terrarium's rules live in :file[CLAUDE.md], in :file[.claude/rules/] and in the docs those point to.

One :term[Workflow] runs the loop from end to end. :file[.claude/workflows/clear-backlog-build.js] has a build agent work test-first with `tdd`, then runs the two review axes as parallel agents of its own, each reading the `code-review` Skill and applying one axis. A fix agent takes the findings worth fixing, and the review runs again, up to a fixed number of rounds:

::excerpt{path=".claude/workflows/clear-backlog-build.js" lines="152,154-156,160,162"}
```js
  for (let round = 1; round <= MAX_ROUNDS; round++) {
    // …
    const axes = ['Standards', 'Spec']
    const reviews = await parallel(axes.map(axis => () =>
      agent(reviewPrompt(b, axis, out.worktree, round, out.decisions), { label: `${axis} ${b.name} r${round}`, phase: 'Review', schema: REVIEW })))
    // …
    const toFix = all.filter(f => f.worthFixing)
    // …
    if (!toFix.length) return { ...out, status: 'ready-to-push' }
```
::

A branch comes out of the loop when only judgement calls are left, and is pushed and then checked again by the :term[Gate] in CI.

The other four are reached for when the work calls for them. `wayfinder` names `prototype` and `research` as two of its ticket types ([Planning with the pack](/t/glassbox/drafts/skill-pack/planning-with-the-pack)). The place where Terrarium keeps research notes is :file[docs/research/], for verified reference material from primary sources; an open idea or question is an issue instead (:file[docs/agents/issue-tracker.md]). Before debugging a tool, push, network or permission error that the diff doesn't explain, :file[CLAUDE.md] has a session read :file[docs/agents/environment-caveats.md] first: it lists the limits of the cloud container that are not bugs in the repo, so none of them gets diagnosed again as new. How much each Skill matters here, and why, is in the :term[Skill Inventory].

### Why it's built this way

Review and the Gate: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

Pack Skills left as installed: ADR-0015 (:file[docs/adr/0015-audit-skills-and-conditional-importance.md]).

Workflow scripts: ADR-0005 (:file[docs/adr/0005-skill-model.md]).

### What to watch for

- **Re-check what a reviewer cites.** A review sub-agent can quote a line that isn't there. Terrarium's Inventory entry for `code-review` asks each review brief to restate "verify before you state", and every cited line to be read again before it is acted on.
- **Only a `research/` or `prototype/` branch gets no PR here.** `wayfinder`'s research tickets push their findings to a branch with no PR, and `prototype` keeps its code on a branch outside `main`. ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]) names those two prefixes; give a branch of that kind one of them.

## Try it in your project

Next time you review a change, run it as two separate passes: first only against your project's written rules, then only against the issue it closes. Note which findings the second pass found that the first missed.
