Left to its defaults, Dependabot opens one pull request for every dependency that has a newer version. Terrarium groups the small updates instead, so each check brings one pull request per ecosystem for the minor and patch updates, rather than a stack of them.

Know Dependabot groups already? Skip to [In Terrarium](#in-terrarium).

## The concept

Dependabot version updates are configured in `.github/dependabot.yml`. The file has `version: 2` and a list of `updates`, one entry per package manager, each with its `package-ecosystem`, the `directory` or `directories` that hold its manifests, and a `schedule.interval` for how often to look.

By default each outdated dependency gets its own pull request. A `groups` entry names a rule, and every update that matches it is combined into a single pull request. `patterns` match dependency names, with `*` as a wildcard, and `update-types` limits a group to `major`, `minor` or `patch` releases. An update that matches several rules goes into the first; one that matches none still gets its own pull request.

`cooldown` delays version updates: a new release isn't considered until it is a set number of days old. It applies to version updates only, never to security updates.

Full reference: [GitHub Docs: Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)

## In Terrarium

:file[.github/dependabot.yml] holds two entries:

::excerpt{path=".github/dependabot.yml" lines="4-25"}
```yaml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    cooldown:
      default-days: 3
    groups:
      npm-minor-patch:
        update-types: [minor, patch]

  # Touches .github/ (human-only, ADR-0004), so never auto-merged.
  - package-ecosystem: github-actions
    directories: [/, /.github/actions/gate]
    schedule:
      interval: weekly
    cooldown:
      default-days: 3
    groups:
      github-actions:
        patterns: ["*"]
```
::

The npm group takes every minor and patch update. A major update matches no rule and arrives as a pull request of its own. The Actions group takes every update, whatever its size. Its second directory names the folder of the Gate's composite action ([A thin CI workflow plus a composite action](/t/glassbox/drafts/git-github/thin-ci-workflow)): with `/` alone, Dependabot reads only `.github/workflows/` and a root `action.yml`.

Who merges is split by the pull request's content. A :term[Routine] runs the `dependabot-sweep` Skill (:file[.agents/skills/dependabot-sweep/SKILL.md]), which reviews each pull request. :file[scripts/github/merge-pr.ts] merges a Dependabot pull request only when it changes just `package.json` and the lockfile and keeps every changed version within its major (a 0.x minor counts as a major). It refuses anything else, so a major update, a pull request that adds a dependency and every Actions pull request wait for a person: the Actions group changes files under `.github/`, which are :term[Human-only] (:file[docs/agents/pr-workflow.md]).

### Why it's built this way

Which dependency updates wait for a person: ADR-0004 (:file[docs/adr/0004-objective-safety-gate.md]).

### What to watch for

- **A group is a pull request, not a review.** One grouped pull request can hold many updates, and a single bad one fails the whole Gate run; read the list in its description before you merge it.
- **`/` doesn't reach a nested action.** For the `github-actions` ecosystem, list every folder that holds an `action.yml` under `directories`.

## Try it in your project

Add one `groups` entry with `update-types: [minor, patch]` to the npm entry of your `dependabot.yml`, and compare the pull requests of the next check with the last one.
