Work an agent can't finish in one session has to wait somewhere a later session will find it. In Terrarium that place is a GitHub issue, and a label on the issue says what may happen to it next: wait for more facts, go to an agent, or go to a person.

Know GitHub labels already? Skip to [In Terrarium](#in-terrarium).

## The concept

A label is a name, a color and a description that you attach to issues, pull requests and discussions. Labels belong to one repository, and once a label exists there, it can go on any issue in that repository. Every new repository starts with a default set, such as `bug`, `enhancement`, `question` and `wontfix`, which you can edit or delete. Anyone with write access can create, edit or delete a label; anyone with triage access can apply one.

Issue lists can be filtered by label, so a label can stand for a step in your own workflow, such as "ready to build", and the filter shows the queue for that step. GitHub doesn't know the labels mean that. Nothing stops an issue from carrying two steps at once or none at all, so the rules for moving between steps are yours to write down and keep.

Full reference: [GitHub Docs: Managing labels](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)

## In Terrarium

Work that has to wait, such as a proposal, a bug or a follow-up, goes in an issue, and the open issues are the work queue. Its five states come from the Skill pack's `triage` Skill: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` and `wontfix`. :file[docs/agents/triage-labels.md] maps each to the label string used here and says what it means.

The `triage` Skill, in :file[.agents/skills/triage/SKILL.md], also gives each issue one category, `bug` or `enhancement`, and expects one category and one state on every triaged issue. Moving an issue to `ready-for-agent` comes with an Agent Brief: a comment that states the behavior wanted and how to tell it is done, without file paths (:file[.agents/skills/triage/AGENT-BRIEF.md]).

Two Skills move issues through these states. A person runs `triage` on the issues they pick. :file[.agents/skills/auto-triage/SKILL.md] is the unattended sweep, started by a person. It looks at every open issue and acts on those that need attention: one with no state label, no comments or `needs-triage`, or one in any state whose latest comment a person wrote. It tells a person's comment from an agent's by the session mark every agent post carries ([Commit and PR attribution](/t/glassbox/guide/git-github/attribution)). Once an agent has answered, the issue stays quiet until a person writes again. The sweep labels, comments and closes; it never builds. It closes only an issue that is already done or a duplicate.

ADR-0022 sets which issues a sweep that a :term[Trusted] user started may mark `ready-for-agent` on its own. The sweep sends a :term[Public] author's issue to `ready-for-human`; it reaches `ready-for-agent` only when a Trusted user approves it, or through the guest pipeline (ADR-0023, :file[docs/adr/0023-guest-driven-demo-pipeline.md]).

Agents then take work from the `ready-for-agent` queue. :file[.agents/skills/clear-backlog/SKILL.md] gathers every open `ready-for-agent` issue together with the ones its own sweep picks up, rechecks each, and carries each to a merged PR, a closed issue or a question for the owner. Big work planned with `wayfinder` keeps its own map and ticket labels next to these; [Planning with the pack](/t/glassbox/drafts/skill-pack/planning-with-the-pack) shows how the two sets live on one issue.

### Why it's built this way

`ready-for-agent` as a Trusted user's approval to build: ADR-0003 (:file[docs/adr/0003-agent-operating-model-and-governance.md]).

What a sweep may mark ready on its own: ADR-0022 (:file[docs/adr/0022-autonomous-triage-sweep.md]).

Public issues waiting for a person: ADR-0020 (:file[docs/adr/0020-requester-trust-tiers.md]).

The guest pipeline's exception: ADR-0023 (:file[docs/adr/0023-guest-driven-demo-pipeline.md]).

### What to watch for

- **A label write replaces the whole set.** Setting labels through the GitHub MCP tools sends the full list the issue ends with, so a call that names only the new state drops the category and any `wayfinder:` label; :file[docs/agents/github-integration.md] lists this trap.
- **A comment can claim a move that never happened.** An agent may write "moved to `ready-for-agent`" and fail to change the label. :file[scripts/github/check-triage-drift.ts] lists the issues whose latest agent comment claims a label its live labels don't show.
- **Ready doesn't mean still needed.** An issue can wait long enough for other work to solve it, so :file[docs/agents/issue-tracker.md] has an agent check for a merged fix before it builds a `ready-for-agent` issue.
- **A spec on hold has no label.** Terrarium marks it in the issue body instead, so a missing label doesn't always mean an issue was never triaged.

## Try it in your project

Create the five state labels in your repository and write one short doc that says, for each, who may set it and what an agent may do with an issue that carries it. Then tell your agent to take work only from the `ready-for-agent` filter, and to move an issue it can't finish to `needs-info` or `ready-for-human` with a comment that says why.
