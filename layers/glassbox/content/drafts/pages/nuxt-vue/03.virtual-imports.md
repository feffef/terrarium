Some data is known before the app runs: it follows from files in the repo. Code can work it out again on every request, or someone can generate a file and commit it, and then keep that copy in step with its source forever. A Nuxt module offers a third way: work the data out each time the app is built, and give it to the code as an ordinary import.

Know Nuxt modules and templates already? Skip to [In Terrarium](#in-terrarium).

## The concept

A Nuxt module is a function that Nuxt runs when it starts, in development or for a build. It is written with `defineNuxtModule`, and its `setup(options, nuxt)` can read the config, add files and change options before the app is compiled. A project's own modules can sit in its [`modules/` folder](https://nuxt.com/docs/4.x/directory-structure/modules), where Nuxt registers every `modules/*.ts` without being told, after the ones `nuxt.config.ts` lists.

One thing a module can add is a template: a file whose text the module computes. `addTemplate({ filename, getContents })` puts it in Nuxt's virtual file system, and `write: true` also writes it to the build folder, `.nuxt/`. App code imports it from `#build/<filename>`, or under a shorter alias the module adds to `nuxt.options.alias`. The data was computed at build time, so the browser receives plain values and none of the code that made them.

A computed file has no types of its own. `addTypeTemplate` writes a `.d.ts` beside it and adds it to the types Nuxt generates for the app, so `vue-tsc` and the editor know what the import holds.

Full reference: [Nuxt Kit: Templates](https://nuxt.com/docs/4.x/api/kit/templates)

## In Terrarium

Every page needs to turn a :term[Tenant] and a :term[Space] into the keys of that Space's Collections. The answer follows from the manifests alone, so :file[modules/routing.ts] works it out at build time. It expands the manifests with the same `expand(loadManifests())` that builds the collections, turns the result into a map from Tenant to Space to Collection to key, and writes that map twice from one JSON string: once as data, once as its type.

::excerpt{path="modules/routing.ts" lines="26-66"}
```ts
    const mapJson = JSON.stringify(map, null, 2)

    // Plain JavaScript (.mjs) so Nitro's Rollup bundler can parse it without a
    // TypeScript plugin. A companion .d.ts provides the types for tsc / vue-tsc.
    const template = addTemplate({
      filename: 'routing.mjs',
      write: true,
      getContents: () =>
        [
          '// Build-time routing data (ADR-0014). Written to .nuxt/ at prepare/build time.',
          '// Derived from tenant manifests via expand(). Do not edit — change the manifests.',
          '',
          `export const routingMap = ${mapJson}`,
          '',
        ].join('\n'),
    })
    // …
    addTypeTemplate({
      filename: 'routing.d.ts',
      getContents: () =>
        [
          `export declare const routingMap: ${mapJson}`,
          '',
        ].join('\n'),
    })

    // Register #routing so shared/routing.ts (and any call site) can import it as
    // a plain static import, keeping the isolation-critical resolver context-free.
    nuxt.options.alias['#routing'] = template.dst
```
::

Every value in the map is a string, so the JSON text is also a valid TypeScript type. The type therefore names each key exactly, such as `"atlas_canopy_pages"`, not just `string`. :file[shared/routing.ts] imports the map from `#routing` and derives from its type, per Tenant, the union of keys a page may query. A Tenant's page gets results typed with that Tenant's own fields, with no cast.

The import is plain, not a composable, so :file[shared/routing.ts] runs in a unit test without Nuxt. Tools that run outside Nuxt need the alias too, and point it at the generated files: :file[vitest.config.ts] maps `#routing` to `.nuxt/routing.mjs`, and :file[tsconfig.node.json] maps it, and `#catalog`, to their `.d.ts` files.

Its sibling :file[modules/catalog.ts] follows the same pattern for `#catalog`, the :term[Catalog], except that its type is a fixed interface: every Collection that opted into a :term[Collection kind], grouped by kind. The two reach Nuxt differently. `./modules/routing` is named in the `modules` list of :file[nuxt.config.ts]; the catalog module is not, and Nuxt registers it because it sits in `modules/`.

### Why it's built this way

The routing map built from the manifests, so the browser gets plain data and unit tests can run the resolver without Nuxt: ADR-0014 (:file[docs/adr/0014-build-time-virtual-routing-module.md]).

Derived files built, not committed: ADR-0007 (:file[docs/adr/0007-generated-config-committed-drift-checked.md]).

The Catalog behind `#catalog`: ADR-0025 (:file[docs/adr/0025-cross-tenant-catalog-and-collection-kinds.md]).

### What to watch for

- **Tools outside Nuxt read a copy in `.nuxt/`.** Run on their own (`pnpm exec vitest`, `tsc -p tsconfig.node.json`, the editor), they see the map from the last `nuxt prepare`; `pnpm test` and `pnpm typecheck` regenerate it first. After a rebase or a new Tenant, run `nuxt prepare` before using them on their own.
- **`addTypeTemplate` reaches only Nuxt's own type-check.** The `vue-tsc` pass finds `routing.d.ts` on its own; the `tsc -p tsconfig.node.json` pass needs the `paths` entry, and a new virtual import needs one there too.
- **The data file is plain JavaScript.** The template is `.mjs`, not `.ts`, so that Nitro's server bundler can read it with no TypeScript step, as the comment in the excerpt says.
- **The map is rebuilt only when Nuxt restarts.** The watch list does that for existing manifests, not for a new Tenant: [Collections expanded from one manifest](/t/glassbox/guide/nuxt-content/manifest-collections).

## Try it in your project

Give your app a build stamp with no code that runs at request time. Add `modules/build-info.ts`:

```ts
// modules/build-info.ts
import { addTemplate, addTypeTemplate, defineNuxtModule } from '@nuxt/kit'

export default defineNuxtModule({
  setup(_options, nuxt) {
    const info = JSON.stringify({ builtAt: new Date().toISOString() })
    const template = addTemplate({
      filename: 'build-info.mjs',
      write: true,
      getContents: () => `export const buildInfo = ${info}\n`,
    })
    addTypeTemplate({
      filename: 'build-info.d.ts',
      getContents: () => `export declare const buildInfo: ${info}\n`,
    })
    nuxt.options.alias['#build-info'] = template.dst
  },
})
```

Run `nuxt prepare`, open `.nuxt/build-info.mjs`, then `import { buildInfo } from '#build-info'` in a page and hover it in your editor to see the exact type.
